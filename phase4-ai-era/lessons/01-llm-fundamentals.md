# Lesson 01: LLM の仕組みの直感的理解

## 学習目標

- LLM (Large Language Model: 大規模言語モデル) がどのように動作するかを直感的に理解する
- トークン・確率的生成・コンテキストウィンドウ・ハルシネーションという 4 つの概念を説明できる
- 「AI がなぜ間違えるのか」を理解し、それを前提とした使い方ができる

---

## 1. LLM とは何か

LLM (Large Language Model) とは、大量のテキストデータを学習し、「次に来るテキストを予測する」能力を持った機械学習モデルです。ChatGPT・Claude・Gemini などはすべて LLM を中心に構築されています。

重要なのは、LLM は「知識を検索している」のではなく、「学習したパターンをもとに確率的にテキストを生成している」という点です。この違いが、後述するハルシネーションの根本原因になります。

---

## 2. トークン (Token)

### トークンとは

LLM はテキストをそのまま処理するのではなく、テキストを「トークン」という単位に分割して処理します。英語では単語や単語の一部がトークンになり、日本語では文字や意味のある単位がトークンになることが多いです。

```
英語の例:
"Hello, world!"
-> ["Hello", ",", " world", "!"]  (4 トークン)

日本語の例:
"こんにちは世界"
-> ["こんにちは", "世界"]  (日本語はより多くのトークンになる場合がある)
```

### トークンを意識すべき理由

1. **コスト**: API の料金はトークン数に比例します。無駄に長いプロンプトはコストを増やします。
2. **上限**: モデルが一度に処理できるトークン数には上限があります (後述)。
3. **日本語の注意点**: 日本語は英語より多くのトークンを消費することが多く、API コストが高くなりがちです。

---

## 3. 確率的生成 (Probabilistic Generation)

### 仕組みの直感的な理解

LLM は「これまでの文脈を見て、次に来る最もそれらしいトークンを選ぶ」という処理を繰り返します。正確には「最も確率が高いトークンを選ぶ」のではなく、確率分布からサンプリングを行います。

これが意味することは以下の通りです。

- **同じ入力でも出力が変わりうる**: 確率分布からサンプリングするため、毎回まったく同じ出力になるとは限りません。
- **Temperature (温度) パラメータ**: この「ランダム性の度合い」を調整するのが Temperature です。低いと出力が安定し、高いとより多様で創造的になります。

```
Temperature = 0.0 の場合: ほぼ毎回同じ (最も確率の高いトークンを選ぶ)
Temperature = 1.0 の場合: ある程度のランダム性あり
Temperature = 2.0 の場合: 非常にランダム (文章が壊れることがある)
```

> **注意**: `temperature=0` でも**完全な再現性は保証されません**。GPU での並列計算は浮動小数点の加算順序が実行ごとに変わりうるため、確率がごく僅差のトークン同士で選択が入れ替わることがあります。「temperature を 0 にしたから毎回同じ出力になる」という前提でテストを書くと、稀に落ちるテストができあがります。LLM の出力を検証するときは、完全一致ではなく**満たすべき条件**で検証します(Lesson 08 の eval を参照)。

### エンジニアへの実践的な意味

確率的生成であることを理解すると、以下のような判断ができます。

- コードの生成に失敗しても、**もう一度試せば異なる出力が来る**
- 重要なロジックは **AI 任せにせず自分で検証** する必要がある
- AI の出力を「正解」ではなく「候補の一つ」として扱う

## 4. コンテキストウィンドウ (Context Window)

### コンテキストウィンドウとは

LLM が一度の処理で参照できるテキストの最大量を「コンテキストウィンドウ」と呼びます。会話の履歴、システムの指示、ユーザーの入力、AI の回答、すべてがこのウィンドウに入ります。

ウィンドウの大きさ、数え方、上限超過時の挙動はmodelとAPIによって異なり、頻繁に更新されます。実装時は選択したproviderの公式documentとAPI responseを確認し、教材内の固定値を前提にしません。

### 実践的な影響

- **長い会話では初期の文脈が薄れる**: ウィンドウサイズを超えると古い情報は切り捨てられます。
- **コードベース全体を渡せる場合とそうでない場合がある**: プロジェクトの規模によっては、関連するファイルだけを選んで渡す必要があります。
- **足りない文脈は補う。ただし多ければ良いわけではない**: 「このコードを直して」だけでは足りず、関連するコードやエラー全文を渡したほうが良い結果になります。一方で、**無関係な情報を大量に詰め込むと精度はむしろ下がります**。

### よくある誤解: 「全部貼れば精度が上がる」

「コンテキストウィンドウが 20 万トークンあるなら、リポジトリ全部貼ればいい」と考えたくなりますが、これは間違いです。

ウィンドウに**入る**ことと、モデルがその全体を**均等に使える**ことは別です。文脈が長くなるほど、途中に置かれた情報は見落とされやすくなります(長い文書の真ん中が読み飛ばされる現象は "lost in the middle" と呼ばれます)。無関係なファイルを大量に混ぜると、モデルは何が重要かを判断する材料を失い、間違ったファイルを参照した回答を返します。

**指針**: 文脈は「量」ではなく「**信号対雑音比**」で考えます。

| 悪い渡し方 | 良い渡し方 |
|---|---|
| リポジトリ全体を貼る | 関係するファイル 2〜3 個に絞る |
| 「動きません」 | エラーメッセージ全文 + 再現手順 + 期待する挙動 |
| 会話を延々と続ける | 話題が変わったら新しい会話を始める |

長い会話ほど良くなるわけでもありません。前半の失敗した試行錯誤が残っていると、モデルはそれに引きずられます。**行き詰まったら、整理した文脈で会話をやり直す**のが有効です。

## 5. ハルシネーション (Hallucination)

### ハルシネーションとは

LLM が「もっともらしいが事実ではない情報」を自信を持って出力することを「ハルシネーション (幻覚)」と呼びます。これは LLM のバグではなく、確率的にテキストを生成するという仕組みの本質的な特性です。

### ハルシネーションの具体例

エンジニアが遭遇しやすいハルシネーションには以下のようなものがあります。

**存在しない関数・メソッドの生成**
```python
# AI が生成した例 (架空の関数)
import pandas as pd
df.auto_clean_nulls(strategy="mean")  # このメソッドは存在しない
```

**古い API の使用**
```python
# AI が古い学習データをもとに生成
import openai
openai.Completion.create(...)  # 旧 API。現在は廃止
```

**ライブラリのバージョン不整合**
```
requirements.txt に書いてある numpy==1.24 は
あなたの Python 3.12 環境では動かない場合がある
(AI はバージョン依存関係を正確に把握していないことがある)
```

### ハルシネーションへの対処

1. **コードは必ず実行して確認する**: 動かしてみるのが最も確実です。
2. **ライブラリの関数は公式ドキュメントで確認する**: AI が知っている情報は学習データのカットオフ時点までです。
3. **「〜らしい」という確信を持たない**: AI が断言していても、あなた自身が確認する責任があります。
4. **事実関係を問う質問には特に注意**: 技術的な事実、統計、日付、バージョン情報などは要確認です。

## 6. AI は「考えている」のではない

最後に、根本的な誤解を解いておきます。

LLM は人間のように「考えて」「理解して」回答しているわけではありません。莫大なテキストデータから学習したパターンをもとに、次に来るテキストを予測しているだけです。

これは LLM を過小評価することではありません。そのメカニズムから生まれる能力は非常に強力です。しかし「LLM が理解している」という前提で使うと、ハルシネーションや誤りに気づけないエンジニアになります。

**「AI は賢い文章生成器である。賢い人間ではない。」**

この認識を持ったうえで、次のレッスンから具体的な使い方を学んでいきます。

---

## 💡 コラム: LLM は「流暢に間違える」— その理由は仕組みにある

現代の LLM の土台は、2017年に Google の研究者たちが発表した論文「**Attention Is All You Need**」で提案された Transformer というアーキテクチャです(タイトルはビートルズの「All You Need Is Love」のもじり。機械翻訳の研究から生まれました)。この一本の論文から10年足らずで、世界が変わりました。

LLM の本質を一言で言えば「**超高性能な次の単語予測装置**」— スマホの予測変換の、桁違いに強力な親玉です。この理解から、LLM の最重要の性質が導けます: **ハルシネーション(もっともらしい嘘)は、バグではなく仕組みの帰結である**ということです。

LLM が最適化しているのは「もっともらしい続きを出すこと」であって、「真実を言うこと」ではありません。だから、存在しない論文をそれらしい著者名付きで引用し、存在しない API を自信満々に提案します。**流暢さと正しさは、別の軸**なのです。この一点を腹の底から理解していれば、LLM との距離感 — どこで頼り、どこで検証するか — は自然に定まります。以降のレッスンすべての土台になる感覚です。

---

## まとめ

| 概念 | 一言で |
|------|--------|
| トークン | LLM がテキストを処理する最小単位。コストと上限に影響する |
| 確率的生成 | 次のトークンを確率で選ぶ。同じ入力でも出力が変わりうる |
| コンテキストウィンドウ | 一度に参照できる最大テキスト量。これを超えると忘れる |
| ハルシネーション | もっともらしいが誤った情報を自信を持って出力する現象 |

## 確認問題

1. トークンとは何か、自分の言葉で説明してください。日本語が英語よりトークンを多く消費しやすい理由も含めて答えてください。

2. LLM の出力が「毎回同じではない」理由を、「確率的生成」というキーワードを使って説明してください。

3. 以下のシナリオで、AI の出力をそのまま信頼することの危険性を述べてください。
   - シナリオ: AI が「このライブラリの最新バージョンは 3.2.1 です」と答えた

4. コンテキストウィンドウが「200,000 トークン」あるモデルを使う場合でも、「コードをすべて貼り付ければいい」とは言い切れない理由を考えてください。

5. ハルシネーションは LLM の「バグ」ではなく「仕組みの本質的な特性」と説明しました。この違いをどう理解しましたか? バグであるという場合と仕組みの特性であるという場合で、エンジニアとしての対処法がどう変わるかを述べてください。
