# Lesson 02: AI コーディングアシスタントの使い方

## 学習目標

- 「補完」「チャット」「エージェント」という 3 つのモードの違いを理解し、場面に応じて使い分けられる
- 生成されたコードの責任がどこにあるかを説明できる
- AI に任せてはいけない場面を判断できる
- 製品が入れ替わっても使える「道具の選び方」を持つ

具体的な製品名と操作手順は [付録: AI コーディングアシスタントの製品と使い方](../appendix/02-assistant-products.md) にあります。**この分野は動きが速く、製品は数年で入れ替わります。**このレッスンでは、入れ替わっても残るものを扱います。

---

## 1. 3 つのモード

AI コーディングアシスタントは、製品名で分類しても意味がありません。**何を任せているか**で分けます。この区分は、製品が入れ替わっても残ります。

| モード | AI がすること | あなたが持っている情報 |
|---|---|---|
| **補完** | 書きかけの続きを推測する | 何を書こうとしているか |
| **チャット** | 質問に答える、提案する | 何を聞くべきか、答えが妥当か |
| **エージェント** | 自分で調べ、複数ファイルを変更する | 何が正しい変更か |

**右の列に注目してください。** どのモードでも、判断に必要な情報を持っているのはあなたです。AI は文脈を推測しますが、**あなたの意図を知りません。**

### モード 1: 補完 (Completion)

コードを書いているときに、続きをリアルタイムで提案します。

**有効な場面**
- 定型的なコード(ループ、条件分岐、関数の雛形)
- 関数名や変数名から処理内容が明らかなとき
- テストケースの網羅的な列挙

**最大の危険は、速すぎることです。**

```python
def calculate_discount(price, discount_rate):
    # AI がここを補完する
    # -> return price * (1 - discount_rate)
    #
    # これは正しいか?
    #   discount_rate が 0.2 なら 20% 引き = 正しい
    #   discount_rate が 20 (%) なら間違い
    #
    # 「どちらの意味か」を知っているのは自分だけ。
    # 補完はもっともらしい方を選ぶが、正しい方を選ぶわけではない
    pass
```

補完は「あなたが書こうとしているコードを推測する」ものです。**Tab キーを反射的に押す癖は、この道具で最も危険な習慣です。**採用する前に必ず読んでください。

### モード 2: チャット (Chat)

質問したり、コードの説明・修正・生成を依頼します。

**有効な場面**
- 特定のコードについて説明を求める
- バグの原因を一緒に調べる
- 「この関数を〇〇するように変えてほしい」という具体的な依頼
- 設計のアイデア出し(最終判断は自分でする)

チャットの結果は自動適用ではなく**提案**です。質問が曖昧なら回答も曖昧になります(次のレッスンで扱うプロンプト設計が効きます)。

### モード 3: エージェント (Agent)

コードベースを読み込み、複数ファイルにまたがる変更・調査・実行を自律的に行います。

**有効な場面**
- 「ログイン機能を追加して」のような複数ファイルにまたがるタスク
- 「既存のコードベースを調査して設計を提案して」
- 反復的なリファクタリング

**注意点**
- 必ず **Git 管理下**で使い、作業前にコミットしておく。差分で確認でき、いつでも戻せる状態が前提です
- 自信を持って行われた変更でも、意図と違うことがあります。**変更後の動作確認とレビューは省けません**
- 「何でもやってもらえる」感覚が、自分で書く機会を奪います。頼む前に「自分ならどうするか」を一度考えてください

## 2. 使い分けの判断基準

```
タスクの性質
    |
    +-- 短い・定型的 → 補完モード
    |      例: ループ、クラスの雛形、テスト関数の列挙
    |
    +-- 質問・調査・局所的な変更 → チャットモード
    |      例: 「この正規表現は何をしているか」「この関数をより効率的に」
    |
    +-- 複数ファイル・複雑な要件 → エージェントモード
           例: 「新しい API エンドポイントを追加する」
               「型エラーをすべて修正する」
```

もう一つ、**取り返しのつきやすさ**という軸があります。戻すのが難しい変更ほど、自律性の低いモードを選び、確認を厚くします。これは Phase 10 で学ぶデプロイの判断と同じ考え方です。

## 3. 責任は移らない

**これがこのレッスンで最も重要な原則です。**

AI が書いたコードでも、リポジトリにコミットした時点で、それは**あなたのコード**です。

- バグがあれば、あなたのバグです
- 脆弱性があれば、あなたの責任です
- レビューで問われるのは、あなたの判断です
- 「AI が生成しました」は、障害報告書に書ける説明ではありません

道具が何であれ、**説明できないコードをコミットしてはいけません。**これは AI に限った話ではなく、Stack Overflow からコピーしたコードでも、同僚に書いてもらったコードでも同じです。AI はこの原則を変えませんが、**違反しやすくします。**大量のもっともらしいコードが一瞬で手に入るからです。

判断の基準は単純です。

> **このコードについて質問されたとき、なぜこう書いたか説明できるか。**

できないなら、まだコミットする段階にありません。

## 4. 「使わないほうがいい」場面

### セキュリティに直接関わる実装

認証・認可・暗号化・SQL クエリの構築など。AI は一般的なベストプラクティスを知っていますが、**あなたの具体的な要件と、あなたの環境のリスクは知りません。**

ここで問題なのは、生成されたコードが「動いてしまう」ことです。動くが安全でないコードは、動かないコードより危険です。**失敗が目に見えないからです。**

### 学習中の概念

「理解できていないが AI が書いてくれた」を積み上げると、技術的負債だけでなく**理解の負債**が積み上がります。しかもこの負債は、本人からは見えません。

だからといって「学習中は AI 禁止」ではありません。**使う順序**の問題です。

| やる順序 | やってはいけない順序 |
|---|---|
| 1. 自分で書く | 1. AI に書かせる |
| 2. 詰まったら AI に**ヒント**を聞く | 2. 動いたので次へ進む |
| 3. 書けたら AI にレビューさせる | |
| 4. 指摘の理由を自分で確かめる | |

AI を「答えを出す装置」ではなく、**「いつでも質問できる先輩」**として使ってください。先輩に宿題を代わりにやってもらう人はいません。

### 機密情報を含む文脈

API キー・パスワード・顧客データ・社内の機密コードを送ることには、規約上のリスクがあります。**業務での利用前に、必ず組織のポリシーを確認してください。**

## 5. 道具の選び方

製品は入れ替わりますが、**評価する軸は変わりません。**新しいツールが出てきたら、この軸で見てください。

| 軸 | 何を確認するか |
|---|---|
| 補完・生成の品質 | 自分が普段書く言語・領域で試す。宣伝や他人の評価ではなく、自分の仕事で |
| コードベースの理解 | ファイル 1 つではなく、プロジェクト全体の文脈を扱えるか |
| 実行できる権限 | 何を勝手に実行できるか。承認を挟めるか |
| データの扱い | 送ったコードが学習に使われるか。履歴がどこに残るか |
| 監査 | 誰が何を生成したかを、あとから追えるか |
| モデルの選択 | 選べるか。将来ほかのモデルに乗り換えられるか |
| 費用 | 個人と組織で体系が違うことが多い |
| 組織のポリシー適合 | そもそも使ってよいか |

**「データの扱い」と「実行できる権限」は、後から取り返しがつきません。**性能より先に確認してください。

## 💡 コラム: 「プログラマー終了」と騒がれた日に、実際に終わったもの

2021年、GitHub Copilot が発表されたとき、世界中の掲示板が「プログラマーの仕事は終わった」という悲鳴で埋まりました。数年経った現在、答え合わせができます。**終わったのはプログラマーではなく、「タイピング」でした。** そして爆発的に需要が伸びたのは、AI の出力を評価できる能力 — つまりレビュー能力です。

AI コーディングアシスタントの正確な人物像は、こうです: 「**百科事典的な知識を持ち、超高速で、疲れを知らず、しかし自信満々に間違える新人**」。ペアプログラミングの相手として超優秀ですが、無監督で本番コードを書かせるには危険 — この距離感がすべてです。

歴史的な比較も役に立ちます。コンパイラが登場したとき、アセンブリ言語のプログラマーたちは「機械にコードを書かせるなんて」と抵抗しました。しかし勝ったのは、コンパイラを道具として使いこなし、より高い抽象度の問題に移った人たちです。AI アシスタントはその再演です。**道具と競争する人は負け、道具を使いこなす人が勝つ** — 産業革命以来、一度も例外のないパターンです。

## まとめ

- モードは「補完」「チャット」「エージェント」の 3 つ。製品ではなく**何を任せているか**で分ける
- どのモードでも、意図を知っているのは自分だけ。AI は「もっともらしい方」を選ぶが「正しい方」ではない
- 補完で最も危険なのは、Tab を反射的に押す癖
- エージェントは Git 管理下で、作業前にコミットしてから使う
- **責任は移らない。** 説明できないコードはコミットしない
- 学習中は「自分で書く → 詰まったらヒント → 書けたらレビュー」の順序を守る
- 道具は評価軸で選ぶ。データの扱いと権限は、性能より先に確認する

## 確認問題

1. 補完モードで Tab キーを押す前に必ずすべきことは何ですか。その理由も答えてください。

2. AI が生成したコードにバグがあり、本番で障害になりました。責任はどこにありますか。理由も説明してください。

3. コミットしてよいかどうかを判断する基準を、本文は 1 つの問いで示しています。それは何ですか。

4. 次のタスクには、補完・チャット・エージェントのどのモードが適切ですか。理由も答えてください。
   - (a) 既存の for ループを内包表記に書き換えたい
   - (b) このファイル全体で足りない型注釈を修正してほしい
   - (c) エラーメッセージの意味を調べたい

5. 「学習中の概念に AI を使うな」とは書かれていません。どう使えばよいか、順序を答えてください。

6. セキュリティに関わるコードで、AI 生成が特に危険なのはなぜですか。「動いてしまう」ことがなぜ問題なのですか。

7. 新しい AI アシスタントを試すとき、性能より先に確認すべき 2 つの軸は何ですか。なぜ先なのですか。
