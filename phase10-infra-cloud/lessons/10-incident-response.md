# Lesson 10: 障害対応入門

## 学習目標

- インシデント対応の基本フローを理解する
- オンコール（緊急対応当番）の心構えを持てる
- ポストモーテムの書き方を理解する
- 「責任追及よりも改善」の文化を理解する

---

## 1. インシデント（Incident）とは

**インシデント**とは、サービスの品質・可用性・セキュリティに影響を与える非計画的な出来事です。

```
例:
- Web サイトが 503 エラーを返し続けている（サービスダウン）
- API のレスポンスタイムが通常の 10 倍以上に劣化している
- DB の空き容量が残り 5% になった
- 不正アクセスの痕跡が発見された
- 誤って本番 DB のデータを削除してしまった
```

---

## 2. 重大度（Severity）の分類

| レベル | 名称 | 定義 | 対応速度の目安 |
|--------|------|------|---------------|
| SEV-1 | Critical | サービス全停止・全ユーザーに影響 | 即時（深夜でも起こす） |
| SEV-2 | Major | 主要機能が停止・多数のユーザーに影響 | 30分以内 |
| SEV-3 | Minor | 一部機能の劣化・限定的な影響 | 業務時間内 |
| SEV-4 | Low | 軽微な問題・ほぼ影響なし | 次のスプリントで対応 |

---

## 3. インシデント対応の5フェーズ

### フェーズ1: 検知（Detection）

異常を発見する。監視・アラートが重要です。

```
検知の方法:
- モニタリングのアラート（Prometheus, CloudWatch）
- ユーザーからの報告
- 社内チームからの報告
- ログ監視ツールによる自動検知
- ヘルスチェックの失敗
```

**やること**:
- アラートを確認し、誤検知ではないことを確認
- 影響範囲を初期評価（SEV レベルを仮決め）
- インシデント対応チャンネル（Slack など）を開設

### フェーズ2: 対応（Response）

チームを集め、役割を決める。

```
インシデントコマンダー（IC）:
  対応全体を指揮する。技術的な作業より指揮に集中する。
  「今誰が何をやっているか」を常に把握する。

技術担当（Responder）:
  実際の調査・修正作業を行う。
  作業内容をチャットに都度記録する。

コミュニケーション担当:
  ステークホルダー（上司、顧客）への状況報告を担当。
  技術担当の作業を邪魔しないよう、報告は技術担当に代わって行う。
```

### フェーズ3: 調査と修正（Investigation & Mitigation）

原因を探り、被害を止める。

```
調査の進め方:

1. 最近のデプロイを確認（「直前に何か変えた？」）
   git log --oneline -20
   docker images | head

2. ログを確認
   kubectl logs -l app=myapp --tail=100  # Kubernetes の場合
   docker compose logs --tail=100 app
   journalctl -u myapp -n 100 --since "30 min ago"

3. メトリクスを確認
   - CPU/メモリ使用率
   - DB 接続数・クエリ時間
   - エラーレート

4. 直近の変更を確認
   - 設定変更
   - スケールイン/アウト
   - インフラ変更

5. 仮説を立てて検証（5WHY で原因を深掘り）
```

### フェーズ4: 解決（Resolution）

サービスを回復させる。

```
緊急対応（Mitigation）の優先順位:
1. まず「元に戻す（ロールバック）」を検討する
   → 直前のデプロイが原因なら即ロールバック
   → 完璧な修正より「今すぐ動く状態」を優先する

2. 回避策（Workaround）を実施する
   → 問題のある機能を無効化（フィーチャーフラグ）
   → トラフィックを別のサービスに向ける
   → 手動で一時的な処置を行う

ロールバックのコマンド例:
  # Docker / Compose の場合
  docker compose pull && docker compose up -d  # 旧イメージに戻す場合
  git revert HEAD && git push origin main       # コードを戻す

  # Kubernetes の場合
  kubectl rollout undo deployment/myapp

  # GitHub Actions でデプロイした場合
  # 前のバージョンのタグを指定して手動で workflow_dispatch
```

### フェーズ5: 振り返りと改善（Post-Incident Review）

再発防止策を決める。

## 4. インシデント対応中のコミュニケーション

### タイムラインの記録

対応中は、やったこととその結果をリアルタイムで記録します。

```
# Slack の #incident-20240115 チャンネル（例）

10:30 @田中 [IC] インシデント開始。サービスが 503 を返している。
              山田さん調査お願いします。鈴木さんは顧客への連絡を担当してください。

10:32 @山田 API サーバーのログを確認中

10:35 @山田 DB への接続エラーが大量に出ている
           `Error: connect ETIMEDOUT postgresql:5432`

10:37 @山田 DB コンテナが再起動ループしている。compose ログ確認中

10:40 @山田 原因判明: ディスクが 100% になって PostgreSQL がクラッシュしている
           df -h で確認: /dev/sda1 は 100% 使用済み

10:42 @田中 [IC] 山田さん: /var/log 以下の古いログを削除してください。
                  鈴木さん: 「調査中・復旧作業中」と顧客にメール

10:45 @山田 古いログ 20GB を削除。ディスク使用率 60% に低下

10:47 @山田 DB コンテナを再起動。起動確認。

10:50 @山田 API サービス正常稼働確認。503 エラー解消。

10:51 @田中 [IC] 解決。全サービス正常。インシデントクローズ。
              ポストモーテムは明日の午前中に作成します。
```

## 5. ポストモーテム（Post-Mortem）

### ポストモーテムとは

インシデント後に、**原因の分析と再発防止策をドキュメント化**することです。
「誰が悪い」を追及するのではなく、**「システムをどう改善するか」** に集中します。

これを **"Blameless Post-Mortem"（責任追及なしのポストモーテム）** と呼びます。

### ポストモーテムのテンプレート

```markdown
# インシデント報告書: データベースディスク満杯によるサービスダウン

**日時**: 2024-01-15 10:30 〜 10:51 JST
**重大度**: SEV-1（サービス全停止）
**影響時間**: 21分
**影響範囲**: 全ユーザー（約 5,000 人）
**担当**: 田中（IC）、山田（技術）、鈴木（コミュニケーション）

---

## 概要（Executive Summary）

本番サーバーのディスク使用量が 100% に達し、PostgreSQL がクラッシュしました。
その結果、API サービス全体が 21 分間停止しました。
古いログファイルの削除とディスク空き容量の確保によって復旧しました。

---

## タイムライン

| 時刻 | 内容 |
|------|------|
| 10:30 | アラート発報（5xx エラーレート 50% 超） |
| 10:30 | 田中がインシデントを宣言 |
| 10:35 | DB 接続エラーを確認 |
| 10:40 | ディスク 100% が原因と特定 |
| 10:45 | 古いログ 20GB を削除 |
| 10:47 | DB 再起動 |
| 10:51 | サービス復旧確認・インシデントクローズ |

---

## 根本原因（Root Cause）

アプリケーションのデバッグログが `DEBUG` レベルのまま本番環境で出力されており、
約 2 週間で 80GB のログファイルが蓄積した。
ディスク容量の監視アラートが設定されておらず、
満杯になるまで気づくことができなかった。

---

## 5 WHY 分析

1. なぜサービスが停止したか？
   → DB がクラッシュしたから
2. なぜ DB がクラッシュしたか？
   → ディスクが満杯になったから
3. なぜディスクが満杯になったか？
   → ログが大量に出力されたから
4. なぜログが大量に出力されたか？
   → LOG_LEVEL=DEBUG のまま本番デプロイされたから
5. なぜ設定ミスに気づけなかったか？
   → ディスク容量の監視アラートが未設定だったから

---

## 影響

- 21 分間のサービスダウン
- 推定影響ユーザー数: 5,000 人
- 顧客からの問い合わせ: 23件

---

## 再発防止策（Action Items）

| 優先度 | 内容 | 担当 | 期日 |
|--------|------|------|------|
| 高 | ディスク使用率 80% でアラートを設定する | 山田 | 2024-01-16 |
| 高 | logrotate の設定を確認・修正する | 山田 | 2024-01-17 |
| 高 | デプロイ前チェックリストに LOG_LEVEL の確認を追加 | 田中 | 2024-01-18 |
| 中 | CI/CD パイプラインに環境変数チェックを追加 | 田中 | 2024-01-25 |
| 低 | ログ集約基盤（Loki など）の導入を検討 | チーム全体 | 2024-02-15 |

---

## 良かった点

- アラートが 5 分以内に発報された
- IC を立てたことで対応が整然と進んだ
- タイムラインの記録が適切に行われた

---

## 改善すべき点

- ディスク容量の監視が未設定だった
- デプロイ環境変数の確認プロセスがなかった
- ロールバック手順がドキュメント化されていなかった
```

## 6. SLO・SLA・SLI

### 基本概念

| 用語 | 説明 | 例 |
|------|------|-----|
| **SLI** (Service Level Indicator) | 測定可能な指標 | エラーレート、レイテンシ、可用性 |
| **SLO** (Service Level Objective) | 達成目標 | 可用性 99.9%（月 43分以内のダウン許容） |
| **SLA** (Service Level Agreement) | 顧客との契約 | 99.9% を下回った場合、月額料金を返金 |

### エラーバジェット（Error Budget）

```
SLO: 月間可用性 99.9%
月間総時間: 30日 × 24時間 × 60分 = 43,200分
エラーバジェット = 43,200分 × (1 - 0.999) = 43.2分

つまり月 43分以内のダウンタイムは許容範囲内。
今月のインシデントで 21分消費 → 残り 22.2分
```

エラーバジェットを使い切ると、新機能のリリースより安定性向上を優先すべき、
というシグナルになります。

## 💡 コラム: タイプミスがインターネットの一部を止めた日

2017年2月28日、AWS の S3(世界中のサービスが使うストレージ)で大規模障害が起き、数時間にわたり無数の Web サービスが道連れになりました。原因の発端は、デバッグ作業中のエンジニアの**コマンドのタイプミス** — 停止するサーバー数の指定を誤り、想定よりはるかに多くのサーバーを削除してしまったのです。おまけに、**AWS 自身の障害情報ダッシュボードが S3 に依存していたため、「障害が起きています」という表示すら更新できない**という皮肉まで起きました。

注目すべきは AWS の事後対応です。詳細な報告書を公開し、そこに「誰のミスか」は書かれませんでした。書かれたのは「**なぜツールは、一度にそれほど多くのサーバーを削除できてしまったのか**」— そしてツール側に安全弁(削除数の上限)が追加されました。

これが **blameless postmortem(非難なき振り返り)** の文化です。人はミスをする、という前提を受け入れ、「犯人」ではなく「ミスを事故に変えた仕組みの穴」を探す。犯人探しをする組織では、次のミスは**隠される**ようになり、学習が止まります。障害対応の最終目標は、復旧でも謝罪でもなく、**組織が学習すること**です。

---

## まとめ

| 概念 | 要点 |
|------|------|
| インシデントフロー | 検知 → 対応（役割決め）→ 調査・修正 → 解決 → 振り返り |
| IC（インシデントコマンダー） | 指揮に専念。技術作業より全体管理を優先 |
| タイムライン記録 | 対応中にやったこととその結果をリアルタイム記録 |
| ポストモーテム | 責任追及なし。「システムをどう改善するか」に集中 |
| エラーバジェット | 許容できるダウンタイムの残量。安定性と開発速度のバランスを取る |

---

## 確認問題

1. インシデントコマンダー（IC）の役割を説明してください。技術担当と何が違いますか？

2. 「Blameless Post-Mortem（責任追及なしのポストモーテム）」の考え方を説明してください。なぜ責任追及をしないのですか？

3. SEV-1（Critical）のインシデントが発生した場合、最初にやるべき3つのことを挙げてください。

4. 以下のインシデントシナリオについて、5 WHY 分析を行ってください：
   「本番 API の p99 レイテンシが突然 5 秒以上になり、タイムアウトエラーが多発した」

5. SLO・SLI・SLA の違いを説明し、「月間可用性 99.9% のサービスのエラーバジェットは何分か」を計算してください。
