## 1. OSI 参照モデルと TCP/IP

### OSI 参照モデル（Open Systems Interconnection Reference Model）

ネットワーク通信は複雑な処理の積み重ねです。この複雑さを整理するために、
ISO（国際標準化機構）が定めた概念モデルが **OSI 参照モデル**です。

```
第7層  アプリケーション層  HTTP, HTTPS, FTP, SMTP, DNS
第6層  プレゼンテーション層 データの暗号化・圧縮・変換
第5層  セッション層        通信セッションの管理
第4層  トランスポート層    TCP, UDP（端点間の通信制御）
第3層  ネットワーク層      IP（経路制御・論理アドレス）
第2層  データリンク層      Ethernet（物理的な隣接ノード間通信）
第1層  物理層              ケーブル・電気信号・光信号
```

実際の開発では「第4層（トランスポート層）以上」を意識する場面が多いです。
特に **TCP/IP の4層モデル** をよく使います。

```
アプリケーション層  HTTP, HTTPS, DNS など（OSI の第5〜7層に対応）
トランスポート層    TCP, UDP
インターネット層    IP
ネットワーク接続層  Ethernet など
```

## 2. IP アドレスとポート番号

### IP アドレス（Internet Protocol Address）

ネットワーク上の各機器を識別するための番号です。

```
IPv4 例: 192.168.1.100  （32ビット、約43億個）
IPv6 例: 2001:0db8:85a3::8a2e:0370:7334  （128ビット）
```

**特殊な IP アドレス**

| アドレス | 意味 |
|---------|------|
| `127.0.0.1` | ループバックアドレス（自分自身）。`localhost` とも呼ぶ |
| `192.168.x.x` | プライベートアドレス（LAN 内のみで使用） |
| `0.0.0.0` | すべてのインターフェース（サーバーがリッスンする際に使用） |

### ポート番号（Port Number）

同じサーバー上で複数のサービスを動かすために、通信の「窓口」を番号で区別します。
IP アドレスが「建物の住所」なら、ポート番号は「部屋番号」です。

```
http://example.com:80/  → IP アドレスのポート 80 番に接続
https://example.com/    → ポート 443 番（省略時のデフォルト）
```

**よく使うポート番号**

| ポート | プロトコル/用途 |
|--------|---------------|
| 22 | SSH |
| 80 | HTTP |
| 443 | HTTPS |
| 3306 | MySQL |
| 5432 | PostgreSQL |
| 6379 | Redis |
| 8080 | 開発用 HTTP サーバー（慣習） |
| 27017 | MongoDB |

## 3. TCP の仕組み

### TCP（Transmission Control Protocol）

TCP は「信頼性のある」通信を提供するプロトコルです。
データが必ず相手に届く（または届かなかったことがわかる）ことを保証します。

### 3-way ハンドシェイク（3-Way Handshake）

TCP 接続を確立するための手順です。

```
クライアント                    サーバー
    |                              |
    |--- SYN（接続要求） ---------->|
    |                              |
    |<-- SYN-ACK（受理・応答） -----|
    |                              |
    |--- ACK（確認応答） ---------->|
    |                              |
    |==== 接続確立（通信開始） ====|
```

1. **SYN**: クライアントが「接続したい」と送信
2. **SYN-ACK**: サーバーが「わかった、準備できた」と返答
3. **ACK**: クライアントが「確認した」と送信 → 通信開始

### TCP vs UDP

| 比較項目 | TCP | UDP |
|---------|-----|-----|
| 信頼性 | 高い（順序保証・再送あり） | 低い（ベストエフォート） |
| 速度 | 遅め | 速め |
| 用途 | HTTP, SMTP, SSH | DNS 問い合わせ, 動画ストリーミング, ゲーム |
| ヘッダサイズ | 大きい | 小さい |

## 4. HTTP と HTTPS の違い

### HTTP（HyperText Transfer Protocol）

Web 上でデータをやり取りするためのプロトコルです。
HTTP はテキストベースで、通信内容は**暗号化されていません**。

```
# HTTP の通信例（平文）
GET /api/users HTTP/1.1
Host: example.com
Authorization: Bearer eyJhbGci...  ← 盗聴されると丸見え
```

### HTTPS（HTTP Secure）

HTTP に **TLS（Transport Layer Security）** による暗号化を追加したものです。
通信内容が暗号化されるため、盗聴・改ざんを防げます。

```
[ブラウザ] ----TLS で暗号化---- [サーバー]
           (中間者には読めない)
```

### TLS の仕組み（TLS Handshake）

TLS 接続が確立されるまでの大まかな流れ：

```
クライアント                         サーバー
    |                                   |
    |--- ClientHello（対応TLSバージョン、暗号スイート一覧）-->|
    |                                   |
    |<-- ServerHello（選択した暗号スイート）-----------------|
    |<-- Certificate（サーバー証明書）------------------------|
    |                                   |
    |  [証明書を CA に照合して検証]      |
    |                                   |
    |--- 鍵交換（Pre-Master Secret）--->|
    |                                   |
    |  [両者がセッション鍵を生成]        |
    |                                   |
    |=== 暗号化通信開始 ==================|
```

### SSL/TLS 証明書の仕組み

証明書とは「このサーバーは本物の example.com である」ことを証明する電子文書です。

```
認証局 CA（Certificate Authority）
└── 中間 CA
    └── example.com の証明書
```

**CA（認証局）**: 証明書の発行・保証を行う第三者機関。
ブラウザには信頼される CA リスト（ルート証明書ストア）が組み込まれています。

**Let's Encrypt**: 無料で TLS 証明書を発行してくれる CA。
現代の Web では標準的に使われています。

## 5. DNS（Domain Name System）

### DNS とは

人間が覚えやすいドメイン名（`example.com`）を、
コンピュータが通信に使う IP アドレス（`93.184.216.34`）に変換するシステムです。

### DNS 解決の流れ

ブラウザで `https://example.com` にアクセスした場合：

```
1. ブラウザのキャッシュを確認 → なければ
2. OS のキャッシュ（/etc/hosts も含む）を確認 → なければ
3. スタブリゾルバ（OS の DNS クライアント）が
   フルサービスリゾルバ（プロバイダや 8.8.8.8 など）に問い合わせ
4. フルサービスリゾルバが：
   a. ルート DNS サーバー（.）に「com を知っている？」
   b. TLD DNS サーバー（.com）に「example.com を知っている？」
   c. 権威 DNS サーバー（example.com 管理）に「www は？」
   d. 答え（A レコード: 93.184.216.34）を受け取る
5. フルサービスリゾルバがブラウザに返答
6. ブラウザが IP アドレスに TCP/TLS 接続を開始
```

### 主な DNS レコードの種類

| レコード | 用途 | 例 |
|---------|------|-----|
| A | ドメイン → IPv4 アドレス | `example.com → 93.184.216.34` |
| AAAA | ドメイン → IPv6 アドレス | `example.com → 2606:2800:...` |
| CNAME | ドメイン → 別のドメイン（エイリアス） | `www.example.com → example.com` |
| MX | メールサーバーの指定 | `example.com → mail.example.com` |
| TXT | テキスト情報（SPF、DKIM 等） | ドメイン所有権の確認など |
| NS | 権威 DNS サーバーの指定 | `example.com → ns1.example.com` |

### TTL（Time To Live）

DNS の回答にはキャッシュ有効期限（TTL）が含まれています。
DNS レコードを変更した際、すぐに世界中に反映されない理由はこの TTL が原因です。

```bash
# DNS 解決を手動で確認する
dig example.com
dig example.com A       # A レコードのみ
dig example.com MX      # MX レコードのみ
nslookup example.com    # dig の代替コマンド

# レスポンスの TTL を確認
dig example.com | grep -i ttl
```

## 6. ハンズオン: ネットワークを実際に観察する

### curl でヘッダを確認する

```bash
# レスポンスヘッダのみ表示
curl -I https://example.com

# 詳細な TLS 情報も表示
curl -vI https://example.com 2>&1 | head -50

# HTTP/2 を確認
curl --http2 -I https://example.com
```

### TLS 証明書を確認する

```bash
# 証明書の情報を表示
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -text | head -30

# 有効期限だけ確認
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates
```

### TCP 接続の観察（tcpdump / Wireshark）

```bash
# ローカルループバック上のトラフィックをキャプチャ（Linux）
sudo tcpdump -i lo -n port 8080

# 特定のホストとの通信をキャプチャ
sudo tcpdump -i eth0 host example.com
```

### ポートスキャン（自分のマシンのみ）

```bash
# 開いているポートを確認
ss -tlnp        # Linux
netstat -an | grep LISTEN  # Mac/Linux 共通

# 特定ポートへの接続テスト
nc -zv localhost 8080
telnet localhost 8080  # 古いが今も使える
```

### dig で DNS を調べる

```bash
# A レコードを確認
dig A google.com

# DNS 解決の各ステップを表示（+trace）
dig +trace example.com

# 特定の DNS サーバーに問い合わせ（Google の 8.8.8.8）
dig @8.8.8.8 example.com
```

## 💡 コラム: 「クラウド」の実体は海の底にある

大陸間のインターネット通信の **99% 以上は、衛星ではなく海底ケーブル**を通っています。太平洋や大西洋の海底に敷かれた光ファイバーの総延長は地球数十周分。あなたが海外のサイトを開くとき、データは文字通り海の底を光の速さで走っています。

海底ケーブルには逸話が豊富です。かつて**サメがケーブルを噛む**事故が確認され、Google はケーブルをケブラー繊維(防弾チョッキの素材)で覆いました。船の錨や漁具による切断は今も起き、専用の敷設船が世界中で修理に走り回っています。

「クラウド」という言葉は、雲のようにどこか空中にデータが漂っている印象を与えますが、実体は**海底の光ファイバーと、地上の巨大な建物(データセンター)の中の物理的なコンピュータ**です。この物理感覚は実務で効きます — 東京とアメリカ東海岸の間の通信に約 150〜200 ミリ秒かかるのは、ソフトウェアが遅いのではなく、**光の速度という物理法則**だからです。どんな最適化も光より速くはなれません。

## まとめ

| 概念 | 要点 |
|------|------|
| OSI モデル | 7層構造でネットワーク通信を抽象化。開発者は主に第4〜7層を意識する |
| IP アドレス | ネットワーク上の住所。`127.0.0.1` は自分自身 |
| ポート番号 | サービスの窓口番号。80=HTTP、443=HTTPS、22=SSH |
| TCP | 信頼性のある通信。3-way ハンドシェイクで接続確立 |
| TLS | 暗号化通信。証明書で相手の身元を確認 |
| DNS | ドメイン名を IP アドレスに変換。階層的な仕組み |

## 確認問題

1. TCP の 3-way ハンドシェイクの手順を順番に説明してください。

2. HTTP と HTTPS の違いを、セキュリティの観点から説明してください。

3. `dig +trace google.com` を実行し、DNS 解決がどのような順序で行われたかを説明してください。

4. `curl -vI https://example.com` を実行し、TLS ハンドシェイクに関する行を見つけて説明してください。

5. ポート番号の意味を説明し、よく使うポート番号を3つ挙げてください。
