# Lesson 05: クラウド基礎

## 学習目標

- クラウドで「何を借りているのか」を 5 つの資源に分けて説明できる
- IaaS / PaaS / SaaS の違いを、管理責任の境界という観点から説明できる
- 事業者が違っても変わらないサービスの役割を理解する
- 最小権限の原則と、可用性ゾーンを分ける理由を説明できる

実際に AWS を触る手順は [付録: AWS を実際に触る](../appendix/05-aws-hands-on.md) にあります。**先にこの本文を読んでください。**手順だけ真似すると、何をしているのか分からないまま請求書だけが届きます。

## 1. クラウドとは「何を借りることか」

### 従来のオンプレミス（On-Premises）

```
自社サーバー室
├── サーバー機器（購入・保守）
├── ネットワーク機器（購入・保守）
├── 電源・冷却設備
└── データセンター契約
   → 初期費用が大きい
   → キャパシティの変更が難しい
   → ハードウェア障害の対応が必要
```

### 借りているものは 5 つしかない

クラウドの製品名は数百あり、毎年増えます。しかし**借りている資源そのものは 5 種類しかありません。**

| 資源 | 何をするものか | 課金のされ方 |
|---|---|---|
| **計算** | プログラムを動かす | 動かしていた時間 × 性能 |
| **保存** | データを置いておく | 置いた量 × 期間 |
| **通信** | データを運ぶ | 運んだ量(特に外向き) |
| **アイデンティティ** | 誰が何をしてよいかを決める | 通常は無料 |
| **観測** | 何が起きているかを見る | 集めたログとメトリクスの量 |

新しいサービス名を見たら、**「これは 5 つのどれを、どう束ねたものか」**と問いてください。この問い方は、製品名がすべて入れ替わっても使えます。

**主な特徴**:
- **オンデマンド**: 必要なときにすぐ調達できる
- **従量課金**: 使った分だけ支払う
- **弾力性**: トラフィックに応じてスケールアップ/ダウンできる
- **可用性**: 世界中にデータセンターを持ち、冗長化されている

## 2. IaaS / PaaS / SaaS

クラウドサービスは「どこまでクラウドに任せるか」によって分類されます。
言い換えると、**責任の境界がどこに引かれているか**の違いです。

### サービスモデルの比較

```
オンプレ     IaaS         PaaS         SaaS
--------    --------     --------     --------
アプリ       アプリ        アプリ        [提供済み]
ランタイム   ランタイム    [提供済み]   [提供済み]
OS          OS           [提供済み]   [提供済み]
仮想化       [提供済み]   [提供済み]   [提供済み]
サーバー     [提供済み]   [提供済み]   [提供済み]
ネットワーク  [提供済み]   [提供済み]   [提供済み]

[提供済み] = クラウド側が管理
```

### IaaS（Infrastructure as a Service）

**インフラをクラウドで提供**するサービスです。
VM・ストレージ・ネットワークを貸し出し、OS 以上の管理はユーザーが行います。

```
用途: OS からカスタマイズしたい、既存のシステムをそのまま移行したい
メリット: 柔軟性が高い
デメリット: OS・ミドルウェアの管理が必要
```

### PaaS（Platform as a Service）

**アプリケーションの実行基盤を提供**するサービスです。
コードをデプロイするだけで動く。OS・ランタイムの管理不要。

```
用途: アプリ開発に集中したい、インフラ管理を減らしたい
メリット: インフラ管理が不要
デメリット: カスタマイズの自由度が低い
```

### SaaS（Software as a Service）

**完成したソフトウェアをクラウドで提供**するサービスです。
ユーザーはソフトウェアを使うだけ。

例: メール、チャット、ソースコードホスティング、顧客管理

```
用途: ソフトウェアをそのまま利用したい
メリット: インストール・管理不要
デメリット: カスタマイズは限定的
```

### 責任は移せるが、消えない

**重要な誤解があります。**「クラウドに任せた部分は自分の責任ではない」というのは正しくありません。

事業者が責任を負うのは**クラウド自体の稼働**であり、あなたが責任を負うのは**クラウドの中に置いたもの**です。設定を間違えて全世界にデータを公開したなら、それはあなたの責任です。実際、大規模な情報漏洩の多くは事業者の障害ではなく、**利用者の設定ミス**で起きています。

PaaS を使えば OS の管理からは解放されますが、権限設計と、置いたデータの中身からは解放されません。

## 3. どの事業者にも同じものがある

主要なクラウド事業者は、同じ役割のサービスを**違う名前で**提供しています。名前を覚えるより、**役割の一覧を覚えるほうが長持ちします。**

| 役割 | AWS | Google Cloud | Azure |
|---|---|---|---|
| 仮想サーバ | EC2 | Compute Engine | Virtual Machines |
| コンテナ実行 | ECS / EKS | Cloud Run / GKE | Container Apps / AKS |
| 関数実行(サーバーレス) | Lambda | Cloud Functions | Functions |
| オブジェクト保存 | S3 | Cloud Storage | Blob Storage |
| マネージド RDB | RDS | Cloud SQL | Database for PostgreSQL |
| マネージド NoSQL | DynamoDB | Firestore | Cosmos DB |
| キャッシュ | ElastiCache | Memorystore | Cache for Redis |
| 仮想ネットワーク | VPC | VPC | Virtual Network |
| DNS | Route 53 | Cloud DNS | DNS |
| CDN | CloudFront | Cloud CDN | Front Door |
| ロードバランサ | ELB | Cloud Load Balancing | Load Balancer |
| 権限管理 | IAM | IAM | Entra ID |
| 秘密情報の保管 | Secrets Manager | Secret Manager | Key Vault |
| 監視・ログ | CloudWatch | Cloud Monitoring | Monitor |
| 操作の監査ログ | CloudTrail | Cloud Audit Logs | Activity Log |

**この表の名前は変わります。役割の列は変わりません。**

事業者を乗り換えるとき、あるいは求人票で知らない名前を見たとき、左の列で考えられれば「ああ、あれのことか」と分かります。逆に AWS の名前だけを暗記していると、乗り換えのたびに学び直しになります。

## 4. 典型的な構成

役割で書くと、どの事業者でも構成はこうなります。

```
インターネット
     |
   [DNS]                ← 名前を IP に変換する
     |
   [CDN]                ← 静的ファイルを利用者の近くでキャッシュする
     |
[ロードバランサ]         ← トラフィックを複数のサーバへ分散する
     |
     +--- [アプリ (可用性ゾーン A)]
     +--- [アプリ (可用性ゾーン B)]   ← 障害の範囲を分ける
     |
     +--- [DB 主系 (ゾーン A)] ←→ [DB 待機系 (ゾーン B)]
     +--- [キャッシュ]
     |
[オブジェクトストレージ]   ← 画像・バックアップ
[監視・ログ]              ← 全体で何が起きているかを見る
[権限管理]                ← 誰が何をしてよいかを決める
```

### 可用性ゾーン（Availability Zone）を分ける理由

可用性ゾーンとは、同じ地域の中にある**電源とネットワークが独立したデータセンター**です。

分けるのは「なんとなく安心だから」ではありません。**障害には必ず範囲(failure domain)があり、その範囲より広く分散させないと意味がない**からです。

- サーバ 1 台の故障 → 同じゾーン内の別サーバで足りる
- データセンターの停電・水没・火災 → **別のゾーンでなければ助からない**
- 地域全体の災害 → 別の地域(リージョン)が必要

同じゾーンにサーバを 10 台並べても、そのゾーンが落ちれば 10 台とも落ちます。**冗長化とは台数を増やすことではなく、同時に壊れない場所に置くことです。**

この考え方はクラウドに限りません。バックアップを同じ建物に置かない理由も、まったく同じです。

## 5. 権限 — 最小権限の原則

### なぜ最も重要か

クラウドで起きる深刻な事故の多くは、計算資源やネットワークではなく**権限の設計ミス**から起きます。「とりあえず全権限」で作ったものが、そのまま本番に残るのが典型です。

### 最小権限の原則（Principle of Least Privilege）

**必要最低限の権限だけを付与する**のが鉄則です。

```
悪い例: アプリのサーバに「すべての操作」を許可する
           → 万が一侵害されると全リソースが危険

良い例: そのアプリが読む必要のあるバケットへの Read 権限だけを許可する
           → 侵害されても被害がその範囲に留まる
```

大事なのは「侵害されないようにする」ことではありません。**侵害されたときに被害がどこで止まるかを、あらかじめ決めておく**ことです。事故は起きる前提で設計します。

### 権限を構成する 4 つの概念

名前は事業者ごとに違いますが、この 4 つはどこにでもあります。

```
ユーザー   → 人間が使うアカウント
ロール     → サービスやアプリが引き受ける身分
             (サーバにロールを割り当てると、その中のアプリが権限を得る)
グループ   → 複数のユーザーをまとめて扱う単位
ポリシー   → 「誰が」「何を」「どこに対して」できるかを書いた文書
```

### ポリシーは「主体・動作・対象」で読む

書式は事業者ごとに違いますが、**読み方は同じ**です。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

- **Effect**: 許可するのか、拒否するのか
- **Action**: 何をしてよいか(この例では、オブジェクトの取得と書き込み)
- **Resource**: どこに対してか(この例では、特定のバケットの中だけ)

`"Resource": "*"`(すべて)や `"Action": "*"`(何でも)を見たら、立ち止まってください。**それが必要な理由を説明できないなら、必要ありません。**

### 長期間有効な鍵を作らない

権限と並んで事故が多いのが、**アクセスキー**です。長期間有効な認証情報をうっかりリポジトリに入れると、公開された瞬間から誰でも使えます。公開リポジトリに置かれた鍵は、自動的に探し回る仕組みによって**数分で発見されます。**

可能な場合は、期限付きの認証情報(ロールの引き受け)を使い、長期の鍵は作らないのが原則です。

## 6. 費用の考え方

具体的な料金と無料枠の条件は変わり続けるので、ここには書きません。**変わらないのは仕組みのほうです。**

| 原則 | 中身 |
|---|---|
| **止めても消えない課金がある** | 計算を止めてもディスクは残り、課金され続ける。消すまで終わらない |
| **外向きの通信は高い** | データを入れるのは安く、出すのは高い。これはどの事業者もほぼ同じ |
| **使っていない資源にも課金される** | 確保したまま使っていない固定 IP など。直感に反するので事故りやすい |
| **気づける状態を先に作る** | 請求アラートは、リソースを 1 つ作る前に設定する |

最後の 1 つが最も重要です。クラウドの費用事故は、金額の大小ではなく**気づくのが遅れること**で深刻になります。

## 💡 コラム: 自家発電をやめた日 — クラウドは電力会社である

20世紀初頭まで、工場は**自前の発電機**を持っていました。発電は工場経営の重要スキルだったのです。しかし電力網が発達すると、ほぼすべての工場が自家発電をやめました。理由は単純 — **電気は「使った分だけ払う」ほうが、安く、確実で、本業に集中できる**からです。今日「うちは自家発電にこだわる工場です」と聞いたら、よほど特殊な事情を想像するでしょう。

クラウドはこの転換のコンピュータ版です。「サーバーを買い、ラックに設置し、電源と空調を管理する」自家発電の時代から、「クレジットカード1枚で、使った分だけ払う」電力網の時代へ。AWS 自体、Amazon が自社の EC サイトを支えるために磨いた内部基盤を、2006年に外販し始めたのが起源です。

見落とされがちな側面も一つ: クラウドは**個人開発者への民主化**でもありました。かつて大企業しか持てなかった規模のインフラを、学生が数百円で数時間だけ借りられる。あなたがこの Phase でデプロイする練習アプリは、Netflix と同じ発電網につながっています。

## まとめ

| 概念 | 要点 |
|------|------|
| 借りているもの | 計算・保存・通信・アイデンティティ・観測の 5 つ。製品名はこれらの組み合わせ |
| IaaS | VM を貸し出し。OS 以上の管理はユーザーが行う |
| PaaS | アプリ実行基盤を提供。コードをデプロイするだけ |
| SaaS | 完成したソフトウェアを使うだけ |
| 責任の境界 | 事業者はクラウド自体を、利用者は中に置いたものを守る。設定ミスは利用者の責任 |
| 事業者の違い | 役割は共通、名前が違うだけ。役割で覚える |
| 可用性ゾーン | 冗長化とは台数ではなく、同時に壊れない場所に置くこと |
| 最小権限の原則 | 侵害されない設計ではなく、侵害されても被害が止まる設計 |
| 費用 | 止めても消えない課金がある。気づける状態を先に作る |

## 確認問題

1. IaaS、PaaS、SaaS の違いを、「管理責任の境界」という観点から説明してください。

2. クラウドで借りている資源を 5 つ挙げ、それぞれの課金のされ方を説明してください。

3. 「クラウドに任せた部分は自分の責任ではない」という考えは、どこが誤りですか。

4. 可用性ゾーンとは何ですか。同じゾーンにサーバを 10 台置くのでは不十分なのはなぜですか。

5. 最小権限の原則とは何ですか。「侵害を防ぐこと」とはどう違いますか。

6. あるサービスのポリシーに `"Resource": "*"` と書かれていました。何を確認すべきですか。

7. 請求アラートを、リソースを作る**前**に設定すべきなのはなぜですか。
