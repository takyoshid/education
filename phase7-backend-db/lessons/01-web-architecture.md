# Lesson 01: バックエンドの役割と Web アプリの全体像

## このレッスンで学ぶこと

- Web アプリケーションが動く仕組みの全体像
- 3 層アーキテクチャ(Three-Tier Architecture)とは何か
- フロントエンドとバックエンドの役割の違い
- クライアント・サーバーモデルの基礎

---

## 1. Web アプリケーションを「外から」見る

ブラウザで `https://example.com/users` にアクセスするとき、裏側では何が起きているのでしょうか。

簡単に言うと、次の 3 ステップです。

```
[ブラウザ] ---(リクエスト)---> [サーバー] ---(クエリ)---> [データベース]
[ブラウザ] <--(レスポンス)--- [サーバー] <--(結果)----- [データベース]
```

このやり取りを **クライアント・サーバーモデル(Client-Server Model)** と呼びます。

- **クライアント(Client)**: ブラウザやスマートフォンアプリ。ユーザーが直接触る側。
- **サーバー(Server)**: クライアントからのリクエストを受け取り、処理を行い、レスポンスを返す側。
- **データベース(Database)**: データを永続的に保存する場所。

---

## 2. 3 層アーキテクチャ

現代の Web アプリケーションは多くの場合、**3 層アーキテクチャ(Three-Tier Architecture)** で構成されます。

```
+---------------------------+
|  プレゼンテーション層      |  (Presentation Layer)
|  フロントエンド            |  HTML / CSS / JavaScript
|  ブラウザで動く            |
+---------------------------+
           |
           | HTTP 通信
           |
+---------------------------+
|  アプリケーション層        |  (Application Layer / Business Logic Layer)
|  バックエンド              |  Python(FastAPI), Node.js, Ruby on Rails など
|  サーバーで動く            |
+---------------------------+
           |
           | SQL / ORM
           |
+---------------------------+
|  データ層                  |  (Data Layer)
|  データベース              |  PostgreSQL, MySQL, SQLite など
|  データを永続化する         |
+---------------------------+
```

### 各層の役割

**プレゼンテーション層**
- ユーザーインターフェース(UI)を担当
- Phase 6 で学んだ React などのフロントエンドがここ
- データを「どう見せるか」を決める
- バックエンドから受け取ったデータを画面に表示する

**アプリケーション層**
- ビジネスロジック(Business Logic)を担当
- 「ユーザーが商品を購入する」「在庫を減らす」「メールを送る」といった処理
- データの整合性チェック(バリデーション)もここで行う
- Phase 7 のメインテーマ

**データ層**
- データの永続化(Persistence)を担当
- アプリケーションが終了してもデータが消えないように保存する
- SQL を使ってデータを操作する

### なぜ層を分けるのか

層を分ける理由は主に 3 つあります。

1. **関心の分離(Separation of Concerns)**: 各層が自分の責務だけに集中できる。UI の変更がデータベースの設計に影響しない。
2. **独立したスケーリング**: アクセスが増えたとき、バックエンドサーバーだけを増やすといった対応ができる。
3. **テストのしやすさ**: 各層を独立してテストできる。

## 3. バックエンドとは何をするものか

バックエンドの主な仕事を整理します。

### 3-1. リクエストの受け付けと処理

クライアントからの HTTP リクエストを受け取り、適切な処理を行ってレスポンスを返します。

```
クライアント: 「/api/users/42 のユーザー情報をください」
バックエンド: データベースに問い合わせ、結果を JSON で返す
```

### 3-2. データの検証(バリデーション)

クライアントから送られてきたデータが正しいかチェックします。

```
クライアント: 「メールアドレス: 'abc' でユーザーを作って」
バックエンド: 「それはメールアドレスの形式ではありません」と拒否する
```

悪意あるユーザーが不正なデータを送ってくる可能性があるため、**バックエンドでの検証は必須**です。フロントエンドでの検証はあくまで UX(ユーザー体験)のためです。

### 3-3. 認証と認可

- **認証(Authentication)**: 「あなたは誰ですか？」→ ログイン処理
- **認可(Authorization)**: 「あなたはこの操作をして良いですか？」→ アクセス制御

### 3-4. データの永続化

データベースへの読み書きを管理します。

### 3-5. 外部サービスとの連携

メール送信サービス、決済サービス、地図 API など、外部の API を呼び出す処理もバックエンドが担当します。

---

## 4. API とは何か

**API(Application Programming Interface)** は、ソフトウェア同士が通信するための「窓口」です。

Web の文脈では特に **Web API** を指し、HTTP を使ってデータをやり取りします。

```
フロントエンド
    |
    | POST /api/login  (JSON でメールとパスワードを送る)
    |
バックエンド (API サーバー)
    |
    | 認証処理
    |
    | レスポンス: { "token": "eyJ..." }
    |
フロントエンド (トークンを保存し、次のリクエストに使う)
```

### なぜ API という形にするのか

フロントエンドがバックエンドに直接アクセスするのではなく、API という「契約(インターフェース)」を介することで：

- フロントエンドとバックエンドを**別チームが開発**できる
- 同じバックエンドを Web アプリ・スマホアプリ・他社サービスで**再利用**できる
- バックエンドの実装を変えても、API の仕様さえ変わらなければフロントエンドに影響しない

## 💡 コラム: レストランで理解する Web アーキテクチャ

Web システム全体は、レストランに置き換えるとほぼ完全に対応します。

- **フロントエンド** = ホール(客が見る内装、メニュー、接客)
- **バックエンド** = 厨房(注文を受けて実際に調理する)
- **データベース** = 食材庫(すべての材料が保管されている)
- **API** = 注文伝票の書式(ホールと厨房の間の取り決め)

この例えの本当の価値は「**分離の理由**」を説明できることです。ホールの改装(UI リニューアル)に厨房を止める必要はなく、厨房の設備更新(バックエンドの改善)は客に見えません。**伝票の書式(API)さえ変わらなければ、両者は独立に進化できる**のです。

逆に、ウェイターが厨房に勝手に入って調理を始める(フロントエンドが DB を直接触る)店は、必ず混乱します。今後アーキテクチャの議論で迷子になったら、「この店ではいま、誰がどこで何をしている?」と翻訳してみてください。

## まとめ

- Web アプリは「フロントエンド → バックエンド → データベース」の 3 層で構成される
- バックエンドはビジネスロジックの実行、バリデーション、認証、DB との通信を担当する
- API はフロントエンドとバックエンドの間の「契約」であり、再利用性と独立した開発を可能にする
- Phase 7 ではバックエンド(アプリケーション層)とデータ層を構築するスキルを習得する

## よくある間違い

**「バックエンドはフロントエンドよりも難しい」という先入観**
バックエンドとフロントエンドは難しさが異なるだけで、どちらが難しいという話ではありません。バックエンドは「見えない部分を設計する」スキル、フロントエンドは「ユーザー体験を設計する」スキルが中心です。

**「データベースはバックエンドサーバーと同じマシンに置くもの」という誤解**
本番環境では多くの場合、バックエンドサーバーとデータベースサーバーは**別のマシン**で動いています。ネットワーク越しに通信します。

**「フロントエンドから直接 DB に接続すれば良いのでは」という疑問**
フロントエンドから直接 DB に接続すると、DB の接続情報(パスワードなど)がブラウザに露出し、セキュリティ上の重大な問題になります。バックエンドはセキュリティのゲートキーパーでもあります。
