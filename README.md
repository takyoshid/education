# 世界で通用するソフトウェアエンジニアへの道

高校生以上、または同等の読解力を持つ完全初学者が、世界のどこでも通用するソフトウェアエンジニアになるための体系的教材。

## 対象となる学習者

この教材は、**高校生以上、または同等の読解力を持つ学習者**を対象とします。年齢だけで判断せず、次を目安にしてください。

- 1,000〜2,000字程度の説明を読み、要点を自分の言葉で説明できる
- 分からない言葉を自分で調べながら読み進められる
- 30分程度、一つの問いについて考えたり試したりできる
- 保護者、先生、メンター、学習仲間のいずれかに成果を説明し、助言を受けられる

小学生・中学生が取り組む場合は、上の目安を満たしていても、環境構築、外部サービスの利用、個人情報、課金、公開作業について保護者または指導者が伴走してください。この教材は低年齢向けに文章や課題時間を調整した版ではありません。

上の読解力へまだ達していない学習者や、手を動かす探究から始めたい8〜14歳程度の学習者には、独立した[子ども版 — くるくる探究ラボ](children-track/)があります。子ども版は13のPhaseを短くしたものではありません。「観察→予想→作る→壊す→説明→改善」を、紙、積み木、料理、ゲームなどから始め、難度を上げながら繰り返す螺旋型教材です。

## 🌟 旅の始まりに: 180年前、最初のプログラマーは詩人の娘だった

1843年、コンピュータが物理的に存在するより100年も前に、世界初のプログラムを発表した人物がいます。詩人バイロンの娘、**エイダ・ラブレス**です。彼女はチャールズ・バベッジの「解析機関」(歯車式の計算機械の設計)について論文の注釈を書き、その中で機械にベルヌーイ数を計算させる手順 — 史上初の公開されたプログラム — を記述しました。

彼女の言葉は、機械の本質を誰よりも早く見抜いていました。

> 「解析機関は、ジャカード織機が花や葉を織り上げるのとまったく同じように、**代数のパターンを織り上げる**。」

さらに彼女は「この機械はいつか、精緻で科学的な音楽を作曲するかもしれない」とまで予言しています。存在しない機械の可能性を、数学と想像力だけで見通した — 彼女は自分の方法を「**詩的科学(poetical science)**」と呼びました。

これからあなたが始める学習は、この180年続く人類の物語の続きです。ようこそ。

## この教材の設計思想

1. **手を動かして学ぶ** — 各Phaseに演習・模範解答・実技試験・総仕上げプロジェクトがある。読むだけでは修了できない
2. **なぜ動くかを理解する** — 暗記ではなく原理から。CS基礎を省略しない
3. **世界基準** — 技術用語は英語併記。英語ドキュメントを読み、英語で発信できる力を育てる
4. **プロの現場を再現** — Git、コードレビュー、テスト、設計を初期から習慣化する
5. **AI時代対応** — AIツールを使いこなしつつ、AIに依存しない基礎力を築く

## 最初に学ぶ「永久層」

技術Phaseへ入る前に、[永久層 — 変化しても使い続ける6つの力](foundation-permanent/)を学びます。

1. 問いを作る
2. 問題を分解する
3. 証拠を集める
4. 仮説を比較する
5. 試して間違いを更新する
6. 他者へ説明し協力する

ここでいう「永久」とは、書かれた答えを永久に信じることではありません。**教材を含むあらゆる主張を、問い、証拠、反例によって検討し、よりよい考えへ更新する方法**が長く使えるという意味です。

永久層は一度で修了する科目ではありません。Phase 0以降の調査、設計、デバッグ、レビュー、AI利用、実ユーザーとの対話で繰り返し使います。

### 子ども版から始める場合

[子ども版](children-track/)の4周は、永久層の考え方を短い活動で体験できる入口です。年齢だけで機械的に進級させず、子ども版で「予想を先に残す」「証拠で考えを変える」「他者の意見を言い直す」が自力ででき、上の読解力の目安を満たした時点で永久層へ進みます。

## 「修了」の定義

この教材では、読了や自己申告だけを修了としません。通常演習に加えて、初見課題、口頭説明、実行ログ、第三者レビューによって到達度を確認します。

- [客観的到達度評価ガイド](assessment/) — AI利用可・不可の評価、Phase別ゲート、証拠の残し方
- [Phase横断プロジェクト](longitudinal-project/) — Phase 2から12まで同じプロダクトを変更・運用し続ける実務課題

各Phaseのチェックリストは学習範囲の確認、上記の評価ゲートは能力の確認です。両方を満たして修了とします。

### 選択 Phase — 5 と 6 はどちらが先でもよい

Phase 5(アルゴリズム)と Phase 6(Web フロントエンド)の間に依存はありません。**Phase 6 のレッスン・演習・プロジェクトは、Phase 5 の内容を一切使いません。**

**順番は自由ですが、Phase 7 へ進むまでに両方を修了してください。**「どちらか片方でよい」という意味ではありません。

| 先にやるもの | 向いている人 |
|---|---|
| **6 → 5** | 早く動くものを見たい。画面が出ると続けられる |
| **5 → 6** | 仕組みを理解してから応用したい |

なお**どちらを選んでも、面接演習の「進め方の練習」は Phase 2 修了後から始められます。**パターン演習は Phase 5 の該当レッスン後です(詳細は[既知の未整備領域](#-既知の未整備領域))。

## 対応バージョン

必要なツールの版は [versions.md](versions.md) の 1 枚にまとめてあります。各 Phase の README や設定ファイルがその表と食い違っていれば CI が失敗します。

版の数字はこの教材で最も早く腐る情報です。1 箇所に集めておけば、更新のたびに触るファイルが 1 つで済み、**100 年もつはずの説明文に不用意な編集が入らずに済みます。**

ただし、レッスン本文に出てくる「`dict` が挿入順を保つのは Python 3.7 以降」のような記述は、この表の管理下にありません。それは要件ではなく歴史的事実であり、**書き換えてはいけないもの**だからです。理由は versions.md に書いてあります。

## 教材に同梱した API サーバ

演習やプロジェクトでデータを取ってくる場面では、外部のサービスではなく**教材に同梱したサーバ**を使います。

```bash
python3 fixtures/server.py
```

依存パッケージはゼロで、オフラインでも動きます。

外部サービスを使わないのは、**教材の寿命を他人のサーバの寿命に縛られないため**です。サービスは止まり、無料枠は消え、レスポンスの形は予告なく変わります。そのどれが起きても原因は教材の外にあるのに、「教材のとおりに書いたのに動かない」という体験をするのは学習者です。

もう一つ、同じくらい重要な理由があります。このサーバは**失敗を狙って起こせます。**

```bash
curl "http://127.0.0.1:8787/posts?_delay=3000"   # 3 秒待ってから返る
curl "http://127.0.0.1:8787/posts?_fail=503"     # 503 で失敗する
curl "http://127.0.0.1:8787/posts?_empty=1"      # 0 件で返る
```

この教材は一貫して「idle / loading / success / empty / error を区別できること」を受け入れ条件に置いています。実在の API ではサーバが落ちるのを待つわけにいかず、これらの状態を確かめられません。

詳細は [fixtures/README.md](fixtures/) にあります。なお、DNS や TLS のように**ネットワークそのものが主題**の場面では、このサーバではなく実在のネットワークを使います。

## 各 Phase の構成

以下は**標準構成**です。Phase の目的に応じて一部のディレクトリを別の成果物で代替します。ディレクトリがない場合も、教材の欠落を意味するとは限りません。

```
phaseN-<name>/
├── README.md        # 学習目標・前提・修了条件チェックリスト
├── lessons/         # 01-xx.md 形式のレッスン
├── exercises/       # 演習問題
│   └── solutions/   # 模範解答(解説付き)
└── project/         # Phase 総仕上げのミニプロジェクト
```

一部の Phase には `appendix/` があります。**特定の製品の手順を、レッスン本文から分けて置く場所**です。

レッスン本文には、製品が入れ替わっても変わらない考え方だけを置きます。クラウドの画面操作、CI の記法、エディタのショートカット、AI ツールの製品名といった「早く古くなるもの」は付録に置きます。

この分け方には目的があります。**製品の更新があっても、触るのは付録だけで済む**ようにするためです。数字や手順を直すたびに本文へ手が入ると、100 年もつはずの説明が少しずつ削れていきます。

付録が実物と合わなくなっていたら、公式ドキュメントを見て**付録のほうを直してください。**本文を疑う必要はありません。

主な例外は次のとおりです。

- **Phase 0:** 調査・質問作成・環境構築などの演習そのものを成果物とするため、独立した `project/` は設けません。
- **Phase 4:** 本編と並走し、後続 Phase の成果物に AI 活用・レビュー・eval を適用し続けるため、独立した `project/` は設けません。
- **Phase 12:** `exercises/`・`project/`・Phase 個別の `assessment/` を、実践課題・総合プロジェクト・評価基準を統合した `capstone/` と `oss/` で代替します。
- **客観的到達度評価:** Phase 個別の `assessment/` がない場合は、ルートの [`assessment/`](assessment/) にある共通基準と Phase 別ゲートを使用します。

## 学習の進め方

1. **[永久層](foundation-permanent/)で6つの力を学び、身近な問題で一巡させる**
2. **Phase 0 → 1 → 2 を順に進める**(ここは直列。飛ばせません)
3. **Phase 2 を終えたら、並走 Phase を開始する** — Git(3)、AI活用(4 の Lesson 01・02・05)、設計基礎(9 の Lesson 01・02・07・08)。**どれも一度で終わらせず、以降ずっと使います**
4. **Phase 5 と 6 は好きな順で進める**(依存はありません)
5. **Phase 2 を始めたら[Phase横断プロジェクト](longitudinal-project/)に着手し、Phase 2 を終えたら[英語トラック](english-track/)も並走させる**
6. 各レッスンの演習を解いてから解答を見る
7. Phase 末のチェックリストに加え、[客観的到達度評価](assessment/)のPhaseゲートを満たしてから次へ進む
8. わからないことは 15 分自力で調べ、それでも解けなければ質問する(質問の仕方も Phase 0 で学ぶ)

```
基礎   永久層 ───────────────────────────────────────────────▶ (全期間で反復)

直列          Phase 0 → 1 → 2 ─┬─▶ 5 ─┐
                               │      ├─▶ 7 → 8 → 10 → 11 → 12
                               ├─▶ 6 ─┘
                               │   ↑ 順不同。ただし 7 までに両方修了
                               │
並走                           ├─▶ Git(3) ──────────────────────────────▶
                               ├─▶ AI活用(4) ───────────────────────────▶
                               ├─▶ 設計・テスト(9) ─────────────────────▶
                               ├─▶ 横断プロジェクト ────────────────────▶
                               └─▶ 英語トラック ────────────────────────▶
                                   ← 始めたら最後まで使い続ける

      Phase 11 と 12 は並走できます(capstone は Phase 10 までの技術で作れます)
      Phase 12 の OSS 貢献レッスンは、Phase 3 修了後から読み始めてください
```

### なぜ全部を直列にしないのか

**基礎をすべて積んでから実践する、という順序は学校の形です。**定着という点では効率が良くありません。

人は「作る → 壊れる → 原理に戻る → 直す」という小さな循環で身につけます。設計の原則は、設計に失敗した経験がないと必要性が分かりません。Git のブランチは、作業を壊した経験がないとありがたみが分かりません。

だから、**すぐ使うもの(Git・AI・設計基礎)は Phase 2 の直後から並走させ、経験が要るもの(SOLID・アーキテクチャ・分散システム)は後ろに置いてあります。**[横断プロジェクト](longitudinal-project/)が意図的に障害を起こしてくるのも、同じ理由です。

### Git は Phase 0 から使います

Git は Phase 3 まで待ちません。[Phase 0 の環境構築演習](phase0-orientation/exercises/ex05-env-check.md)で `init / status / add / commit / log` の最小セットを実行し、Phase 2 の演習とプロジェクトは最初から履歴を残します。Phase 3 では、その実体験を土台にブランチ、マージ、GitHub、コードレビュー、誤操作からの復旧を学びます。

## ⚠️ 既知の未整備領域

この教材にも、まだ十分に整備できていない領域があります。**隠さず書いておきます。該当する時期には外部リソースで補ってください。**

### 1. コーディング面接の演習量(未着手)

Phase 5 の演習は**概念の理解には十分**ですが、**面接対策としての問題数が足りません。**

面接を突破する水準に達するには、**同種の問題を大量に解く**ことが実質的な要件とされています。この教材にはその量がなく、外部演習への導線も用意できていません。

**当面の補い方**: 外部の演習プラットフォームを使います。ただし**始める時期は、やる内容によって分かれます。**

**Phase 2 修了後から始めるのは「量」ではありません。**次の 2 つは矛盾しません。

| 時期 | やること | 理由 |
|---|---|---|
| **Phase 2 修了後** | 配列・文字列の易しい問題を 1 日 1 問。**解法の型は使わない** | 問題文を例に変換する、入出力と境界条件を書き出す、まず総当たりで解く、解法を声に出して説明する — これらは**パターンを知らなくてもできる**うえ、面接で最も見られる部分 |
| **Phase 5 の各レッスン修了後** | そのレッスンのパターンの問題を積む | two pointers、スライディングウィンドウ、DFS/BFS、動的計画法。**先に量から入ると解法の暗記になる** |

つまり早く始めるのは**進め方の練習**であって、パターン演習ではありません。Phase 5 を待たずに始められるのは前者だけです。

Phase 5 と Phase 6 は順不同なので、Web を先にした場合、Phase 5 の開始を待つと助走が数か月短くなります。だからこそ、**待たずに始められる部分と、待つべき部分を分けてあります。**

必要な問題数や、どのプラットフォームが定番かは**時期によって変わります**。具体的な目安と現在のリソースは[キャリアと市場](career-track/)にまとめてあり、そこだけを更新すれば済むようにしてあります。就職活動をしないのであれば、**この節は読み飛ばして構いません。**

時期が変わっても変わらないのは、この**順序**のほうです。暗記した解法は、少し形を変えられただけで使えなくなります。

### 2. 英語アウトプットの並走の仕組み(未整備)

やること自体は [英語トラックの「推奨学習ペース」](english-track/#推奨学習ペース)に定義されています(毎朝10分の記事購読、コミットメッセージを英語で書く、週1回の模擬面接など)。内容は妥当です。

**未整備なのは、それを Phase 2 から実行させる仕組みのほうです。**

- Phase 2 を学んでいる学習者には、**英語トラックの README を開く理由がありません**
- 各 Phase のチェックリストに、英語の継続を確認する項目が**ありません**
- [客観的評価ガイド](assessment/)の Phase ゲートに、英語の証拠提出を求める項目が**ありません**

結果として「Phase 2 から並走」は方針として書かれているだけで、**続かなくても誰も気づかない**状態です。語学は最後にまとめて習得できないため、ここが空いていると就職活動の段階で詰みます。

**当面の補い方**: [英語トラックの推奨学習ペース](english-track/#推奨学習ペース)を**今すぐ開いて**、次の 2 つだけでも Phase 2 の時点から始めてください。

1. **コミットメッセージと PR の説明をすべて英語で書く**(Phase 3 の Git 開始時から。追加コストがほぼゼロで、毎日続く)
2. **英語の技術記事を週 1 本読み、3 行で要約して記録する**(記録を残すことが重要)

そして各 Phase の証拠フォルダ `evidence/phase-N/` に `english-log.md` を自分で追加し、継続の記録を残してください。仕組みが無いなら、自分で作るのが最短です。

重要なのは分量ではなく**毎週続くこと**です。週 15 分でも、18 か月続けば別人になります。

## 教材自体の品質確認

CI の検査範囲は次のとおりです。

| 対象 | CI で確認すること |
|---|---|
| 教材全体 | 教材内リンク、Phase 構造、対象ディレクトリ内の Python 構文 |
| 対応バージョン | [versions.md](versions.md) の表と、CI 設定・`package.json`・Docker イメージ・各 Phase の前提知識が一致していること |
| フロントエンドの依存 | `package-lock.json` のとおりに入ること(再現性)と、ロックを無視して解決し直しても壊れないこと(腐りの早期発見)の両方 |
| 同梱 API サーバ | 依存を一切入れずに起動でき、契約テストが通ること(複数の Python で検査) |
| 完成済み Python 成果物 | Phase 2・7・9・10 の4プロジェクトについて、Python 3.12・3.13でテストが通ること |
| 未実装 starter | Phase 8・11の公開演習・Phase 8プロジェクト・Phase横断プロジェクトについて、テストが収集・実行され、意図した未実装箇所で失敗すること |
| 参照実装 | Phase 8・11の実行可能演習とPhase 8プロジェクトについて、同じ公開テストがすべて通ること |
| フロントエンド完成版 | Phase 6 の React プロジェクトと演習の模範実装をbuildできること |

未実装 starter は、公開テストが通ることを検査する対象ではありません。テスト未検出、import エラー、構文エラーを誤って「想定どおりの失敗」と扱わず、`NotImplementedError` のスタブまで到達することを専用検査で確認します。

ローカルでは次を実行できます。

```bash
ruby scripts/validate_curriculum.rb
python3 scripts/validate_versions.py
python3 -m unittest discover -s fixtures/tests
python3 -m compileall -q fixtures phase2-programming phase5-algorithms phase7-backend-db \
  phase9-software-design phase10-infra-cloud phase8-concurrency-reliability \
  phase11-distributed-systems longitudinal-project
python3 scripts/validate_starter_contracts.py
python3 scripts/validate_reference_implementations.py
```
