# 提出前セルフレビューチェックリスト

## このファイルの使い方

キャップストーンプロジェクトの提出前に、このチェックリストをすべて確認します。

**確認方法:** 各項目を実際に操作・確認して `[ ]` を `[x]` に変えてください。「たぶん大丈夫」は通過とみなしません。必ず手を動かして確認します。

チェックリストは 6 つのカテゴリに分かれています。上から順に確認してください。

---

## カテゴリ 1: セキュリティ(Security)

セキュリティの問題があると、採用担当者の評価が大きく下がります。最初に確認します。

```
[ ] .env ファイルが GitHub にコミットされていない
    確認方法: git log --all -- .env で履歴を確認。出力がなければ OK。

[ ] .gitignore に .env が含まれている

[ ] .env.example が存在し、キーの一覧が書かれているが値は仮の値になっている

[ ] 本番環境の SECRET_KEY が開発用の値("your-secret-key" 等)ではない
    確認方法: デプロイサービスの環境変数設定を開いて確認する。

[ ] パスワードが DB に平文で保存されていない
    確認方法: DB の users テーブルを直接確認し、password カラムが $2b$ 等で始まるハッシュ値になっている。

[ ] 認可(Authorization)が正しく実装されている
    確認方法: ユーザー A でログインし、ユーザー B のリソース ID に直接 API リクエストを送る。
    期待値: 403 Forbidden または 404 Not Found が返ること。
```

**詰まりやすいポイント:**

`.env` を一度でもコミットしてしまった場合、単純に削除しても git の履歴に残ります。この場合の対処:

```bash
# 1. git-filter-repo をインストール(pip または brew)
pip install git-filter-repo

# 2. 履歴から .env を完全削除
git filter-repo --path .env --invert-paths

# 3. 強制プッシュ
git push origin --force --all

# 4. 本番の秘密情報(SECRET_KEY 等)を必ず再生成する
```

## カテゴリ 2: 機能(Functionality)

```
[ ] 本番 URL でユーザー登録ができる(新規アカウントを実際に作る)

[ ] 登録したアカウントでログインできる

[ ] ログイン状態でページをリロードしてもログイン状態が維持される

[ ] ログアウトできる

[ ] コア機能のデータを作成できる

[ ] コア機能のデータが一覧で表示される

[ ] コア機能のデータを編集できる

[ ] コア機能のデータを削除できる

[ ] 別のユーザーアカウントを作成し、ユーザー A のデータがユーザー B の画面に表示されない

[ ] 存在しないページ(例: /nonexistent)にアクセスすると 404 画面が表示される

[ ] API エラー時にユーザーが理解できるメッセージが表示される(「エラーが発生しました」等)

[ ] ネットワークタブで 500 エラーが出ていない
    確認方法: ブラウザの開発者ツール → Network タブで赤いリクエストがないことを確認。
```

**詰まりやすいポイント:**

**「ローカルでは動くが本番で動かない」:** 最も多い失敗パターンです。原因は 3 つに絞られます。

1. 環境変数の設定漏れ(デプロイサービスの環境変数を確認)
2. データベースのマイグレーション未実行(本番 DB で `alembic upgrade head` を実行したか確認)
3. CORS の設定(本番フロントエンド URL がバックエンドの `CORS_ORIGINS` に含まれているか確認)

## カテゴリ 3: テスト(Testing)

```
[ ] pytest がすべて通過する
    確認方法: ローカルで pytest を実行し、"passed" のみ表示されることを確認。

[ ] テストが 20 件以上ある

[ ] 認証なしでアクセス保護されたエンドポイントを叩くと 401 が返るテストがある

[ ] 他ユーザーのリソースを操作しようとすると 403 または 404 が返るテストがある

[ ] GitHub Actions で CI が緑(全ジョブ通過)になっている
    確認方法: GitHub リポジトリの Actions タブを開き、最新の実行が成功していることを確認。

[ ] フロントエンドのテストが少なくとも 1 件ある
```

**詰まりやすいポイント:**

**「ローカルで pytest が通るが CI で失敗する」:** 原因として多いのは以下の 3 つです。

1. テスト用 DB の接続設定が CI の GitHub Actions と一致していない
   - `.github/workflows/ci.yml` の `DATABASE_URL` の値と `conftest.py` の値を照合してください。

2. 非同期テストで `pytest-asyncio` の設定が足りない
   ```python
   # pytest.ini または pyproject.toml に追加
   [pytest]
   asyncio_mode = auto
   ```

3. テストの実行順序依存(テスト間で DB の状態が残る)
   - 各テストの `setup` / `teardown` で DB をクリーンアップしているか確認してください。

## カテゴリ 4: インフラ・CI/CD(Infrastructure / CI/CD)

```
[ ] docker compose up --build でローカル環境が起動する

[ ] docker compose down && docker compose up で DB のデータが消えない(volume が設定されている)

[ ] 本番環境が HTTPS で動いている(URL が https:// で始まる)

[ ] 本番 DB で alembic upgrade head が実行済みである

[ ] GitHub Actions の最新実行が成功している

[ ] main ブランチへのプッシュ後に自動でデプロイが実行される(CD が設定されている)
    ※ 手動デプロイの場合はこの項目はスキップ可
```

**詰まりやすいポイント:**

**「Render の無料プランでアプリがスリープする」:** Render の無料プランはアクセスがないと 15 分でスリープします。デモ時に「読み込みに 30 秒かかる」という状態を避けるには:

- デモ前に自分でアクセスして起こしておく
- Cron-job.org 等で 10 分おきに `/healthz` をリクエストするように設定する
- README に「初回ロードに最大 30 秒かかる場合があります」と記載する

**「本番の Alembic マイグレーション失敗」:** Render の場合、ビルドコマンドに `alembic upgrade head` を含めると、ビルド時に DB 接続が必要になります。`DATABASE_URL` の環境変数が設定前にビルドが走るとエラーになります。環境変数を先に設定してから再デプロイしてください。

## カテゴリ 5: コード品質(Code Quality)

```
[ ] ruff / flake8 のエラーが 0 件
    確認方法: ruff check backend/ を実行。

[ ] ESLint のエラーが 0 件
    確認方法: npm run lint を frontend/ で実行。

[ ] TypeScript のコンパイルエラーが 0 件
    確認方法: npx tsc --noEmit を frontend/ で実行。

[ ] コードに使われていない import がない

[ ] console.log のデバッグ出力がプロダクションコードに残っていない
    確認方法: git grep "console.log" frontend/src

[ ] TODO コメントが残っている場合、意図的に残しているもののみである

[ ] any 型の使用が 3 か所以下である
    確認方法: git grep ": any" frontend/src
```

**詰まりやすいポイント:**

**「ruff が大量のエラーを出す」:** `ruff check --fix backend/` で自動修正できるものは一括修正できます。残ったエラーを一つずつ確認してください。

**「ESLint のルールを無効化したい」:** 正当な理由がある場合のみ `eslint-disable` コメントを使います。その場合、なぜ無効化するかをコメントで説明してください。

```typescript
// eslint-disable-next-line @typescript-eslint/no-explicit-any
// サードパーティライブラリ X の型定義が不完全なため any を使用
const response: any = await externalLib.call()
```

## カテゴリ 6: ドキュメント(Documentation)

```
[ ] README.md にプロジェクトの説明がある(何ができるか、なぜ作ったか)

[ ] README.md に本番 URL へのリンクがある

[ ] README.md にスクリーンショットが 1 枚以上あり、画像が表示される(リンク切れでない)

[ ] README.md にローカル環境のセットアップ手順がある(コピペで再現できる)

[ ] README.md に使用技術スタックの一覧がある

[ ] Swagger UI(/docs または /api/docs)が本番環境でも開ける
    ※ セキュリティ上の理由で閉じている場合はスキップ可

[ ] docs/ ディレクトリに要件定義書と Design Doc が格納されている

[ ] GitHub リポジトリの「About」欄に説明文と本番 URL が設定されている
    確認方法: リポジトリのトップページ右上の「About」セクション。
```

**詰まりやすいポイント:**

**「スクリーンショットが GitHub で表示されない」:** 画像ファイルを Git リポジトリに追加するか、GitHub の Issue に画像をドラッグ&ドロップしてアップロードし、生成された URL を README に貼る方法が安定します。

```markdown
<!-- ローカルファイルを参照する場合 -->
![ダッシュボード画面](./docs/screenshots/dashboard.png)

<!-- GitHub にアップロードした画像を参照する場合 -->
![ダッシュボード画面](https://github.com/USERNAME/REPO/assets/XXXXX/dashboard.png)
```

## 最終確認: ポートフォリオとしての完成度

上記のすべてを確認した後、以下の質問に答えてください。

```
[ ] 見知らぬエンジニアに GitHub リポジトリの URL を送って「見てください」と言えるか?

[ ] 採用担当者が本番 URL を開いて、30 秒以内に何ができるアプリか理解できるか?

[ ] 「このプロジェクトで技術的に一番難しかった点は何ですか?」という面接質問に
    具体的に答えられるか?
```

この 3 つに自信を持って「はい」と答えられる状態が、Phase 9 キャップストーンの完成です。
