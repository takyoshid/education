# キャップストーンプロジェクト 評価ルーブリック

## ルーブリックの使い方

このルーブリックは、キャップストーンプロジェクトの完成度を **5 つの観点** × **3 段階** で自己評価するためのものです。

**3 段階の定義:**

- **初級(Beginner):** 基本的な要件を満たしている。動くが改善の余地が大きい。
- **中級(Intermediate):** 実務で通用する品質。採用担当者に見せられる水準。
- **世界レベル(World-class):** OSS のメンテナーやシニアエンジニアが見ても「よくできている」と評価する水準。

提出前に各観点を確認し、「自分は今どの段階にいるか」を正直に記録してください。全観点で中級以上を目指すことが Phase 9 のゴールです。

---

## 観点 1: 機能(Functionality)

### 初級

```
- Must have として定義した機能がすべて動作する
- ユーザー登録・ログイン・ログアウトが動作する
- CRUD(Create / Read / Update / Delete)の基本操作が画面上で完結する
- 本番 URL でアプリにアクセスできる
```

### 中級

```
- Must have に加えて Should have の機能が 1 つ以上実装されている
- 認可(Authorization)が正しく実装されている(他ユーザーのデータを操作できない)
- エラーケース(存在しないリソースへのアクセス、バリデーション違反等)が適切に処理される
- ローディング状態・エラー状態のフィードバックがユーザーに表示される
- デモ用のサンプルデータが本番環境に投入されており、すぐに試せる
```

### 世界レベル

```
- Could have(余力機能)まで実装されている
- レート制限(Rate Limiting)やページネーション(Pagination)が実装されている
- リアルタイム更新(WebSocket または Server-Sent Events)が 1 か所以上ある
- オフライン時のフォールバックまたは楽観的更新(Optimistic Update)が実装されている
- アクセシビリティ(Accessibility / a11y)対応: キーボード操作・スクリーンリーダー対応
```

## 観点 2: コード品質(Code Quality)

### 初級

```
- コードが動いている(構文エラー・実行時エラーがない)
- TypeScript を使っている(any 型が多用されていない)
- コミットが 1 件以上ある
- .env が .gitignore に含まれており、秘密情報がリポジトリにない
```

### 中級

```
- 単一責任の原則(Single Responsibility Principle)に沿ってファイルが分割されている
  - 例: ルーター / サービス / リポジトリ / スキーマ が分離されている
- TypeScript で any 型の使用がない(または最小限)
- 関数・変数名が意図を表している(コードを読めば動作が推測できる)
- linter(ruff / ESLint)・フォーマッター(Black / Prettier)のエラーが 0 件
- コミット粒度が適切で、コミットメッセージが Conventional Commits 形式に従っている
- SECRET_KEY・API キー等の秘密情報が環境変数で管理されている
```

### 世界レベル

```
- 依存性注入(Dependency Injection)が実装されており、テスタビリティが高い
- 循環インポート(Circular Import)がない
- 型安全性が徹底されている(TypeScript の strict モードが有効、Python の型ヒントが完全)
- 設計原則(SOLID)が意識されており、将来の機能追加でも大きな修正が不要な設計になっている
- コードレビューを想定した PR 単位のコミット履歴がある
- セキュリティの観点からコードが書かれている(入力サニタイズ、SQLi / XSS 対策の確認)
```

## 観点 3: テスト(Testing)

### 初級

```
- バックエンドのユニットテスト(Unit Test)が 5 件以上通過する
- pytest が CI 上で実行される
```

### 中級

```
- バックエンドのテストが 20 件以上通過する
- 以下のケースがカバーされている:
  - 正常系(Happy Path): 期待通りの入力で期待通りの結果が返る
  - 異常系(Error Case): 存在しない ID / バリデーション違反 / 認証なし のときに正しいエラーが返る
  - 認可テスト: 他ユーザーのリソースを操作しようとすると 403 が返る
- フロントエンドの主要コンポーネントに Vitest + React Testing Library のテストがある
- GitHub Actions で lint / test / build がすべて通過している(緑になっている)
```

### 世界レベル

```
- バックエンドの API カバレッジが 80% 以上(pytest-cov で計測)
- フロントエンドのテストがユーザーの操作フローをカバーしている
  (ログイン → データ作成 → 表示の確認 等)
- E2E テスト(End-to-End Test)が Playwright または Cypress で 1 フロー以上実装されている
- テストがドキュメントの役割を果たしている
  (テスト名を読めば仕様が分かる命名になっている)
- パフォーマンステスト・負荷テストの実施記録がある
```

## 観点 4: インフラ・CI/CD(Infrastructure / CI/CD)

### 初級

```
- Docker Compose でローカル環境が一発起動できる
- 本番環境 URL でアプリが動いている
- GitHub Actions で CI が設定されている
```

### 中級

```
- docker compose up --build の一コマンドで開発環境が再現できる
- .env.example が最新の状態に保たれており、新規参加者がセットアップできる
- 本番環境で HTTPS が有効になっている
- Alembic のマイグレーションが管理されており、alembic upgrade head で DB が最新状態になる
- 本番環境の環境変数が適切に管理されている(GitHub Secrets または デプロイサービスの環境変数機能)
- GitHub Actions で main ブランチへのプッシュ時に自動デプロイが実行される(CD が実現されている)
```

### 世界レベル

```
- 本番環境のログが可視化されている(Render のログ、または Datadog / Sentry 等)
- エラー監視(Error Monitoring)が実装されており、本番エラーが通知される
- データベースバックアップの仕組みがある
- ゼロダウンタイムデプロイ(Zero-downtime Deployment)を意識した設定がある
- IaC(Infrastructure as Code)の考え方でインフラ設定がコード化されている
- セキュリティヘッダー(Content-Security-Policy, X-Frame-Options 等)が設定されている
```

## 観点 5: ドキュメント(Documentation)

### 初級

```
- README.md が存在する
- プロジェクトの説明が 1 文以上ある
- セットアップ手順が書かれている
```

### 中級

```
- README.md に以下がすべて含まれている:
  - プロジェクトの概要(何ができるか、なぜ作ったか)
  - デモ URL へのリンク
  - スクリーンショットまたはデモ GIF
  - ローカル開発環境のセットアップ手順(コピペで再現できる)
  - 使用技術スタック一覧
  - ディレクトリ構成の説明
- API のエンドポイント一覧が Swagger UI(/docs)または README に記載されている
- 要件定義書・Design Doc が docs/ ディレクトリに格納されている
```

### 世界レベル

```
- README が「採用担当者」「技術的レビュアー」「利用者」それぞれの視点で読めるよう構成されている
- 設計上の意思決定(なぜこの技術を選んだか、どのトレードオフを選択したか)が
  Design Doc または README の ADR(Architecture Decision Record)セクションに記録されている
- コントリビューションガイド(CONTRIBUTING.md)が整備されており、他者が開発に参加できる
- チェンジログ(CHANGELOG.md)または GitHub Releases でバージョン管理されている
- デモ動画(Loom / YouTube)または詳細な技術ブログ記事が公開されている
```

## 自己評価シート

プロジェクト提出前に、以下の表を記入してください。

| 観点 | 自己評価 | 根拠(1〜2 文) |
|------|----------|---------------|
| 機能 | 初級 / 中級 / 世界レベル | |
| コード品質 | 初級 / 中級 / 世界レベル | |
| テスト | 初級 / 中級 / 世界レベル | |
| インフラ・CI/CD | 初級 / 中級 / 世界レベル | |
| ドキュメント | 初級 / 中級 / 世界レベル | |

**Phase 9 の合格基準:** 全観点で「初級」以上、かつ 3 観点以上で「中級」以上。

## 観点別の改善優先順位

時間が限られている場合、以下の順序で改善することを推奨します。

1. **機能(Functionality):** 動かないアプリは評価できません。Must have をすべて実装することが最優先です。
2. **インフラ・CI/CD:** 本番 URL がないとポートフォリオになりません。デプロイを後回しにしないでください。
3. **テスト:** 採用担当者が最も差を感じるポイントです。20 件以上を目指します。
4. **ドキュメント:** README の質が第一印象を決めます。スクリーンショットは必ず入れてください。
5. **コード品質:** コードレビューができるエンジニアには見抜かれますが、まず動くものを作ることが先です。

次のステップ: `capstone/self-review-checklist.md` で提出前の最終確認をしてください。
