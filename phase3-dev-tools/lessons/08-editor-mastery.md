# レッスン 08: エディタを使いこなす

## このレッスンで学ぶこと

- エディタに何を期待すべきかを、機能の一覧として説明できる
- 「意味を理解した変更」と「文字列置換」の違いを説明できる
- 言語サーバが何をしているのかを理解する
- デバッガの操作モデル(ブレークポイント、ステップ、コールスタック)を説明できる
- `print` デバッグとデバッガの使い分けを判断できる

このレッスンは特定の製品の説明ではありません。**どのエディタを使っても必要になる考え方**を扱います。VS Code での具体的な操作は [付録: VS Code の操作](../appendix/08-vscode.md) にあります。

## 1. なぜエディタの話をするのか

プログラマは 1 日の多くをエディタの中で過ごします。**同じ作業を、10 秒かける人と 1 秒で終える人がいます。**その差は才能ではなく、道具に何ができるかを知っているかどうかです。

ただし、覚えるべきはショートカットの一覧ではありません。**「この道具は何を知っているのか」**です。それが分かれば、機能は自分で探せます。

---

## 2. エディタに求める 7 つの機能

エディタを選ぶとき、あるいは乗り換えるとき、確認すべきはこの 7 つです。**製品名が何であれ、この一覧は変わりません。**

| 機能 | 何ができること | これが無いと |
|---|---|---|
| **意味を理解した補完・移動** | 定義へ飛ぶ、参照を全部見つける | コードを追うのに grep しか使えない |
| **意味を理解した名前変更** | 同じ名前でも別のものは変えない | 置換のたびに壊す危険がある |
| **その場でのエラー表示** | 実行する前に間違いが分かる | 実行して初めて気づく |
| **デバッガ** | 止めて、中を見て、進める | `print` を入れては消す作業が続く |
| **差分表示と履歴** | 何をどう変えたかが見える | コミットする内容を把握できない |
| **複数箇所の同時編集** | 繰り返しの作業を 1 回で終える | 単純作業に時間を溶かす |
| **拡張の仕組み** | 必要な機能を後から足せる | 道具の都合に自分が合わせることになる |

## 3. 言語サーバ — エディタはなぜコードを「理解」できるのか

「定義へジャンプ」や「参照をすべて検索」は、文字列検索ではありません。エディタが**コードの構造を解析している**から可能です。

かつては、この解析をエディタごと・言語ごとに実装していました。エディタが M 個、言語が N 個あれば、M×N 通りの実装が必要になります。

そこで**言語サーバ**という考え方が生まれました。解析はエディタから独立した別のプログラムが行い、エディタとは決まった手順でやり取りします。

```
        かつて                          いま

  エディタA ── 独自解析 ─ Python     エディタA ─┐
  エディタA ── 独自解析 ─ Go         エディタB ─┼─ 決まった手順 ─ Python の言語サーバ
  エディタB ── 独自解析 ─ Python     エディタC ─┘
  エディタB ── 独自解析 ─ Go
        M × N 個の実装                    M + N 個の実装
```

これは Phase 9 で学ぶ設計の考え方そのものです。**共通の取り決めを間に挟むと、組み合わせの数が掛け算から足し算に変わります。**

実務上、大事な帰結が 2 つあります。

1. **補完が効かないときは、たいてい言語サーバが動いていない。** エディタの不調ではなく、言語の拡張が入っていないか、依存が解決できていないかです。
2. **同じ言語サーバは、他のエディタでも使えます。** エディタを乗り換えても、コードの理解の質は落ちません。

## 4. 意味を理解した変更 vs 文字列置換

これはこのレッスンで**最も重要な区別**です。

### 同じ「名前の変更」に見えて、別物

```python
def calculate_total(items):
    result = 0
    for item in items:
        result += item.price
    return result

total = calculate_total(cart_items)
print(f"Total: {total}")
```

`calculate_total` を `compute_total` に変えたいとき、方法は 2 つあります。

**文字列置換**は、その文字の並びを探して差し替えます。コードの意味は見ていません。

**意味を理解した名前変更**は、その識別子が指しているものを追跡し、**同じものを指している箇所だけ**を変更します。

### なぜ違いが致命的になるか

```python
# 「total」を文字列置換で変えると…
total = calculate_total(cart_items)   # ← 変えたい変数
print(f"Total: {total}")              # ← ここも変わってしまう
# コメント: total を計算する           # ← コメントまで変わる
subtotal = 100                        # ← 部分一致で壊れる
```

文字列置換は、**変数名・コメント・文字列リテラル・たまたま部分一致した別の単語**を区別できません。一方、意味を理解した名前変更は、スコープが違えば同じ名前でも変更しません。

```python
def foo():
    count = 1      # ← これを変えたい

def bar():
    count = 2      # ← こちらは別物。変えてはいけない
```

**原則: 名前を変えるときは、必ず意味を理解した機能を使ってください。** 文字列置換は、それが使えない場面(設定ファイル、ドキュメント)のための最後の手段です。

この区別は道具に依存しません。どのエディタにも両方あり、**どちらを使うかはあなたの判断です。**

## 5. デバッガ

### `print` デバッグの限界

`print` を入れて動かす方法は、有効ですし、恥ずかしいことでもありません。実際、熟練者もよく使います。

しかし限界があります。

- 見たい値を**事前に決めておく**必要がある。予想が外れたら入れ直して再実行
- 実行に時間がかかる場合、往復のたびに待つ
- 消し忘れが本番に混入する
- 「その時点で他に何が起きていたか」は見えない

デバッガは、**動いているプログラムを止めて、中を自由に見られます。** 何を見るかを事前に決めなくてよいのが決定的な違いです。

### 操作モデル

どのデバッガでも、概念は同じです。

| 概念 | 意味 |
|---|---|
| **ブレークポイント** | 「ここに来たら止まれ」という印 |
| **ステップオーバー** | 今の行を実行して次の行へ。関数の中には入らない |
| **ステップイン** | 今の行の関数の**中に**入る |
| **ステップアウト** | 今の関数を最後まで実行して、呼び出し元に戻る |
| **継続** | 次のブレークポイントまで走らせる |
| **コールスタック** | 「今ここに来るまでに、どの関数を通ってきたか」の一覧 |
| **ウォッチ** | 特定の式を、止まるたびに評価して見せる |

### ステップインとステップオーバーの使い分け

これが分かると、デバッグの速度が変わります。

```python
result = calculate_average(data)   # ← ここで止まっている
```

- `calculate_average` が**怪しい** → **ステップイン**して中を見る
- `calculate_average` は**信用している**(標準ライブラリなど) → **ステップオーバー**で飛ばす

初心者はすべてステップインしてしまい、ライブラリの奥深くで迷子になります。**疑っている場所にだけ入る**のがコツです。

### コールスタックが一番大事

エラーが出たとき、多くの人はエラーが出た行だけを見ます。しかし**本当の原因は、たいていもっと手前にあります。**

```
calculate_average()   ← ここで ZeroDivisionError
  ← process_data() から呼ばれた
    ← main() から呼ばれた   ← 空リストを渡したのは、実はここ
```

`calculate_average` は正しく、**空リストを渡した呼び出し元が間違っている**かもしれません。コールスタックは、そこへ遡るための地図です。

### やってみる

```python
def calculate_average(numbers):
    total = 0
    for n in numbers:
        total += n
    return total / len(numbers)

data = [10, 20, 30, 40, 50]
result = calculate_average(data)
print(f"Average: {result}")
```

`total += n` にブレークポイントを置いて、ループのたびに `total` と `n` がどう変わるかを見てください。次に `data = []` にして実行し、**どこで、なぜ落ちるか**をコールスタックで確認してください。

## 6. 複数箇所を一度に編集する

同じ編集を何行にも繰り返すのは、時間の無駄であると同時に**間違いの原因**です。人間は 20 行のうち 1 行を必ず打ち間違えます。

道具には 2 つの方法があります。

| 方法 | 向いている場面 |
|---|---|
| **マルチカーソル** | 見えている範囲の、似た形の行をまとめて直す |
| **正規表現による置換** | ファイル全体・複数ファイルで、規則的に変換する |

どちらも「手で繰り返さない」ための道具です。**3 回以上同じ編集をしていると気づいたら、手を止めてください。**もっと速い方法があります。

## 7. 道具に飲まれないために

最後に、逆の注意です。

- **設定に凝りすぎない。** 環境構築が趣味になると、コードを書く時間が減ります
- **拡張機能を入れすぎない。** 遅くなり、衝突します。困ってから入れれば十分です
- **画面のボタンで Git を覚えない。** [レッスン 01〜06](../lessons/) でコマンドを学ぶのは、何が起きているかを理解するためです。理解せずにボタンを押すと、壊れたときに直せません
- **エディタが無くても仕事はできる状態にしておく。** 障害対応でサーバに入ったとき、そこにあるのは `vi` だけかもしれません

道具は上達を助けますが、**上達そのものではありません。**

## 💡 コラム: VS Code を設計したのは「デザインパターン」の著者

VS Code の開発を率いるエリック・ガンマは、実はソフトウェア設計史の伝説的人物です。1994年の名著『デザインパターン』(通称 GoF 本 — Phase 9 で学びます)の著者の一人であり、テストフレームワーク JUnit をケント・ベックと共同開発し、Java の定番エディタ Eclipse の中核を設計した人物でもあります。

1990年代に設計理論の教科書を書いた人が、2020年代に世界で最も使われるエディタを作っている — ここには重要な示唆があります。**エディタもフレームワークも流行り廃りしますが、「良い設計とは何か」という基礎は数十年単位で通用する**のです。

VS Code 自体が設計の教材でもあります。本体は最小限に保ち、機能は拡張機能(プラグイン)として分離するアーキテクチャは、Phase 9 で学ぶ「開放閉鎖原則」の実践例そのもの。ショートカットを覚えるついでに、「なぜこの道具はこう作られているのか」という視点も持ってみてください。

## 確認問題

1. エディタに求める機能を 7 つ挙げ、それぞれが無いと何に困るかを説明してください。

2. 言語サーバという仕組みが生まれる前と後で、実装しなければならない数はどう変わりましたか。

3. 「意味を理解した名前変更」と「文字列置換」の違いを説明してください。次のコードで文字列置換を使うと何が起きますか。
   ```python
   total = 100
   subtotal = 50
   print(f"Total: {total}")
   ```

4. 次のコードで、`old_name` を `new_name` に変える最も安全な方法は何ですか。
   ```python
   old_name = "Alice"
   print(old_name)
   return old_name
   ```

5. ステップオーバーとステップインの違いを説明してください。どちらを使うかは何で決まりますか。

6. エラーが出た行だけを見ても原因が分からないのはなぜですか。デバッガのどの機能を見るべきですか。

7. `print` デバッグが有効な場面と、デバッガのほうが速い場面を、それぞれ挙げてください。
