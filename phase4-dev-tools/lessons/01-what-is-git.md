# レッスン 01: バージョン管理とは何か、Git の内部モデル

## このレッスンで学ぶこと

- バージョン管理が必要な理由
- Git が「差分保存」ではなく「スナップショット保存」である理由
- Git が内部でデータをどのように持つか(blob / tree / commit オブジェクト)
- ステージングエリア(インデックス)の役割

---

## 1. バージョン管理が必要な理由

プログラムを書いていると、次のような場面に必ず遭遇します。

- 「昨日まで動いていたのに、今日急に動かなくなった。どこを変えたんだっけ?」
- 「A という機能を試しながら、B という別の機能も並行して開発したい」
- 「2 人で同じファイルを編集したら、片方の変更が上書きされて消えた」
- 「先週のバージョンに戻したい」

こういった問題を解決するのが**バージョン管理システム(Version Control System, VCS)**です。

Git はその中でも世界で最も広く使われている分散型 VCS です。「分散型」とは、各開発者のマシンにリポジトリの完全なコピーが存在することを意味します。インターネットに繋がっていなくても履歴を見たりコミットしたりできます。

---

## 2. Git はスナップショットを保存する

Git を学ぶ上で最初に押さえるべき最重要概念があります。

**Git は差分(diff)ではなく、スナップショット(snapshot)を保存します。**

多くの人が誤解しますが、Git は「前のバージョンとの差分」を記録しているわけではありません。コミットするたびに、その時点のプロジェクト全体の状態を丸ごと記録します(ただし変更のないファイルは参照を再利用することで効率化しています)。

この設計がブランチの高速な切り替えや、履歴の柔軟な操作を可能にしています。

---

## 3. Git の内部構造: 3 種類のオブジェクト

Git は `.git/objects/` ディレクトリにすべてのデータを格納します。オブジェクトは 3 種類あります。

### 3-1. blob オブジェクト

**ファイルの中身そのもの**を格納します。ファイル名やパスの情報は持ちません。

```
[blob]
 hello.py の内容
 "print('Hello, World!')"
```

### 3-2. tree オブジェクト

**ディレクトリ構造**を格納します。blob や他の tree への参照(SHA-1 ハッシュ値)と名前のマッピングを持ちます。

```
[tree: ルートディレクトリ]
  100644 hello.py  --> [blob: "print('Hello, World!')"]
  100644 README.md --> [blob: "# My Project"]
  040000 src/      --> [tree: src ディレクトリ]
```

### 3-3. commit オブジェクト

**スナップショットのメタ情報**を格納します。

```
[commit]
  tree    --> [tree: ルートディレクトリのスナップショット]
  parent  --> [前のコミット(最初のコミットはなし)]
  author  --> Taro Yamada <taro@example.com>
  date    --> 2026-07-05 10:00:00
  message --> "feat: add hello world script"
```

### オブジェクトの連鎖を図で見る

```
commit C3 -----> tree T3 -----> blob B1 (main.py の内容)
  |                  \--------> blob B2 (README.md の内容)
  | parent
  v
commit C2 -----> tree T2 -----> blob B1 (main.py は変更なし → 同じ blob を参照)
  |                  \--------> blob B3 (README.md の新しい内容)
  | parent
  v
commit C1 -----> tree T1 -----> blob B1 (main.py の最初の内容)
                     \--------> blob B2 (README.md の最初の内容)
```

ポイント: main.py を変更しなかった C2 では、B1 への参照を使い回しています。これが Git が効率的にスナップショットを保存できる理由です。

### 実際にオブジェクトを覗いてみる

```bash
# リポジトリを作成してコミットする
mkdir git-internals-demo
cd git-internals-demo
git init
echo "print('Hello, World!')" > hello.py
git add hello.py
git commit -m "first commit"

# オブジェクト一覧を確認
find .git/objects -type f
# 出力例:
# .git/objects/5e/1c309dae7f45e0f39b1bf3ac3cd9db12e7d689  <- blob
# .git/objects/8e/5a3c7f2d0e1a4b6c9f2a5d8e1b4c7a0f3d6e9  <- tree
# .git/objects/3a/7b2c1d0e4f5a6b7c8d9e0f1a2b3c4d5e6f7a  <- commit

# commit オブジェクトの内容を見る(ハッシュ値は実際のものに置き換える)
git cat-file -p HEAD
# 出力例:
# tree 8e5a3c7f2d0e1a4b6c9f2a5d8e1b4c7a0f3d6e9
# author Taro Yamada <taro@example.com> 1751764800 +0900
# committer Taro Yamada <taro@example.com> 1751764800 +0900
#
# first commit

# tree オブジェクトの内容を見る
git cat-file -p HEAD^{tree}
# 出力例:
# 100644 blob 5e1c309dae7f45e0f39b1bf3ac3cd9db12e7d689    hello.py

# blob オブジェクトの内容を見る
git cat-file -p 5e1c309dae7f45e0f39b1bf3ac3cd9db12e7d689
# 出力例:
# print('Hello, World!')
```

## 4. HEAD とブランチは何者か

Git を理解するもう一つの鍵が「HEAD」と「ブランチ」の実体を知ることです。

**ブランチ**は、コミットへのポインタ(参照)にすぎません。`main` ブランチは、最新コミットの SHA-1 ハッシュ値を格納したテキストファイルです。

```bash
cat .git/refs/heads/main
# 出力例:
# 3a7b2c1d0e4f5a6b7c8d9e0f1a2b3c4d5e6f7a
```

**HEAD**は、「現在どのブランチ(またはコミット)にいるか」を示すポインタです。

```bash
cat .git/HEAD
# 出力例:
# ref: refs/heads/main
```

これを図で表すと:

```
HEAD --> main --> [commit C3] --> [commit C2] --> [commit C1]
```

新しいコミットをすると、main が指すコミットが自動的に更新されます。HEAD は main を指したままです。

```
HEAD --> main --> [commit C4(新)] --> [commit C3] --> [commit C2] --> ...
```

## 5. ステージングエリア(インデックス)

Git には 3 つの「場所」があります。

```
ワーキングディレクトリ  -->  ステージングエリア  -->  リポジトリ
 (作業フォルダ)            (コミット予定の変更)      (.git/の中)
     git add で移動 -->       git commit で記録 -->
```

| 場所                 | 説明                                         |
|----------------------|----------------------------------------------|
| ワーキングディレクトリ | 実際にファイルを編集する場所                  |
| ステージングエリア     | 「次のコミットに含めるもの」を選んで置く場所   |
| リポジトリ            | コミット履歴が保存される場所(.git/ フォルダ) |

### なぜステージングエリアが必要なのか

「一度に 10 個のファイルを変更したが、コミットは機能ごとに分けたい」という状況を考えてください。

```
変更したファイル:
  - login.py     (ログイン機能)
  - logout.py    (ログアウト機能)
  - style.css    (ログイン画面のデザイン)
  - report.py    (別の機能: バグ修正)

コミットを分ける:
  コミット1: git add login.py logout.py style.css
             git commit -m "feat: add login/logout feature"

  コミット2: git add report.py
             git commit -m "fix: fix report generation bug"
```

ステージングエリアがあることで、変更をコミット単位で整理できます。これが「1 コミット = 1 論理的変更」という良い習慣を実現するための仕組みです。

## まとめ

| 概念               | 内容                                                         |
|--------------------|--------------------------------------------------------------|
| バージョン管理      | 変更履歴を記録し、過去に戻ったり並行作業したりできる仕組み    |
| スナップショット     | Git はその時点のファイル全体の状態を記録する                  |
| blob               | ファイルの内容を格納するオブジェクト                          |
| tree               | ディレクトリ構造を格納するオブジェクト                        |
| commit             | スナップショットのメタ情報(著者、日時、メッセージ)            |
| HEAD               | 現在地を示すポインタ                                          |
| ブランチ            | コミットへの軽量なポインタ                                    |
| ステージングエリア   | コミット前に変更を整理する中間置き場                          |
