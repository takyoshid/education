# Phase横断プロジェクト — Learning Hub

各Phaseで別の完成品を作るだけでなく、Phase 2から12まで**同じプロダクトを変更し続ける**課題です。新規実装だけでなく、仕様変更、移行、障害、他者レビューを経験します。

題材は「学習目標・学習セッション・振り返りを管理するLearning Hub」です。独自テーマに置き換えても構いませんが、各段階の制約と証拠は維持してください。

最初は [Phase 2 starter](starter/phase2/) を自分のリポジトリへコピーします。starterにはインターフェースと公開テストだけがあり、完成実装はありません。

## この課題の形 — 作る → 壊す → 原理へ戻る → 改善する

各段階には**強制障害**があります。うまくいっている状態から、意図的に壊れる状況を作る指示です。

これは意地悪ではありません。**順序の問題です。**

```
よくある順序                     この課題の順序
原理を学ぶ                        作る
   ↓                              ↓
正しく作る                        壊れる(強制障害)
   ↓                              ↓
なぜ正しいか分からないまま進む      なぜ壊れたかを知りたくなる
                                  ↓
                                 原理へ戻る ← ここで初めて頭に入る
                                  ↓
                                 直す
```

冪等性の必要は、二重登録が起きてから分かります。計算量の話は、自分の画面が固まってから頭に入ります。テストの価値は、テストが無くて手が止まってから分かります。**必要性を感じていない知識は、読んでも通り過ぎます。**

だから、**強制障害を飛ばさないでください。**「うまく動いているのにわざわざ壊すのは無駄」と感じたら、それはこの課題が効いている合図です。

[子ども版](../children-track/)が「観察→予想→作る→壊す→説明→改善」を繰り返すのと、同じ設計です。大人版では、それが14か月かけて育てる1つのプロダクトの中で起きます。

## 最重要ルール

- 模範実装は提供しない。仕様、受け入れ条件、レビュー観点だけを提供する
- Phase 0で練習した最小操作を使い、Phase 2開始時からGitで管理して履歴を消さない
- Phase 2では作業項目をREADMEへ記録し、小さなコミットで変更する。Phase 3以降は各PhaseでGitHub Issueを作る
- 動作している既存機能を守りながら拡張する
- 設計判断を `docs/decisions/` に残す
- Phase 3でタグを学んだら、`v0.2`を含む各リリースにタグ `v0.2`〜`v1.0` を付ける

## ロードマップ

節の番号は本編のPhase番号に対応します。Phase 4(AI活用)・8(並行処理)・11(分散システム)に対応する節はありません。これらは横断プロジェクトの段階ではなく、**各Phaseの中で扱う**ためです(ただし下の「変更要求カード」には関連する課題が含まれます)。

### Phase 2 — CLI版 `v0.2`

学習セッションの追加、一覧、編集、削除、JSON保存を実装します。

Phase 2の学習と同時に着手します。この段階ではローカルで `init / status / add / commit / log` が使えれば十分です。GitHubへの公開、ブランチ、Pull RequestはPhase 3で行います。

受け入れ条件:

- 不正入力でデータが壊れず、利用者向けエラーを返す
- 保存中に失敗しても既存ファイルを失わない
- ドメイン処理と入出力を分離する
- 正常系・境界値・異常系の自動テストがある
- `ruff`、`mypy`、`pytest` を実行できる

公開テストは標準ライブラリの `unittest` で実行でき、追加依存なしで開始できます。

```bash
cd starter/phase2
python3 -m unittest discover -s tests -v
```

強制変更: 完成後に「1セッションへ複数タグを追加する」という仕様変更を行います。既存データを読み込めることが必要です。

### Phase 3 — 共同開発 `v0.3`

GitHubへ公開し、Issue、feature branch、PRで開発します。

受け入れ条件:

- 3件以上のIssueと、それに対応するPRがある
- 他者のレビューを最低1回受ける
- 意図的にコンフリクトを作り、安全に解消する
- 不具合を `git bisect` で特定した記録がある

強制障害: **すでにpushしたコミットの中に、消したいもの(誤ってコミットした大きなファイル、恥ずかしい記述、誤った変更)を1つ作ってください。**そのうえで安全に取り消します。

`revert` で打ち消すのか、履歴そのものを書き換えるのか。**他人がすでにpullしていたらどちらを選ぶべきか。**判断と理由を記録してください。この判断を一度もしないままチーム開発に入ると、いつか取り返しのつかない操作をします。

### Phase 5 — 検索と計測 `v0.4`

日付・タグ・キーワード検索と学習統計を追加します。データ件数を生成して、少なくとも2方式を比較してください。

受け入れ条件:

- 選択したデータ構造と計算量を説明できる
- 100、10,000、100,000件の計測結果を保存する
- 「最も複雑な方式」ではなく、計測と要件から方式を選ぶ

強制障害: **まず、最も素朴な実装(全件を線形に走査する)で動かしてください。**そのうえで件数を100,000件まで増やし、**実際に遅くて使い物にならなくなるところまで持っていきます。**

遅くなってから初めて、計算量の話を読み直してください。「O(n) は遅い」と読んで納得するのと、自分の画面が固まるのを見るのとでは、理解の質が違います。**改善前の計測値を必ず残してください。**それがないと、何を良くしたのか説明できません。

### Phase 6 — Web UI `v0.5`

CLIと同じユースケースをブラウザで操作できるようにします。この時点ではmock APIでも構いません。

受け入れ条件:

- キーボードだけで主要操作を完了できる
- loading、empty、error、success状態が区別される
- TypeScript strict modeでbuildできる
- 主要ユーザーフローのコンポーネントテストがある
- モバイル幅とデスクトップ幅で利用できる

強制障害: **[同梱のAPIサーバ](../fixtures/)の `_delay` と `_fail` を使って、自分のUIを壊してください。**

- `_delay=3000` で、応答が遅いときに二重送信できてしまわないか
- `_fail=500` で、エラーを利用者が理解できる言葉で伝えられているか
- `_empty=1` で、「0件」と「失敗」を区別して表示できているか
- 検索語をすばやく2回変えたとき、**古い応答が新しい結果を上書きしないか**

最後の1つは、通信が常に速い開発環境では絶対に気づけません。**壊してから直してください。**順序を逆にすると、直したつもりで直っていないことに気づけません。

### Phase 7 — API・DB・認証 `v0.6`

FastAPIとPostgreSQLへ移行し、複数ユーザーに対応します。

受け入れ条件:

- 所有者以外のデータを読み書きできないことをテストする
- DB制約とトランザクション境界を説明できる
- migrationのupgradeとdowngradeが通る
- ページネーション、入力上限、適切なHTTP statusを実装する
- 認証情報の保存方式を脅威モデルから選び、理由を記録する

強制障害: 同一リクエストが2回届いても重複登録しない必要が生じます。冪等性の設計とテストを追加してください。

### Phase 9 — レガシー変更 `v0.7`

第三者に、内部構造を知らずに変更要求を書いてもらいます。先にcharacterization testを追加し、挙動を守りながら設計を改善します。

受け入れ条件:

- リファクタリング前後で同じテストが通る
- 大きな一括書き換えではなく、小さな検証可能なコミットにする
- ADRに選択肢、決定、トレードオフ、見直し条件を書く
- 自分以外の人がPRをレビューする

強制障害: **characterization testを書く前に、一度リファクタリングを始めてみてください。**そして手が止まる感覚を確かめます。

「この関数を変えて大丈夫か分からない」「壊したかどうか確かめる方法がない」。この不安こそが、テストが無いコードの正体です。そこで作業を中断し、テストを先に書いてから、もう一度やり直してください。

**この往復を経験しないと、「テストは後で書けばいい」という考えが抜けません。**あなたが半年前に書いたコードは、他人が書いたコードと同じです。

### Phase 10 — 運用と障害 `v0.8`

Docker Compose、CI/CD、監視を追加し、ステージング環境で障害演習を行います。

受け入れ条件:

- 新しい環境でREADMEだけを使って起動できる
- lint、test、build、秘密情報検査がCIで動く
- health check、構造化ログ、主要メトリクスがある
- backupとrestoreを実演する
- 障害タイムライン、原因、再発防止をpostmortemに残す

強制障害: **次から最低1つを、ステージング環境で実際に起こしてください。**読んで対策を書くのではなく、起こしてから直します。

- DB接続枯渇
- migration失敗
- 外部API timeout
- ディスクまたはメモリ圧迫
- キャッシュ障害

**起こす前に「何が起きると思うか」を書き残してください。**予想と実際のずれが、この演習で最も価値のある記録です。監視が本当に役に立つかどうかも、実際に落ちたときにしか分かりません。

### Phase 12 — 実ユーザー公開 `v1.0`

少なくとも3人に使ってもらい、観察またはインタビューから改善します。「技術を追加した数」ではなく、解決した問題と判断の質を評価します。

受け入れ条件:

- 対象ユーザーと解決する問題を1文で説明できる
- 成功指標を公開前に決める
- 3人以上のフィードバックを匿名化して記録する
- フィードバックを根拠に最低1回仕様を変更する
- 外部レビューを受け、指摘への対応を残す
- runbook、脅威モデル、ADR、デモ、英語READMEを揃える

強制障害: **利用者の前で、説明も手助けもせずに使ってもらってください。**

作った本人は迷いません。作った本人だけが迷いません。**利用者が詰まった場所、押さないボタン、誤解した言葉を記録してください。**そこがあなたの設計の穴です。

このPhaseで最も苦しい作業であり、**最も学びが大きい作業**です。技術的な障害は自分で直せますが、「伝わらない」という障害は、他人に触ってもらうまで存在すら見えません。

## 変更要求カード

順調すぎる場合は、各Phase終了後に次から1枚選びます。

1. 過去データとの互換性を維持してスキーマを変更する
2. 外部APIが10回に1回timeoutする
3. 同じ操作が並行して実行される
4. ユーザーが誤操作から復元したい
5. 個人情報の削除依頼へ対応する
6. 主要依存ライブラリを更新する
7. 初見の開発者が機能を追加する
8. レスポンス時間の目標が設定される

変更前にテストを追加し、対応後に「なぜこの解決策か」を記録してください。
