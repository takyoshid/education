# レッスン 12: フロントエンドのテスト

## 学習目標

- 何をテストし、何をテストしないかを判断できる
- 実装の詳細ではなく、利用者から見える振る舞いを検証できる
- 5 つの状態(idle / loading / success / empty / error)をテストで確認できる
- 遅延・失敗・競合を、狙って再現して検証できる
- 偽物(モック)を、どこに、どこまで忠実に置くべきかを説明できる

> **先に教材用の API サーバを起動してください。**
>
> ```bash
> python3 fixtures/server.py
> ```
>
> このレッスンで扱うアプリは `http://127.0.0.1:8787` を使います。外部のサービスを使わない理由は [fixtures/README.md](../../fixtures/README.md) にあります。

## 1. なぜテストを書くのか

「動いたから完成」と思った直後に壊れるのが UI です。理由は単純で、**UI の状態の組み合わせが多すぎて、手で全部確かめられない**からです。

前のレッスンまでで作った天気アプリには、次の状態があります。

```
検索していない / 検索中 / 成功 / 0 件 / 通信失敗
    × 履歴あり / なし
    × 画面が狭い / 広い
```

手で確認するなら毎回 20 通り近くを試すことになります。1 行直すたびにそれをやる人はいません。**だから手で確認する方式は、必ず「たぶん大丈夫」に変わります。**

もう一つ、より重要な理由があります。**手では起こせない状況がある**ことです。

- 通信が 3 秒かかる状態
- サーバが 503 を返す状態
- **古い検索の応答が、新しい検索より後に届く状態**

最後の 1 つは、開発環境では通信が速すぎて、まず再現しません。しかし利用者の回線では起きます。**狙って起こせなければ、直したかどうかも確かめられません。**

---

## 2. 何をテストしないか

先にこちらを決めます。テストは書けば書くほど良いものではありません。**壊れやすいテストは、いずれ「また落ちてる」と言われて消されます。**

| テストしない | なぜ |
|---|---|
| CSS の見た目、色、余白 | 変わって当たり前。変えるたびにテストを直すことになる |
| コンポーネントの内部 state | 実装の詳細。リファクタリングで壊れる |
| 関数が呼ばれた回数(多くの場合) | 呼ばれ方ではなく、結果を見るべき |
| ライブラリ自体の動作 | React が動くことは React が保証している |

判断の基準は 1 つです。

> **その検証は、利用者が困ることに対応しているか。**

「`useState` が呼ばれた」は利用者にとって何の意味もありません。「エラーが出たのに何も表示されない」は困ります。**後者だけを書きます。**

## 3. 利用者に見えるもので探す

Testing Library の中心にある考え方です。要素を探すとき、**利用者や支援技術が使う手がかりで探します。**

```tsx
// ✗ 実装に依存する。クラス名を変えた瞬間に壊れる
container.querySelector(".search-input");

// ○ 利用者が見るものに依存する
screen.getByRole("textbox", { name: "都市名" });
```

優先順位はこうです。

| 優先 | 探し方 | 対応するもの |
|---|---|---|
| 1 | `getByRole` (+ `name`) | 支援技術が読み上げる役割と名前 |
| 2 | `getByLabelText` | フォームのラベル |
| 3 | `getByText` | 画面に見えている文字 |
| 最後 | `getByTestId` | どうしても他で特定できないとき |

### この書き方には副作用があります

`getByRole("textbox", { name: "都市名" })` が見つからないとき、それは**テストの書き方が悪いのではなく、アクセシビリティに問題があることが多い**のです。

実際、この教材の天気アプリでこのテストを書いたところ、2 つの欠陥が見つかりました。

1. ラベルが `display: none` で隠されていた → **スクリーンリーダーからも消えていた**
2. 都市名が、見た目だけ大きい `<p>` だった → **見出しとして辿れなかった**

どちらも画面を見ているだけでは気づけません。**役割で探すテストは、アクセシビリティの検査を兼ねます。** これがクラス名で探さない、もう一つの理由です。

## 4. 環境を用意する

```bash
npm install -D vitest jsdom \
  @testing-library/react @testing-library/user-event @testing-library/jest-dom
```

| パッケージ | 役割 |
|---|---|
| `vitest` | テストの実行。Vite の設定をそのまま使える |
| `jsdom` | Node の中にブラウザの API(document、要素、イベント)を再現する |
| `@testing-library/react` | コンポーネントを描画し、利用者の見え方で要素を探す |
| `@testing-library/user-event` | 入力・クリック・キー操作を、実際の操作に近い形で行う |
| `@testing-library/jest-dom` | `toBeInTheDocument()` のような読みやすい検証を足す |

```ts
// vite.config.ts
export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    setupFiles: ["./src/setupTests.ts"],
    globals: true,
  },
});
```

### テスト環境は本物のブラウザではありません

`jsdom` はブラウザの再現であって、ブラウザではありません。**足りないものがあります。**

この教材のアプリでは `localStorage` が足りませんでした。アプリは `try/catch` で守ってあるので落ちませんが、それでは履歴の保存を検証できません。そこで `setupTests.ts` で最小限の実装を補っています。

**何を補ったかを覚えておいてください。**忘れると「本番では動くのにテストだけ落ちる」で悩みます。

## 5. 5 つの状態をテストする

### success

```tsx
it("初回に取得した天気を表示する", async () => {
  render(<App />);
  expect(await screen.findByRole("heading", { name: /東京/ })).toBeInTheDocument();
});
```

`findBy*` は「見つかるまで待つ」問い合わせです。非同期に表示されるものには必ずこれを使います。`getBy*` は待たないので、通信を伴う画面では失敗します。

### loading — 解決を保留して、その瞬間で止める

```tsx
/** 解決するタイミングを自分で決められる Promise */
function deferred<T>() {
  let resolve!: (value: T) => void;
  const promise = new Promise<T>(res => { resolve = res; });
  return { promise, resolve };
}

it("取得中はそれと分かる表示になる", async () => {
  const pending = deferred<GeocodingResult[]>();
  geocodeMock.mockReturnValue(pending.promise);

  await user.type(input, "札幌{Enter}");

  // まだ resolve していないので、画面は loading のまま止まっている
  expect(await screen.findByRole("button", { name: /検索中/ })).toBeDisabled();

  pending.resolve([makeLocation("札幌")]);   // ここで進める
  await screen.findByRole("heading", { name: /札幌/ });
});
```

**「待つ」のではなく「止める」のが要点です。**`setTimeout` で 100 ミリ秒待つテストは、遅いうえに、遅いマシンでは落ちます。

### empty と error を、別のものとして扱う

```tsx
it("empty と error を同じ文言で片付けない", async () => {
  // 「見つからない」→ 別の言葉で探す
  // 「通信できない」→ 待ってやり直す
  // 利用者が取るべき行動が違うので、同じ表示にしてはいけない
  expect(emptyText).not.toEqual(errorText);
});
```

この 2 つを混同した実装は非常に多く、[Phase 6 の実技試験](../assessment/)でも明示的に問われます。

## 6. 偽物をどこに置くか

通信を伴うテストでは、本物の通信をしません。問題は**どこで差し替えるか**です。

```
[コンポーネント] → [api モジュール] → [fetch] → ネットワーク
                        ↑ ここで差し替える
```

`fetch` そのものではなく、**api モジュールを差し替えます。**境界が 1 つなら、テストは読みやすく、実装を変えても壊れません。

```tsx
vi.mock("./api/weather", () => ({
  fetchGeocode: vi.fn(),
  fetchWeather: vi.fn(),
}));
```

### 偽物は、テストする軸については忠実であること

**これが最も間違えやすい点です。**

本物の `fetchGeocode` は、`AbortSignal` が中断されると `AbortError` を投げます。この性質を無視した偽物を使うと、**中断されたはずの応答がそのまま返り**、アプリが正しいのにテストが落ちます。

```tsx
// 中断を尊重する偽物
function abortableDeferred<T>() {
  const { promise, resolve, reject } = deferred<T>();
  const impl = (_arg: unknown, signal?: AbortSignal) => {
    signal?.addEventListener("abort", () => {
      const error = new Error("Aborted");
      error.name = "AbortError";     // ← 名前が AbortError であることが重要
      reject(error);
    });
    return promise;
  };
  return { impl, resolve };
}
```

偽物を**全ての面で**本物に似せる必要はありません。しかし**テストしている軸については、本物と同じに振る舞う必要があります。**これを外すと、アプリではなく偽物の作りが原因でテストが赤くなり、最も時間を溶かします。

## 7. 競合するリクエスト — このレッスンの本題

「東京」を検索した直後に「大阪」を検索し、**東京の応答が後から返る**とどうなるか。

```
時刻 →
東京を検索 ──────────────────────────▶ 応答(遅い)
      大阪を検索 ──▶ 応答(速い)

素朴な実装: 画面は「大阪」→ その後「東京」に戻ってしまう
```

利用者から見れば、**選んでいない都市が表示される**という不可解な不具合です。開発環境では通信が速いので、まず再現しません。

### 起こせる経路を探す

このアプリでは、検索中は入力欄が無効になります。つまりフォームからは二重に送信できません。**しかし履歴のボタンは無効になっていません。**

```tsx
// 履歴から「東京」を選ぶ。この応答をわざと遅らせる
const slowTokyo = abortableDeferred<GeocodingResult[]>();
geocodeMock.mockImplementationOnce(slowTokyo.impl as never);
await user.click(screen.getByRole("button", { name: "東京" }));

// 応答を待たずに、履歴から「大阪」を選ぶ
await user.click(screen.getByRole("button", { name: "大阪" }));
await screen.findByRole("heading", { name: /大阪/ });

// ここで、遅れていた東京の応答が返る
slowTokyo.resolve([makeLocation("東京")]);

// 画面は大阪のまま。東京に戻ってはいけない
expect(screen.queryByRole("heading", { name: /東京/ })).not.toBeInTheDocument();
```

**「利用者が実際に取れる操作」でテストしてください。**起こせない経路をテストしても意味がありません。逆に、起こせる経路を探す過程で「ここは無効化すべきでは?」という設計の問いが出てきます。

### テストが空振りしていないか確かめる

書いたテストが本当に不具合を捕まえるかは、**わざと壊してみれば分かります。**

```bash
# useWeather.ts の abortRef.current?.abort() をコメントアウトして…
npx vitest run
# → 競合のテストだけが落ちる。落ちなければ、そのテストは無意味
```

**通っているテストは、通っていることしか教えてくれません。**一度落として、落ちることを確かめてください。

## 8. 教材同梱サーバで壊す

自動テストとは別に、**実際に動かして壊す**確認もしてください。

```bash
# 3 秒待たせる。二重送信できてしまわないか
curl "http://127.0.0.1:8787/v1/search?name=Tokyo&_delay=3000"

# 503 で失敗させる。利用者に伝わる言葉になっているか
curl "http://127.0.0.1:8787/v1/search?name=Tokyo&_fail=503"

# 0 件で返す。「見つからない」と「失敗」を区別できているか
curl "http://127.0.0.1:8787/v1/search?name=Tokyo&_empty=1"
```

自動テストは**壊れていないことを毎回確かめる**ためのもの、手で壊すのは**気づいていない壊れ方を見つける**ためのものです。役割が違うので、両方やります。

## 💡 コラム: テストを書く時間が無い、という話

「テストを書く時間が無い」とよく言われます。しかし観察すると、その人たちが時間を使っているのはたいてい**手作業の確認**です。

1 行直すたびに、ブラウザを開き、都市名を入力し、検索し、履歴をクリックし、画面を狭めて確認する。1 回 3 分として、1 日 20 回で 1 時間。それを毎日続けます。

自動テストを書けば、同じ確認が数秒で終わります。**書く時間が無いのではなく、書かないから時間が無い**のです。

ただし逆もあります。**すべてを自動化しようとすると、テストの保守にかかる時間が、確認で浮いた時間を上回ります。**色や余白のテストを書かないのは、そのためです。

このレッスンで扱った 4 つ — **5 つの状態、キーボード操作、競合、アクセシブルな名前** — は、手で確認するのが特に大変で、壊れたときの影響が大きい部分です。**そこだけを自動化する**のが、時間の使い方として一番効きます。

## まとめ

| 概念 | 要点 |
|------|------|
| 何をテストしないか | 見た目、内部 state、ライブラリ自体。壊れやすいテストは消される |
| 判断基準 | その検証は、利用者が困ることに対応しているか |
| 探し方 | 役割とラベルで探す。**アクセシビリティの検査を兼ねる** |
| `findBy*` | 非同期に出るものは待つ問い合わせを使う |
| loading | 待つのではなく、解決を保留して止める |
| empty と error | 別のものとして扱う。利用者が取るべき行動が違う |
| 偽物の位置 | `fetch` ではなく api モジュール。境界を 1 つにする |
| 偽物の忠実さ | テストする軸については本物と同じに振る舞わせる |
| 競合 | 利用者が実際に取れる経路でテストする |
| 空振り確認 | わざと壊して、テストが落ちることを確かめる |

## 確認問題

1. UI を手で確認する方式が、必ず「たぶん大丈夫」に変わるのはなぜですか。

2. テストを書かないほうがよいものを 3 つ挙げ、理由を説明してください。

3. `container.querySelector(".search-input")` ではなく `getByRole("textbox", { name: "都市名" })` を使うと、何が得られますか。

4. `getByText` と `findByText` の違いは何ですか。通信を伴う画面ではどちらを使いますか。

5. loading 状態をテストするとき、`setTimeout` で待つのではなく解決を保留するのはなぜですか。

6. 「見つかりませんでした」と「通信に失敗しました」を同じ表示にしてはいけないのはなぜですか。

7. 偽物(モック)を `fetch` ではなく api モジュールに置くのはなぜですか。

8. 中断(AbortSignal)を尊重しない偽物を使うと、どんな紛らわしい失敗が起きますか。

9. 「古い応答が新しい結果を上書きする」不具合が、開発環境で再現しにくいのはなぜですか。

10. 書いたテストが空振りしていないことを、どう確かめますか。
