# Lesson 05: キャッシュ戦略 (Caching Strategies)

## 学習目標

- cache-aside / read-through / write-through / write-behind を使い分けられる
- 無効化 (invalidation) の 3 方式とその失敗パターンを説明できる
- thundering herd と cache stampede を防ぐ手法を実装できる
- キャッシュに起因する障害(スタンピード、ペナルティ、ポイズニング)を説明できる

---

## 1. キャッシュは「速くする」道具ではない

まず前提を正します。キャッシュの本質は**速度**ではなく、**元のデータソースへの負荷を減らすこと**です。

```
キャッシュなし: 全リクエストが DB へ    → DB が律速する
キャッシュあり: 95% がキャッシュで完結  → DB は 5% だけ処理すればよい
```

そして代償は**必ず古いデータを配ること**です。

> **Phil Karlton の有名な言葉**
> "There are only two hard things in Computer Science: cache invalidation and naming things."
> (コンピュータサイエンスで難しいことは 2 つだけ。キャッシュの無効化と、命名だ。)

キャッシュを入れる前に、必ず答えてください。

```
□ どれくらい古いデータなら許容できるか(秒? 分? 時間?)
□ キャッシュが全部消えたとき、DB は生き残れるか
□ 古い値が表示されて困る操作はどれか
```

3 番目に答えられないなら、まだキャッシュを入れるべきではありません。

## 2. 4 つの基本パターン

### Cache-Aside(遅延読み込み)— 最も一般的

アプリケーションがキャッシュと DB の両方を明示的に操作します。

```python
def get_user(user_id: str) -> dict:
    cached = cache.get(f"user:{user_id}")
    if cached is not None:
        return json.loads(cached)              # ヒット

    user = db.query_user(user_id)              # ミス → DB から
    cache.set(f"user:{user_id}", json.dumps(user), ex=300)
    return user
```

| 利点 | 欠点 |
|---|---|
| 実装が単純で、挙動が読みやすい | ミス時に 3 回の往復(get → DB → set) |
| キャッシュが落ちても DB で動き続ける | 初回アクセスは必ず遅い |
| 使われるデータだけがキャッシュされる | 更新時の無効化を自分で書く必要がある |

**迷ったらこれです。**

### Read-Through

キャッシュ層自身が、ミス時に DB から読みます。アプリはキャッシュだけを見ます。

アプリのコードは単純になりますが、**キャッシュが落ちるとアプリ全体が落ちます**。cache-aside の「キャッシュが死んでも DB で動く」という耐障害性が失われる点に注意してください。

### Write-Through

書き込み時に、DB とキャッシュの両方を更新します。

```python
def update_user(user_id: str, data: dict) -> None:
    db.update_user(user_id, data)
    cache.set(f"user:{user_id}", json.dumps(data), ex=300)
```

キャッシュが常に最新になりますが、**書き込みが遅くなり**、読まれないデータまでキャッシュします。

### Write-Behind(write-back)

キャッシュにだけ書いて、DB へは非同期で反映します。書き込みが非常に速い代わりに、**キャッシュが落ちるとデータが失われます**。

カウンタや閲覧数など「多少失っても構わないもの」に限定してください。**決済や注文には絶対に使わないこと。**

### 選び方

```
読み取りが多く、多少古くてよい      → cache-aside
更新直後に必ず最新を返したい        → write-through(+ cache-aside)
書き込みが極端に多く、損失を許容できる → write-behind
```

## 3. 無効化 (invalidation)

データが更新されたとき、古いキャッシュをどうするか。**3 つの方式**があります。

| 方式 | 内容 | 特徴 |
|---|---|---|
| **TTL** | 一定時間で自動的に消える | 単純で堅牢。**その時間だけ古い**ことを受け入れる |
| **明示的削除** | 更新時に `cache.delete(key)` | 即座に反映。**消し忘れると永遠に古いまま** |
| **バージョン付きキー** | キーに版を含める | 消す必要がない。古いキーは TTL で自然に消える |

### まず TTL を使う

```python
cache.set(key, value, ex=300)   # 5 分で消える
```

**TTL は「最悪でもこの時間で復旧する」という保証**です。バグで無効化に失敗しても、TTL があれば必ず正常化します。**TTL を設定しないキャッシュは、いつか必ず事故を起こします。**

### 明示的削除の罠 — 更新と削除の競合

```python
db.update_user(user_id, data)      # ①
cache.delete(f"user:{user_id}")    # ②
```

一見正しいですが、並行実行で壊れます。

```
時刻  スレッドA(更新)          スレッドB(読み取り)
 1                              cache ミス
 2                              DB から古い値を読む
 3    DB を新しい値に更新
 4    cache を削除
 5                              古い値を cache に書き込む  ← 古い値が残る
```

Phase 8 の check-then-act と同じ構造です。**TTL があれば最悪でも 5 分で直りますが、TTL が無ければ永久に古い値が残ります。**

### バージョン付きキー — 削除しないという解法

```python
version = db.get_user_version(user_id)   # 更新のたびに増える
key = f"user:{user_id}:v{version}"
```

更新するとキーが変わるので、古いキーは誰も参照しなくなり、TTL で自然に消えます。**「消す」という操作自体を無くす**のがこの手法の美点です。

同じ発想が、フロントエンドのアセット配信でも使われます(`app.a1b2c3.js` のようにファイル名にハッシュを含める)。

## 4. Cache Stampede(キャッシュスタンピード)

キャッシュの最も危険な障害です。

```
人気のキーの TTL が切れる
        ↓
1000 リクエストが同時にミスする
        ↓
1000 リクエストが同時に DB へ殺到する
        ↓
DB が落ちる
        ↓
キャッシュも埋まらないので、次も同じことが起きる
```

**キャッシュを入れたことで、キャッシュが無いときより脆くなる**という皮肉な状態です。Phase 8 の thundering herd が、キャッシュ層に現れたものです。

### 対策 1: ロックで 1 本だけ通す

最初にミスした 1 リクエストだけが DB へ行き、他は待ちます。

```python
def get_with_lock(key: str, loader, ttl: int = 300):
    cached = cache.get(key)
    if cached is not None:
        return cached

    lock_key = f"lock:{key}"
    # SET NX は「無ければセット」を不可分に行う(Phase 8 の check-then-act 対策)
    if cache.set(lock_key, "1", nx=True, ex=10):
        try:
            value = loader()
            cache.set(key, value, ex=ttl)
            return value
        finally:
            cache.delete(lock_key)

    # ロックを取れなかった側は、少し待って再取得
    time.sleep(0.05)
    return cache.get(key) or loader()      # フォールバック
```

### 対策 2: 早期再計算(確率的期限切れ)

TTL が近づいたら、**確率的に**一部のリクエストだけが先回りして更新します。全員が同時に切れることを防げます。

```python
import random

def should_refresh_early(ttl_remaining: float, total_ttl: float) -> bool:
    """残り時間が短いほど、更新する確率が上がる"""
    if ttl_remaining <= 0:
        return True
    ratio = ttl_remaining / total_ttl
    return random.random() > ratio
```

### 対策 3: TTL にジッターを入れる

同時に大量のキーを作ると、同時に切れます。

```python
ttl = 300 + random.randint(0, 60)   # 300〜360 秒でばらす
```

Phase 8 の jitter とまったく同じ発想です。**一斉に何かが起きることが危険**、という原則が繰り返し現れます。

### 対策 4: stale-while-revalidate

期限切れの値を**返しつつ**、裏で更新します。ユーザーは待たされず、DB への負荷も 1 本で済みます。

```
リクエスト → 古い値を即座に返す
              └→ 裏で新しい値を取得してキャッシュを更新
```

HTTP の `Cache-Control: stale-while-revalidate` も同じ考え方です。**「少し古い値」を返すことが許されるなら、これが最良の選択肢**であることが多くあります。

## 5. その他のキャッシュ障害

### Cache Penetration(キャッシュ貫通)

**存在しないキー**へのアクセスは、常にキャッシュミスになり、常に DB へ届きます。攻撃者がランダムな ID を大量に投げると、キャッシュを素通りして DB を攻撃できます。

**対策**: 「存在しない」という結果もキャッシュします(短い TTL で)。

```python
user = db.query_user(user_id)
if user is None:
    cache.set(key, "__NULL__", ex=60)     # 存在しないこともキャッシュ
    return None
```

### Cache Avalanche(キャッシュ雪崩)

キャッシュサーバー自体が落ちると、**全リクエストが DB へ流れます**。

**対策**:
- キャッシュも冗長化する
- **キャッシュが落ちた状態で DB が耐えられるか**を、事前に負荷試験で確認する
- circuit breaker で DB を守る(Phase 8)

**「キャッシュが落ちたら DB も落ちる」構成は、キャッシュが単一障害点になっています。**

### Cache Poisoning(キャッシュ汚染)

誤った値をキャッシュしてしまうと、TTL が切れるまで全ユーザーに配られます。

特に危険なのは**認証情報や個人情報のキャッシュキーを間違える**ことです。

```python
# ✗ 全ユーザーで同じキー。他人のデータが見える
cache.set("current_user_profile", profile)

# ○ ユーザーごとに分ける
cache.set(f"user:{user_id}:profile", profile)
```

**キャッシュキーにユーザー識別子が含まれているかは、コードレビューの必須確認項目**です。これは性能問題ではなく、セキュリティ問題です。

## 💡 コラム: キャッシュを消したら、世界最大級のサイトが落ちた

キャッシュの怖さは、「無くても動くはず」という思い込みにあります。

大規模サービスの障害報告には、同じ構図が繰り返し登場します。あるチームがキャッシュ層のメンテナンスを行い、安全のためにキャッシュを一度クリアしました。キャッシュが空でも DB から読めるのだから、少し遅くなるだけのはずです。

**そうはなりませんでした。**

平常時、そのサービスはキャッシュヒット率 99% で動いていました。DB が実際に処理していたのは、全リクエストの 1% です。キャッシュを空にした瞬間、DB へのリクエストは **100 倍**になりました。DB は即座に飽和し、応答が遅くなります。応答が遅くなると、アプリ側でタイムアウトが起き、リトライが走ります(Phase 8 の retry storm)。DB への負荷はさらに増えます。

そして最悪なことに、**DB が遅いのでキャッシュを埋めることもできません**。システムは自力では回復できない状態に入りました。復旧には、トラフィックを段階的に流し込みながらキャッシュを温め直す、慎重な作業が必要でした。

Facebook は 2010年、設定システムの不整合を修正するロジックが暴走し、全ノードが一斉に同じキーへ殺到する事態を経験しています。彼らはサイト全体を停止し、トラフィックを遮断した状態でクラスタを立て直すという判断をしました。**サービスを止めることでしか復旧できなかった**のです。

ここから得られる教訓は 3 つです。

1. **キャッシュヒット率は、隠れた依存度である。** ヒット率 99% とは「DB は本来の負荷の 100 倍に耐えられない」という意味です。この数字を知らずに運用してはいけません。
2. **「キャッシュが空の状態」を試したことがあるか。** 本番と同等の負荷で、キャッシュを空にして起動できますか。答えられないなら、それは検証されていない前提です。
3. **回復動作が回復を妨げる。** リトライがDBを潰し、DBが潰れるからキャッシュが埋まらない。Phase 8 の re-mirroring storm と同じ構造です。

キャッシュは「あると速い」ものではありません。**入れた瞬間から、あなたのシステムはそれに依存します。**依存していることを自覚し、それが消えた日のことを設計しておくのが、この Lesson の目的です。

## まとめ

- キャッシュの本質は速度ではなく**データソースの負荷軽減**。代償は必ず古い値を配ること
- 迷ったら **cache-aside**。キャッシュが落ちても DB で動き続ける
- **write-behind は損失を許容できるものだけ**。決済・注文には使わない
- **TTL を必ず設定する**。「最悪でもこの時間で復旧する」という保証になる
- 明示的削除は更新と読み取りの競合で古い値が残りうる。TTL が救う
- **バージョン付きキー**は「消す」操作自体を無くす
- **cache stampede** 対策は、ロック・早期再計算・**TTL のジッター**・stale-while-revalidate
- 存在しない値もキャッシュする(**penetration** 対策)
- **キャッシュヒット率は隠れた依存度**。空の状態で DB が耐えられるか検証する
- **キャッシュキーにユーザー識別子が入っているかはセキュリティ問題**

## 確認問題

1. キャッシュを入れる前に答えるべき 3 つの問いは何ですか。
2. cache-aside と read-through の、耐障害性における違いを説明してください。
3. 「DB を更新してからキャッシュを削除する」実装が並行実行で壊れる順序を、時刻表で示してください。
4. TTL を設定しないキャッシュの危険性を説明してください。
5. バージョン付きキーの利点は何ですか。フロントエンドのどんな仕組みと同じ発想ですか。
6. cache stampede とは何ですか。対策を 4 つ挙げ、それぞれの適用場面を述べてください。
7. キャッシュヒット率 99% のシステムでキャッシュを全消去すると、DB の負荷は何倍になりますか。
8. あなたのシステムでキャッシュサーバーが全滅したとき、DB は耐えられますか。どう検証しますか。
9. キャッシュキーの設計で、セキュリティ上必ず確認すべきことは何ですか。
