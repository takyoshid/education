# Lesson 01: なぜ分散するのか、そして何を失うのか

## 学習目標

- 単一サーバーの限界と、分散が必要になる 3 つの理由を説明できる
- 分散が持ち込む本質的な難しさ(部分障害)を説明できる
- 「分散コンピューティングの落とし穴」を挙げ、身近な実例と結びつけられる
- 分散すべきでない場面を判断できる

---

## 1. まず、分散しないという選択肢

この Phase の最初に、最も重要なことを言います。

> **分散システムにするな。できる限り、1 台で済ませろ。**

分散は性能のための魔法ではありません。**正しさを犠牲にして、規模と可用性を買う取引**です。そして代金は、あなたが想像しているより高くつきます。

現代のサーバー 1 台の実力を、具体的な数字で見てください。

| 資源 | 単一サーバーで到達できる規模の目安 |
|---|---|
| メモリ | 1〜24 TB |
| CPU | 128〜384 コア |
| NVMe SSD | 数百 TB、数百万 IOPS |
| PostgreSQL | 適切に設計すれば毎秒数万トランザクション |

**多くのサービスは、一生 1 台で足ります。** Stack Overflow が長年、少数のサーバーで世界有数のトラフィックを捌いていたのは有名な話です。

「スケールしないと」と思ったら、先にこれを確認してください。

```
1. N+1 クエリを潰したか
2. インデックスを張ったか
3. キャッシュを入れたか
4. 重い処理を非同期化したか(Phase 8)
5. サーバーを大きくしたか(垂直スケール)
```

**この 5 つをやり切る前に分散を始めるのは、ほぼ必ず早すぎます。**

---

## 2. それでも分散する 3 つの理由

| 理由 | 内容 | 例 |
|---|---|---|
| **規模 (scale)** | 1 台の CPU・メモリ・ディスクに収まらない | ペタバイトのデータ、毎秒 100 万リクエスト |
| **可用性 (availability)** | 1 台が壊れてもサービスを続けたい | サーバーの故障、データセンターの停電 |
| **地理 (geography)** | 世界中のユーザーに低遅延で届けたい | 東京のユーザーに東京から応答する |

3 番目は物理法則の問題なので、お金では解決できません。

```
東京 ⇄ ロンドン の物理的な最短往復時間
  距離 約 9,600 km × 2 = 19,200 km
  光ファイバー中の光速 ≒ 20万 km/秒
  → 約 96 ミリ秒(理論下限。実際は 200〜250 ミリ秒)
```

**光より速くはできません。**ロンドンのユーザーに 50 ミリ秒で応答したいなら、ロンドンにデータを置くしかありません。CDN もリードレプリカも、この 1 点から生まれています。

---

## 3. 分散が持ち込むもの — 部分障害 (partial failure)

単一プロセスと分散システムの決定的な違いは、性能でも複雑さでもありません。**部分障害**です。

```
単一プロセス:
  関数を呼ぶ → 成功する か 例外が飛ぶ
  プロセスが死ぬ → 全部が死ぬ。中途半端な状態は残らない

分散システム:
  リモートを呼ぶ → 成功 か 失敗 か 【結果が分からない】
  ノードが死ぬ  → 他は生きている。中途半端な状態が残り続ける
```

「結果が分からない」という**第 3 の状態**が現れることが、すべての難しさの根源です。Phase 8 の二将軍問題で見たとおり、タイムアウトしたリクエストが「届かなかった」のか「処理されたが応答が消えた」のかを、呼び出し側は区別できません。

さらに厄介なのは、**故障したノードと、遅いだけのノードも区別できない**ことです。

```
5 秒応答がない
  ├─ ノードが停止した?
  ├─ ネットワークが切れた?
  ├─ GC で止まっているだけ?
  └─ ただ重い処理をしている?
              ↓
        外からは区別できない
```

「死んだと判断して処理を引き継いだら、実は生きていて両方が動いた」— これが **split-brain** です。分散システムの障害の多くは、ここから生まれます。

---

## 4. 分散コンピューティングの 8 つの落とし穴

1990年代に Sun Microsystems の技術者たち(L. Peter Deutsch ほか)がまとめた **Fallacies of Distributed Computing** です。**新人が必ず前提してしまい、必ず裏切られる 8 つの思い込み**です。

| # | 誤った前提 | 現実 |
|---|---|---|
| 1 | ネットワークは信頼できる | パケットは失われる。ケーブルは抜ける |
| 2 | レイテンシはゼロ | 同一 DC 内でも 0.5ms、大陸間なら 200ms |
| 3 | 帯域は無限 | 大きなレスポンスは詰まる |
| 4 | ネットワークは安全 | 盗聴・改竄・なりすましがある |
| 5 | トポロジーは変わらない | オートスケールで毎分変わる |
| 6 | 管理者は 1 人 | 依存先は別チームが別の判断で動かす |
| 7 | 転送コストはゼロ | シリアライズ・デシリアライズは CPU を食う |
| 8 | ネットワークは均質 | クラウド間、リージョン間で挙動が違う |

### なぜこれが「落とし穴」なのか

ローカル関数呼び出しとリモート呼び出しが、**コード上は同じに見える**からです。

```python
user = get_user(user_id)          # ローカル? リモート?
```

見た目が同じでも、実態はまったく違います。

| | ローカル関数 | リモート呼び出し |
|---|---|---|
| 所要時間 | ナノ秒 | ミリ秒〜秒(**100万倍**) |
| 失敗 | 例外(原因が明確) | タイムアウト、切断、部分成功 |
| 結果不明 | ありえない | **ありうる** |
| 相手の状態 | 同じプロセス | 独立に落ちる、独立にデプロイされる |

**「リモート呼び出しをローカル呼び出しのように見せる」抽象化は、必ず漏れます。** タイムアウトを設定し、失敗を扱い、冪等にする — Phase 8 で学んだことは、すべてこの境界のためにあります。

## 5. 分散を始める前のチェックリスト

マイクロサービスへの分割を検討しているなら、次に答えてください。

```
□ 単一サーバーの限界に、実際に到達したか(計測したか)
□ 分割したサービス間のトランザクションをどう扱うか決めたか
□ 1 つのサービスが落ちたとき、他が何を返すか決めたか
□ 分散トレーシングを入れる用意があるか
□ ローカルで全体を起動できるか
□ デプロイの順序依存をどう扱うか決めたか
□ データの整合性が一時的に崩れることを、業務が許容できるか
```

**答えられない項目があるなら、まだ分割しないでください。**

> **モノリスは負債ではありません。** 適切に設計されたモノリス(モジュラーモノリス)は、多くの組織にとって最良の選択です。分割は、組織が大きくなり「チームが互いをブロックし始めた」ときに検討するものです。技術的な理由より、**組織的な理由**で分割することのほうが多いのが実情です。

## 💡 コラム: 「ネットワークは信頼できる」を信じた結果、5億円が消えた

2015年、ある大手クラウドサービスの障害報告書に、こんな一節がありました。障害の引き金は、ネットワーク機器のファームウェア更新でした。更新自体は成功しています。ただ、その最中の**数十秒間だけ**、一部のノード間でパケットの往復が通常の数百倍遅くなりました。

それだけです。ネットワークは切れていません。ただ遅くなっただけ。

しかしそのシステムでは、ノード同士が「相手が生きているか」をハートビートで確認し、一定時間応答がなければ「死んだ」と判断してデータを引き継ぐ設計になっていました。数十秒の遅延は、その閾値を超えました。

ノード A は「B が死んだ」と判断し、B の担当データを引き継ぎます。同時に B は「A が死んだ」と判断し、A の担当データを引き継ぎます。**両方が生きていて、両方が「自分が唯一の担当者だ」と信じている状態** — split-brain です。

その後ネットワークが正常に戻ったとき、システムは 2 つの食い違うデータの版を抱えていました。どちらが正しいのか、機械には判断できません。復旧チームは手作業で照合するしかなく、その間サービスは止まり続けました。

この種の障害は、名前を変えて何度も繰り返し起きています。GitHub は 2018年、東海岸と西海岸の間の **43 秒間**のネットワーク分断で、MySQL クラスタが split-brain に陥り、**24 時間以上**にわたってサービスが劣化しました。原因は 43 秒。復旧は 24 時間。**壊すのは一瞬で、直すのは何桁も時間がかかる**のが分散システムです。

ここから学ぶべきことは、「ハートビートを使うな」ではありません。

**「応答がない」は「死んだ」を意味しない**、ということです。遅いだけかもしれない。GC で止まっているだけかもしれない。そして、外側からは絶対に区別できません。

だから成熟した分散システムは、多数決を取ります(Lesson 06 の合意アルゴリズム)。「私が B を死んだと思う」ではなく、「過半数のノードが B を死んだと思う」で初めて動く。1 人の判断を信じないという、きわめて人間的な知恵です。

あなたがこの Phase で身につけるのは、速いシステムの作り方ではありません。**「分からない」という状態を、正直に扱う技術**です。

## まとめ

- **まず分散しない**。1 台の実力は想像よりはるかに高い。N+1・インデックス・キャッシュ・非同期化・垂直スケールを先に尽くす
- 分散する理由は **規模・可用性・地理**の 3 つ。地理だけは物理法則の問題でお金では解決できない
- 分散の本質的な難しさは**部分障害**。「成功」「失敗」に加えて「**結果が分からない**」が現れる
- **故障したノードと遅いノードは区別できない**。誤判定は split-brain を生む
- **8 つの落とし穴**は「必ず前提してしまい、必ず裏切られる」思い込み
- リモート呼び出しをローカルのように見せる抽象化は必ず漏れる
- モノリスは負債ではない。分割は技術的理由より**組織的理由**で必要になることが多い

## 確認問題

1. 「スケールしない」と相談されました。分散を提案する前に確認すべきことを 5 つ挙げてください。
2. 部分障害とは何ですか。単一プロセスの障害とどう違いますか。
3. 「ノードが応答しない」とき、考えられる原因を 4 つ挙げてください。それらを外部から区別できますか。
4. split-brain とは何ですか。なぜ起きますか。
5. 8 つの落とし穴のうち 3 つを選び、あなたが実際に踏んだ(または踏みそうな)場面を書いてください。
6. 東京のサーバーからロンドンのユーザーへ応答する場合の、理論上の最小往復時間を計算してください。この制約を回避する方法は何ですか。
7. モノリスをマイクロサービスに分割すべき「組織的な理由」とは何ですか。
