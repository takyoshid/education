# Lesson 04: 整合性モデル (Consistency Models) と CAP

## 学習目標

- linearizability・causal・eventual の違いを、観測できる挙動で説明できる
- CAP 定理を正確に述べられる(よくある誤用を指摘できる)
- PACELC で「平常時のトレードオフ」まで含めて議論できる
- 業務要件から必要な整合性の強さを選べる

---

## 1. 「整合性」という言葉の混乱

`consistency` は、文脈によって**まったく違うもの**を指します。まずここを整理しないと議論が噛み合いません。

| 用語 | 意味 | 出てくる場所 |
|---|---|---|
| ACID の **C** | DB の制約(外部キー、CHECK)を満たす | 単一 DB のトランザクション |
| CAP の **C** | **linearizability**(下記) | 分散システム |
| 結果整合性 (eventual) | いつかは全複製が同じ値に落ち着く | 分散システム |

**ACID の C と CAP の C は別物です。** 面接でも実務でも取り違えている人が多いので、自分は正確に使ってください。

以降この Phase で「整合性」と言うときは、**複数の複製にまたがって、読み取りが何を返しうるか**の話をしています。

---

## 2. 整合性モデルの階層

```
強い ←──────────────────────────────────────────────→ 弱い

Linearizability   Sequential   Causal      Eventual
(線形化可能性)                 (因果整合性)  (結果整合性)

 直感的で安全       ←─────────────→        速くて可用
 遅くて壊れやすい                          異常が観測される
```

### Linearizability(線形化可能性)

**「複製が 1 つしか無いかのように見える」**という保証です。

```
書き込みが完了した瞬間から、
それ以降に始まるすべての読み取りは、その値かそれ以降の値を返す。
```

```
Client A: ──[write x=1]──┐
Client B:                └──[read x]──▶ 必ず 1 が返る
Client C:                  [read x]──▶ 必ず 1 が返る
```

最も直感的で、最も高価です。**ノード間の調整(合意)が必要**なので、遅く、ネットワーク分断時には応答できません。

### Sequential(逐次一貫性)

全員が**同じ順序**で操作を観測しますが、その順序が**実時間と一致する必要はありません**。書き込みが「少し古く」見えることを許します。

### Causal(因果整合性)

**因果関係のある操作だけ**順序を保証します。無関係な操作の順序は問いません。

```
保証される: 「質問」→「その返信」の順に見える
保証されない: 無関係な2人の投稿の前後関係
```

Lesson 02 の consistent prefix reads の問題を解決します。**実用上、多くのアプリに必要十分**で、しかも linearizability よりずっと安く実現できます。「因果整合性は、ネットワーク分断中も可用でいられる最強のモデル」であることが知られています。

### Eventual(結果整合性)

**「更新が止まれば、いつかは全複製が同じ値に収束する」**だけを保証します。

```
いつまでに?   → 保証しない
それまで何が読める? → 何でも(古い値、順序の入れ替わり)
```

保証としては非常に弱いですが、**最も速く、最も可用**です。DNS、CDN、SNS のタイムラインなど、身の回りの大規模システムの多くがこれです。

## 3. CAP 定理 — 正確に述べる

CAP 定理ほど誤って引用される定理はありません。まず正確な形を書きます。

> **ネットワーク分断 (Partition) が発生したとき、
> 一貫性 (Consistency = linearizability) と可用性 (Availability) の
> 両方を同時に満たすことはできない。**

```
ネットワーク分断が起きた

  ┌───────────┐   ╳   ┌───────────┐
  │ ノード A   │  分断  │ ノード B   │
  └───────────┘       └───────────┘
       │                    │
   書き込み要求が来た      読み取り要求が来た

  選択肢は 2 つしかない:

  CP: 一貫性を守る → B は「答えられません」と拒否する(可用性を捨てる)
  AP: 可用性を守る → B は古い値を返す(一貫性を捨てる)
```

### よくある誤用

| 誤り | 正しくは |
|---|---|
| 「CAP の 3 つから 2 つを選ぶ」 | **P は選べない**。ネットワーク分断は起きる。選べるのは分断時の C か A |
| 「うちは CA システムです」 | **存在しません**。分断を諦めるのは単一ノードの話 |
| 「NoSQL は AP、RDB は CP」 | 製品ではなく**設定と操作**で決まる。同じ製品で両方できる |
| 「CAP があるから一貫性は諦めるしかない」 | 分断は稀。**平常時の話をしていない**(次節) |

**「P を選ばない」という選択肢はありません。**ネットワークは必ず分断します(Lesson 01 の落とし穴 #1)。だから CAP が問うているのは、**分断が起きたときにどう振る舞うか**の 1 点だけです。

## 4. PACELC — 平常時のトレードオフ

CAP の最大の弱点は、**分断していないとき(=ほとんどの時間)について何も言っていない**ことです。それを補うのが **PACELC** です。

> **if (P)artition: (A)vailability か (C)onsistency か。
> (E)lse: (L)atency か (C)onsistency か。**

```
分断時    : A か C か   ← CAP が扱う範囲
平常時    : L か C か   ← 実は毎日効いてくるのはこっち
```

平常時でも、強い一貫性を保つにはノード間の往復が必要です。**一貫性は常にレイテンシで支払われます。**

| システム | 分断時 | 平常時 |
|---|---|---|
| PostgreSQL(同期レプリケーション) | PC(一貫性優先) | EC(一貫性優先) |
| PostgreSQL(非同期レプリケーション) | PA | EL |
| Cassandra(既定) | PA | EL |
| DynamoDB(強い整合性の読み取り) | PC | EC |
| DynamoDB(結果整合性の読み取り) | PA | EL |

**同じ製品でも設定で変わる**ことが分かります。「この DB は CP だ」という言い方が雑である理由がこれです。

> **面接での使い方**: 「CAP でいうと AP です」で止めず、「**分断時は古い値を返して可用性を優先し、平常時は結果整合性の読み取りでレイテンシを取ります。ただし残高表示だけは強い整合性の読み取りを使います**」と言えると、実際に設計できる人だと伝わります。

## 5. 業務要件から選ぶ

整合性は「強いほど良い」ものではありません。**必要な場所にだけ、必要な強さを使います。**

| 業務 | 必要な整合性 | 理由 |
|---|---|---|
| 銀行の残高、在庫の引当 | **強い(linearizable)** | 二重引き落とし・売り越しが許されない |
| ユーザーの認証情報 | 強い | 無効化したトークンが通ってはいけない |
| 注文の作成 | 強い(または冪等性で代替) | 二重注文が許されない |
| 会話・コメントスレッド | **因果** | 返信が質問より先に見えてはいけない |
| いいね数、閲覧数 | **結果整合性** | 数秒古くても誰も困らない |
| おすすめ、検索インデックス | 結果整合性 | 少し古くて構わない |
| 通知の既読状態 | 結果整合性 | 多少ずれても実害が小さい |

### 同じシステムの中で混ぜる

これが実務の要点です。**サービス全体で 1 つの整合性モデルを選ぶ必要はありません。**

```
EC サイト
  ├─ 在庫の引当     → 強い整合性(単一 leader、条件付き UPDATE)
  ├─ 注文の作成     → 強い整合性 + 冪等キー(Phase 8)
  ├─ 商品ページ表示 → 結果整合性(レプリカから読む、CDN でキャッシュ)
  └─ レビュー一覧   → 結果整合性
```

**強い整合性が必要なのは、たいていシステムのごく一部です。**そこを見極めて絞り込むことが、性能と可用性を両立させる唯一の方法です。

### 「強い整合性が要る」と言われたら

要件を疑ってください。多くの場合、本当に必要なのは linearizability ではなく、次のどれかです。

- **冪等性**があれば足りる(重複しても正しい → Phase 8)
- **因果順序**があれば足りる(会話が成立すればよい)
- **単調性**があれば足りる(値が巻き戻らなければよい)
- **業務上の制約**として表現できる(残高が負にならない = DB の CHECK 制約)

## 💡 コラム: 「結果整合性」でチケットを二重に売った話、あるいは売らなかった話

分散システムの教科書的な失敗例として、こんな筋書きがよく語られます。

人気公演のチケット販売サイトが、負荷対策として在庫数を複数のリージョンにレプリケートしていた。読み取りは近いレプリカから。ある瞬間、残り 1 席に対して東京とロンドンの利用者が同時に購入した。両方のレプリカが「残り 1 席」と答え、両方が売れた。**存在しない座席が 1 つ売れた。**

これは Phase 8 の check-then-act が、地球規模に拡大したものです。lock を取らずに `if stock > 0` を評価した — ただそれだけのことが、大陸をまたぐと「レプリカが古い」という形で現れます。

さて、ここからが本題です。**この設計は間違いだったのでしょうか。**

実は、多くの実在のチケットシステムは、意図的に似た設計を選んでいます。ただし 1 点だけ違います。**在庫の「表示」は結果整合性で、在庫の「確保」は強い整合性で行う**のです。

```
商品ページに「残りわずか」と表示   → 結果整合性(古くてよい。速さが優先)
        ↓
「購入」ボタンを押す
        ↓
在庫を確保する                    → 強い整合性(単一の権威で直列化)
        ↓
確保できなかった                  → 「申し訳ありません、売り切れました」
```

購入ボタンを押した後に売り切れを知らされるのは、UX として最良ではありません。しかし、**全世界の閲覧リクエストに強い整合性を課すコスト**と比べれば、はるかに安い。そして「表示が少し古い」ことによる実害は、謝罪文ひとつで済みます。

ここに、この Lesson の結論があります。

**整合性は、システムの属性ではなく、操作ごとの選択です。**

「うちは結果整合性です」という設計は存在しません。存在するのは、「**この操作は古い値でよい、この操作は絶対に駄目**」という、一つひとつの判断の集合です。そしてその判断ができるかどうかが、分散システムを設計できる人とできない人を分けます。

読み取りの 99.9% は古くて構いません。残りの 0.1% を正確に見つけ出せますか。それがこの Phase の問いです。

---

## まとめ

- **ACID の C と CAP の C は別物**。CAP の C は linearizability
- 整合性モデルは階層をなす: **linearizable > sequential > causal > eventual**
- **因果整合性**は実用上多くのアプリに必要十分で、分断中も可用でいられる
- CAP は「**分断時に** C か A か」だけを述べている。**P は選べない**。「CA システム」は存在しない
- 製品ではなく**設定と操作**で C/A が決まる
- **PACELC** は平常時のトレードオフ(レイテンシ vs 一貫性)まで含む。日常的に効くのはこちら
- **一貫性は常にレイテンシで支払われる**
- 整合性はシステム全体ではなく**操作ごとに選ぶ**。強い整合性が要るのは、たいていごく一部
- 「強い整合性が必要」と言われたら、冪等性・因果順序・単調性・DB 制約で代替できないか疑う

## 確認問題

1. ACID の C と CAP の C の違いを説明してください。
2. 「CAP の 3 つから 2 つを選ぶ」という説明はなぜ不正確ですか。
3. 「うちは CA システムです」と言われました。どう指摘しますか。
4. linearizability と causal consistency の違いを、観測できる挙動の例で説明してください。
5. PACELC が CAP を補っているのは何ですか。なぜそれが実務上重要ですか。
6. あなたのサービスの機能を 5 つ挙げ、それぞれに必要な整合性の強さを判断してください。
7. 「在庫表示は結果整合性、在庫確保は強い整合性」という設計の利点と、受け入れている欠点を述べてください。
8. 「この処理には強い整合性が必要だ」と主張されたとき、代替案として検討すべきものを 4 つ挙げてください。
