# Lesson 03: 時間と順序

## 学習目標

- 分散システムで「時刻」が信用できない理由を説明できる
- happens-before 関係と、因果関係のない「並行」を区別できる
- 論理時計(Lamport clock / vector clock)が何を解決するかを説明できる
- 「遅いノード」と「死んだノード」を区別できないという事実と、その帰結を説明できる
- last-write-wins が黙ってデータを捨てることを説明できる

---

## 1. 「いつ起きたか」が分からない

前のレッスンで、レプリケーションには遅延があることを見ました。ここで自然に出てくる疑問があります。

> 2 つの書き込みが競合したら、**新しいほうを採用すればいい**のでは?

もっともに聞こえます。そして**これが、分散システムで最も多いデータ消失の原因です。**

理由は単純です。**「新しいほう」を判定できないからです。**

### 壁時計は合っていない

各サーバは自分の時計を持っています。時刻同期の仕組み(NTP など)で合わせていますが、完全には合いません。ずれる理由はいくらでもあります。

- 同期の通信自体に遅延がある(往復時間の半分を推定するしかない)
- 水晶振動子の精度は温度で変わる
- 仮想マシンが一時停止されると、その間の時間が飛ぶ
- うるう秒や、管理者による手動変更で**時刻が巻き戻る**ことがある

**時刻が巻き戻る**という点が特に厄介です。多くのプログラムは時刻が単調に増えることを前提にしていますが、壁時計はその保証をしません。

```
サーバ A の時計: 10:00:05  ← 5 秒進んでいる
サーバ B の時計: 10:00:00

10:00:00 実時刻: B に「値を X にする」書き込み  → B は 10:00:00 と記録
10:00:01 実時刻: A に「値を Y にする」書き込み  → A は 10:00:06 と記録

後で突き合わせると、A のほうが「新しい」と判定される。
実際に後から起きたのは A なので、たまたま正しい。

しかし A の時計が 5 秒「遅れて」いたら、
実際には後の書き込みが「古い」と判定され、黙って捨てられる。
```

### last-write-wins は「勝者」を決めているだけ

タイムスタンプが大きいほうを採用する方式を **last-write-wins (LWW)** と呼びます。広く使われていますが、正確に理解しておく必要があります。

**LWW は競合を解決していません。片方を黙って捨てているだけです。**

捨てられた書き込みは、エラーにもならず、ログにも残らないことがあります。ユーザーから見ると「保存したはずの変更が消えた」という現象になります。

LWW を使ってよいのは、**失われても業務上問題ない**と判断できる場合だけです。その判断をせずに既定値として使うのは、事故を待っている状態です。

## 2. 時刻ではなく「順序」を考える

壁時計が信用できないなら、何を使えばよいのか。

答えは、**時刻をあきらめて、順序だけを扱う**ことです。

「何時何分に起きたか」を知る必要はありません。知りたいのは**「A と B のどちらが先か」**だけです。そしてこれは、時計がなくても決められる場合があります。

### happens-before 関係

1978 年にレスリー・ランポートが定式化した考え方です。次の 3 つの場合、「A は B より前に起きた」(A → B)と言えます。

1. **同じプロセスの中で、A の後に B が実行された**
2. **A がメッセージの送信で、B がその受信である**
3. **A → C かつ C → B なら、A → B**(推移律)

これだけです。時計は一度も出てきません。**因果関係だけで順序を決めています。**

### 「並行」とは、順序が決まらないこと

重要なのは、**この関係で順序が決まらない組み合わせがある**ことです。

```
プロセス P: ──a1──────a2─────────────▶
                 \
                  \  メッセージ
                   \
プロセス Q: ─────────b1──────b2───────▶
```

- `a1 → a2`(同じプロセス内)
- `a1 → b1`(送信 → 受信)
- `a1 → b2`(推移律)
- **`a2` と `b1` の間には、どちらの向きの矢印もない**

`a2` と `b1` は **並行(concurrent)** です。これは「同時刻に起きた」という意味ではありません。**互いに影響を与えようがなかった**という意味です。

この区別が決定的です。

| 関係 | 意味 | どう扱うか |
|---|---|---|
| `A → B` | B は A を知りうる。因果がある | 順序どおりに適用すればよい |
| **並行** | 互いを知らない。順序に意味がない | **競合として扱う。勝手に片方を捨ててはいけない** |

**壁時計を使う方式の根本的な誤りは、並行な操作にも無理やり順序をつけてしまうことです。** 順序がないものに順序をつければ、片方が理由なく負けます。

## 3. 論理時計

happens-before を、プログラムで扱える数値にしたものが論理時計です。

### Lamport clock

各プロセスがカウンタを 1 つ持ちます。規則は 2 つだけです。

1. 何か起きるたびに、自分のカウンタを 1 増やす
2. メッセージを送るときはカウンタを添える。受け取った側は
   `自分のカウンタ = max(自分, 受け取った値) + 1` とする

```
P: 1 ──── 2 ────────────── 3
      \
       \ (値 2 を添えて送信)
        \
Q: ───── 3 ──── 4 ─────────────
         ↑ max(0, 2) + 1 = 3
```

これで次が成り立ちます。

> **A → B ならば、C(A) < C(B)**

しかし**逆は成り立ちません。**

> C(A) < C(B) でも、A → B とは限らない(並行かもしれない)

つまり Lamport clock は、**因果があれば必ず数値の大小に反映されるが、数値の大小から因果は判定できません。**全順序をつけられますが、その順序の一部は「本当は並行なのに、便宜的に並べたもの」です。

### Vector clock

「並行かどうかを判定したい」場合は、ベクトル時計を使います。各プロセスが**全プロセス分のカウンタ**を持ちます。

```
P の時計: [P=2, Q=0]
Q の時計: [P=1, Q=3]
```

2 つの時計を比べたとき、

- **すべての要素が「以下」で、1 つ以上が「未満」** → 一方が他方より前
- **どちらでもない**(お互いに勝っている要素がある) → **並行**

上の例では、P は P の値で勝ち(2 > 1)、Q は Q の値で勝っています(3 > 0)。したがって**並行**です。

これで「これは競合だ」と**検出できる**ようになりました。

### 検出できても、解決はしてくれない

ベクトル時計が教えてくれるのは「並行である」という事実までです。**どちらを採用すべきかは、業務のルールでしか決められません。**

| 場面 | 妥当な解決 |
|---|---|
| ショッピングカート | 両方の商品を残す(和をとる) |
| 文書の同時編集 | 両方の変更を統合する、または利用者に見せて選ばせる |
| アカウント残高 | **自動解決してはいけない。**業務として決める |
| 最終ログイン時刻 | どちらでもよい。LWW で構わない |

**技術は競合を検出できますが、何が正しいかは決められません。** これは分散システムに限らず、設計全般に言えることです。

## 4. 「遅い」と「死んだ」は区別できない

もう一つ、時間にまつわる基本的な事実があります。

あるノードに要求を送り、応答が返ってきません。何が起きたのでしょうか。

```
考えられること:
  1. ノードが落ちている
  2. ノードは生きているが、非常に遅い
  3. 要求が途中で失われた
  4. 応答が途中で失われた
  5. ノードは処理を完了したが、応答がまだ届いていない
```

**外から観測して、これらを区別する方法はありません。** どれだけ待っても、「あと 1 秒待てば返ってくる」可能性は消えません。

これは実装の未熟さではなく、**非同期ネットワークにおける原理的な限界**です。「応答が無限に遅れうる」という前提のもとでは、故障の検出は原理的に不可能であることが証明されています。

### だから timeout は「推測」である

現実のシステムは timeout で打ち切ります。しかし理解しておくべきことがあります。

> **timeout は障害の検出ではありません。「障害だと決めること」です。**

そして、この決定は間違いえます。

| timeout が短すぎる | timeout が長すぎる |
|---|---|
| 生きているノードを死んだと誤判定する | 死んだノードを待ち続ける |
| 不要なフェイルオーバーが起きる | 障害からの復旧が遅れる |
| **split-brain の原因になる** | 利用者を待たせる |

Phase 8 で「timeout は失敗ではなく予算である」と学びました。ここでの言い方は、**その予算を使い切ったとき、あなたは推測をしている**ということです。

### 帰結: 誤判定を前提に設計する

「遅いノードを死んだと誤判定する」ことは必ず起きます。だから次が要ります。

- **冪等性** — 死んだと判定して再送した要求が、実は届いていて二重に処理されうる(Phase 8 で学んだ理由が、ここでも同じ形で現れます)
- **フェンシング** — 「自分はまだリーダーだ」と思い込んでいる古いノードの操作を、後段で拒否できる仕組み(Lesson 07 の分散ロックの罠で扱います)
- **クォーラム** — 1 つのノードの判断を信じず、過半数の合意で決める(Lesson 07)

## 💡 コラム: 時計を捨てた論文が、40年後の分散システムを支えている

レスリー・ランポートが 1978 年に発表した論文「Time, Clocks, and the Ordering of Events in a Distributed System」は、コンピュータ科学で最も引用された論文の一つです。

この論文が画期的だったのは、**問題を解いたからではなく、問題を捨てたから**でした。当時の研究者は「分散したコンピュータの時計をどう正確に合わせるか」を考えていました。ランポートは「**そもそも時刻を知る必要があるのか**」と問い、必要なのは順序だけであり、順序は因果関係だけで定義できることを示しました。

面白いのは、彼がこの着想を得たきっかけです。ランポートは特殊相対性理論を思い出したと語っています。相対論では、離れた 2 つの出来事の「同時刻」は観測者によって変わります。しかし**因果関係の順序だけは、どの観測者から見ても変わりません。**光より速く情報は伝わらないからです。分散システムのメッセージも同じで、届くまでは知りようがない。物理学の制約と、ネットワークの制約が、同じ数学的構造を持っていたのです。

ランポートは 2013 年にチューリング賞を受賞しました。**この論文は 1978 年のものですが、内容が古びる気配はありません。**時計が合わないことも、光より速く情報が伝わらないことも、これから 100 年で変わる見込みがないからです。

余談ですが、彼は論文執筆システム LaTeX の作者でもあります。この教材を含む世界中の技術文書が、いまも彼の作った道具で書かれています。

## まとめ

| 概念 | 要点 |
|------|------|
| 壁時計 | 分散環境では信用できない。ずれるうえに、巻き戻ることもある |
| last-write-wins | 競合を解決していない。片方を黙って捨てている |
| happens-before | 時計を使わず、因果関係だけで順序を決める |
| 並行(concurrent) | 「同時刻」ではなく「互いに影響しようがなかった」。順序をつけてはいけない |
| Lamport clock | 因果があれば数値に反映される。逆は成り立たない |
| Vector clock | 並行かどうかを**検出**できる。解決はしてくれない |
| 競合の解決 | 技術では決められない。業務のルールで決める |
| 故障検出 | 「遅い」と「死んだ」は原理的に区別できない |
| timeout | 障害の検出ではなく、障害だと**決めること**。間違いうる |

## 確認問題

1. 2 つの書き込みのうち「新しいほう」をタイムスタンプで選ぶ方式には、どんな問題がありますか。

2. 壁時計が巻き戻ることがあるのはなぜですか。巻き戻ると何が起きますか。

3. happens-before 関係の 3 つの規則を挙げてください。この定義に時計が登場しないのはなぜですか。

4. 2 つの操作が「並行である」とは、どういう意味ですか。「同時刻に起きた」との違いを説明してください。

5. Lamport clock で `C(A) < C(B)` だったとき、「A は B より前に起きた」と結論できますか。理由も答えてください。

6. ベクトル時計が「並行だ」と教えてくれました。次に何をすべきですか。

7. 次の場面で、競合をどう解決すべきか答えてください。理由も述べてください。
   - (a) ショッピングカートへの商品追加が 2 か所で並行に起きた
   - (b) 銀行口座の残高更新が 2 か所で並行に起きた

8. ノードに要求を送って応答が返らないとき、考えられる原因を 5 つ挙げてください。これらを外から区別できますか。

9. timeout を短くしすぎると何が起きますか。長くしすぎると何が起きますか。

10. 「遅いノードを死んだと誤判定する」ことを前提にすると、どんな仕組みが必要になりますか。3 つ挙げてください。
