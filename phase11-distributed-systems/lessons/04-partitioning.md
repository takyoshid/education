# Lesson 04: パーティショニング / シャーディング

## 学習目標

- レンジ分割とハッシュ分割の違いと適用場面を判断できる
- ホットスポットが生まれる原因と対策を挙げられる
- コンシステントハッシュ法がリバランスの何を解決するか説明できる
- 分割後に難しくなる操作(結合・トランザクション・二次インデックス)を説明できる

---

## 1. なぜ分割するのか

レプリケーション(Lesson 02)は**同じデータを複数持つ**ことでした。パーティショニングは**違うデータを別のノードに置く**ことです。

```
レプリケーション          パーティショニング(シャーディング)
[全データ][全データ]      [A〜F][G〜M][N〜S][T〜Z]
   同じもの                    別々のもの
   読み取りがスケール           書き込みとデータ量がスケール
```

目的は 3 つです。

- **データ量**が 1 台のディスクに収まらない
- **書き込み量**が 1 台の性能を超える
- 特定のデータへの**アクセス集中**を分散したい

実務では両方を組み合わせます。

```
パーティション1: Leader → Follower, Follower
パーティション2: Leader → Follower, Follower
パーティション3: Leader → Follower, Follower
```

> **先に確認**: Lesson 01 と同じ警告です。**分割は最後の手段**です。一度分割すると元に戻すのは非常に困難で、それまで当たり前だった `JOIN` と `TRANSACTION` が使えなくなります。インデックス、キャッシュ、垂直スケール、不要データの削除・アーカイブを先に尽くしてください。

## 2. 分割の方法

### レンジ分割 (range partitioning)

キーの範囲でノードを決めます。

```
[a〜f] → ノード1      [2026-01] → ノード1
[g〜m] → ノード2      [2026-02] → ノード2
[n〜s] → ノード3      [2026-03] → ノード3
[t〜z] → ノード4      [2026-04] → ノード4
```

| 利点 | 欠点 |
|---|---|
| **範囲検索が効率的**(1 ノードで完結) | **偏りやすい** |
| 順序を保った走査ができる | 時系列キーだと最新のノードに集中する |

**典型的な失敗**: 主キーをタイムスタンプにすると、**書き込みが常に最後のノードだけに集中**します。他のノードは遊んでいるのに 1 台だけが火を噴きます。

### ハッシュ分割 (hash partitioning)

キーのハッシュ値でノードを決めます。

```python
node = hash(key) % node_count
```

| 利点 | 欠点 |
|---|---|
| **均等に分散する** | **範囲検索ができない**(全ノードに問い合わせ) |
| ホットスポットが起きにくい | 順序が失われる |

**注意**: Python の組み込み `hash()` は文字列に対してプロセスごとに変わります(ハッシュ衝突攻撃対策の salt)。**永続的な分割には使えません。**

```python
# ✗ プロセスを再起動すると別のノードに割り当てられる
node = hash(user_id) % n

# ○ 決定的なハッシュを使う
import hashlib
node = int(hashlib.sha256(user_id.encode()).hexdigest(), 16) % n
```

### 組み合わせ

先頭をハッシュ、残りをレンジにすると両方の利点を取れます。Cassandra の「複合主キー」がこの形です。

```
(user_id をハッシュ, timestamp でソート)
  → ユーザーごとに分散し、そのユーザー内では時系列で範囲検索できる
```

## 3. ホットスポット

分割しても、負荷が均等になるとは限りません。**特定のパーティションに集中する状態**をホットスポットと呼びます。

### 原因 1: キーの偏り

```
SNS で「有名人」のフォロワー一覧を user_id で分割
  → 一般ユーザー: 数百件
  → 有名人:      1 億件
  → そのパーティションだけ破綻する
```

**対策**: ホットなキーだけを、さらに細かく分割します。

```python
# 通常のキー
partition_key = celebrity_id

# ホットなキーには乱数のサフィックスを付けて 100 分割
partition_key = f"{celebrity_id}:{random.randint(0, 99)}"
```

代償は、読み取り時に 100 個すべてを集めて結合する必要があることです。**「書き込みの分散」と「読み取りの単純さ」のトレードオフ**です。

### 原因 2: 時系列キー

```
主キー = timestamp  → 常に最後のパーティションだけに書き込む
```

**対策**: 先頭に別の要素を置きます。`(user_id, timestamp)` のようにすれば、書き込みは user_id で分散します。

### 原因 3: 順序保証を持つ ID

`AUTO_INCREMENT` の連番も時系列キーと同じ問題を起こします。UUID や、時系列とランダム性を併せ持つ ID(ULID、Snowflake ID)を検討します。

> **設計の鉄則**: **パーティションキーの選択は、後から変更するのが最も難しい決定**です。テーブル設計時に「このキーで負荷は均等に散るか」「範囲検索は必要か」「将来の偏りは?」を必ず検討してください。

## 4. リバランス — ノードを増やすとき

ノードを追加したら、データを移し替える必要があります。ここに大きな落とし穴があります。

### ✗ `hash(key) % N` の罠

```
N=4 のとき: hash=17 → 17 % 4 = 1 番ノード
N=5 にすると: 17 % 5 = 2 番ノード   ← 移動する
```

ノード数が変わると、**ほぼ全てのキーの割り当てが変わります**。4 台から 5 台にするだけで、データの 80% 以上が移動します。移動中はネットワークとディスクが飽和し、サービスは実質停止します。

### ○ 対策 1: 固定数のパーティション

**ノード数よりずっと多い**パーティションを最初に作り、パーティションをノードへ割り当てます。

```
1000 個のパーティションを作っておく

4 ノードのとき : 各ノードが 250 パーティションを担当
5 ノードにする : 各ノードが 200 パーティション
                 → 移動するのは 1000 個中 200 個だけ
```

パーティションの数は変えず、**割り当てだけを変える**のがポイントです。Elasticsearch や Riak がこの方式です。

欠点は、パーティション数を最初に決め打ちする必要があること。少なすぎると将来スケールできず、多すぎると管理コストがかかります。

### ○ 対策 2: コンシステントハッシュ法

ハッシュ空間を**円環**とみなし、ノードもキーもその上に配置します。キーは「時計回りで最初に出会ったノード」が担当します。

```
        0
        │
  ノードC   ノードA
     ╲   ○   ╱
      ╲  │  ╱
   ────●──●────      ○ = キー
      ╱     ╲        ● = ノード
     ╱  ノードB ╲

ノードを 1 台追加すると、
その隣接区間のキーだけが移動する(全体の 1/N 程度)
```

ノードの増減で移動するデータが **1/N 程度**に収まります。実際には各ノードを複数の「仮想ノード」として円環上に配置し、偏りを減らします。

Cassandra、DynamoDB、多くの分散キャッシュ(memcached クライアント)がこの方式を使っています。

## 5. 分割すると失われるもの

ここが最も重要です。**分割はタダではありません。**

### JOIN ができなくなる

```sql
-- 分割前: 一発で書ける
SELECT u.name, o.amount
  FROM users u JOIN orders o ON u.id = o.user_id;
```

`users` と `orders` が別のノードにあると、この SQL は実行できません。アプリ側で 2 回問い合わせて結合します。

**対策**: 一緒に使うデータを同じパーティションに置きます(**colocation**)。`orders` を `user_id` で分割すれば、あるユーザーの注文は必ずそのユーザーと同じノードに載ります。

### トランザクションが効かなくなる

```python
# 単一 DB なら簡単
with db.begin():
    accounts.withdraw(a, 1000)
    accounts.deposit(b, 1000)
```

a と b が別のノードにあると、この原子性は保証されません。

**選択肢**:

| 手法 | 内容 | 代償 |
|---|---|---|
| **設計で回避** | 関連データを同じパーティションに置く | 分割キーの制約が強くなる |
| **Saga パターン** | 段階的に実行し、失敗したら補償処理で戻す | 中間状態が観測される。補償処理の設計が必要 |
| 2 相コミット (2PC) | コーディネータが全員に合意させる | 遅い。コーディネータが単一障害点 |

**まず「設計で回避」を検討してください。**分散トランザクションは、避けられるなら避けるべきものです。

### 二次インデックスが難しくなる

`user_id` で分割したのに「メールアドレスで検索したい」場合。

| 方式 | 内容 | 特徴 |
|---|---|---|
| **ローカルインデックス** | 各パーティションが自分の分だけ索引を持つ | 書き込みは速い。**読み取りは全ノードに問い合わせる**(scatter-gather) |
| **グローバルインデックス** | インデックス自体を別のキーで分割 | 読み取りは速い。**書き込みが複数ノードにまたがる** |

どちらも「読み取りが速い/書き込みが速い」のどちらかしか取れません。

### 集計が難しくなる

`SELECT COUNT(*)`、`SUM()`、`ORDER BY ... LIMIT 10` — これらは全パーティションに問い合わせて結果を統合する必要があります。**1 台でも遅いノードがあれば、全体がその速度になります**(tail latency の増幅)。

## 💡 コラム: 「あとで分ければいい」が通用しなかった Instagram の話

サービスが成長し、DB が悲鳴を上げ始める。誰もが一度は通る道です。そのとき多くのチームが「とりあえず今は 1 台で、必要になったら分ければいい」と考えます。

**この判断が高くつく理由**を、実例で見てみます。

Instagram は初期、単一の PostgreSQL で運用していました。ユーザー数が爆発的に伸びる中、彼らはシャーディングに踏み切ります。このとき彼らが直面したのは「どう分割するか」ではなく、**「どうやって、止めずに分割するか」**でした。

すでに数億行のデータがあり、そのすべてに連番の ID が振られています。ID は時系列順で、しかもアプリ全体が「ID は一意である」ことに依存しています。分割すると、各シャードが独立に ID を発行するため、そのままでは衝突します。

彼らが取った解法は、ID そのものを再設計することでした。64 ビットの整数を、こう分解します。

```
[ 41 ビット: ミリ秒単位の時刻 ][ 13 ビット: シャード ID ][ 10 ビット: 連番 ]
```

**ID を見ればどのシャードにあるか分かる**ようにしたのです。しかも時系列でソート可能。彼らはこれを PostgreSQL のストアドプロシージャとして実装しました。似た発想は Twitter の Snowflake ID にもあり、現在の ULID の系譜にもつながっています。

ここで注目すべきは、この設計変更が**サービスが動いている最中に**行われたことです。既存データの移行、新旧 ID の共存、アプリケーション全体の書き換え。「あとで分ければいい」の「あとで」は、ユーザーが増え、コードが増え、止められなくなった後にやってきます。

とはいえ、教訓は「最初からシャーディングしろ」ではありません。**それも間違いです。**ユーザーが 100 人のサービスに 1000 パーティションを用意するのは、ただの過剰設計で、開発速度を殺します。

正しい教訓はこうです。

**分割しなくてよい。ただし、「分割するとしたらどのキーか」だけは最初に考えておく。**

主キーを連番にするか ULID にするか。`orders` テーブルに `user_id` を必ず持たせるか。この 2 つは、今日決めても明日決めても実装コストは同じです。しかし 3 年後に変更しようとすると、Instagram と同じ道を歩くことになります。

**設計とは、将来の選択肢を安く保つ技術**です。今すぐ分割する必要はありません。「分割したくなったとき、それが可能な形になっているか」だけを確認してください。

## まとめ

- パーティショニングは**データ量と書き込み**をスケールさせる。レプリケーションとは目的が違う
- **レンジ分割**は範囲検索に強いが偏りやすい。**ハッシュ分割**は均等だが範囲検索ができない
- `hash()` の組み込み関数は永続化に使えない。**決定的なハッシュ**を使う
- ホットスポットの原因は**キーの偏り・時系列キー・連番 ID**。ホットキーはさらに分割する
- **パーティションキーの選択は、最も変更が難しい決定**
- `hash(key) % N` はノード追加でほぼ全データが移動する。**固定数パーティション**か**コンシステントハッシュ**を使う
- 分割すると **JOIN・トランザクション・二次インデックス・集計**が難しくなる
- 分散トランザクションは避ける。**まず colocation で設計回避**を検討する
- 今すぐ分割しなくてよい。ただし「**分割するならどのキーか**」は最初に考えておく
