# Lesson 06: 合意 (Consensus) とリーダー選出

## 学習目標

- なぜ「全員が同じことに合意する」のが難しいかを説明できる
- クォーラム(過半数)がなぜ split-brain を防ぐかを説明できる
- Raft の 3 つの仕組み(任期・選出・ログ複製)を直感的に説明できる
- **分散ロックの危険性**を理解し、自前実装を避ける判断ができる

---

## 1. 合意問題とは

**合意 (consensus)** とは、複数のノードが**1 つの値について一致すること**です。

```
「次のリーダーは誰か」
「このトランザクションはコミットされたか」
「このロックは誰が持っているか」
「設定値は今どれか」
```

一見簡単そうですが、Lesson 01 で見た制約の下では驚くほど難しくなります。

- メッセージは失われる、遅延する、順序が入れ替わる
- ノードはいつでも停止しうる。しかも**停止と遅延を区別できない**
- 各ノードの時計はずれている

### 理論的な限界

**FLP 不可能性定理**(Fischer, Lynch, Paterson, 1985)という有名な結果があります。

> **非同期システムにおいて、1 つでもノードが故障しうるなら、
> 必ず有限時間で合意に達するアルゴリズムは存在しない。**

「絶対に決着がつくことを保証できない」ということです。

実用的なシステムは、この壁を**タイムアウトを導入する**ことで回避します。「一定時間応答がなければ死んだとみなす」というルールを置くと、理論上の非同期性が崩れ、実用的な合意が可能になります。

代わりに、**誤判定を受け入れる**ことになります。ここまで何度も出てきた「遅いだけのノードを死んだと判断する」問題です。

## 2. クォーラム — 過半数が split-brain を防ぐ

Lesson 01 のコラムで見た split-brain を、どう防ぐか。答えは驚くほど単純です。

> **過半数 (majority quorum) の同意がなければ、何も決定しない。**

```
5 ノードのクラスタが分断された

  ┌──────────────┐        ┌──────────┐
  │  A   B   C   │   ╳    │  D   E   │
  │  (3ノード)    │  分断   │ (2ノード) │
  └──────────────┘        └──────────┘
       過半数 ✓                過半数 ✗
   リーダーを選べる          何も決定できない
   書き込みを受け付ける       読み書きを拒否する
```

**過半数の集合は、必ず互いに重なります。**5 ノードなら 3 ノードが過半数で、どの 2 つの「3 ノードの集合」も必ず 1 台以上共有します。だから**2 つの過半数が同時に存在することはありえません**。リーダーが 2 人生まれることも、ありえません。

これが分散システムにおける最も重要な道具の 1 つです。

### 実務上の帰結

| ノード数 | 過半数 | 耐えられる障害数 |
|---|---|---|
| 3 | 2 | 1 |
| 4 | 3 | 1 ← **3 台と同じ** |
| 5 | 3 | 2 |
| 6 | 4 | 2 ← **5 台と同じ** |
| 7 | 4 | 3 |

**偶数台にする意味はありません。**4 台は 3 台と同じ耐障害性で、コストだけが増えます。しかも分断が 2:2 になると**どちらも過半数を取れず、クラスタ全体が停止**します。

> **原則**: 合意を必要とするクラスタ(etcd、ZooKeeper、Consul など)は**必ず奇数台**にしてください。3 台か 5 台が実用的な選択です。

## 3. Raft の直感

**Raft** は「理解しやすさ」を明示的な設計目標に掲げた合意アルゴリズムです(2014年、Ongaro と Ousterhout)。それ以前の Paxos が難解すぎたことへの回答として作られました。etcd、Consul、TiDB、CockroachDB などが採用しています。

Raft は問題を 3 つに分解します。

### ① 任期 (term) — 論理的な時計

Raft は物理時計を信用しません。代わりに**単調増加する整数**を使います。

```
term 1: A がリーダー
term 2: (A が落ちた) B がリーダー
term 3: (分断が起きた) C がリーダー
```

各ノードは自分が知る最大の term を覚えています。**古い term のメッセージは無条件に拒否**します。

これが split-brain の後始末を可能にします。旧リーダー A が復帰して「私はリーダーだ(term 1)」と主張しても、他のノードは「今は term 3 だ」と拒否します。A は自分が古いことを知り、フォロワーに戻ります。**時計を合わせる必要がありません。**

### ② リーダー選出 (leader election)

```
すべてのノードは Follower として始まる
        ↓
リーダーからのハートビートが一定時間来ない
        ↓
Candidate になり、term を +1 して自分に投票し、全員に投票を求める
        ↓
過半数の票を得たら Leader になる
        ↓
定期的にハートビートを送り、自分が生きていることを知らせる
```

**投票のルール**が重要です。

- 1 つの term につき、各ノードは **1 票しか投じない**
- **自分より古いログしか持たない候補者には投票しない**

1 番目のルールにより、1 つの term に 2 人のリーダーは生まれません。2 番目により、**コミット済みのデータを持つノードだけがリーダーになれます**。

**選挙タイムアウトはランダム化**されます(例: 150〜300ms からランダムに選ぶ)。全員が同時に立候補すると票が割れて決まらないため、ばらけさせるのです。**Phase 8 の jitter と同じ発想**がここにも現れます。

### ③ ログ複製 (log replication)

```
Client → Leader: "x = 5 にせよ"
   Leader: 自分のログに追記(まだコミットしない)
   Leader → 全 Follower: このエントリを追記せよ
   Follower → Leader: 追記した ✓
   Leader: 【過半数が追記した】ので、コミット確定
   Leader → Client: OK
   Leader → Follower: あのエントリはコミット済みだ
```

**過半数が受け取ったらコミット**します。全員を待ちません。だから 1〜2 台が遅くても停止しません。

そして「コミット済み」の情報は過半数に存在するので、**次のリーダーは必ずそれを持っています**(投票ルール ②)。データが失われません。

## 4. 分散ロックの罠 — ここが実務で最も危険

「複数のサーバーで 1 つの処理を排他したい」— よくある要求です。そして**最も多くの事故が起きる場所**でもあります。

### 素朴な実装

```python
# Redis を使った分散ロック(危険な例)
if redis.set("lock:job", token, nx=True, ex=10):
    try:
        do_critical_work()
    finally:
        redis.delete("lock:job")
```

一見正しく見えます。しかし壊れます。

### なぜ壊れるか — GC で止まったクライアント

```
時刻  Client A                          Client B          ロック
 1    ロック取得 ✓ (TTL 10秒)                              A
 2    処理を開始
 3    【GC で 15 秒停止】
 4                                                        (TTL 切れ)
 5                                      ロック取得 ✓        B
 6                                      処理を開始
 7    GC から復帰(自分はまだ
      ロックを持っていると思っている)
 8    処理を継続  ← 【A と B が同時に critical section にいる】
```

**A は自分がロックを失ったことを知りません。**そして知る方法もありません。GC の停止、ネットワークの遅延、OS のスケジューリング — いずれも起こりえます。

TTL を長くしても解決しません。長くすれば、本当に落ちたときの復旧が遅れるだけです。**Lesson 02 のフェイルオーバーのタイムアウトと同じジレンマ**です。

### Redlock 論争

Redis の作者は、複数の Redis インスタンスを使う **Redlock** というアルゴリズムを提案しました。これに対し、分散システム研究者の Martin Kleppmann が「安全ではない」と批判し、有名な論争になりました。

争点は上記の停止問題と、**時計の進み方への依存**です。Redlock は各ノードの時計がおおむね同じ速度で進むことを仮定しますが、仮想マシンのライブマイグレーションや NTP の調整で時計は飛びます。

### 実務での結論

**分散ロックには 2 種類あります。区別してください。**

| 目的 | 要求 | 実装 |
|---|---|---|
| **効率化**(重複作業を減らしたい) | 稀に重複しても損しない | Redis で十分。TTL 付きの素朴な実装で OK |
| **正しさ**(絶対に重複してはいけない) | 重複すると業務が壊れる | **ロックで解決してはいけない** |

**正しさが必要な場面でロックを使わないでください。**代わりに使うのは、この教材で繰り返し出てきた道具です。

```
✗ 分散ロックで排他する
○ DB の一意制約で二重実行を弾く          (Phase 8 Lesson 04)
○ 冪等キーで重複しても 1 回にする         (Phase 8 Lesson 04)
○ 条件付き UPDATE で直列化する            (Phase 8 Lesson 04)
○ fencing token を使う(下記)
○ 合意アルゴリズムの実装済みシステムに任せる (etcd, ZooKeeper)
```

### fencing token

どうしてもロックが必要なら、**単調増加するトークン**を発行し、リソース側で検証します。

```
Client A: ロック取得 → token 33 を受け取る
          【GC で停止】
Client B: ロック取得 → token 34 を受け取る
Client B: ストレージへ書き込み (token 34) → 受理される
Client A: 復帰。ストレージへ書き込み (token 33)
          → ストレージが「もう 34 を見た」ので拒否 ✓
```

**リソース側が古いトークンを拒否する**ことで、停止していたクライアントの書き込みを防げます。Raft の term とまったく同じ考え方です。

## 5. 自分で実装しない

この Lesson の実務的な結論です。

> **合意アルゴリズムを自分で実装しないでください。**

Raft の論文は理解できます。しかし、正しく実装するのは別の話です。メンバーシップ変更、ログの圧縮、スナップショット、ネットワーク分断からの復帰 — 実運用に必要な部分は、論文の数倍の複雑さがあります。実際、著名な分散システムの多くが、リリース後に合意層のバグを修正しています。

代わりに、実績のある実装を使います。

| 用途 | 使うもの |
|---|---|
| リーダー選出、設定共有、サービス発見 | **etcd**, **ZooKeeper**, **Consul** |
| 分散 DB | CockroachDB, TiDB, Spanner |
| 単純な排他(効率化目的) | Redis(正しさに依存しない範囲で) |
| **正しさが必要な排他** | **DB の一意制約・冪等キー**(ロックを使わない) |

**では、なぜ仕組みを学ぶのか。**選ぶため、そして壊れ方を理解するためです。「etcd は奇数台にする」「過半数を失うと書けなくなる」「ネットワーク分断時にどちら側が生き残るか」— これらは仕組みを知らなければ判断できません。

## 💡 コラム: 「理解しやすさ」を設計目標にした論文

1989年、Leslie Lamport は分散合意のアルゴリズム **Paxos** を発表しました。古代ギリシャのパクソス島の議会という寓話の形で書かれたその論文を、当時ほとんど誰も理解できませんでした。Lamport 自身、後に「私はユーモアのつもりだったのだが」と振り返っています。

論文は一度却下され、正式に出版されたのは**8 年後の 1998 年**でした。そして出版後も、状況は良くなりませんでした。Paxos は理論的には正しいものの、**実装しようとすると論文に書かれていないことばかり**だったのです。Google の技術者たちは、Chubby という分散ロックサービスを Paxos で実装した経験を、こう記しています。

> 「Paxos のアルゴリズムの記述と、実際に動くシステムの間には、大きな隔たりがある。…最終的なシステムは、特定のアルゴリズムではなく、未証明のプロトコルに基づくものになる。」

2014年、スタンフォード大学の Diego Ongaro と John Ousterhout は、この状況そのものを問題として定式化しました。彼らの論文タイトルは、こうです。

> **"In Search of an Understandable Consensus Algorithm"**
> (理解可能な合意アルゴリズムを求めて)

彼らが設定した設計目標は、性能でも理論的な優雅さでもありませんでした。**「理解しやすいこと」**です。そのために彼らは、学生を集めて Paxos と Raft を教え、どちらをよく理解できたかを**実際に測定**しました。アルゴリズムの評価に、人間の理解度テストを使ったのです。

そして Raft は、問題を「リーダー選出」「ログ複製」「安全性」の 3 つに分解し、それぞれを独立に理解できるようにしました。状態を減らし、非決定性を減らし、ランダム化タイムアウトのような単純な道具で複雑さを回避しました。

結果は歴史が示しています。etcd、Consul、TiKV、CockroachDB — 現代の分散システムの多くが Raft を採用しました。Kubernetes のすべての状態は、Raft で合意された etcd の中にあります。**あなたがコンテナを 1 つデプロイするたびに、Raft が動いています。**

ここに、エンジニアリングの深い教訓があります。

**正しいだけの設計は、広まりません。**Paxos は 1989年から正しかった。しかし人間が理解できなかったために、25年間、実装のたびに事故が起きました。Raft は理論的に新しいことをほとんどしていません。**同じ問題を、人間が扱える形に整理し直しただけ**です。それが世界を変えました。

あなたが書くコードも、設計書も、レビューコメントも同じです。**正しさは最低条件であって、到達点ではありません。**他人が理解できて初めて、それは動くシステムになります。

## まとめ

- **合意**とは複数ノードが 1 つの値に一致すること。停止と遅延を区別できないため難しい
- **FLP 不可能性**により、非同期システムで必ず決着する保証は作れない。実用系はタイムアウトで回避する
- **過半数クォーラム**は必ず互いに重なるため、2 人のリーダーは生まれない
- **クラスタは必ず奇数台**。4 台は 3 台と同じ耐障害性で、2:2 分断では全停止する
- Raft は **term(論理時計)・選挙・ログ複製**の 3 つに分解。古い term を拒否することで時計合わせが不要
- 選挙タイムアウトは**ランダム化**する(jitter と同じ発想)
- **分散ロックには「効率化目的」と「正しさ目的」がある。後者をロックで解決してはいけない**
- 停止したクライアントは自分がロックを失ったことを知れない。**fencing token** が必要
- **合意アルゴリズムを自分で実装しない。**etcd / ZooKeeper を使う
- 仕組みを学ぶのは、選ぶためと、壊れ方を理解するため
