## 課題: チケット販売システムの設計

次の要件を満たすシステムを設計してください。

```
サービス: ライブチケットの販売
規模    : 通常時 100 req/s、人気公演の発売開始時に瞬間 50,000 req/s
利用者  : 日本 70%、北米 20%、欧州 10%
データ  : 公演 10万件、座席 5000万件、注文 年間 2000万件

絶対条件:
  - 同じ座席を 2 人に売ってはいけない
  - 決済が二重に走ってはいけない
  - 発売開始の瞬間にサービスが停止してはいけない

許容できること:
  - 「残席数」の表示が数秒古いこと
  - 購入ボタンを押した後に売り切れを知らされること
```

### 提出物 1: 設計文書 `design.md`

次の 6 点について、**選択・理由・捨てたもの・見直す条件**を書いてください。

| # | 決めること | 最低限触れること |
|---|---|---|
| 1 | レプリケーション構成 | 方式、同期/非同期、地理配置、フェイルオーバー手順 |
| 2 | パーティション設計 | 分割キー、ホットスポット対策、リバランス方式 |
| 3 | 操作ごとの整合性 | **機能を最低 6 つ挙げ**、それぞれに必要な強さと理由 |
| 4 | キャッシュ戦略 | 対象、TTL、無効化、stampede 対策、キャッシュ全損時の挙動 |
| 5 | 座席確保の仕組み | **分散ロックを使わずに**二重販売を防ぐ方法 |
| 6 | 決済の冪等性 | key の発行主体、保存方法、同 key 別内容の扱い |

### 提出物 2: 障害シナリオ `failure-modes.md`

次の 5 つについて、**何が起きるか・利用者に何が見えるか・どう復旧するか**を書いてください。

1. 東京リージョンの leader が停止した
2. 東京と北米の間のネットワークが 60 秒間分断された
3. キャッシュクラスタが全滅した
4. 決済 API が 30% の確率でタイムアウトするようになった
5. 1 つの公演に負荷が集中し、そのパーティションだけが飽和した

### 提出物 3: 計算 `capacity.md`

- 発売開始時の 50,000 req/s のうち、**実際に DB へ到達する req/s** を見積もり、根拠を示す
- キャッシュヒット率が 0% になったとき、DB は何倍の負荷を受けるか
- 欧州の利用者への応答時間の**理論下限**を計算する

### 提出物 4: 口頭説明(5〜10分の録画または対面)

- 最も難しかった判断と、なぜそれを選んだか
- あなたの設計が**壊れる条件**
- 予算が半分になったら、どこを削るか

## 採点

| 観点 | 点 |
|---|---:|
| 絶対条件を満たす設計になっているか | 30 |
| 操作ごとに整合性を選び分けているか(全部を強くしていないか) | 20 |
| 障害シナリオへの回答の具体性 | 20 |
| トレードオフと「捨てたもの」の明示 | 15 |
| 計算の妥当性と根拠 | 10 |
| 説明の明快さ | 5 |

**80点以上**、かつ次の必須項目をすべて満たせば合格です。

- 二重販売と二重決済が、**設計として**防がれている(「気をつける」ではない)
- **分散ロックに依存していない**(依存している場合、その危険性を説明できていれば可)
- 整合性を機能ごとに選び分けている
- キャッシュ全損時の挙動が書かれている

## 不合格になりやすい回答

| 回答 | なぜ不合格か |
|---|---|
| 「すべて強整合性にします」 | 50,000 req/s を捌けない。トレードオフを判断していない |
| 「Redis で分散ロックを取ります」 | Lesson 06 の停止問題。正しさをロックに依存している |
| 「マイクロサービスに分割します」 | 問われているのは分割ではない。要件から導かれていない |
| 「AWS の Aurora を使うので大丈夫です」 | 製品名は設計ではない。何が保証され何が保証されないか |
| 「CAP でいうと AP です」 | それだけでは何も決まっていない。操作ごとの判断が必要 |
