# Lesson 03: キャップストーンプロジェクト概要

## このレッスンで学ぶこと

- キャップストーンプロジェクトの意義と進め方
- 3 つの推奨テーマとその選び方
- 8 週間の開発スケジュール管理
- 詰まったときの対処法

---

## 1. キャップストーンプロジェクトとは

キャップストーン(Capstone)とは建築用語で「アーチの頂点に置かれる石」のことです。転じて、学習の総仕上げを意味します。

このプロジェクトは単なる「課題」ではありません。あなたが世界のどの採用担当者にも「私はこれを作りました」と示せる、実際に動くプロダクトです。

### キャップストーンで達成すること

1. 要件定義 → 設計 → 実装 → テスト → デプロイ の全工程を一人で経験する
2. 本番環境で動いているアプリを持つ
3. コードベースとドキュメントを公開し、ポートフォリオの中心に据える

---

## 2. 推奨テーマの選び方

`capstone/` ディレクトリに 3 つのテーマの詳細仕様があります。

| テーマ | 難易度 | 特徴 |
|--------|--------|------|
| A: タスク管理アプリ (Task Manager) | 標準 | CRUD の典型例。就職時の実績としてわかりやすい |
| B: リンクキュレーターアプリ (Link Curator) | 標準〜やや難 | 外部 URL の取得処理、全文検索など実用的な機能 |
| C: 習慣トラッカー (Habit Tracker) | 標準〜やや難 | データ可視化・カレンダー UI など UI/UX に深みが出る |

**選び方の指針:**

- 「自分が実際に使いたいか」を最優先にしてください。モチベーションが継続力を左右します
- どれも技術スタックは同じです。テーマによって有利・不利はありません
- オリジナルテーマも可能です。その場合は Lesson 01 と 02 で要件定義と Design Doc を必ず作成してください

## 3. 技術スタックの確認

キャップストーンで使用する技術スタックは以下のとおりです。Phase 10 までに学んだ技術をすべて統合します。

```
フロントエンド:   React (TypeScript 推奨)
```

## 4. 開発の進め方: イテレーティブ開発

「全部設計してから全部実装する」方法は失敗しやすいです。代わりに、機能を小さく区切って繰り返し(イテレーティブ / Iterative)開発します。

```
[ 設計 ] → [ 実装 ] → [ 動作確認 ] → [ 改善 ] → [ 次の機能へ ]
    ↑                                                    |
    +----------------------------------------------------+
```

各機能ごとにこのサイクルを回します。「ユーザー登録が動いた」「ログインが動いた」「タスク作成が動いた」と小さく積み上げます。

## 5. 詰まったときの対処フロー

開発中に詰まることは必ず起きます。以下のフローで対処します。

```
1. エラーメッセージを正確に読む (5 分)
   → スタックトレース全体を読む。最初の行だけ読んでいないか確認

2. 公式ドキュメントを確認する (15 分)
   → FastAPI docs, React docs, PostgreSQL docs

3. エラーメッセージをそのまま検索する (15 分)
   → Google, Stack Overflow

4. 最小再現コードを作る (30 分)
   → 問題が起きている箇所だけを切り出した小さなコードを書く
   → この作業で原因が判明することが多い

5. 他者に質問する
   → 最小再現コード + 試したこと + 期待した動作 + 実際の動作 をセットで伝える
```

**「詰まる」こと自体は問題ではありません。「詰まったまま黙っている」ことが問題です。**

## 6. コードレビューの習慣

キャップストーンでは、定期的に自分のコードをセルフレビューします。以下のチェックリストを毎週末に使います。

```
セルフレビューチェックリスト (毎週末)

[ ] 変数名・関数名は読んで意味が分かるか
[ ] 1 つの関数が 1 つのことをしているか (単一責任の原則)
[ ] コメントが「何をしているか」ではなく「なぜしているか」を説明しているか
[ ] ハードコードされた値(マジックナンバー)が設定ファイルに移っているか
[ ] テストを書いていない箇所はないか
[ ] 環境変数に機密情報が入っていて、.gitignore されているか
[ ] エラーハンドリングが適切か(500 エラーが起きたとき何が起きるか)
```

## 🌟 コラム: 史上最も売れたゲームは、会社員の個人プロジェクトだった

2009年、スウェーデンの会社員プログラマー、マルクス・ペルソン(通称 Notch)は、勤めの傍らで小さなゲームを作り始めました。四角いブロックを置いたり壊したりするだけの、グラフィックも粗削りなゲームです。

彼のやり方が印象的です。完成を待たず、**開発初期の粗いバージョンを約10ユーロで販売し始めた**のです。買ったプレイヤーたちはフォーラムで遊び方を発明し、要望を送り、ゲームはコミュニティとの対話の中で成長していきました。 — そのゲーム『**Minecraft**』は、やがて**史上最も売れたゲーム**(3億本以上)になります。

映画的な天才の一撃ではありません。動く最小版を早く出す、遊んでくれる人の声を聞く、少しずつ育てる — あなたがこのレッスンで学んだキャップストーンの進め方、そのままです。週末の個人プロジェクトと世界的プロダクトの間に、断絶はありません。あるのは反復の回数だけです。

## 💡 コラム: Dropbox は「存在しない製品のデモ動画」から始まった

2007年、Dropbox の創業者ドリュー・ヒューストンには問題がありました。ファイル同期という製品の価値は、完成品を触らせないと伝わらない。しかし完成には長い開発期間が必要 — そこで彼が作ったのは製品ではなく、**製品が動いているように見せる3分のデモ動画**でした。

技術系コミュニティに投稿された動画は一晩で拡散し、ベータ版の**待機リストは一夜で7万5千人**に膨れ上がりました。作る前に「これは人が欲しがるものだ」という検証が済んだのです。これは MVP(Minimum Viable Product = 検証可能な最小限の製品)の伝説的な実例として、今も語り継がれています。

キャップストーンにも同じ原則が効きます。全機能を並行で作り始めるのではなく、**まず「一連の流れが最後まで動く最小版」を最短で作る**。動くものがあると、モチベーションも、フィードバックも、計画の精度も、すべてが好転します。合言葉は Facebook の初期の標語から — 「**Done is better than perfect(完璧よりも完成)**」。完璧な未完成品を、誰も評価できません。

---

## まとめ

- キャップストーンは「動くプロダクトを世界に届ける」経験
- テーマは「自分が使いたいもの」を選ぶ。モチベーションが継続力を決める
- 詰まることは正常。フローに従って対処し、解決したことを記録する
- 毎週セルフレビューして品質を保つ

次のレッスンでは、完成したプロジェクトを世界に見せるポートフォリオの作り方を学びます。
