# Lesson 01: プロジェクトの企画と要件定義

## このレッスンで学ぶこと

- 解くべき課題をどう発見するか
- 要件定義(Requirements Definition)の構造と書き方
- スコープ(Scope)の切り方と MVP 思考
- 要件定義がなぜ実装より重要なのか

---

## 1. 課題発見: 「何を作るか」の前に「誰が何に困っているか」

多くの初学者が最初にぶつかる壁は「何を作ればいいかわからない」です。しかしこれは問いの立て方が逆です。

**正しい順序:**

```
課題を発見する → 解決策を考える → 作るものを決める
```

**間違った順序:**

```
作りたいものを決める → 課題に当てはめる → 無理やり正当化する
```

### 課題発見の 3 つのアプローチ

**アプローチ 1: 自分の不満リスト**

日常生活で「これ不便だな」と感じた瞬間をすべてメモします。1 週間続けると 20〜30 件たまります。その中から技術で解決できそうなものを選びます。

例:
- 読んだ記事を後から探せない
- 習慣化したいことがいつも三日坊主になる
- チームのタスクが Slack と Google スプレッドシートに散らばっている

**アプローチ 2: 既存ツールの不満点**

すでに使っているツールに何が足りないかを考えます。「Notion は高機能すぎて使いこなせない」「Trello は個人利用には向いていない」など。

**アプローチ 3: インタビュー**

友人・家族・同僚に「仕事や日常で一番時間を無駄にしていることは何か」を 5 人に聞きます。共通するテーマが本物の課題です。

---

## 2. 課題の深掘り: 5W1H フレームワーク

課題を見つけたら、以下の観点で整理します。

| 項目 | 問い | 例 |
|------|------|----|
| Who (誰が) | 誰がこの課題を持っているか | 個人で学習している社会人 |
| What (何を) | 何に困っているか | 参考にした URL をあとで見つけられない |
| When (いつ) | いつ困るか | 学習の振り返り時、同じ情報を再度調べるとき |
| Where (どこで) | どこで困るか | ブラウザ、スマートフォン |
| Why (なぜ) | なぜ現状の解決策では不十分か | ブックマークが散らかる、検索できない |
| How (どう) | 理想はどんな状態か | タグとメモ付きで URL を整理し、全文検索できる |

## 3. 要件定義の構造

要件定義(Requirements Definition)は「何を作るか」を文書化したものです。実装前に必ず書きます。

### 要件の 2 分類

**機能要件(Functional Requirements)**

システムが「何をするか」を記述します。

例:
- ユーザーはメールアドレスとパスワードで登録できる
- URL を入力するとページタイトルが自動取得される
- タグを複数付けて URL を保存できる
- 保存した URL はタイトル・タグ・メモで全文検索できる

**非機能要件(Non-functional Requirements)**

システムが「どのように動くか」を記述します。

例:
- 検索結果は 1 秒以内に返る
- モバイルブラウザで使いやすいレスポンシブデザイン
- HTTPS 通信のみ許可
- 月額コストが 5 ドル以下で運用できる

### ユーザーストーリー(User Story)

機能要件を「ユーザー視点」で書く手法です。フォーマットは以下です。

```
As a [ユーザーの役割],
I want to [したいこと],
So that [その理由・得られる価値].
```

例:
```
As a ソフトウェアエンジニア志望の学習者,
I want to 読んだ技術記事の URL にタグとメモを付けて保存したい,
So that あとで同じ内容を調べ直す手間を省きたい.
```

ユーザーストーリーは各機能について 1 つ書くことが目安です。

## 4. MVP 思考: 最小限で価値を届ける

MVP(Minimum Viable Product / 実用最小限のプロダクト)とは、「ユーザーに価値を届けられる、最もシンプルなバージョン」です。

### なぜ MVP が重要か

- 作りすぎると時間を無駄にする
- ユーザーの反応を見る前に作りすぎると方向が間違っていても気づけない
- 小さく完成させることで自信とフィードバックが得られる

### MVP の決め方: MoSCoW 法

機能を 4 段階に分類します。

| 分類 | 意味 | 例 |
|------|------|----|
| Must have | これがないとプロダクトが成立しない | URL の保存・表示 |
| Should have | あると価値が高いが、なくても使える | タグ付け |
| Could have | あれば嬉しいが優先度は低い | ブラウザ拡張機能 |
| Won't have (今回は) | 今回のスコープには含めない | 他ユーザーとの共有機能 |

MVP に含めるのは「Must have」だけです。「Should have」は MVP の後に追加します。

### スコープクリープ(Scope Creep)に注意

スコープクリープとは、開発中に機能が少しずつ増えていく現象です。

「ここまで来たついでに〇〇も追加しよう」という思考が積み重なり、納期が大幅に遅れます。

対策:
1. 機能を追加したくなったら、まず要件定義ドキュメントに書く
2. 「これは Must have か?」を自問する
3. MVP が完成するまでは Could have / Won't have には着手しない

---

## 5. 要件定義書のテンプレート

以下のテンプレートを使って要件定義書を書きます。キャップストーンプロジェクトでもこの形式を使用します。

```markdown
# プロジェクト名: [アプリ名]

## 1. 背景と課題

[誰がどんな課題を持っているかを 3〜5 文で説明する]

## 2. 目的

[このプロダクトが解決すること、1〜2 文]

## 3. ターゲットユーザー

[具体的なユーザー像を 1〜2 文。「誰でも」は NG]

## 4. 機能要件

### MVP に含める機能(Must have)

- [ ] 機能 1: [説明]
  - 受け入れ条件: [何ができれば完成と見なすか]
- [ ] 機能 2: [説明]
  - 受け入れ条件: [何ができれば完成と見なすか]

### 将来の機能(Should have / Could have)

- 機能 A: [説明]
- 機能 B: [説明]

## 5. 非機能要件

- パフォーマンス: [応答時間等]
- セキュリティ: [認証方式等]
- 運用コスト: [目安の月額]
- 対応ブラウザ・デバイス: [Chrome 最新版 / モバイル対応等]

## 6. スコープ外(Won't have)

[今回は作らないと明示するもの。理由も書く]

## 7. 技術スタック

- フロントエンド: React
- バックエンド: FastAPI (Python)
- データベース: PostgreSQL
- インフラ: Docker Compose + [デプロイ先]
- CI/CD: GitHub Actions

## 8. 用語定義

[ドメイン固有の用語があれば定義する]
```

## 6. 実践演習

### 演習 1: 課題発見

1 週間、日常の「不便だな」をメモしてください。スマートフォンのメモアプリで構いません。
週末に見返して、技術で解決できそうなものを 3 つ選んでください。

### 演習 2: 要件定義書を書く

選んだ課題のうち 1 つについて、上記テンプレートを使って要件定義書を書いてください。

チェックポイント:
- Must have の機能が 3〜5 個に絞られているか
- 受け入れ条件が「動作確認できる具体的な内容」になっているか
- 非機能要件が書かれているか
- Won't have が明示されているか

### 演習 3: 仲間にレビューを依頼する

書いた要件定義書を他者(同学習者、友人など)に見せて、以下を確認してもらいます。

- 課題の背景が理解できたか
- MVP の機能だけで「使ってみたい」と思えるか
- 追加したくなる機能はあるか(= スコープクリープの候補)

## 💡 コラム: ホフスタッターの法則と、14倍かかったオペラハウス

認知科学者ダグラス・ホフスタッターが定式化した、見積もりに関する皮肉な法則があります。

「**作業は、予想よりも常に長くかかる。ホフスタッターの法則を考慮に入れて見積もっても。**」

法則自体が再帰している(Phase 4 参照)ところがミソです。人類はこの法則から逃れられていません。シドニーのオペラハウスは当初「4年・700万豪ドル」の計画が、完成まで **14年・1億豪ドル超** — 約14倍かかりました。心理学ではこれを「計画錯誤」と呼び、**自分の作業については楽観的に、他人の作業については現実的に**見積もる傾向が実験で確認されています。

対策は「もっと気合いを入れて見積もる」ことではありません。構造で守ります: (1) **大きな塊を小さく割る**(小さいタスクほど見積もり誤差が小さい)、(2) **最初に「動く最小版」を作る**(全体の難易度が早期に判明する)、(3) **過去の実績を使う**(「前回、似た機能に3日かかった」は、どんな楽観よりも正確です)。あなたのキャップストーンの計画にも、そのまま使えます。

---

## まとめ

- 「何を作るか」より「誰が何に困っているか」から始める
- 要件定義書は実装前に書く。書かずに始めるのは地図なしで登山するようなもの
- MVP は「最小限で価値を届けられる版」。完璧を目指さない
- スコープクリープは意識的に防ぐ。追加したくなったら要件定義書に書いてから判断する
