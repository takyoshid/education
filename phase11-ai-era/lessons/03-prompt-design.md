# Lesson 03: 効果的なプロンプトと文脈設計

## 学習目標

- 効果的なプロンプト (AI への指示文) の構成要素を理解する
- 良いプロンプトと悪いプロンプトを具体例で比較できる
- CLAUDE.md などのプロジェクト文脈ファイルを作成・活用できる
- 反復的なプロンプト改善のサイクルを実践できる

---

## 1. プロンプトとは何か

プロンプト (Prompt) とは、AI への入力テキスト全体のことです。「質問文を入力する」という単純な行為に見えますが、プロンプトの質は AI の出力の質に直接影響します。

良いプロンプトを書く技術は「プロンプトエンジニアリング (Prompt Engineering)」とも呼ばれます。ただし、これは特別な魔法ではありません。「相手 (AI) が答えやすいように、十分な情報と明確な指示を与える」という、コミュニケーションの基本です。

---

## 2. 悪いプロンプトの特徴

まず失敗のパターンを学びます。

### 悪いプロンプト例 1: 曖昧すぎる

```
悪い例:
「コードを直して」

何が問題か:
- どのコードなのかわからない
- 何が「直っていない」のかわからない
- 何を達成したいのかわからない
```

### 悪いプロンプト例 2: 文脈が欠けている

```
悪い例:
「このエラーを直して: TypeError: 'NoneType' object is not subscriptable」

何が問題か:
- どのコードで発生しているかわからない
- どんな入力のときに発生するかわからない
- プロジェクト全体の構成がわからない
```

### 悪いプロンプト例 3: 制約が示されていない

```
悪い例:
「ユーザー認証の機能を作って」

何が問題か:
- どの言語・フレームワークを使うかわからない
- セッション? JWT? OAuth? 方式の指定がない
- データベースは何を使うかわからない
- セキュリティ要件が示されていない
```

---

## 3. 良いプロンプトの 5 つの構成要素

効果的なプロンプトには以下の要素が含まれます。すべてが必須ではありませんが、タスクが複雑になるほど多くの要素が必要になります。

### 要素 1: 役割・文脈 (Role / Context)

AI にどの視点から答えてほしいかを示します。

```
例:
「あなたは Python の Flask を使った Web API 開発の経験豊富なエンジニアです。」
```

### 要素 2: タスクの明示 (Task)

何をしてほしいかを動詞で明確に示します。

```
良い:「以下のコードをレビューして、潜在的なバグとパフォーマンスの問題を指摘してください」
悪い:「コードをみてください」
```

### 要素 3: 必要な情報・文脈 (Information)

AI が正確に答えるために必要な情報を提供します。

```
含めると良いもの:
- 問題のコード (全体または関連部分)
- エラーメッセージ (そのまま全文を貼る)
- 使用している言語・フレームワーク・バージョン
- 何をしようとしているのか (目的)
- すでに試したこと
```

### 要素 4: 制約・条件 (Constraints)

出力の形式や守ってほしい条件を示します。

```
例:
「以下の制約を守ってください:
- 外部ライブラリは追加しない (標準ライブラリのみ使用)
- Python 3.11 以上で動作すること
- 変更した箇所にはコメントを入れること
- 回答は変更後の関数コードのみ。説明は不要」
```

### 要素 5: 出力形式 (Output Format)

何をどのような形式で出力してほしいかを示します。

```
例:
「以下の形式で回答してください:
1. 問題の概要 (1-2 行)
2. 修正後のコード
3. 修正内容の箇条書き (3 点以内)」
```

## 4. 良いプロンプト vs 悪いプロンプトの対比

### ケース 1: バグ修正の依頼

```
悪いプロンプト:
「エラーが出ます。直してください。」


良いプロンプト:
「Python 3.11 + FastAPI 0.104 の環境で以下のコードを実行すると
エラーが発生します。原因と修正方法を教えてください。

[エラーメッセージ]
ValidationError: 1 validation error for UserCreate
email
  value is not a valid email address (type=value_error.email)

[コード]
from pydantic import BaseModel

class UserCreate(BaseModel):
    name: str
    email: str

# POST /users に送ったリクエストボディ
{
    "name": "田中太郎",
    "email": "tanaka_at_example.com"
}

試したこと: email フィールドの型を str から EmailStr に変えたが、
同じエラーが出ました。

制約: pydantic の標準機能のみ使用。外部ライブラリの追加なし。」
```

### ケース 2: 機能実装の依頼

```
悪いプロンプト:
「ファイルアップロード機能を作ってください。」


良いプロンプト:
「以下の仕様で、Flask アプリケーションにファイルアップロード機能を追加してください。

[仕様]
- エンドポイント: POST /upload
- 受け付けるファイル形式: PNG, JPEG, PDF のみ
- 最大ファイルサイズ: 10MB
- アップロード先: ローカルの uploads/ ディレクトリ
- レスポンス: JSON で { "filename": "保存したファイル名", "size": バイト数 }

[既存のコードの構成]
app.py - Flask アプリケーション本体
config.py - 設定ファイル (UPLOAD_FOLDER などの定数が定義されている)

[制約]
- セキュリティ上の考慮点があれば、コメントで説明を入れること
- werkzeug の secure_filename を使うこと
- エラーハンドリングを含めること

[出力形式]
追加・変更するコードのみ出力してください。」
```

## 5. 反復的改善 (Iterative Refinement)

最初のプロンプトで完璧な出力が得られることは稀です。プロンプトは対話的に改善していきます。

### 改善のサイクル

```
1. 最初のプロンプトを送る
2. 出力を評価する
   - 意図と合っているか?
   - 足りない要素はあるか?
   - 間違っている部分はあるか?
3. フォローアップで補足・修正を依頼する
4. 満足いく出力になるまで繰り返す
```

### フォローアップの例

```
最初の依頼:
「上記の関数をリファクタリングしてください」

出力: 関数が分割されたが、エラーハンドリングが消えた

フォローアップ:
「ありがとうございます。ただ、元の関数にあった ValueError のハンドリングが
なくなっています。エラーハンドリングを保持しながら、同じリファクタリングを
やり直していただけますか?」
```

## 6. CLAUDE.md によるプロジェクト文脈の設計

### CLAUDE.md とは

Claude Code を使う際、プロジェクトのルートに `CLAUDE.md` というファイルを置くと、Claude Code がそのプロジェクトで作業を始める際に自動的に読み込みます。「このプロジェクトでの作業ルール」を AI に事前に伝えるファイルです。

同様の仕組みは他のツールにも存在します (GitHub Copilot Instructions など)。

### CLAUDE.md に書くべき内容

```markdown
# Project Name

## プロジェクト概要
このリポジトリは〇〇を行う Python 製 Web API です。
Flask 3.0 + SQLAlchemy 2.0 + PostgreSQL 15 を使用しています。

## 技術スタック
- Python 3.12
- Flask 3.0
- SQLAlchemy 2.0 (ORM)
- PostgreSQL 15
- pytest (テスト)
- black + ruff (フォーマット・リント)

## ディレクトリ構成
src/
  models/     - SQLAlchemy モデル
  routes/     - Flask Blueprint ルーター
  services/   - ビジネスロジック
  schemas/    - Pydantic スキーマ
tests/        - pytest テスト

## コーディング規約
- 型アノテーションを必ず付ける
- 関数には docstring を書く (Google スタイル)
- テストは pytest で書き、カバレッジ 80% 以上を維持する
- 変数名・関数名は snake_case、クラス名は PascalCase

## 禁止事項
- print デバッグは使わない (logging モジュールを使う)
- raw SQL は使わない (SQLAlchemy ORM を使う)
- secrets や API キーをコードに直書きしない

## よく使うコマンド
- テスト実行: pytest tests/ -v
- フォーマット: black src/ && ruff check src/
- 開発サーバー起動: flask --app src/app run --debug
```

### CLAUDE.md の効果

CLAUDE.md がない場合と比べて、以下の点が改善されます。

- AI がプロジェクト固有の慣習に合ったコードを生成する
- 毎回「このプロジェクトは Flask を使っています」と説明しなくてよくなる
- コーディング規約の違反を AI 自身が避けるようになる

ただし CLAUDE.md は完全ではありません。AI は CLAUDE.md に書かれたルールを無視することがあります。最終的な確認は常に人間が行います。

## 7. プロンプトのアンチパターン

### アンチパターン 1: 全部任せる

```
悪い例:
「ECサイトのバックエンドをフルスクラッチで作ってください」

問題:
要件定義をしていない。AI は「もっともらしい ECサイト」を作るが、
あなたが本当に必要なものとは限らない。
```

### アンチパターン 2: 答えだけ求める

```
悪い例:
「このアルゴリズムの実装を書いてください」

問題:
なぜそのアルゴリズムが適切なのかを理解しないまま使うことになる。
「このアルゴリズムを実装してください。実装前にアルゴリズムの
動作原理を説明してください」と修正する。
```

### アンチパターン 3: 検証なしに貼り付ける

```
悪い例の行動:
AI が生成したコードをコピー -> そのままリポジトリにプッシュ

問題:
コードの内容を理解していない。テストしていない。
セキュリティリスクに気づけない。
```

## 💡 コラム: 「プロンプトエンジニアリング」の正体は、新人への仕事の頼み方

「いい感じにやっておいて」— この頼み方で新人が期待通りの成果を出したら奇跡です。優秀な先輩は、こう頼みます: 背景(なぜこの作業が必要か)、具体例(この形式で、こんな出力がほしい)、制約(この API は使わない)、完成条件(この条件を満たしたら完了)。

気づいたでしょうか。**これはそのまま、良いプロンプトの構成要素です。** 「プロンプトエンジニアリング」という仰々しい名前の中身は、Phase 0 からあなたが学んできた「明確に伝える技術」— 質問の仕方(XY 問題を避ける)、仕様の書き方、コードレビューでの指摘の仕方 — の応用にすぎません。

これは朗報です。プロンプト設計は、AI 時代に突然現れた新スキルではなく、**エンジニアが昔から磨いてきたコミュニケーション能力の別の顔**です。曖昧な指示で部下(人間でも AI でも)を働かせると、曖昧な成果が返ってくる。明確な期待値を言語化できる人は、人間のチームでも AI 相手でも強い。あなたがこのレッスンで磨くのは、実は両方に効くスキルです。

---

## まとめ

- 良いプロンプトは「役割・タスク・情報・制約・出力形式」の 5 要素を持つ
- 最初から完璧なプロンプトは書けない。反復的に改善する
- CLAUDE.md でプロジェクト文脈を事前に与えると、毎回の指示が減り精度が上がる
- 「全部任せる」「答えだけ求める」「検証なしに使う」の 3 つは避ける
- 良いプロンプトスキルは AI 専用ではなく、人間とのコミュニケーション全般に通じる

## 確認問題

1. 以下のプロンプトを、Lesson で学んだ 5 要素を使って改善してください。
   「ソートのコードを書いてください」

2. 「反復的改善」が重要な理由を説明してください。「最初から完璧なプロンプトを書けばいい」という考え方のどこが現実的でないのか答えてください。

3. あなたが取り組んでいる (または想定している) プロジェクトについて、CLAUDE.md に書くべき内容を考えてみてください。技術スタック・ディレクトリ構成・コーディング規約の 3 項目を含めて草案を書いてください。

4. 「アンチパターン 2: 答えだけ求める」は、特に学習の場面でなぜ有害なのか説明してください。

5. 以下の 2 つのプロンプトの違いを説明し、どちらが良いプロンプトかを理由とともに答えてください。
   - プロンプト A: 「Python で二分探索を実装して」
   - プロンプト B: 「Python 3.12 でソート済みリストに対する二分探索を実装してください。整数のリストを対象とし、見つかった場合はインデックスを、見つからない場合は -1 を返してください。組み込みの bisect モジュールは使わず、アルゴリズムを手動実装してください。実装後、いくつかのテストケースも示してください。」
