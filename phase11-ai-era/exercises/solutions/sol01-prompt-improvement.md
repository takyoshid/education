# 演習 01 模範解答: プロンプト改善演習

## この解答の使い方

自分で解答を作成してから、この模範解答と照らし合わせてください。
プロンプトには「唯一の正解」はありません。ここで示す解答は一例です。
「改善の理由が説明できているか」を自己採点の基準にしてください。

---

## 問題 1: バグ修正の依頼

### 悪いプロンプト (元のまま)

```
「このコードのバグを直してください。
def divide(a, b):
    return a / b」
```

### なぜ悪いのか

| 欠けている要素 | 影響 |
|--------------|------|
| 関数の目的が不明 | AI は「何を直すべきか」の判断基準を持てない |
| 想定する入力値が不明 | ゼロ除算以外のエッジケースを考慮できない |
| 期待する出力形式が不明 | コードだけ返すか、説明付きで返すか判断できない |
| 使用言語・バージョンが不明 | Python 2 / Python 3 の違い等を考慮できない |

### 良いプロンプト (改善例)

```
あなたは Python のコードレビューを専門とするエンジニアです。

以下の Python 3.12 の関数を確認し、潜在的なバグを修正してください。

[関数の目的]
2 つの数値を受け取り、割り算の結果を返す関数です。
計算ツールの一部として使われ、ユーザーが入力した任意の数値が渡されます。

[コード]
def divide(a, b):
    return a / b

[想定される問題]
- b に 0 が渡されたときの挙動
- a または b に数値以外 (文字列など) が渡されたときの挙動

[制約]
- 外部ライブラリは使わない (Python 標準のみ)
- 型アノテーションを付ける
- 異常系は例外を発生させるのではなく、呼び出し元が判断できるよう None を返す方式にする

[出力形式]
1. 修正後のコードのみ
2. 修正した箇所とその理由を箇条書きで 3 点以内
```

### 改善の理由 (解説)

**改善点 1: 役割 (Role) の設定**
「コードレビューを専門とするエンジニア」という役割を与えることで、AI が「コードの正確さ・安全性・可読性」の観点で回答するよう誘導しています。役割なしでは、AI は「とりあえず動くコード」を返しがちです。

**改善点 2: 関数の目的と使用文脈を明示**
「ユーザーが入力した任意の数値が渡される」という情報を加えることで、AI は「信頼できない入力への対処」が必要だと判断できます。社内ツールで信頼できる入力しか来ない場合とは修正方針が変わります。

**改善点 3: 想定する問題を明示**
「何がバグか」を AI に推測させるのではなく、修正してほしいポイントを明示します。AI への指示は「完全に任せる」よりも「方向を示して詳細を任せる」方が精度が上がります。

**改善点 4: 制約で出力の形を制御**
「None を返す方式」という制約を加えることで、AI が勝手に「例外を発生させる方式」を選ぶことを防いでいます。制約のないプロンプトでは、AI は最も一般的と思われる方式を選ぶため、あなたのプロジェクトの方針と合わない場合があります。

### 改善後の期待される AI 出力 (参考)

```python
def divide(a: float | int, b: float | int) -> float | None:
    """
    2 つの数値を割り算して結果を返す。

    Args:
        a: 被除数
        b: 除数

    Returns:
        a / b の結果。b が 0 の場合、または数値でない場合は None を返す。
    """
    if not isinstance(a, (int, float)) or not isinstance(b, (int, float)):
        return None
    if b == 0:
        return None
    return a / b
```

**修正箇所:**
- ゼロ除算チェックを追加 (b == 0 のとき None を返す)
- 型チェックを追加 (数値以外の入力を弾く)
- 型アノテーションと docstring を追加

## 問題 2: 機能実装の依頼

### 悪い版プロンプト (例)

```
Python で CSV を読み込んで統計情報を JSON に保存するコードを書いてください。
```

### なぜ悪いのか

- CSV のどの列を集計するのか不明
- JSON の構造が不明 (AI が適当な構造を決める)
- エラー処理の有無が不明
- 標準ライブラリのみか、pandas を使うかが不明
- Python のバージョンが不明

### 良い版プロンプト (模範例)

```
Python 3.12 で以下の仕様を満たすスクリプトを実装してください。

[目的]
CSV ファイルを読み込み、指定した列の統計情報を計算して JSON ファイルに保存します。

[入力: CSV ファイルの構造]
- ヘッダー行あり
- 数値列が複数存在する (列名は実行時に指定)
- 欠損値 (空セル) が含まれる場合がある

サンプル:
name,age,score
Alice,25,88.5
Bob,,72.0
Carol,30,

[出力: JSON の構造]
{
    "column": "age",
    "count": 2,
    "mean": 27.5,
    "max": 30,
    "min": 25,
    "std": 2.5
}

[エラーハンドリング要件]
- ファイルが存在しない場合: わかりやすいメッセージを出して終了
- 指定した列が CSV に存在しない場合: 利用可能な列名を表示して終了
- 指定した列に数値以外のデータが含まれる場合: その行をスキップしてカウントに反映する

[ライブラリ制約]
- pandas は使わない
- Python 標準ライブラリの csv、json、statistics モジュールのみ使用する

[コードスタイル]
- 関数に分割する (ファイル読み込み / 統計計算 / JSON 保存 を別関数に)
- 各関数に型アノテーションと 1 行 docstring を付ける
- コマンドライン引数で CSV ファイルパス・列名・出力 JSON パスを受け取る

[出力形式]
完成したスクリプト全体を出力してください。説明は不要です。
```

### 改善の理由 (解説)

**サンプルデータを示す:** 「ヘッダー行あり」と書くより、実際のサンプルを見せる方が AI の解釈のズレがなくなります。特に CSV や JSON など構造のあるデータを扱う場合、サンプルは必須と考えてください。

**ライブラリを明示する:** 「pandas を使わない」という制約がなければ、多くのケースで AI は pandas を使った実装を返します。pandas が使えない環境での学習や、依存を減らしたいプロジェクトでは、明示的に禁止する必要があります。

**関数分割の指示:** 「関数に分割する」という指示がなければ、AI は手続き的な 1 つの長い関数を書くことがあります。保守しやすいコードを得るには、構造への要求も明示します。

## 問題 3: ソクラテス式プロンプトの作成

### 「答えを直接求める」プロンプト (例)

```
Python の yield キーワードとジェネレータ (Generator) について、
以下を教えてください。

1. yield の基本的な動作
2. return との違い
3. ジェネレータを使うメリット
4. 具体的なコード例 (フィボナッチ数列を使ったもの)
```

### 「ソクラテス式」プロンプト (例)

```
あなたは Socratic Method (ソクラテス式問答法) を使って教える
Python 講師です。答えは直接教えず、私が自分で考えて答えに
たどり着けるよう、問いかけだけをしてください。

テーマ: Python の yield キーワードとジェネレータ (Generator)

まず最初の問いかけから始めてください。
私が答えたら、その答えを深掘りする次の問いを投げかけてください。
私が間違っていても直接修正せず、矛盾に気づかせる問いを立てください。
```

### 比較コメントと気づき

| 観点 | 答えを直接求める | ソクラテス式 |
|------|----------------|------------|
| 速度 | 速い (すぐに答えが得られる) | 遅い (何往復も必要) |
| 記憶定着 | 低い (読んで終わり) | 高い (自分で考えて答えるため) |
| 理解の深さ | 表面的 (知識として知っている) | 深い (なぜそうなるかを理解) |
| 使いどき | リファレンスとして参照したいとき | 概念を本当に理解したいとき |

**重要な気づき:**

「答えを直接求める」プロンプトは**参照には便利**ですが、学習効果は低い傾向があります。「なぜ yield を使うのか」「return と何が根本的に違うのか」といった理解は、自分で考えてから答えと照合することで定着します。

ソクラテス式のプロンプトを使うと、AI は「あなたが最後に実行したコードで、ループが完全に終了した後に next() を呼ぶとどうなると思いますか?」のように、考えさせる問いを出してきます。この「考えてから確認する」プロセスが学習効果を高めます。

## 問題 4: CLAUDE.md の作成

### 悪い例の CLAUDE.md

```markdown
# TODO アプリ

Flask を使った TODO アプリです。

## 技術
- Python
- Flask
- データベース

## ルール
- きれいなコードを書く
- テストを書く
```

**なぜ悪いのか:**
- バージョンが不明 (Python 2? 3? Flask 1? 3?)
- 「データベース」とだけあり、何を使うかわからない
- 「きれいなコード」は主観的で AI には伝わらない
- ディレクトリ構成がなく、どこにファイルを置けばいいか不明

### 良い例の CLAUDE.md

```markdown
# TODO App

## プロジェクト概要
Python 3.12 + Flask 3.0 で作るシンプルな TODO 管理 API。
SQLite をデータベースとして使用し、REST API を提供する。
フロントエンドは持たず、curl や HTTPie でテストする。

## 技術スタック
- Python 3.12
- Flask 3.0.3
- SQLAlchemy 2.0 (ORM)
- SQLite 3 (開発環境)
- pytest 8.0 (テスト)
- black 24.0 (フォーマッタ)
- ruff 0.4 (リンタ)

## ディレクトリ構成
todo_app/
├── app.py              # Flask アプリのエントリポイント
├── models.py           # SQLAlchemy モデル定義
├── routes/
│   └── todos.py        # /todos エンドポイントのルーター
├── schemas.py          # リクエスト/レスポンスの型定義
├── tests/
│   └── test_todos.py   # pytest テスト
├── CLAUDE.md
└── requirements.txt

## コーディング規約
1. 型アノテーションを必ずつける (引数・戻り値)
2. 関数名・変数名は snake_case、クラス名は PascalCase
3. 1 関数は 20 行以内を目安にする。超える場合は分割を検討する
4. print デバッグは使わない。logging モジュールの logger.debug() を使う
5. マジックナンバーは定数化する (例: MAX_TITLE_LENGTH = 100)

## テスト
- テストは pytest で書く
- テストファイルは tests/ 以下に置く
- テストクラスは Test で始める (例: class TestTodoCreate:)
- 実行: pytest tests/ -v

## よく使うコマンド
```bash
# 開発サーバー起動
flask --app app run --debug

# テスト実行
pytest tests/ -v

# フォーマット & リント
black . && ruff check .

# DB の初期化 (初回またはリセット時)
python -c "from app import db; db.create_all()"
```

## 禁止事項・注意事項
- API キーやパスワードを app.py や models.py に直書きしない。必ず .env ファイルと python-dotenv を使う
- raw SQL (db.session.execute("SELECT ...") の文字列埋め込み) は使わない。SQLAlchemy の ORM メソッドを使う
- テストを書かずに routes/ にコードを追加しない
```

### 各記述の意図解説

**バージョンを明記する理由:**
「Flask 3.0.3」と書くことで、AI はそのバージョンの API 仕様に基づいてコードを生成します。バージョンなしで「Flask を使って」と書くと、古い API (Flask 1.x の `@app.before_first_request` など) を使ったコードが生成されることがあります。

**ディレクトリ構成を書く理由:**
「新しいエンドポイントを追加して」と頼んだとき、CLAUDE.md にディレクトリ構成がなければ AI は適当なファイルに関数を追加します。構成があれば、AI は `routes/todos.py` に追加することを理解します。

**禁止事項を「なぜ禁止か」なしで書く理由:**
CLAUDE.md は指示書です。理由の説明は不要で、守るべきことを簡潔に書きます。「raw SQL を使わない」という事実だけで十分です。

## まとめ: プロンプト改善の原則

良いプロンプトを書くための判断基準をまとめます。

```
チェック 1: 「誰が読んでも同じ解釈になるか?」
  -> 曖昧な言葉 (「きれいに」「うまく」「適切に」) は具体的な言葉に置き換える

チェック 2: 「必要な情報がすべて揃っているか?」
  -> コードがあればコード、エラーがあればエラー全文、バージョンがあればバージョンを貼る

チェック 3: 「出力の形式を指定したか?」
  -> 「コードのみ」「箇条書きで 3 点」「JSON 形式で」など形式を指定すると後処理が楽になる

チェック 4: 「制約が抜けていないか?」
  -> 「使ってはいけないライブラリ」「守るべきコーディング規約」を明示する

チェック 5: 「AI の役割を設定したか?」
  -> 複雑なタスクでは「あなたはXXの専門家です」と役割を与えることで精度が上がる
```
