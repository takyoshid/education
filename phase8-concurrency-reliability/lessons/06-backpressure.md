# Lesson 06: 背圧と負荷制御

## 学習目標

- 到着が処理を上回ったとき、システムに何が起きるかを説明できる
- 無限のキューが問題を隠すだけで解決しないことを説明できる
- 利用率が上がると待ち時間が急激に伸びる理由を説明できる
- 背圧(backpressure)と負荷制御(load shedding)を使い分けられる
- 「全部受けて全部遅い」より「一部を断って残りは速い」ほうがよい場面を判断できる

---

## 1. 入ってくる量が、捌ける量を超えたら

ここまでのレッスンでは「1 つの処理を正しく行う」ことを扱ってきました。このレッスンで扱うのは、**量の問題**です。

毎秒 100 件の要求が来て、毎秒 100 件を捌けるなら問題ありません。では、毎秒 120 件になったら何が起きるでしょうか。

**選択肢は 3 つしかありません。**

```
1. 溜める    → キューに積む
2. 断る      → エラーを返す
3. 落とす    → 黙って捨てる
```

「速く処理する」は選択肢に入っていないことに注意してください。それができるならそもそも問題は起きていません。**能力を超えた入力に対して、システムは必ずこの 3 つのどれかをします。**設計しなければ、勝手にどれかが起きます。

そして「設計しなかった場合に起きること」は、たいてい最悪の形になります。

---

## 2. 無限のキューは、問題を隠すだけ

最も直感的な対処は「溜める」です。キューを置けば、一時的な波を吸収できます。実際、これは正しい設計です — **上限がある限りは。**

上限のないキューを置くと、次が起きます。

```
毎秒 120 件到着、毎秒 100 件処理

  1 分後: キューに   1,200 件  → 待ち時間 12 秒
 10 分後: キューに  12,000 件  → 待ち時間 2 分
 60 分後: キューに  72,000 件  → 待ち時間 12 分
```

処理は止まっていません。エラーも出ていません。**それでもサービスは壊れています。**

### 誰も待っていない仕事をしている

12 分待たされる利用者は、とっくに画面を閉じています。あるいはクライアント側のタイムアウトで諦めています。

つまりサーバは、**もう誰も結果を必要としていない仕事**を全力で処理し続けています。その間、新しく来た要求も列の最後尾に並びます。

これは単に遅いのではありません。**システムが有用な仕事を 1 件もしていない状態**です。処理能力の 100% が、捨てられる結果の生成に使われています。

### メモリが尽きるまで気づけない

さらに悪いことに、上限のないキューは最終的にメモリを食い尽くします。そのとき落ちるのは、キューに積んだプロセス全体です。**溜めていた仕事も、いま処理中の仕事も、まとめて消えます。**

> **原則: キューには必ず上限を設ける。**
>
> 上限のないキューは「まだ問題が起きていない」のではなく、「問題を見えない場所に溜めている」状態です。

---

## 3. 利用率が上がると、待ち時間は急に伸びる

「能力の 100% まで使えばいい」と考えたくなりますが、そうはいきません。

待ち行列の理論には、直感に反する結果があります。**到着にばらつきがある限り、待ち時間は利用率に比例せず、100% に近づくと急激に発散します。**

```
利用率      待ち時間の目安(利用率 50% を 1 とする)
 50%   →   1
 70%   →   2.3
 80%   →   4
 90%   →   9
 95%   →   19
 99%   →   99
```

利用率を 50% から 90% に上げると、使用効率は 1.8 倍にしかなりませんが、**待ち時間は 9 倍**になります。

### なぜそうなるのか

到着が完全に一定間隔なら、100% まで使えます。しかし現実の到着はばらつきます。

利用率に余裕があるうちは、**たまたま重なった要求を、その後の空き時間で取り戻せます。**利用率が 100% に近いと、取り戻す空き時間がありません。一度できた遅れは解消されず、次の重なりに積み上がります。

**これは実装の問題ではなく、確率の性質です。**どんな言語で書いても、どんなハードウェアを使っても変わりません。

> **実務的な帰結: 平常時の利用率には余裕を持たせる。**
>
> 「サーバの CPU が 50% しか使われていないのはもったいない」という発想は、待ち時間を犠牲にしています。何を買っているのかを理解したうえで決めてください。

---

## 4. 背圧 (backpressure)

**背圧とは、「これ以上は受け取れない」という信号を、送り手に伝えることです。**

キューが埋まったら、送り手を待たせる。送り手はそれ以上送れないので、さらにその送り手が待つ。この圧力が、系全体の入口まで遡って伝わります。

```
[利用者] ← 待たされる
   ↓
[API] ← キューが埋まっているので受け付けを止める
   ↓
[キュー: 満杯]
   ↓
[ワーカー] ← 全力で処理中
```

背圧が効いていると、**システムは自分の能力以上の仕事を抱え込みません。**遅くはなりますが、壊れません。

### 実装は「有界のキュー」で始まる

背圧は特別な仕組みではありません。**上限のあるキューを使い、満杯のときに書き込みをブロックする**だけで、最も基本的な背圧になります。

- 上限つきキューに `put` する。満杯ならブロックする
- 同時実行数に上限を設ける(Lesson 03 の並行数制限がこれです)
- ネットワークなら、受信側が「受け取れる量」を送信側に伝える(TCP のウィンドウ制御がまさにこれです)

**背圧は新しい発明ではありません。**TCP は 1970 年代からこれをやっています。ダムの放流量を下流の状況で決めるのと同じ発想です。

### 背圧が効かない構成に注意

背圧は、**送り手が待てる場合にだけ**機能します。

待てない送り手もいます。センサーからのデータ、外部から届くイベント、利用者のクリック。これらは「待って」と言っても止まりません。**その場合、背圧では解けません。**次の節が必要になります。

---

## 5. 負荷制御 (load shedding)

送り手を止められないなら、**受け取ったものを断るか、捨てる**しかありません。これを負荷制御と呼びます。

### 「断る」は失敗ではない

即座にエラーを返すことは、設計上の失敗ではありません。**むしろ最も誠実な応答です。**

| 応答 | 利用者にとって |
|---|---|
| 12 分待たせて結果を返す | 最悪。待った時間が完全に無駄 |
| 12 分待たせてタイムアウト | さらに最悪。待たせたうえに何も返さない |
| **即座に「いま混んでいます」と返す** | **最善。すぐ諦めるか、あとで再試行するか判断できる** |

早く断れば、送り手は再試行の計画を立てられます(Lesson 05 の backoff と jitter が、まさにここで効きます)。断らずに抱え込むと、送り手は待つしかありません。

### 何から捨てるかは、業務が決める

全部を等しく扱う必要はありません。

| 捨てる基準 | 例 |
|---|---|
| 優先度が低いもの | 分析用のログ収集より、決済を優先する |
| もう意味がないもの | クライアントが諦めた要求は処理しない |
| **古いものから** | 直近の値だけが要るなら、古いデータは捨てる |
| 新しいものから | 順序が重要なら、新しい到着を断る |

**「古いものから捨てる」と「新しいものから断る」は、正反対の判断です。** どちらが正しいかは、扱っているデータで決まります。

- 株価の表示 → 最新の値だけが要る。**古いものを捨てる**
- 銀行の取引 → 1 件も失えない。**新しいものを断る(そして送り手に再試行させる)**

### 期限切れの仕事はやらない

最も効果的な負荷制御の一つは、**キューから取り出したときに「まだ意味があるか」を確認する**ことです。

```
キューから取り出す
  → この要求は 30 秒前に来た
  → クライアントのタイムアウトは 10 秒
  → 結果を返しても、もう誰も受け取らない
  → 処理せずに捨てる
```

これだけで、過負荷時に**能力を有用な仕事に振り向けられます。**混雑しているときほど効果が大きく、混雑していないときは何も起きません。

---

## 6. 選び方

```
到着が能力を超えたとき、どうするか

送り手を待たせられるか?
   |
   +-- はい → 背圧(有界キュー + ブロック)
   |          例: 内部のワーカー、バッチ処理、TCP
   |
   +-- いいえ → 負荷制御
              |
              +-- 失ってはいけないデータか?
                    |
                    +-- はい → 早く断り、送り手に再試行させる
                    |          (Lesson 05 の backoff と組み合わせる)
                    |
                    +-- いいえ → 捨てる
                                 (古いものから / 優先度が低いものから)
```

どの経路を通っても、**「上限を決める」ことだけは共通です。** 上限を決めないという選択肢は、実際には「メモリの上限まで溜める」という選択をしていることになります。

## 💡 コラム: 「もっと速く走れ」と言えないから、信号がある

交通渋滞と、システムの過負荷は、同じ数学で説明できます。

高速道路の車の密度を上げていくと、ある点までは通行量が増えます。しかしある密度を超えると、**通行量が減り始めます。**車が増えているのに、通過する車の数は減る。誰も止まれと言っていないのに、全体が止まる。これが渋滞です。

対策として世界中で使われているのが、**入口の信号(ramp metering)**です。合流地点の手前に信号を置き、本線に入れる車の数を制限します。

一見すると理不尽です。空いている入口で、わざわざ車を待たせるのですから。しかし結果として、**本線の流れが保たれ、全体の所要時間は短くなります。**入口で 30 秒待つほうが、本線で 20 分渋滞するより速いのです。

これは負荷制御そのものです。「全員を受け入れて全員が遅い」より、「入口で少し待たせて中は流れている」ほうが、システム全体としては速い。

同じ話は病院の救急にもあります。全員を到着順に診るのではなく、**重症度で選別(トリアージ)します。**軽症の人を待たせるのは冷たく見えますが、そうしなければ助かる命が助からない。優先度による負荷制御です。

**過負荷への対処法は、コンピュータが発明したものではありません。**交通も医療も、限られた能力で需要をさばく問題を、何十年も前から解いてきました。だからこの分野の考え方は、コンピュータが姿を変えても残ります。

## まとめ

| 概念 | 要点 |
|------|------|
| 選択肢は 3 つ | 溜める・断る・落とす。設計しなければ勝手にどれかが起きる |
| 無限のキュー | 問題を隠すだけ。誰も待っていない仕事をし続け、最後はメモリで落ちる |
| 利用率と待ち時間 | 比例しない。100% に近づくと急激に発散する。確率の性質であり実装の問題ではない |
| 背圧 | 「受け取れない」を送り手に伝える。**送り手が待てる場合にだけ**効く |
| 有界キュー | 最も基本的な背圧の実装 |
| 負荷制御 | 送り手を止められないときに断る・捨てる。**早く断るのは誠実な応答** |
| 何を捨てるか | 業務が決める。「古いものから」と「新しいものから」は正反対の判断 |
| 期限切れの仕事 | 取り出したときに意味を確認する。混雑時ほど効果が大きい |

## 確認問題

1. 到着が処理能力を超えたとき、システムが取りうる選択肢を 3 つ挙げてください。

2. 上限のないキューを使うと、最終的に何が起きますか。「処理は止まっていないのに壊れている」とはどういう状態ですか。

3. 利用率を 50% から 90% に上げると、待ち時間はどうなりますか。なぜ比例しないのですか。

4. 「サーバの CPU が 50% しか使われていないのはもったいない」という主張に、どう答えますか。

5. 背圧とは何ですか。背圧が機能**しない**のはどんな場合ですか。

6. 12 分待たせて結果を返すより、即座に「混んでいます」と返すほうがよいのはなぜですか。

7. 次の 2 つで、過負荷時に捨てるべきものはそれぞれ何ですか。理由も述べてください。
   - (a) 株価をリアルタイム表示する画面への配信
   - (b) 銀行の振込処理

8. 「キューから取り出したときに、まだ意味があるかを確認する」という工夫は、なぜ混雑時ほど効果が大きいのですか。
