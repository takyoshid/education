# Lesson 01: 並行性のモデル (Concurrency Models)

## 学習目標

- 並行性 (concurrency) と並列性 (parallelism) の違いを説明できる
- プロセス・スレッド・非同期タスクの使い分けを、根拠を持って判断できる
- Python の GIL (Global Interpreter Lock) が何に効いて何に効かないかを説明できる
- API を選ぶ前に「守るべき不変条件」を書き出せる

---

## 1. Concurrency と Parallelism は別の概念

この 2 つは日本語だとどちらも「同時」と訳されがちですが、まったく違うことを指しています。

- **Concurrency (並行性)**: 複数の仕事が**進行中**である構造
- **Parallelism (並列性)**: 複数の仕事が**同じ瞬間に実行**されている状態

```
Concurrency (1コア) — 進行中の仕事は2つ、同時に走ってはいない
  タスクA: ██──────██────██
  タスクB: ──██████──██████
           ↑ A が I/O 待ちの間に B が進む

Parallelism (2コア) — 同じ瞬間に2つ走っている
  コア1 A: ████████████████
  コア2 B: ████████████████
```

Go の作者 Rob Pike の有名な定義があります。

> **Concurrency is about dealing with lots of things at once.**
> **Parallelism is about doing lots of things at once.**
> (並行性は多くのことを「扱う」こと。並列性は多くのことを「行う」こと。)

なぜこの区別が実務で重要かというと、**「非同期にしたのに速くならない」という現象の原因がここにある**からです。I/O 待ちが支配的な処理なら concurrency で劇的に速くなります。CPU 計算が支配的なら、コアを増やさない限り速くなりません。

## 2. 3つのモデル

| モデル | 向く処理 | メモリ | 主な失敗 | 切り替えコスト |
|---|---|---|---|---|
| **プロセス** | CPU-bound、障害の分離 | 原則分離 | IPC の複雑さ、起動コスト | 大 |
| **スレッド** | ブロッキング I/O、既存の同期 API | 共有 | race condition、deadlock | 中 |
| **非同期タスク** | 多数の I/O 接続 | イベントループ内で共有 | ブロック、取消漏れ | 小 |

### プロセス (process)

OS が管理する独立した実行単位です。メモリ空間が分かれているため、**片方が壊れてももう片方に波及しません**。

```python
from concurrent.futures import ProcessPoolExecutor


def heavy_calculation(n: int) -> int:
    return sum(i * i for i in range(n))


with ProcessPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(heavy_calculation, [10_000_000] * 4))
```

メモリを共有しないので、データの受け渡しには**シリアライズ (pickle 化)** が必要です。大きなデータをやり取りすると、そのコストが並列化の利益を食い潰します。

### スレッド (thread)

同じプロセス内で複数の実行の流れを持ちます。**メモリを共有する**ので受け渡しは速いですが、それがそのまま race condition の原因になります。

```python
from concurrent.futures import ThreadPoolExecutor
import requests


def fetch(url: str) -> int:
    return len(requests.get(url, timeout=5).content)


with ThreadPoolExecutor(max_workers=10) as pool:
    sizes = list(pool.map(fetch, urls))
```

`requests` のようにブロッキング I/O を行うライブラリを並行化したいときは、スレッドが最も手軽です。

### 非同期タスク (async task)

1 つのスレッドの上で、**待機地点で明示的に制御を譲り合う**方式です。

```python
import asyncio
import httpx


async def fetch(client: httpx.AsyncClient, url: str) -> int:
    response = await client.get(url, timeout=5)
    return len(response.content)


async def main(urls: list[str]) -> list[int]:
    async with httpx.AsyncClient() as client:
        async with asyncio.TaskGroup() as group:
            tasks = [group.create_task(fetch(client, u)) for u in urls]
    return [t.result() for t in tasks]
```

タスク 1 つあたりのメモリはスレッドよりはるかに小さく(数 KB 対 数百 KB〜数 MB)、切り替えも OS を経由しないため軽量です。**接続を数万本抱える**ようなサーバーではこの差が決定的になります。

## 3. Python の GIL — 何に効いて、何に効かないか

CPython には **GIL (Global Interpreter Lock)** があり、**1 プロセス内で同時に Python のバイトコードを実行できるスレッドは 1 つだけ**です。

ここでよくある誤解を正します。

| 誤解 | 実際 |
|---|---|
| 「GIL があるからスレッドは無意味」 | ✗ I/O 待ちの間 GIL は解放されるので、I/O-bound には有効 |
| 「GIL があるから race condition は起きない」 | ✗ **起きる**。バイトコード単位では切り替わる |
| 「GIL があるから CPU 処理は速くならない」 | ○ 正しい。プロセスを使う |

2 番目が特に危険です。次のコードは GIL があっても壊れます。

```python
counter = 0

def increment():
    global counter
    for _ in range(100_000):
        counter += 1        # 読み取り → 加算 → 書き込み の3ステップ
```

`counter += 1` は不可分な 1 命令ではありません。ステップの途中でスレッドが切り替わると、更新が失われます。詳しくは Lesson 02 で実際に壊してみます。

> **補足**: Python 3.13 から GIL を無効化できるビルド (free-threaded build, PEP 703) が実験的に提供されています。将来は状況が変わりますが、**GIL が無くなると race condition はむしろ起きやすくなります**。「GIL があったから偶然守られていた」コードが露出するためです。本 Phase で学ぶ考え方の重要性は下がりません。

## 4. まず「不変条件」を書く

並行処理の設計は、`Lock` や `async` といった **API の選択から始めてはいけません**。順序はこうです。

```
1. 不変条件 (invariant) を書く      ← 常に成り立っていてほしい条件
2. その条件を壊しうる操作の組を列挙する
3. どこで直列化するかを決める
4. はじめて API を選ぶ
```

### 不変条件の例

| システム | 不変条件 |
|---|---|
| 送金 | 全口座の残高合計は変わらない。残高は負にならない |
| 在庫 | 引当済み数量は在庫数を超えない |
| 注文 | 同じ注文 ID の注文は 1 件しか作られない |
| 座席予約 | 1 つの座席に 2 人以上を割り当てない |

### 壊れ方を列挙する: check-then-act

最も多い競合パターンが **check-then-act (確認してから行動する)** です。

```python
if stock > 0:        # ← check
    stock -= 1       # ← act
    ship_item()
```

`check` と `act` の**間**に別のスレッドが割り込むと、両方が「在庫あり」と判断して両方が減らします。在庫が `-1` になります。

```
時刻  スレッドA              スレッドB           stock
 1    if stock > 0 → True                        1
 2                          if stock > 0 → True  1
 3    stock -= 1                                 0
 4                          stock -= 1          -1  ← 不変条件が壊れた
```

**「読んで、判断して、書く」の 3 つが分かれている場所はすべて競合の候補**です。これを見つける訓練が、この Phase で一番大事な技能です。

## 5. 選び方の判断基準

「非同期のほうが今風だから」で選ばないでください。判断材料はこの順です。

1. **何がボトルネックか計測する** — CPU 使用率が張り付いているのか、I/O 待ちなのか
2. **使うライブラリが対応しているか** — 同期専用のドライバしかないなら async にできない
3. **運用の複雑さに見合うか** — async はスタックトレースもデバッグも難しくなる

```
CPU使用率が100%に張り付いている
  → プロセス (または処理そのものを見直す)

I/O 待ちが支配的、接続数は数百まで
  → スレッド (最も素直。既存の同期ライブラリがそのまま使える)

I/O 待ちが支配的、接続数が数千〜数万
  → 非同期タスク

わからない
  → まず計測する。推測で並行化しない
```

> **原則**: 並行処理は**最後の手段**です。まず N+1 クエリを直す、インデックスを張る、無駄な処理を消す。それでも足りないときに並行化を検討します。並行化は必ずバグの温床を持ち込みます。

## 💡 コラム: C10K 問題 — モデルの選択がインターネットを変えた

1999 年、Dan Kegel というエンジニアが「**C10K problem**」という文書を公開しました。問いはシンプルです。

> 1台のサーバーで、**1万本の同時接続**を捌くにはどうすればいいか。

当時の主流だった Apache は「**接続 1 本につきプロセス(またはスレッド)1 つ**」というモデルでした。分かりやすく、1990年代の Web には十分でした。しかし 1 万接続となると、1 万個のプロセスが必要になります。1 プロセスあたり数 MB のメモリ、そして OS はコンテキストスイッチだけで CPU を使い果たします。**接続がほとんど何もしていなくても**、抱えているだけでコストがかかったのです。

2004年、ロシアのエンジニア **Igor Sysoev** が nginx を公開しました。設計はまったく違いました。少数のプロセスが**イベントループ**を回し、「読めるようになった接続」「書けるようになった接続」だけを処理する。接続は単なるデータ構造であり、実行の単位ではない。1 万接続を抱えても、実際に動いているのは数プロセスだけです。

結果は歴史が示すとおりです。nginx は世界の Web サーバーの中心的存在になり、Node.js も同じイベントループのモデルで登場しました。Python の `asyncio`、Go の goroutine、Rust の async — 現代の並行処理の基盤は、すべてこの問いへの回答です。

ここから学ぶべきことは「イベントループが優れている」ではありません。**同じ仕事に対して、実行モデルを変えるだけで桁違いの差が出る**ということです。そして nginx がやったのは新しいアルゴリズムの発明ではなく、「接続 = 実行単位」という前提を疑うことでした。

あなたが「遅い」と感じたとき、最適化すべきはコードの中身ではなく、**仕事の並べ方**かもしれません。

## 🌟 コラム: 公安9課とタチコマ — 「9人で回る組織」と「同時に展開する部隊」

『攻殻機動隊 STAND ALONE COMPLEX』の公安9課は、**驚くほど少人数**の組織です。それでいて、同時に複数の事件を抱え、政治的な駆け引きに対応し、現場に踏み込みます。人数を増やして対応しているわけではありません。

一方、彼らが運用する **タチコマ**は同型機の部隊です。必要な場面では複数機が**同じ瞬間に**別々の地点へ展開し、それぞれが戦闘・偵察を実行します。

この 2 つの違いが、そのまま concurrency と parallelism です。

| | 攻殻の世界 | 技術用語 |
|---|---|---|
| 少人数が複数の事案を**切り替えながら**進める | 公安9課の運用 | **Concurrency**(並行性) |
| 同型の実体が**同じ瞬間に**別々の仕事を実行する | タチコマ部隊の展開 | **Parallelism**(並列性) |

ここで注目してほしいのは、**9課が少人数のままで機能している理由**です。彼らが増員で解決していないのは、ボトルネックが「手の数」ではないからです。待っている時間 — 分析結果を待つ、相手の出方を待つ、許可を待つ — その間に別の線を進める。**待ち時間を遊ばせない構造**こそが、少人数で多くを扱える理由です。

これは §1 で見た「1 コアでも I/O 待ちの間に別タスクを進めれば concurrent」と、まったく同じ話です。そして逆も真で、**タチコマを何機並べても、1 機でしかできない仕事は速くなりません**。CPU 計算が支配的な処理をいくら非同期にしても速くならないのと同じです。

あなたのシステムが遅いとき、問うべきはこうです。**「手が足りないのか、待ち時間が無駄なのか」**。前者ならプロセスを増やす(parallelism)。後者なら待ち方を変える(concurrency)。この 2 つを取り違えると、増やしても速くならないか、複雑さだけが増えます。

> タチコマの「並列化」については、[Phase 11 Lesson 02](../../phase11-distributed-systems/lessons/02-replication.md) でレプリケーションの観点から、[Phase 4 Lesson 07](../../phase4-ai-era/lessons/07-engineer-value-in-ai-era.md) で「個の価値」の観点から、それぞれ別の角度で扱います。

## まとめ

- **Concurrency** は「複数の仕事を扱う構造」、**Parallelism** は「同じ瞬間に実行すること」。別物
- プロセスは分離、スレッドは共有、非同期タスクは軽量 — トレードオフで選ぶ
- **GIL があっても race condition は起きる**。I/O では GIL は解放される
- API を選ぶ前に**不変条件**を書く。次にそれを壊す操作の組を列挙する
- **check-then-act** は最頻出の競合パターン。「読む・判断する・書く」が分かれている場所を疑う
- 並行化は最後の手段。まず計測する

## 確認問題

1. 「非同期にしたのに速くなりませんでした」と相談されました。原因を切り分けるために、まず何を確認しますか。
2. GIL があるにもかかわらず、スレッドを使うと `counter += 1` が壊れるのはなぜですか。
3. プロセス分離を選ぶと「正しさ」が簡単になる場合があります。それはどういう場合ですか。逆に何が難しくなりますか。
4. 次のコードに含まれる check-then-act を指摘し、壊れる実行順序を時刻表で書いてください。

   ```python
   def reserve_seat(seat_id: str, user_id: str) -> bool:
       if seats[seat_id] is None:
           seats[seat_id] = user_id
           return True
       return False
   ```

5. あなたが担当するシステムの不変条件を 3 つ書き出してください。それぞれについて「その条件を読む操作」と「書く操作」を挙げてください。
6. スループット (throughput) を最適化しているのか、レイテンシ (latency) を最適化しているのか。この 2 つはどう違い、どちらを見ているかをどう確認しますか。
