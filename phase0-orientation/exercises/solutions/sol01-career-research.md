# 自己評価ガイド 01: キャリアリサーチ

## このガイドの使い方

自分の回答を先に書いてからこのファイルを開くこと。
「答え合わせ」が目的ではなく、「自分の考えとの比較」が目的だ。
考え方のプロセスを参考にして、自分の回答を深めてほしい。

---

## 演習 1-A: 職種の整理 — 評価の考え方

**思考プロセス:**

「求人票を読む」という指示の意図は、教科書的な定義ではなく「実際に何が求められているか」を
知ることにある。求人票には「必須スキル」と「歓迎スキル」が分かれており、
「必須」に書かれていることは最低限、「歓迎」に書かれていることは加点要素だ。

フロントエンドの求人票を読んでいると「React」「TypeScript」「レスポンシブデザイン」という
単語が繰り返し出てくる。これらが「現在の実態」だ。

**記入例(参考):**

| 職種名 | 主な仕事内容 | 主要技術 | 向いている人の特徴 |
|---|---|---|---|
| フロントエンド | ユーザーが操作する画面の実装・デザインとの連携 | HTML/CSS、JavaScript、React | デザインへの感度が高い、細部にこだわれる |
| バックエンド | API設計・DB設計・ビジネスロジックの実装 | Python/Go/Java、SQL、REST API | 設計思考が得意、データの整合性を重視できる |
| インフラ/SRE | クラウド構成・CI/CD・監視・障害対応 | AWS/GCP、Linux、Terraform | システム全体像を把握するのが好き、障害に冷静に対処できる |
| データエンジニア | データパイプライン構築・分析基盤整備 | Python、SQL、Spark、BigQuery | 数字を読むのが好き、地道な作業を厭わない |
| モバイル | iOS/Androidアプリ開発 | Swift、Kotlin、React Native | アプリを作って人に使ってもらうことが好き |

## 演習 1-B: 自分が興味を持てる分野 — 解答の評価基準

**良い回答の特徴:**

良い回答は「フロントエンドが好きだと思います」で終わらない。
「自分の○○という性格・○○という経験から、△△を作る仕事に惹かれる」という
**理由の連鎖**がある。

例:
```
私はデザインより、データを正確に処理することに関心があるため、
バックエンドが最も面白そうに感じた。
学生時代に表計算ソフトでデータ整理をするのが好きだったこともあり、
「見えない部分の仕組みを作る」仕事に共感できる。
```

**よくある回答の問題点:**
- 「全部やってみたい」→ 具体性がない。今は無理でも優先順位をつける練習をする
- 「まだわからない」→ わからなくてよいが、「現時点で最もピンとくるものはどれか」は答えられる

## 演習 1-C: 給与の実態調査 — 調べ方のポイント

**思考プロセス:**

**この演習に「正解の数字」は載せない。**載せた時点から古くなり、古い数字は無いより悪いからだ。読んだ人がそれを現在の相場だと信じてしまう。

この演習で身につけるのは金額ではなく、**数字の読み方**のほうだ。こちらは 20 年経っても使える。

給与の数字は「平均値」「中央値」「範囲」を区別することが重要だ。
「平均年収600万円」という数字は、200万円の人と1,000万円の人がいれば成り立つ。

調べた数字を見るときに確認すべきこと:

| 確認すること | なぜ |
|---|---|
| 平均値か中央値か | 平均は極端な値に引っ張られる。中央値のほうが実感に近いことが多い |
| 範囲はどれだけ広いか | 中央値だけでは、自分がどこに入るか分からない |
| サンプル数は十分か | 数十件では参考程度にしかならない |
| 地域は絞られているか | 東京と地方では大きく違う |
| 経験年数が混ざっていないか | 未経験と10年目を平均した数字に意味はない |
| いつのデータか | 3年前の数字は、もう現在の数字ではない |

**自分が調べた数字が、この6項目を満たしているか確認してほしい。**満たしていないなら、その数字はまだ判断材料にならない。

複数の情報源で調べて、**食い違ったときにその理由を説明できる**ようになれば、この演習の目的は達成されている。食い違いの理由は、たいてい上の6項目のどれかにある。

さらに詳しくは[キャリアと市場](../../../career-track/)を参照。

## 演習 1-D: エンジニアのキャリアストーリー — 読み方のポイント

**良い読み方:**

記事を「情報収集」として読むのではなく、「パターンの抽出」として読む。

よくあるパターン:
- 「最初の1〜2年は量をこなした」
- 「つまらないと思う仕事も、基礎を固めた」
- 「キャリアの転機はアウトプットした瞬間だった(ブログ、OSS貢献、登壇など)」

複数の記事を読んでいると、成功しているエンジニアに共通する行動パターンが見えてくる。
それが「再現性のある戦略」のヒントになる。

**批判的に読む視点:**

- この人の成功体験が自分に再現できるとは限らない
- 「運良くうまくいった」要素がどの程度あるか考える
- 失敗談や苦労話により多くの情報が含まれていることが多い

## 演習 1-E: 5年後のビジョン — 良い回答の条件

良いビジョンは「夢」ではなく「仮説」だ。
「こうなりたい、なぜなら現在の自分の○○からこの方向が合っていると思うから」
という論理がある。

5年後のビジョンを持つことの価値は「正確な予測」ではなく、
「今の学習の優先順位を決めるための基準」を得ることにある。

「フルスタックエンジニアとして小規模なチームで開発したい」という仮説があれば、
「まずフロントとバックの基礎を両方触る」という学習方針が導ける。

ビジョンは変わってよい。半年後に全く違うことを目指していても問題ない。
大切なのは「今日の自分にとって最も合理的な方針を持っている」ことだ。
