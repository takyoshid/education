## 演習 2-A: フェインマン技法 — 回答例

**お題: バージョン管理とは何か**

**回答例:**

```
作文を書くとき、「第1稿」「第2稿」「最終稿」とファイル名を変えて
何度も保存した経験があるだろう。バージョン管理とは、この「変更履歴を記録する仕組み」を
自動化したものだ。いつ・誰が・何を変えたかが記録されるため、
「ある時点の状態に戻す」「別の方向で試してみる」ことが安全に行える。
```

**採点基準:**

良い回答の条件:
- 技術用語(「コミット」「リポジトリ」など)を使っていない
- 日常生活の具体例が1つ以上ある
- 「なぜ便利か」が1文以上書かれている

**よくある失敗パターン:**

「バージョン管理とは、ソフトウェアのバージョンを管理するシステムです」
→ 定義の中に定義する単語が入っている。フェインマン技法の意味がない。

「Gitとは、コードの変更を記録するツールです」
→ 問いは「バージョン管理」であり「Git」ではない。概念とツールを混同している。

**自己評価の方法:**

書いた説明を本当に技術を知らない人に声に出して読んでみる。
「これで理解できる?」と聞いて「ここがわからない」と言われた箇所が、
自分がまだ理解できていない部分だ。

## 演習 2-B: 受動的学習 vs 能動的学習 — 分析

**なぜ差が生まれるのか**

受動的学習(ただ読む)では、脳は「処理した気分」になるが、実際には情報を
**符号化(encoding)**していない状態が多い。見た瞬間は「わかった」と感じるが、
何も見ずに再現しようとすると出てこない。

能動的学習(要約する、疑問を持つ、比喩を考える)では、脳が情報を「処理」している。
処理とは「既存の知識と関連付ける」「構造化する」「言い換える」といった行動を指す。

**振り返りで確認したいポイント:**

- ステップ1より ステップ2の方が、同じ5分でも「疲れた」感覚があるはず
  これは「脳が実際に働いた」証拠だ
- 能動的学習は最初は「大変で非効率に感じる」
  それが「本当の学習をしている感覚」だ
- 受動的学習の方が「楽で進んでいる気がする」
  これがチュートリアル地獄の感覚的な入り口だ

## 演習 2-C: フラッシュカード10枚 — 良いカードの基準

**良いカードの条件:**

1. 問い(表)が1つの概念に絞られている
2. 答え(裏)に「なぜそうなのか」の理由が含まれている
3. 覚えやすくするための比喩・例が1つある

**良いカードの例:**

```
[表] フロントエンドとバックエンドの違いは?
[裏] フロントエンドはユーザーが見る画面(HTML/CSS/JS)を担当。
     バックエンドはデータ処理・保存を担当。
     レストランで例えると: フロントは「ホール」、バックは「厨房」。
```

**悪いカードの例:**

```
[表] バックエンドとは?
[裏] バックエンドエンジニアのこと
```
→ 答えになっていない。「○○とは?」という問いには「○○とは△△のことだ。なぜなら…」という形で答える。

**カードを使うタイミング:**

- 作った当日: 全カードを一度確認する
- 翌日: 再度確認し、思い出せなかったカードをマーク
- 3日後: マークしたカードを重点的に確認
- 1週間後: 全カードを再確認

## 演習 2-D: チュートリアル地獄の特定 — 確認ポイント

**Q1. 典型的なパターンが見られる箇所:**

1. **「次は別のチュートリアルもやっておこう」という判断**
   1つ目が終わった時点で自分のプロジェクトに移るべきだった。
   「もっと学んでから作る」という発想がチュートリアル地獄の入り口。

2. **「Flaskの方がシンプルと聞いた」のでDjangoから切り替えた**
   「他のツールが良さそうに見える」という誘惑はチュートリアル地獄で頻繁に起きる。
   1つを終えてから次に移るべきであり、途中で切り替えると何も完成しない。

3. **「まだ知識が足りない」と判断して次のコースを探し始めた**
   「実際に何か作れないこと」の原因を「知識不足」に帰属させている。
   本当の原因は「アウトプットの経験不足」だ。知識をいくら増やしても解決しない。

**Q2. Aさんが今すぐ取るべき行動:**

「Lesson 02 の処方箋に従い、次のチュートリアルを探すのをやめて、
今ある知識で作れるものを1つ完成させる」

具体的には:
- ToDoリストアプリ、日記アプリなど、シンプルなものを1つ選ぶ
- チュートリアルを参照してよい。ただし「作りながら調べる」順序を守る
- 完成度より「完成させること」を優先する

**Q3. 「まだ知識が足りない」という判断が問題な理由:**

実際の開発で「知識が全部揃ってから始める」状況は存在しない。
常に「知らないことがある状態」で、調べながら進めることが開発の実態だ。

「知識不足」という診断は「もっと見ればできるようになる」という行動を誘発するが、
問題の本質は「詰まっても調べて解決する」という経験の不足にある。
この経験はチュートリアルをいくら増やしても得られない。

良い表現:「準備が整ったら始めるのではなく、始めながら準備する」
