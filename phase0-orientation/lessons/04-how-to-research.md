# Lesson 04: 情報の調べ方

## このレッスンで学ぶこと

- 公式ドキュメント(official documentation)の読み方と重要性
- 英語資料との向き合い方
- Stack Overflow の正しい使い方
- GitHub での情報収集
- 情報の信頼性を評価する方法

---

## 1. 情報源の信頼性ヒエラルキー

インターネット上のプログラミング情報は玉石混淆(ぎょくせきこんこう)だ。
古い情報、誤った情報、文脈が違う情報が大量に流通している。
情報源の信頼性を判断する能力は、エンジニアにとって必須スキルのひとつだ。

信頼性の高い順に並べると、おおよそ次のようになる。

```
1. 公式ドキュメント・仕様書(specification)
2. 公式GitHub リポジトリのソースコード・Issues
3. 公式ブログ・リリースノート(release notes)
4. 著名なエンジニアの技術ブログ(最終更新日要確認)
5. Stack Overflow(スコアと日付を確認)
6. Qiita / Zenn / はてなブログ(日付と著者の実績を確認)
7. ChatGPT / AI 生成コンテンツ(知識カットオフと誤りに注意)
```

**「有名そうなサイトに書いてあった」は信頼性の根拠にならない。**
常に「いつ書かれたか」「誰が書いたか」「公式の情報と一致するか」を確認する習慣をつける。

---

## 2. 公式ドキュメントの読み方

### 公式ドキュメントとは

プログラミング言語・ライブラリ・フレームワークを作った人たち自身が書いた、
最も正確で最新の情報源だ。英語で書かれていることが多く、初学者は敬遠しがちだが、
「読もうとしない習慣」こそが成長の上限を作る。

### ドキュメントの構造を理解する

多くの公式ドキュメントは次のような構造を持つ。

| セクション | 内容 |
|---|---|
| Getting Started / Quick Start | 最小限の動作例。初心者向け |
| Guides / Tutorials | 機能別のまとまった解説 |
| API Reference | 全関数・クラスの詳細仕様。辞書的に使う |
| Changelog | バージョンごとの変更点 |
| Examples | 実際の使用例 |

最初から全部読む必要はない。「今解決したい問題に関係するセクション」を見つけて
ピンポイントで読む。辞書を引くイメージだ。

### ドキュメントを読むコツ

**サンプルコード(sample code)を先に見る**

説明文を全部読む前に、まずサンプルコードの「入力と出力」を確認する。
多くの場合、そこに答えが凝縮されている。

**バージョンを確認する**

ドキュメントには必ずバージョンが書かれている。
自分が使っているバージョンと一致しているか確認する。
例えば Python 2 と Python 3 では同じ関数名でも動作が違う場合がある。

**用語の定義を追う**

「この単語はこのドキュメント内でどういう意味で使われているか」を意識する。
同じ単語でも分野によって意味が違うことがある。

## 3. 英語資料との向き合い方

### 英語を避けることのコスト

技術情報の大半は英語で発信される。これは変わらない事実だ。

- 最新のフレームワークのドキュメントはまず英語で公開される
- Stack Overflow の解決例の99%以上は英語
- GitHubの Issue・PR のコメントはほぼ英語
- 求人票のスキル要件は英語が増えている

日本語情報だけで学習しようとすると、情報が1〜2年遅れ、量も数十分の一になる。

### 英語が苦手でも読み進める方法

**技術英語は特殊だ**

技術ドキュメントで使われる英語は、日常英語より語彙が限定されていてパターン化されている。
実際に多用される表現は以下のような単語だ。

よく出る動詞: `returns`(〜を返す), `accepts`(〜を受け取る), `takes`(〜を引数にとる),
`throws`(例外を投げる), `initializes`(初期化する), `deprecated`(非推奨になった)

よく出る名詞: `argument`(引数), `parameter`(パラメータ), `instance`(インスタンス),
`callback`(コールバック), `middleware`(ミドルウェア), `payload`(ペイロード)

これらのパターンに慣れると、英語のドキュメントが格段に読みやすくなる。

**翻訳ツールを補助的に使う**

Google 翻訳や DeepL は「辞書的に使う」ツールとして有用だ。
ただし**訳文を鵜呑みにせず、原文と照らし合わせる**習慣をつける。
技術的な文脈では翻訳が不正確になることがある。

**段落単位で読む**

一言一句を完全に理解しようとすると止まってしまう。
まず段落全体の「大意」を把握し、詳細は必要に応じて確認する。

## 4. Stack Overflow の使い方

Stack Overflow(スタックオーバーフロー)はプログラミングに関するQ&Aサイトで、
世界最大の技術的Q&Aコミュニティだ。

### 検索の前に

Stack Overflow を開く前に、まず以下を試す:

1. エラーメッセージをそのままGoogle/Bing で検索する
2. `[言語名] [やりたいこと]` の形で検索する(例: `python read csv file`)
3. 公式ドキュメントのサイト内検索を使う

多くの場合、検索結果の上位に Stack Overflow のページが出てくる。

### Stack Overflow で回答を評価する方法

すべての回答を信じてはいけない。以下の基準で評価する。

**スコア(vote数)**
上向き矢印のスコアが高いほど、多くのエンジニアが有用と判断した回答だ。
マイナスのスコアがついている回答は問題がある可能性が高い。

**チェックマーク(accepted answer)**
質問者が「これで解決した」とマークした回答。ただし古い場合は最新のやり方でない可能性がある。

**日付**
技術情報は古くなる。特に2015年以前の回答は現在のバージョンでは動かない可能性がある。
スコアが高くても、日付が古い回答より、スコアはやや低くても最近の回答の方が正確なことがある。

**コメント欄**
回答に対するコメントに「これは動かない」「バージョン○○以降は△△を使うべき」などの
重要な補足情報が書かれていることがある。必ず確認する。

### Stack Overflow に質問を投稿する場合

質問を投稿するときは Lesson 03 の「良い質問テンプレート」に準拠した形にする。
さらに Stack Overflow では、問題を再現できる**最小限のコード(MRE: Minimal Reproducible Example)**
の提供が求められる。

MRE とは:
- 問題を再現するのに必要な**最小限**のコード
- 余分なコードを取り除いた状態
- コピーして実行すれば問題が再現できるもの

MRE を作る過程で問題が自己解決することもある。

## 5. GitHub での情報収集

GitHub(ギットハブ)は世界最大のコード管理・共有プラットフォームだ。
コードを管理するだけでなく、**情報収集ツール**としても非常に有用だ。

### Issue(イシュー)を読む

使っているライブラリのバグや疑問点を調べるとき、
その**公式 GitHub リポジトリ(repository)の Issues タブ**を確認する。

同じ問題を他のユーザーが既に報告していることが多く、
開発者のコメントや公式の対処法が書かれている。

検索方法: `is:issue is:open [キーワード]` または `is:issue is:closed [キーワード]`

### README を読む

ライブラリのリポジトリの `README.md` には、インストール方法・基本的な使い方・
注意点がまとめられている。ドキュメントより簡潔なことが多く、まず最初に読む価値がある。

### ソースコードを読む

中級者以降の話になるが、「ドキュメントに書いていない挙動」を確認するには
ソースコード自体を読むのが最終手段として有効だ。
「コードは嘘をつかない」というエンジニアの言葉はここから来ている。

## 6. AI(人工知能)ツールの使い方

ChatGPT や Claude などの AI アシスタントは強力な学習補助ツールだが、
**信頼性の高い情報源としてではなく、思考の補助として使う**のが正しい姿勢だ。

### AI が得意なこと

- 概念の説明(複数の視点・比喩でわかりやすく説明してくれる)
- コードの一般的なパターンの提示
- エラーメッセージの意味の解説
- ラバーダック的な壁打ち相手

### AI が苦手なこと・注意が必要なこと

- 最新ライブラリの最新バージョンの正確な情報(知識に期限がある)
- 細かい仕様の正確な情報(「もっともらしいが誤った情報」を生成することがある)
- 自分のコードベース固有の問題の解決(文脈を完全には把握できない)

**AI が生成したコードは必ず自分で読んで理解してから使う。**
意味を理解せずにコードを貼り付けることは、長期的には学習の妨げになる。

## 💡 コラム: 「その薬をください」と言う患者 — XY問題

医者に行って症状を説明する代わりに「この薬をください」とだけ言う患者がいたら、医者は困ってしまいます。もしその薬の選択が間違っていたら、本当の病気は治りません。

技術の質問サイトで最も嫌われるパターンがこれで、「XY問題」と呼ばれています。本当に解決したい問題(Y)があるのに、自分が思いついた解決策(X)についてだけ質問してしまう。「ファイル名の末尾3文字を取る方法は?」と聞く人の本当の目的が「拡張子を取りたい」なら、正解は全く別の方法(拡張子が4文字の場合も動く方法)かもしれません。

調べるときも聞くときも、まず「自分が本当に解決したい問題は何か」を一段上に戻って言語化する習慣が、回り道に見えて最短ルートです。

## まとめ

- 情報源には信頼性のヒエラルキーがある。公式ドキュメントを最初に参照する習慣をつける
- 英語ドキュメントは「技術英語の語彙」を覚えることで読みやすくなる。避けない
- Stack Overflow では「スコア」「日付」「コメント欄」を必ず確認する
- GitHub の Issues や README は重要な情報源だ
- AI ツールは「思考の補助」として使い、生成されたコードは必ず自分で理解する

---

## 確認問題

1. 信頼性のヒエラルキーに従って、公式ドキュメントと技術ブログのどちらを先に参照すべきか、
   その理由とともに説明してください。
2. Stack Overflow の回答を評価するときに確認する3つのポイントを挙げてください。
3. 「MRE(Minimal Reproducible Example)」とは何か説明し、なぜ重要なのかを述べてください。
4. AI ツールを使う際に注意すべき点を2つ挙げてください。
5. 技術英語でよく使われる動詞を3つ、その意味とともに挙げてください。
