# Lesson 03: 問題解決とデバッグの思考法

## このレッスンで学ぶこと

- 問題解決の一般的なフレームワーク
- 15分ルールとその根拠
- デバッグ(debugging)の体系的なアプローチ
- 質問の仕方: 良い質問と悪い質問の違い
- 良い質問テンプレートの使い方

---

## 1. エンジニアの仕事の大部分は「問題解決」だ

コードを書く時間より、「なぜ動かないのか」「どう設計すべきか」を考える時間の方が長い、
というのがエンジニアの実態だ。

初学者のうちは「正しいコードを書くこと」が課題に見えるが、
実際には「問題を正確に定義し、原因を特定し、解決策を検証する」という
思考プロセスが核心にある。

---

## 2. 問題解決の4ステップ

数学者ジョージ・ポリア(George Pólya)が著書 "How to Solve It" で提唱した問題解決の枠組みは、
プログラミングにも完全に当てはまる。

### ステップ1: 問題を理解する(Understand)

エラーが出たとき、多くの初学者はすぐに「直し方」を探す。
しかしまず「**何が起きているのか**」を正確に把握することが先だ。

確認すべきこと:
- エラーメッセージ(error message)は何と言っているか
- どの行(line)でエラーが出ているか
- 「期待している動作」と「実際の動作」の差は何か

### ステップ2: 計画を立てる(Plan)

「どこから調べるか」「何を確認するか」の仮説を立てる。

例えば:
- 「最後に変更したのは○○の行だから、そこが原因かもしれない」
- 「同じ処理が他の場所では動いているから、入力値の問題かもしれない」

根拠のない試行錯誤を繰り返すより、仮説を立ててから検証する方が圧倒的に速い。

### ステップ3: 実行する(Execute)

仮説に基づいて変更・確認を行う。一度に多くの箇所を変えない。
変更は**1箇所ずつ**行い、それぞれ結果を確認する。
複数箇所を同時に変えると、どの変更が効果的だったか判別できなくなる。

### ステップ4: 振り返る(Review)

問題が解決したら、「なぜ解決したのか」を必ず理解する。
「なんとなく直った」は最悪のパターンだ。同じ問題が起きたとき、また迷子になる。

解決した内容をメモに残す習慣をつけると、将来の自分が助かる。

## 3. 15分ルール

### ルールの内容

詰まったとき、**まず15分間は自力で解決を試みる**。
15分経っても解決の糸口が見えなければ、他者に質問する。

### なぜ15分か

**15分未満で諦めること**の問題:
- 自力で考える力が育たない
- 「少し考えればわかった問題」でも質問してしまい、周囲の時間を奪う
- 試行錯誤の経験が蓄積されず、応用力が身につかない

**15分以上こだわりすぎること**の問題:
- 時間を無駄にする(解決できない問題を1人で考え続けても非効率)
- 行き詰まりによるモチベーション低下
- 「知らない」という状態に気づかないまま進んでしまう

15分という数字は絶対ではないが、「すぐに諦める」「いつまでも1人で抱える」の
両方の罠を避けるための目安として機能する。

### 15分間に何をするか

1. エラーメッセージ全文をコピーして検索する
2. 公式ドキュメント(official documentation)を確認する
3. 問題を小さく分解して、どこまでは動くか確認する
4. 同じ処理を別の書き方で試す
5. コメントアウト(comment out)して問題の範囲を絞り込む

## 4. デバッグ(Debugging)の体系的アプローチ

「バグ(bug)」の語源は、1947年にハーバード大学のコンピュータの内部で
本物の虫(蛾)が回路に挟まり誤動作したことに由来する。

デバッグは芸術ではなく、体系的に行うことができる技術だ。

### デバッグの基本テクニック

**プリントデバッグ(Print Debugging)**

最もシンプルで有効な手法。コードの各所に `print()` や `console.log()` などで
変数の値を出力し、「どこまでは期待通りに動いているか」を確認する。

```
処理A → 出力:OK
処理B → 出力:OK
処理C → 出力:おかしい値が出ている  ← バグはここかその前
処理D → エラー
```

このように「二分探索(binary search)」の要領で、問題の範囲を半分ずつ絞り込む。

**ラバーダックデバッグ(Rubber Duck Debugging)**

机の上のラバーダック(ゴムのアヒル)に向かってコードを声に出して説明すると、
バグが見つかることが多いという経験から生まれた手法。

相手はアヒルでもAIでも紙に書く行為でもよい。「誰かに説明しようとすること」で、
「なんとなく理解していた」部分の矛盾が浮かび上がる。

**仮定を確認する(Check Your Assumptions)**

バグの多くは「こうなっているはずだ」という思い込みが原因だ。

例えば:
- 「この変数には数値が入っているはず」→ 実際は文字列(string)だった
- 「この関数は呼ばれているはず」→ 実際は呼ばれていなかった
- 「この条件は真(true)のはず」→ 実際は偽(false)だった

「はず」という言葉が頭に浮かんだら、それを実際に確認するのがデバッグの鉄則だ。

**変更を最小化する**

動いていたコードが急に動かなくなった場合、「最後に何を変更したか」を振り返る。
バージョン管理(version control)ツール(Git)を使っていれば差分(diff)を確認できる。
これがGitを使う重要な理由の一つだ。

## 5. 質問の仕方

### 良い質問が重要な理由

「バカな質問はない」という言葉があるが、**質問の仕方**によって回答の質は大きく変わる。
良い質問は相手の時間を節約し、問題解決を速め、自分の信頼性を高める。

さらに重要なのは、良い質問を書こうとする過程で問題が解決することが多い、という事実だ。
これを**ラバーダック効果**とも呼ぶ。

### 悪い質問の例

```
「エラーが出ます。助けてください」
```

これでは回答者は何もわからない。以下の情報が欠けている:
- どのようなコードを書いているか
- どのようなエラーが出ているか
- 何を試みたか
- 何を期待していたか

### 良い質問の構成要素

1. **何をしようとしているか(目的)**: 大目標・小目標
2. **何が起きているか(現象)**: エラーメッセージの全文
3. **何を期待していたか(期待値)**: こう動くはずだった
4. **何を試みたか(試行履歴)**: ○○を調べた、△△を試した
5. **環境情報(environment)**: OS、言語バージョン、フレームワークのバージョン
6. **関連するコード**: 問題の再現に必要な最小限のコード

### 良い質問テンプレート

```
【状況】
○○を実装しようとしています。具体的には、××という処理を行いたいです。

【問題】
以下のエラーが発生しています。
（エラーメッセージ全文をここに貼る）

【期待していた動作】
本来は△△という結果になるはずでした。

【試みたこと】
1. □□を確認した(結果: ◇◇だった)
2. ■■を試した(結果: ◆◆になった)
3. 公式ドキュメントの○○のページを確認した

【環境】
- OS: macOS 14.x / Windows 11
- 言語バージョン: Python 3.12
- その他: （関連するライブラリとバージョン）

【関連コード】
（問題を再現する最小限のコードをここに貼る）
```

### 質問する場所

| 場所 | 向いている質問 |
|---|---|
| Stack Overflow | 技術的な質問。検索してもない場合 |
| GitHub Issues | 特定のライブラリ・ツールのバグ疑い |
| 公式ドキュメント | まず最初に確認する場所 |
| Discord/Slack コミュニティ | 特定技術のコミュニティに参加している場合 |
| ChatGPT / Claude | ラバーダック的な使い方、概念の理解補助 |

AIに質問する場合も、上記のテンプレートに従って情報を整理して渡すと、
回答の質が劇的に上がる。

## 6. 「わからない」と認識すること

「わからないことがわかる」ことは高度なスキルだ。

初学者のうちは「わかっていないことに気づかない」状態(無意識的無能)が最も危険だ。
「この概念は理解できていない」と明確に認識できれば、学習すべき箇所が特定できる。

詰まったとき「自分はバカだ」と思う必要はない。
詰まることは「ここが理解不足だ」という具体的な情報を得ているということだ。
それは進歩の証拠でもある。

## 💡 コラム: アヒルのおもちゃに話しかけるプログラマー

世界中の開発者の机に、ゴム製のアヒルが置かれていることがあります。飾りではありません。「ラバーダック・デバッグ」という由緒ある問題解決法の道具です。

名著『達人プログラマー』で紹介されたこの手法は、**行き詰まったらアヒル(何でもいい)に向かって、問題を声に出して最初から説明する**というもの。不思議なことに、説明している途中で「…あれ、ここおかしくない?」と自分で気づくことが非常に多いのです。

なぜ効くのか。頭の中の「分かっているつもり」は曖昧さを許しますが、言語化は曖昧さを許さないからです。同僚に質問を書いている途中で自己解決する現象も同じ原理です。つまり: **問題を正確に説明できた時点で、問題は半分解けています。**

---

## まとめ

- 問題解決は「理解→計画→実行→振り返り」の4ステップで行う
- 15分ルールで「すぐ諦める」と「いつまでも1人で抱える」の両方を避ける
- デバッグはプリントデバッグ・仮定の検証・範囲の絞り込みで体系的に行う
- 良い質問を書くために情報を整理する過程で、問題が自己解決することも多い
- 「わからない」と認識できることは、成長の前提条件だ

## 確認問題

1. 問題解決の4ステップを順番に説明してください。
2. 15分ルールはなぜ「15分未満」でも「15分以上」でも問題があるのですか?
3. プリントデバッグとは何か、具体的な使い方とともに説明してください。
4. 「良い質問テンプレート」に含まれる6つの要素を列挙してください。
5. 「仮定を確認する」というデバッグ手法が重要な理由を説明してください。
