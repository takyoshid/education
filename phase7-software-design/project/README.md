# 総仕上げプロジェクト: レガシーコードのリファクタリング

## プロジェクト概要

このプロジェクトでは、意図的に問題を仕込んだレガシーコード(legacy/)を、
テストを書きながら安全にリファクタリングする総仕上げ課題に取り組みます。

**レガシーコードとは**: 動くが、設計上の問題を抱えているコード。
テストがなく、変更が怖い状態のコードを指すことが多い。

Phase 7 で学んだ全ての技術を組み合わせて使います:
- コードスメルの発見と命名
- SOLID原則の適用
- デザインパターンの選択
- テストを先に書いてから安全にリファクタリング
- ADRによる設計判断の記録

## 進め方 (重要: この順番で進めること)

### Step 1: レガシーコードを読む

`legacy/` の3ファイルを読み、以下を書き出す:

1. **コードスメルのリスト**: 何という名前のスメルか
2. **SOLID違反のリスト**: どの原則に違反しているか
3. **テストが書きにくい理由**: どの外部依存が問題か

### Step 2: テストを書く (変更前)

**リファクタリングの黄金律: テストを先に書く**

まず `legacy/` のコードをそのまま呼び出すテストを書く。
これが「安全網」になる。リファクタリング後もこのテストが通ることで、
振る舞いが壊れていないことを保証できる。

```bash
mkdir -p project/tests_for_legacy
# project/tests_for_legacy/test_legacy.py を作成する
pytest project/tests_for_legacy/ -v
```

### Step 3: 小さなステップでリファクタリング

`refactored/` に新しい実装を作っていく。
1回の変更は小さくし、その都度テストが通ることを確認する。

```
変更 → pytest → 全グリーン → 次の変更
                ↓
             失敗したらすぐに変更を戻す
```

### Step 4: ADRを書く

リファクタリングで行った主要な設計判断を ADR に記録する。
最低1つは書くこと。

```
refactored/adr/001-layered-architecture.md
```

## 評価基準

### 必須 (Phase 7 修了条件)

- [ ] `legacy/` の全ファイルに対してテストを書いた
- [ ] 書いたテストが全て通る
- [ ] リファクタリング後のコードでも同じテストが通る
- [ ] 発見したコードスメルを3つ以上名前をつけて挙げられる
- [ ] ADRを最低1つ書いた

### 発展 (余力がある場合)

- [ ] 依存性注入(DI)を使って DB/メール依存を切り離した
- [ ] 型ヒントが全ての公開関数・メソッドに付いている
- [ ] テストカバレッジ(coverage)が主要なビジネスロジックで80%以上
- [ ] リファクタリング後のモジュール間依存がレイヤードアーキテクチャに従っている

### テストカバレッジの確認方法

```bash
pip install pytest-cov
pytest refactored/tests/ --cov=refactored --cov-report=term-missing
```

## ヒント: 問題のある箇所の目安

`legacy/order_system.py`:
- 1つの関数が注文処理・メール送信・DB保存を全て行っている
- 認証情報がハードコードされている
- テストするためには DB とメールサーバーが必要

`legacy/user_manager.py`:
- 神クラス(God Class)になっている
- 複数の責務が混在している
- 外部サービスへの直接依存がある

`legacy/report_generator.py`:
- 出力フォーマットとデータ収集が混在している
- 同じ分岐ロジックが複数箇所にある
- マジックナンバーが使われている

## 参考解答について

`refactored/` には参考解答が含まれています。
**必ず自分で試してから確認してください。**

参考解答は「唯一の正解」ではありません。
設計には複数の正しいアプローチがあります。
自分の解答と参考解答の違いを考察することが最も大きな学びになります。
