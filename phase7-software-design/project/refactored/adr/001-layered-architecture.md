# ADR-001: レイヤードアーキテクチャと Repository パターンを採用する

- **日付**: 2024-06-01
- **ステータス**: Accepted
- **決定者**: Phase 7 総仕上げプロジェクト

---

## 背景

リファクタリング前のレガシーコード (`legacy/`) は以下の問題を持っていた:

1. `proc()` (注文処理)、`gen_rep()` (レポート生成) が、ビジネスロジック・DB操作・外部サービス通知を1つの関数に混在させていた
2. `UserManager` クラスが認証・メール送信・レポート・アバター管理の責務を持つ神クラスになっていた
3. SQLite への直接依存がビジネスロジックと分かちがたく結合しており、ユニットテストを書くためにDBが必要だった
4. `smtplib` や `requests` が関数の途中でインポートされ、テスト時に実際のサーバーへの接続が発生していた

これらの問題を解決しつつ、将来の変更に対応できる構造を設計する必要があった。

## 検討した選択肢

1. **レイヤードアーキテクチャ (Layered Architecture) + Repository パターン**: モデル層・リポジトリ層・サービス層・フォーマット層に分割
2. **ヘキサゴナルアーキテクチャ (Hexagonal / Ports & Adapters)**: ポートとアダプターで外部依存を明示的に分離
3. **最小限のリファクタリング**: 関数を分割するだけで、アーキテクチャは変えない

## 決定

**レイヤードアーキテクチャ + Repository パターン**を採用する。

```
┌────────────────────────────────┐
│  formatters.py (出力フォーマット) │  ← 表示の責務
├────────────────────────────────┤
│  services.py (ビジネスロジック)   │  ← ビジネスルールの責務
├────────────────────────────────┤
│  repositories.py (データアクセス) │  ← 永続化の責務
├────────────────────────────────┤
│  models.py (データモデル)        │  ← データ表現の責務
└────────────────────────────────┘
```

依存方向は上から下へのみ。下の層が上の層を知ることはない。

## 理由

**Repository パターンを選んだ理由**:
- サービス層が `OrderRepository (抽象)` に依存することで、テスト時は `InMemoryOrderRepository` を渡すだけでDBなしのテストが書ける
- 将来 SQLite から PostgreSQL に移行するとき、`SQLiteOrderRepository` を `PostgreSQLOrderRepository` に差し替えるだけでサービス層を変更しなくてよい

**ヘキサゴナルアーキテクチャを選ばなかった理由**:
- 現在の規模(3ファイル程度)に対しては過剰な複雑さになる
- 学習教材として、より一般的なレイヤードアーキテクチャの方が理解しやすい
- ヘキサゴナルアーキテクチャが解決する問題(複数の入出力ポート)が現時点では存在しない

**最小限リファクタリングを選ばなかった理由**:
- 関数分割だけでは外部依存の問題(テスト時にDBやメールサーバーが必要)が解決しない
- 設計の問題は「コードが大きくなるほど修正コストが指数関数的に増える」ため、早期に解決する価値がある

## トレードオフ

### メリット

- **テスタビリティ**: DB・メール・HTTP などの外部依存をインメモリ実装に差し替えてテストできる。テストが速く、CI環境での実行が容易になる
- **変更の局所化**: DB実装を変えるときはリポジトリ層のみ、ビジネスルールを変えるときはサービス層のみを変更すればよい
- **責務の明確化**: 「このバグはどの層にあるか」を絞り込みやすくなる

### デメリット・リスク

- **ファイル数の増加**: 元の3ファイルが `models.py`、`repositories.py`、`services.py`、`formatters.py` と4ファイルになる。小規模プロジェクトでは過剰に感じることもある
- **抽象クラスの導入コスト**: `ProductRepository`、`OrderRepository` などの抽象クラスを理解するコストが発生する
- **学習コスト**: 依存性注入(DI)に不慣れなメンバーには最初の理解コストが必要

### 軽減策

- ディレクトリ構成と各ファイルの役割を README に記録する (このADRがその役割を担う)
- テストコードを見ることで「DIがどのように使われるか」を学べるようにする

このADRは「参考解答がなぜこの構造を選んだか」を説明するために書いた。

あなた自身のリファクタリングで異なる設計を選んだ場合、それが間違いとは限らない。
重要なのは「なぜその設計を選んだか」を説明できることである。
