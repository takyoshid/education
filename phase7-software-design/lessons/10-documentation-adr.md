## 1. ドキュメントはなぜ腐るのか

コードが変わっても、ドキュメントは自動では更新されません。
これが「ドキュメントの腐敗(documentation rot)」と呼ばれる問題です。

```
コード変更 → テストが失敗 → 開発者が気づく  (テストは腐敗しない)
コード変更 → ドキュメント更新忘れ → 誰も気づかない (ドキュメントは腐敗する)
```

### 対策の原則: コードに近いほど腐敗しにくい

腐敗しにくい順番:

1. **型ヒント(type hints)**: コードそのもの。静的解析ツールで検証可能
2. **docstring**: コードと同じファイルにある。読んだとき目に入る
3. **コードコメント**: コードと同じ行・ブロックにある
4. **README.md**: リポジトリにあるが、コードと別ファイル
5. **外部Wiki/Confluence**: コードから完全に分離。最も腐敗しやすい

「コードを読めば分かること」は極力コードに表現し、ドキュメントの量を減らすことが根本的な対策です。

## 2. 型ヒントとdocstring

### 型ヒント(type hints)の正しい使い方

Python 3.12以降の型ヒント記法:

```python
# 悪い: 型情報がない
def calculate_discount(price, rate, is_member):
    ...

# 良い: 引数と戻り値の型が明確
def calculate_discount(
    price: int,
    rate: float,
    is_member: bool,
) -> int:
    ...
```

複雑な型:

```python
from typing import Optional
from collections.abc import Sequence


# Optional: None になりうる場合
def find_user_by_email(email: str) -> Optional["User"]:
    ...


# list, dict, set は小文字で書ける (Python 3.9+)
def filter_active_users(users: list["User"]) -> list["User"]:
    ...


# ユニオン型 (Python 3.10+)
def parse_id(raw: str | int) -> int:
    ...
```

型ヒントはドキュメントではなく「実行可能な仕様」です。
`mypy` や `pyright` で静的にチェックできます。

```bash
pip install mypy
mypy your_module.py
```

### docstringの書き方

docstringは「関数・クラスの契約(contract)」を記述します。
「何をするか」「何を受け取るか」「何を返すか」「何が起きうるか」の4点です。

#### Google スタイル(推奨)

```python
def transfer_money(
    from_account_id: str,
    to_account_id: str,
    amount: int,
) -> "TransferResult":
    """2つの口座間で送金を行う。

    送金元の残高が不足している場合は例外を送出する。
    同一口座間への送金は許可しない。

    Args:
        from_account_id: 送金元の口座ID。形式: "ACC-XXXXXXXX"
        to_account_id: 送金先の口座ID。形式: "ACC-XXXXXXXX"
        amount: 送金額(円)。1以上の整数。

    Returns:
        送金結果を含む TransferResult オブジェクト。
        transaction_id、実行日時、手数料を含む。

    Raises:
        InsufficientBalanceError: 送金元の残高が amount を下回る場合。
        SameAccountError: from_account_id と to_account_id が同一の場合。
        AccountNotFoundError: いずれかの口座IDが存在しない場合。

    Example:
        >>> result = transfer_money("ACC-00000001", "ACC-00000002", 10000)
        >>> result.transaction_id
        'TXN-20240101-001'
    """
    ...
```

#### docstringを書く基準

全ての関数に書く必要はありません。次の基準で判断します。

| 書くべきケース | 書かなくてよいケース |
|--------------|-------------------|
| 公開API(外部から呼ばれる関数・クラス) | 名前で自明な内部ヘルパー |
| 副作用がある | ロジックが1行で完結する |
| 例外を送出する | テストコードの補助関数 |
| 引数に制約がある(範囲、形式など) | |
| 戻り値の構造が複雑 | |

## 3. READMEの構成

プロジェクトのREADMEには、次の5項目を含めます。

```markdown
# プロジェクト名

## 概要 (What)
このプロジェクトが何をするものか、1〜3文で説明する。

## セットアップ (How to run)
ゼロから動かすまでの手順。コマンドは全てコピペで動くものを書く。

## 使い方 (How to use)
最も典型的な使い方を例示する。

## アーキテクチャ (Why this structure)
なぜこの構造になっているかを説明する。ディレクトリ構成の意味。

## 開発者向け情報 (How to contribute)
テストの実行方法、コーディング規約へのリンク。
```

**アンチパターン**: 何ヶ月も前のインストール手順だけ書いてある。機能は増えているのにREADMEは最初のまま。

対策: READMEの更新をPRチェックリストに含める。

## 4. ADR(Architecture Decision Record)とは

ADRは「なぜそのアーキテクチャ上の決定をしたか」を記録する短い文書です。

### なぜADRが必要か

「なぜこの設計にしたのか」という問いに答えられる人は、時間とともに減っていきます。

- 担当者がチームを離れる
- 数ヶ月後に自分自身が忘れる
- 新しいメンバーが「なぜこうなっているか」を理解できない

その結果、何が起きるか:

```
新メンバー: 「このORMなんで使ってるんですか? 標準のSQLAlchemyじゃダメなんですか?」
古参メンバー: 「なんか昔の人がそう決めたらしくて…」
→ 変更できるのかできないのかも分からないまま手が止まる
```

ADRがあると:

```
新メンバー: 「このORMなんで使ってるんですか?」
古参メンバー: 「docs/adr/004-orm-selection.md を見てください」
→ 背景・理由・トレードオフが記録されている
→ 「当時の制約は今も有効か」を判断して再検討できる
```

## 5. ADRテンプレート

```markdown
# ADR-{番号}: {タイトル}

- **日付**: YYYY-MM-DD
- **ステータス**: Proposed / Accepted / Deprecated / Superseded by ADR-XXX
- **決定者**: {名前またはチーム名}

---

## 背景(Context)

この決定が必要になった背景・状況を説明する。
読者はこのプロジェクトを知っているが、この決定の経緯は知らない前提で書く。

## 検討した選択肢(Considered Options)

1. **選択肢A**: 〜
2. **選択肢B**: 〜
3. **選択肢C**: 〜

## 決定(Decision)

「選択肢A を採用する」のように一文で明記する。

## 理由(Rationale)

なぜその選択肢を選んだかを説明する。
他の選択肢を選ばなかった理由も書く。

## トレードオフ(Consequences)

### メリット
- 〜

### デメリット・リスク
- 〜

### 軽減策(Mitigation)
デメリットをどう軽減するか。

## 関連リンク

- 参照したドキュメント、Issue、PRのリンク
```

## 6. ADRの実例

### 実例1: テストフレームワークの選定

```markdown
# ADR-001: テストフレームワークとして pytest を採用する

- **日付**: 2024-03-15
- **ステータス**: Accepted
- **決定者**: バックエンドチーム

---

## 背景

新プロジェクトのテストフレームワークを決定する必要がある。
現在チームには Python の経験者が3名おり、標準ライブラリの
unittest を使っているメンバーと pytest を使っているメンバーが混在している。

## 検討した選択肢

1. **unittest**: Python 標準ライブラリ。追加インストール不要。
2. **pytest**: サードパーティ。豊富なプラグイン、簡潔な記法。
3. **nose2**: pytest の代替。コミュニティが縮小傾向。

## 決定

pytest を採用する。

## 理由

- フィクスチャ(fixture)の仕組みが柔軟で、テストの依存関係を
  宣言的に管理できる
- `assert` 文をそのまま使え、assertEqual / assertTrue などの
  メソッド名を覚える必要がない
- pytest-cov、pytest-mock など、必要なプラグインが充実している
- チームの過半数がすでに pytest の経験を持つ

nose2 は選ばない理由: コミュニティが縮小しており、長期的なメンテナンス
が不安。現時点で pytest に対するアドバンテージがない。

## トレードオフ

### メリット
- テストコードが簡潔になる
- フィクスチャによる依存関係の管理が明確
- CIでのレポート出力が充実している

### デメリット・リスク
- 追加依存が1つ増える
- pytest 固有の概念(conftest.py, fixture スコープ)を学ぶコストがある

### 軽減策
- 初回スプリントでハンズオン勉強会を実施する

## 関連リンク

- [pytest 公式ドキュメント](https://docs.pytest.org/)
- Issue #42: テスト基盤の選定
```

### 実例2: データアクセス層の設計

```markdown
# ADR-002: データアクセス層に Repository パターンを採用する

- **日付**: 2024-04-02
- **ステータス**: Accepted
- **決定者**: アーキテクチャレビュー会

---

## 背景

現在のコードベースでは、ビジネスロジック(サービス層)が
SQLAlchemy の ORM モデルを直接操作している。
その結果:
- ビジネスロジックのテストに DB が必要になっている
- DB を PostgreSQL から別のものに変えた場合、サービス層の
  コードを全て変更しなければならない

## 検討した選択肢

1. **現状維持(Active Record パターン)**: モデルが自分自身をDBに保存する
2. **Repository パターン**: データアクセスを専用クラスに隔離する
3. **CQRS(Command Query Responsibility Segregation)**: 読み取りと書き込みを分離

## 決定

Repository パターンを採用する。

## 理由

- サービス層のテストで DB モックが使えるようになり、テストが速くなる
- DB の実装をサービス層から隠蔽できるため、将来のDB変更影響を局所化できる
- CQRS は現時点の規模では過剰。チームの習熟コストに見合わない

## トレードオフ

### メリット
- サービス層の単体テストが DB なしで書ける
- DB変更の影響範囲が Repository 実装クラスのみに限定される

### デメリット・リスク
- ファイル数が増える(各エンティティに Repository クラスが必要)
- ORM の機能(遅延ロードなど)を Repository 経由で使うのが難しくなる場合がある

### 軽減策
- 複雑なクエリは Repository 内にカプセル化し、サービス層から
  DB 固有の知識を排除する

## 関連リンク

- Lesson 05: アーキテクチャ入門(レイヤードアーキテクチャの解説)
- PR #78: UserRepository の初期実装
```

## 7. どの決定をADRに記録するか

全ての技術的決定を記録する必要はありません。以下の基準で判断します。

### 記録すべき決定

- **後から覆すコストが高いもの**: フレームワーク選定、DB選定、言語選定
- **チームで議論して決めたもの**: コーディング規約、ブランチ戦略
- **直感に反する選択**: 「なぜ一般的でない方法を選んだのか」が自明でないもの
- **既存のベストプラクティスからあえて外れるもの**

### 記録しなくてよい決定

- コードレビューで当然分かるもの
- 簡単に変更できるもの(変数名、関数分割など)
- 業界標準に従っているだけのもの

### 判断の目安: 「6ヶ月後の新メンバーが読んで『なぜ?』と思うか」

思うなら書く。思わないなら書かない。

## 8. ADRのライフサイクル

ADRのステータスは変化します。

```
Proposed → Accepted → Deprecated
                    ↘ Superseded by ADR-XXX
```

- **Proposed**: 検討中。まだ決定していない
- **Accepted**: 採用。現在有効な決定
- **Deprecated**: 廃止。理由は残すが、もう有効ではない
- **Superseded**: 別のADRに置き換えられた

**重要**: ADRは「上書き」しません。古い決定を変更するときは新しいADRを作成し、
古いADRに「Superseded by ADR-XXX」と記載します。
これにより、「いつ、なぜ方針が変わったか」の経緯が残ります。

## 9. ドキュメンテーションのトレードオフ

ドキュメントは「書けば良い」ではありません。適切な量と場所を判断することが重要です。

| ドキュメントの種類 | メリット | デメリット |
|-----------------|---------|-----------|
| 型ヒント | 静的検証可能、腐敗しにくい | 複雑な型は記述が冗長になる |
| docstring | コードと一体、IDEで表示される | 更新漏れリスク |
| ADR | 「なぜ」を永続記録できる | 書くコスト、読む習慣がないと意味がない |
| 外部Wiki | 整形自由、検索しやすい | コードと乖離しやすい |

### 実用的な方針

1. 「何をするか」はコード(型ヒント・命名)で表現する
2. 「なぜそうするか」はdocstringかコメントで書く
3. 「なぜこの設計にしたか」はADRで記録する
4. 外部Wikiは「コードを読まなくても概要を把握したい人向け」に絞る

---

## 💡 コラム: チェスタトンの柵 — 「なぜ」を記録する理由

作家 G.K. チェスタトンが1929年に書いた思考実験があります。道の真ん中に、**何のためにあるのか分からない柵**が立っている。改革者が「無意味だから撤去しよう」と言うと、賢者はこう答える — 「**理由が分からないなら、撤去させるわけにはいかない。立てた理由が分かったときに、初めて撤去を許可しよう。**」柵は誰かが理由があって立てたはずで、理由を知らずに壊すと、柵が防いでいた問題(牛の脱走かもしれない)が再来するからです。

コードベースは「理由の分からない柵」だらけです。「この謎の sleep(1) は消していい?」「なぜ標準ライブラリを使わず自前実装している?」— 理由を知らずに撤去して、柵が防いでいた障害を再発させるのは、開発現場の日常です。

ADR(Architecture Decision Record)は、**未来のチームへの「柵の設置理由メモ」**です。コードは「何をしているか」を語れますが、「**なぜこうしたか、なぜ他の道を選ばなかったか**」は文書にしか残せません。半年後、その文書の最大の読者はあなた自身です。

---

## まとめ

| 概念 | 要点 |
|------|------|
| ドキュメントの腐敗 | コードと離れるほど腐敗しやすい。コードで表現できることはコードで書く |
| 型ヒント | 実行可能な仕様。mypy で検証できる |
| docstring | 公開APIと副作用・例外を持つ関数に書く |
| ADR | 「なぜそうしたか」を記録する。後から覆せない決定に使う |
| ADRのライフサイクル | 上書きせず新しいADRを作成する |
