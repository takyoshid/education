# 総仕上げ: 既存サービスの分散設計を読み解き、自分の設計を書く

このプロジェクトには「模範解答」がありません。分散設計に唯一の正解が無いためです。代わりに、**判断の質**を検証する手順を示します。

## 目的

- 実在するシステムの設計判断を読み解き、なぜそう決めたかを説明できるようになる
- 自分のサービスについて、レプリケーション・パーティション・整合性・キャッシュを設計する
- 設計を第三者にレビューしてもらい、指摘に応答する

---

## Part 1: 既存システムを読み解く(2〜3日)

次から 1 つ選び、公開されている設計文書・技術ブログ・障害報告書を読んでください。

| 対象 | 読むべきもの |
|---|---|
| PostgreSQL のレプリケーション | 公式ドキュメントの High Availability 章 |
| Cassandra / DynamoDB | Dynamo 論文、公式の一貫性モデルの説明 |
| Kafka | 公式ドキュメントの Replication と Delivery Semantics |
| etcd / ZooKeeper | 公式ドキュメントの運用ガイド(推奨ノード数とその理由) |
| 任意の大規模サービス | 公開されている**ポストモーテム(障害報告書)** |

**ポストモーテムを読むことを特に勧めます。** 設計文書は「うまくいく話」しか書きませんが、障害報告書には「前提が崩れた瞬間」が書かれています。

### 提出物: `analysis.md`

- そのシステムが選んだ整合性モデルと、その代償
- パーティション方式と、リバランスの扱い
- 「この設計が壊れるのはどんなときか」を自分の言葉で
- 読んでいて**理解できなかった箇所**とその調査結果

最後の項目を必ず書いてください。分からなかったことを記録するのは、Phase 0 で学んだ学習法の実践です。

---

## Part 2: 自分のサービスを設計する(1週間)

[Phase横断プロジェクト](../../longitudinal-project/)の Learning Hub、または自分のキャップストーンを対象にします。

**「今のままで十分」という結論も正解です。** その場合は、なぜ十分なのかを数字で示してください(Lesson 01 の「まず分散しない」)。

### 想定する成長シナリオ

現在の 1000 倍の規模になったと仮定します。

```
利用者   : 100人 → 10万人
データ   : 10万件 → 1億件
書き込み : 1 req/s → 1000 req/s
地域     : 日本のみ → 日本・北米・欧州
```

### 提出物: `docs/decisions/adr-distributed.md`

Phase 7 の ADR 形式で書きます。

```markdown
# ADR-00X: 学習セッションデータの分散方針

## 状況
（何が問題になっているか。数字で）

## 決定
（何を選んだか）

## 理由
（なぜそれか。他の選択肢を退けた理由）

## 捨てたもの
（この決定で失うもの。明示すること）

## 見直す条件
（どうなったらこの決定を再検討するか。数値で）
```

最低 4 本の ADR を書いてください。

1. レプリケーション構成
2. パーティション方針(または「分割しない」判断)
3. 機能ごとの整合性の選択
4. キャッシュ戦略と、キャッシュ全損時の挙動

### 提出物: `capacity.md`

- 各操作の想定 req/s
- キャッシュヒット率の想定と、その根拠
- **キャッシュが全損したときに DB が受ける負荷**
- 各地域への応答時間の理論下限

## Part 3: 障害演習(2〜3日)

設計だけでは終わりません。**動くもので確かめます。**

Phase 8 の Docker Compose 環境、または Phase 12 の Reliable Worker を拡張して、次のうち **2 つ以上**を実際に再現してください。

| 障害 | 再現方法の例 |
|---|---|
| replication lag | follower への反映を意図的に遅らせる |
| ネットワーク分断 | コンテナのネットワークを切断する |
| キャッシュ全損 | Redis を停止し、DB の負荷を計測する |
| ホットスポット | 特定キーへ負荷を集中させる |
| フェイルオーバー | leader コンテナを停止し、切り替え時間を測る |

### 提出物: `postmortem.md`

Phase 8 と同じ形式で書きます。

- タイムライン(何時何分に何が起きたか)
- 利用者から何が見えたか
- 検知できたか。できなかったなら何を追加すべきか
- 復旧に要した時間
- 再発防止策

## 第三者レビュー(必須)

この Phase の成果物は、**自己評価だけで合格にしません。**

メンター、学習仲間、勉強会の参加者など、最低 1 人にレビューを依頼してください。レビュアーには次を聞いてもらいます。

```
1. この設計が壊れるのはどんなときですか
2. なぜ他の選択肢ではなくこれを選んだのですか
3. これを運用するのに、どんな監視が必要ですか
4. 予算が半分になったら、どこを削りますか
```

### 提出物: `review.md`

- 指摘された内容
- 採用したもの／却下したものと、その理由
- 修正したコミット
- 再検証の結果

**「答えられなかった質問」も必ず記録してください。** それがあなたの次の学習項目です。

---

## 評価の観点

| 観点 | 見るところ |
|---|---|
| 判断の根拠 | 「流行っているから」ではなく、要件と数字から導かれているか |
| **捨てたもの**の明示 | トレードオフを認識しているか |
| 過剰設計の回避 | 必要ないものを入れていないか。「分散しない」判断ができているか |
| 障害への具体性 | 「気をつける」ではなく、仕組みで防いでいるか |
| 実測 | 推測ではなく、動かして数字を出したか |
| 説明可能性 | 第三者の質問に答えられたか |

**最も重視するのは、最初と最後の項目です。**設計は他人に説明できて初めて価値を持ちます(Lesson 06 のコラム、Raft の教訓)。
