# Phase 13: 分散システムの基礎 (Distributed Systems)

> 推奨受講時期: **Phase 8 修了後、Phase 9 の前**。Phase 番号は追加順を表し、学習順ではありません。

1 台では収まらなくなったとき、システムは複数のノードに分かれます。そこから先は、これまでの常識が通用しません。**関数呼び出しが「成功」でも「失敗」でもなく「結果不明」を返し、ノードは死んだのか遅いだけなのか区別できず、時計は互いにずれています。**

この Phase では、その世界で正しく動くシステムの作り方を学びます。

## 🌟 旅の始まりに: 「分散システムとは、あなたが存在すら知らなかったコンピュータの故障によって、自分のコンピュータが使えなくなるようなシステムである」

これは Leslie Lamport の言葉です。彼は論理時計、Paxos、Byzantine 将軍問題といった、この分野の基礎の多くを作った人物であり、その功績でチューリング賞を受賞しています。

この定義の辛辣さに注目してください。分散システムの本質を、**利点ではなく被害の形で**述べています。あなたが名前も知らない、地球の裏側にあるサーバーが 1 台不調になっただけで、あなたのサービスが止まる。それが分散システムです。

なぜそんなものを作るのか。答えは単純で、**それ以外に方法がないから**です。1 台のコンピュータには限界があります。1 台のコンピュータは壊れます。そして 1 台のコンピュータは、東京とロンドンの両方には置けません。

だから人類は、壊れるものを大量に並べて、全体としては壊れないシステムを作る方法を探してきました。それは「速いプログラムの書き方」とはまったく別の技術です。**「壊れることを前提に、それでも正しさを保つ」技術**です。

Lamport は別のところでこうも書いています。

> **「分散システムの理論の多くは、『何が不可能か』を明らかにすることに費やされてきた。」**

この Phase でもそれは同じです。あなたはここで、たくさんの「できないこと」を学びます。ネットワーク越しに確実な合意は取れない。故障と遅延は区別できない。一貫性と可用性は両立しない。

落胆する必要はありません。**何ができないかを正確に知っている人だけが、できることを設計できます。**できないことを知らない人は、できるつもりで作り、本番で学ぶことになります。その授業料は、たいてい非常に高くつきます。

## 学習目標

- 分散する理由と、分散が持ち込む本質的な難しさ(部分障害)を説明できる
- レプリケーションの 3 方式を使い分け、replication lag の異常に対処できる
- 整合性モデルを操作ごとに選び、CAP と PACELC で議論できる
- パーティショニングの方式を選び、ホットスポットとリバランスに対処できる
- キャッシュ戦略と、キャッシュ由来の障害(stampede など)を設計できる
- クォーラムと合意アルゴリズムの役割を理解し、**自前実装を避ける判断**ができる

## 前提

- **Phase 6**(API と DB)、**Phase 8**(インフラ・クラウド)を修了していること
- **Phase 12**(並行処理と信頼性)を修了していること — 冪等性・retry・timeout がこの Phase の土台です

> Phase 12 を飛ばしてここに来ないでください。この Phase の内容の半分は、Phase 12 で学ぶ「二将軍問題」「冪等性」「backoff と jitter」の、規模を拡大した応用です。

## 進め方

この Phase では、**設計判断とその根拠**を言語化する訓練をします。各レッスンの後、次の形式でメモを残してください。

```
決定    : 在庫の引当は単一 leader への条件付き UPDATE で行う
理由    : 売り越しが業務上許容できないため
捨てたもの: 拠点ローカルでの書き込み(遅延が増える)
見直す条件: 書き込みが毎秒 5000 を超えたら再検討する
```

これは Phase 7 で学ぶ ADR (Architecture Decision Record) の形式であり、Phase 10 のシステム設計面接でそのまま使えます。**「何を選んだか」より「何を捨てたか」を言えることが評価されます。**
