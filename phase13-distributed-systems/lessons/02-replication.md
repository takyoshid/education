# Lesson 02: レプリケーション (Replication)

## 学習目標

- single-leader / multi-leader / leaderless の違いと適用場面を説明できる
- 同期レプリケーションと非同期レプリケーションのトレードオフを判断できる
- replication lag が生む 3 つの異常を挙げ、対策を選べる
- フェイルオーバーで何が失われうるかを説明できる

---

## 1. なぜ複製するのか

同じデータを複数のノードに持つことを **レプリケーション (replication)** と呼びます。理由は 3 つです。

| 理由 | 内容 |
|---|---|
| **可用性** | 1 台が壊れても、別の複製が応答できる |
| **読み取りスケール** | 読み取りを複数ノードに分散できる |
| **地理的近接** | ユーザーの近くに複製を置いて遅延を減らす |

**書き込みはスケールしません。** すべての複製に書く必要があるので、書き込み量が増えれば全ノードの負荷が増えます。書き込みをスケールさせたいならパーティショニング(Lesson 04)が必要です。

> **重要**: レプリケーションはバックアップではありません。`DELETE FROM users;` を実行すれば、その削除も全複製へ忠実に複製されます。**バックアップ(過去の時点を復元できること)は別に必要です。**

## 2. Single-Leader レプリケーション

最も広く使われる方式です。PostgreSQL、MySQL、MongoDB、多くの RDB がこれを採用しています。

```
            書き込み
               ↓
        ┌─────────────┐
        │   Leader    │  (primary / master)
        │  (書き込み可) │
        └──────┬──────┘
               │ 変更ログを転送
        ┌──────┼──────┐
        ▼      ▼      ▼
   ┌────────┐    ┌────────┐
   │Follower│    │Follower│   (replica / standby)
   │(読取専用)│    │(読取専用)│
   └────────┘    └────────┘
        ▲             ▲
        └── 読み取り ──┘
```

ルールは単純です。

- **書き込みは必ず leader へ**
- **読み取りはどのノードでもよい**
- leader は変更を **replication log** として follower へ送る

「書き込みは 1 か所」という制約により、**書き込みの順序が一意に決まります**。これが正しさの土台です。Phase 12 で見た「直列化点を 1 つ作る」の、システム規模での適用です。

### 同期 vs 非同期

leader は、follower の適用を**待つ**か**待たない**かを選べます。

```
同期レプリケーション
  Client → Leader → Follower ─┐
                   ←──── ack ─┘
         ← OK                        ← follower に届いてから応答

非同期レプリケーション
  Client → Leader
         ← OK                        ← 即座に応答
                  → Follower         ← 後から送る
```

| | 同期 | 非同期 |
|---|---|---|
| 書き込み遅延 | 遅い(往復が加わる) | 速い |
| データ損失 | leader 障害でも失わない | **失いうる** |
| 可用性 | follower が落ちると**書けなくなる** | follower が落ちても書ける |

**両方は取れません。**これが Lesson 03 の CAP 定理につながります。

### 準同期 (semi-synchronous)

実務でよく使われる折衷案です。**1 台だけ同期、残りは非同期**にします。

```
Leader ──同期──▶ Follower1   (この 1 台が追いつくのを待つ)
       ──非同期─▶ Follower2
       ──非同期─▶ Follower3
```

「少なくとも 2 台にはデータがある」ことを保証しつつ、全台を待つコストは払いません。同期先が落ちたら、別の follower を同期先に昇格させます。

## 3. Replication lag が生む 3 つの異常

非同期レプリケーションでは、follower が leader から遅れます。これを **replication lag** と呼びます。平常時は数ミリ秒ですが、負荷が高いときは数秒〜数分になります。

この遅れが、ユーザーから見て「おかしい」挙動を生みます。

### 異常 1: Read-your-writes の破れ

```
ユーザーがコメントを投稿
  → Leader に書き込み ✓
  → 画面をリロード
  → Follower から読む(まだ複製されていない)
  → 【自分のコメントが消えている】
```

自分が書いたものが自分に見えない。ユーザーは必ずバグだと思います。

**対策**:

| 手法 | 内容 |
|---|---|
| 自分の書き込みは leader から読む | 「自分のプロフィール」は常に leader |
| 書き込み後 N 秒は leader から読む | 単純で効果的 |
| 書き込み位置を記録して追いつきを待つ | 正確だが実装が重い |

### 異常 2: Monotonic reads の破れ

```
1回目の読み取り → Follower1 (最新) → コメントが見える
2回目の読み取り → Follower2 (遅れ) → コメントが消えている
                                      【時間が巻き戻った】
```

複数の follower にランダムに振り分けると起きます。

**対策**: 同じユーザーは常に同じ follower に振り分ける(ユーザー ID のハッシュで固定)。

### 異常 3: Consistent prefix reads の破れ

因果関係のある書き込みが、順序を入れ替えて見えることがあります。

```
実際の順序:
  Aさん「今日の天気は?」
  Bさん「晴れです」

観測される順序:
  Bさん「晴れです」        ← 先に見える
  Aさん「今日の天気は?」    ← 後から見える
```

会話が成立しません。パーティションをまたぐと起きやすくなります。

**対策**: 因果関係のある書き込みを同じパーティションに置く、または因果順序を追跡する(Lesson 03)。

> **判断のしかた**: これらは「直す/直さない」の二択ではありません。**どの異常が業務上許容できないか**を決めるのが設計です。SNS の「いいね」の数が数秒古くても誰も困りませんが、銀行残高が巻き戻ったら大問題です。

## 4. フェイルオーバー — leader が落ちたとき

leader の障害時に、follower の 1 台を新しい leader に昇格させることを **フェイルオーバー (failover)** と呼びます。ここが分散システムで最も事故が起きる場面です。

```
1. leader の障害を検知する      ← タイムアウトで判断(誤判定しうる)
2. 新しい leader を選ぶ         ← 最も進んだ follower を選ぶ
3. システムを再構成する         ← 全員に新 leader を伝える
```

### 何が起きうるか

**① 非同期レプリケーションでは、書き込みが失われる**

まだ複製されていなかった変更は、新 leader には存在しません。旧 leader が復帰したとき、そのデータをどうするか。多くのシステムは**破棄**します。「成功」と応答したはずの書き込みが消えます。

**② 誤検知による split-brain**

Lesson 01 で見たとおり、「遅い」と「死んだ」は区別できません。旧 leader が実は生きていた場合、**2 つの leader** ができます。

対策: 新 leader が立ったら旧 leader を強制的に停止する(**fencing** / STONITH)。過半数の合意を必要とする(Lesson 06)。

**③ タイムアウト値のジレンマ**

```
短すぎる → 一時的な負荷スパイクで不要なフェイルオーバーが起きる
          → フェイルオーバー中は書けないので、可用性が下がる
          → 負荷が高いときほど、さらに悪化する
長すぎる → 本当に落ちたときの復旧が遅れる
```

**正解の値はありません。**システムの特性から選び、実際にフェイルオーバー訓練を行って調整します。

> **実務での原則**: **フェイルオーバーは、平時に訓練していなければ本番で必ず失敗します。** Phase 8 の障害演習と同じで、「動くはず」の仕組みは動きません。定期的に手動で切り替えて、手順と所要時間を記録してください。

## 5. Multi-Leader と Leaderless

### Multi-Leader

複数のノードが書き込みを受け付けます。データセンターをまたぐ構成や、オフライン編集を許すアプリで使われます。

```
[DC 東京]  Leader ⇄ Leader  [DC ロンドン]
              ↓        ↓
          Follower  Follower
```

利点は、各拠点でローカルに書けること(低遅延、拠点が孤立しても書ける)。

**代償は書き込み競合です。**

```
東京で   : title を "A" に変更
ロンドンで: title を "B" に変更   ← 同時刻
              ↓
        どちらが正しい?
```

解決策と、それぞれの問題:

| 手法 | 内容 | 問題 |
|---|---|---|
| Last Write Wins (LWW) | タイムスタンプが新しい方を採用 | **データが黙って消える**。時計のずれで誤判定 |
| バージョンベクトル | 競合を検出してアプリに渡す | アプリ側で解決ロジックが必要 |
| CRDT | 数学的に自動マージできるデータ型 | 表現できるデータ構造が限られる |
| アプリで解決 | ユーザーに選ばせる | UX の設計が必要 |

**LWW は手軽ですが、データを失います。**「後勝ち」で消えた側の書き込みは、成功と応答されていたのに存在しなくなります。使う前に、それが許容できるか確認してください。

### Leaderless

Dynamo、Cassandra、Riak が採用する方式です。leader を置かず、**クライアントが複数ノードへ直接読み書き**します。

```
書き込み: N 台中 W 台が成功したら OK
読み取り: N 台中 R 台から読んで、最新のものを採用

  W + R > N   ならば、読み取りは必ず最新の書き込みを含む
```

**クォーラム (quorum)** と呼ばれる考え方です。

```
N=3, W=2, R=2 の場合:  W + R = 4 > 3 ✓
  書き込んだ 2 台と、読んだ 2 台は必ず 1 台以上重なる
  → 最新の値が必ず読み取り結果に含まれる

  [1][2][3]
   W  W        ← 書いた
      R  R     ← 読んだ
      ↑ ノード2が重なる
```

W や R を小さくすると速く・可用になり、大きくすると一貫性が上がります。**パラメータで一貫性を調節できる**のがこの方式の特徴です。

ただし `W + R > N` は万能ではありません。ノード障害や並行書き込みがあると、古い値を読むことがあります。厳密な保証が必要なら Lesson 06 の合意アルゴリズムが必要です。

## 6. どれを選ぶか

```
まず single-leader を選ぶ
   ├─ 書き込みが 1 台に収まらない?      → パーティショニング (Lesson 04)
   ├─ 複数拠点でローカルに書きたい?      → multi-leader (競合解決を設計する)
   └─ 可用性を最優先し、一貫性を調節したい → leaderless
```

**迷ったら single-leader です。**理解しやすく、運用実績が豊富で、多くの問題を最初から回避できます。multi-leader と leaderless は「必要になったときだけ」選んでください。

## 💡 コラム: 「11 個の 9」— 失われないことを設計で買う

Amazon S3 は、オブジェクトの耐久性 (durability) を **99.999999999%(9 が 11 個)** と公称しています。1000 万個のオブジェクトを預けて、1 個失うのに 1 万年かかる計算です。

この数字はどこから来るのでしょうか。魔法ではありません。**複製の数と、故障の独立性の掛け算**です。

S3 は、1 つのオブジェクトを最低 3 つのアベイラビリティゾーン(物理的に分離されたデータセンター群)へ複製します。各 AZ は独立した電源、独立した冷却、独立したネットワークを持ちます。**同時に壊れる理由が無いように、意図的に設計されている**のです。

ディスク 1 本の年間故障率を仮に 2% とします。3 本すべてが同じ年に壊れる確率は、故障が独立なら 0.02³ = 0.0008%。さらに S3 は故障を検知すると即座に複製を作り直すので、「3 本同時」ではなく「復旧が完了する前に 3 本」でなければなりません。この時間窓は数十分です。こうして 9 が 11 個並びます。

ここに重要な前提があります。**「故障が独立であること」**です。この前提が崩れると、計算は一瞬で無意味になります。

- 3 本とも同じロットのディスクなら、同じ時期に同じ理由で壊れます
- 3 本とも同じラックにあれば、そのラックの電源で全滅します
- 3 つとも同じ AZ にあれば、その AZ の火災で全滅します
- そして **3 つとも同じ `DELETE` コマンドを受け取れば、忠実に全部消えます**

最後の 1 行が、この Phase で最も覚えてほしいことです。**レプリケーションが守るのは「ハードウェアの故障」だけであり、「人間の操作ミス」や「アプリのバグ」からは何も守りません。**

2017年、GitLab のエンジニアが本番データベースのディレクトリを誤って削除したとき、5 種類あったはずのバックアップ機構が**すべて機能していませんでした**。復旧に使えたのは、たまたま 6 時間前に取られていた検証用のスナップショットだけでした。彼らはこの顛末を包み隠さず公開し、業界全体の教訓になりました。

**「複製がある」は「バックアップがある」ではありません。**そして「バックアップがある」は「復元できる」ではありません。復元を試したことがないバックアップは、存在しないのと同じです。

あなたが次にレプリケーションを設定するとき、必ず自分に聞いてください。**「今、間違って全部消したら、どこから戻せますか?」**

## まとめ

- レプリケーションの目的は**可用性・読み取りスケール・地理的近接**。書き込みはスケールしない
- **レプリケーションはバックアップではない**。削除も忠実に複製される
- **single-leader** が第一選択。書き込み順序が一意に決まることが正しさの土台
- 同期は「失わないが遅く、follower 障害で書けなくなる」、非同期は「速いが失いうる」
- replication lag は **read-your-writes / monotonic reads / consistent prefix** の 3 異常を生む
- どの異常が業務上許容できないかを決めるのが設計
- **フェイルオーバーは最も事故が起きる場面**。書き込み損失、split-brain、タイムアウト値のジレンマ
- **平時に訓練していないフェイルオーバーは本番で失敗する**
- multi-leader は書き込み競合の解決が必須。**LWW はデータを黙って失う**
- leaderless は `W + R > N` のクォーラムで一貫性を調節する

## 確認問題

1. レプリケーションで書き込みがスケールしないのはなぜですか。
2. 「レプリカが 3 つあるからバックアップは不要」という主張に反論してください。
3. 同期レプリケーションで follower が 1 台落ちると何が起きますか。準同期はこれをどう解決しますか。
4. read-your-writes が破れる状況を具体的に説明し、対策を 2 つ挙げてください。
5. あなたのサービスで、replication lag による 3 つの異常のうち、最も許容できないものはどれですか。理由も述べてください。
6. フェイルオーバーの検知タイムアウトを短くした場合と長くした場合の弊害を、それぞれ述べてください。
7. Last Write Wins の問題点は何ですか。それでも使ってよいのはどんな場面ですか。
8. N=5 のクラスタで、読み取りが必ず最新を含むための W と R の組み合わせを 2 つ挙げてください。
