## 1. データベースとは

**データベース(Database)** はデータを整理して保存・検索・更新できるシステムです。

「ファイルに保存すればいいのでは？」と思うかもしれません。しかしファイルには以下の問題があります。

| 問題 | データベースでの解決 |
|------|---------------------|
| 複数人が同時に書き込むとデータが壊れる | トランザクションによる排他制御 |
| データが増えると検索が遅くなる | インデックスによる高速化 |
| 関連するデータの整合性が保てない | 外部キー制約 |
| プログラムがクラッシュするとデータが消える | WAL(書き込み前ログ)による耐障害性 |

### データベース管理システム(DBMS)

データベースを管理するソフトウェアを **DBMS(Database Management System)** と呼びます。

主な DBMS：

| DBMS | 特徴 |
|------|------|
| SQLite | ファイル 1 つで動く。組み込み・開発用 |
| PostgreSQL | 高機能・高性能。本番環境に多く使われる |
| MySQL / MariaDB | Web アプリで広く使われる |
| Microsoft SQL Server | Windows 環境・企業向け |

このフェーズでは **SQLite** を使います。インストール不要でファイル 1 つで動くため、学習に最適です。

## 2. リレーショナルデータベース(RDB)

**リレーショナルデータベース(Relational Database)** は、データを**テーブル(表)**の形式で管理するデータベースです。

### テーブルの構成

```
users テーブル

id  | name     | email              | created_at
----|----------|--------------------|--------------------
 1  | 田中太郎  | taro@example.com   | 2024-01-15 10:00:00
 2  | 鈴木花子  | hanako@example.com | 2024-01-16 09:30:00
 3  | 佐藤次郎  | jiro@example.com   | 2024-01-17 14:00:00
```

用語の整理：

| 用語 | 別名 | 説明 |
|------|------|------|
| テーブル(Table) | リレーション | データの種類を表す表 |
| 行(Row) | レコード、タプル | 1件のデータ |
| 列(Column) | フィールド、属性 | データの項目 |
| 値(Value) | セル | 行と列の交点 |

---

## 3. 主キーと外部キー

### 主キー(Primary Key)

テーブルの各行を**一意に識別**するための列です。

```
id  | name     | email
----|----------|-------
 1  | 田中太郎  | ...    ← id=1 は世界に1つだけ
 2  | 鈴木花子  | ...    ← id=2 は世界に1つだけ
```

主キーの特性：
- NULL(空)にできない
- 重複できない
- テーブルにつき 1 つ

多くの場合、連番の整数(`id`)を主キーにします。これを **サロゲートキー(代理キー)** と呼びます。

### 外部キー(Foreign Key)

他のテーブルの主キーを参照する列です。テーブル間の**関係(リレーションシップ)** を表します。

```
posts テーブル

id  | user_id | title              | body
----|---------|--------------------|---------
 1  |    1    | Python入門          | ...
 2  |    1    | FastAPIチュートリアル | ...
 3  |    2    | SQLの基礎           | ...
     ↑
     これが外部キー: users テーブルの id を参照
```

外部キーの効果：
- 存在しない `user_id` を持つ投稿を作れなくする(参照整合性)
- ユーザーを削除するときに、そのユーザーの投稿をどうするか指定できる(CASCADE DELETE など)

## 4. テーブル間の関係

### 1対1(One-to-One)

1つのレコードが相手テーブルの1つのレコードと対応する。

```
users テーブル          user_profiles テーブル
id | name              user_id | bio    | avatar_url
---|------             --------|--------|----------
 1 | 田中太郎           1       | ...    | ...
 2 | 鈴木花子           2       | ...    | ...
```

使い所: メインのテーブルにはよく使う情報、サブのテーブルにはたまにしか使わない情報を分ける。

### 1対多(One-to-Many)

1つのレコードが相手テーブルの複数のレコードと対応する。最もよく使われる関係。

```
users(1) --- posts(多)
1人のユーザーは多数の投稿を持てる
1つの投稿は必ず1人のユーザーに属する
```

```
users テーブル          posts テーブル
id | name              id | user_id | title
---|------             ---|---------|------
 1 | 田中太郎           1  |    1    | Python入門
                       2  |    1    | FastAPI入門  ← user_id=1 が2件
```

### 多対多(Many-to-Many)

複数のレコードが相手テーブルの複数のレコードと対応する。

```
articles(多) --- tags(多)
1つの記事は複数のタグを持てる
1つのタグは複数の記事に付けられる
```

多対多は**中間テーブル(Junction Table)**を使って表現します。

```
articles          article_tags(中間テーブル)   tags
id | title        article_id | tag_id         id | name
---|------        -----------|--------        ---|------
 1 | Python入門   1          | 1              1  | Python
 2 | SQL入門      1          | 2              2  | 初心者
                 2          | 2              3  | データベース
                 2          | 3
```

## 5. データ型

SQLite で使える主なデータ型：

| 型 | 説明 | 例 |
|----|------|-----|
| INTEGER | 整数 | 1, -5, 1000 |
| REAL | 浮動小数点数 | 3.14, -0.5 |
| TEXT | 文字列 | "田中太郎", "taro@example.com" |
| BLOB | バイナリデータ | 画像データなど |
| NULL | 値なし | NULL |

PostgreSQL などではより多くの型があります：

| 型 | 説明 |
|----|------|
| VARCHAR(n) | 最大 n 文字の文字列 |
| BOOLEAN | 真偽値 |
| DATE | 日付 |
| TIMESTAMP | 日時 |
| DECIMAL(p, s) | 精度指定の小数(金額に使う) |
| JSON / JSONB | JSON データ |
| UUID | UUID |

## 6. 正規化(Normalization)

**正規化**は、データの重複を排除してデータの整合性を保ちやすいテーブル構造にする作業です。

### 正規化していない例(非正規形)

```
orders テーブル(問題あり)

id | customer_name | customer_email      | product_name | product_price | quantity
---|---------------|---------------------|--------------|---------------|--------
 1 | 田中太郎       | taro@example.com    | リンゴ        | 100           | 3
 2 | 田中太郎       | taro@example.com    | バナナ        | 50            | 5
 3 | 鈴木花子       | hanako@example.com  | リンゴ        | 100           | 2
```

問題点：
- 田中太郎のメールが変わったら複数行を更新しなければならない(更新異常)
- 田中太郎の注文がすべて消えると、田中太郎の情報も消える(削除異常)
- 商品を追加するだけなら注文を作らなければならない(挿入異常)

### 第1正規形(1NF)

**ルール**: 各セルには1つの値のみ。繰り返しグループを排除する。

```
# 問題あり: 1つのセルに複数の値
id | name   | phone_numbers
---|--------|---------------------------
 1 | 田中   | 090-1234-5678, 03-1234-5678

# 1NF 後
id | name   | phone_type | phone_number
---|--------|------------|-------------
 1 | 田中   | mobile     | 090-1234-5678
 1 | 田中   | home       | 03-1234-5678
```

### 第2正規形(2NF)

**ルール**: 1NF を満たし、かつすべての非キー列が主キー全体に依存している。

(複合主キーを持つテーブルに適用されることが多い)

### 第3正規形(3NF)

**ルール**: 2NF を満たし、かつ非キー列が他の非キー列に依存していない(推移的関数従属の排除)。

```
# 問題あり: zip_code → prefecture(都道府県)という依存関係がある
orders テーブル
id | customer_id | zip_code | prefecture
---|-------------|----------|-----------
 1 |           1 | 150-0001 | 東京都
 2 |           2 | 530-0001 | 大阪府

# 3NF 後: zip_code のデータを別テーブルに
zip_codes テーブル
zip_code | prefecture
---------|----------
150-0001 | 東京都
530-0001 | 大阪府

orders テーブル
id | customer_id | zip_code
---|-------------|----------
 1 |           1 | 150-0001
 2 |           2 | 530-0001
```

### 先ほどの例を正規化する

```
非正規形のテーブルを3つに分割

customers テーブル
id | name   | email
---|--------|--------------------
 1 | 田中太郎 | taro@example.com
 2 | 鈴木花子 | hanako@example.com

products テーブル
id | name   | price
---|--------|------
 1 | リンゴ  | 100
 2 | バナナ  | 50

orders テーブル
id | customer_id | product_id | quantity
---|-------------|------------|--------
 1 |      1      |     1      | 3
 2 |      1      |     2      | 5
 3 |      2      |     1      | 2
```

## 7. ER 図(Entity-Relationship Diagram)

**ER 図**はテーブル(エンティティ)とその関係を視覚的に表したものです。

### シンプルなブログシステムの ER 図

```
[users]
 PK id          INTEGER
    name        TEXT
    email       TEXT UNIQUE
    password    TEXT
    created_at  TIMESTAMP
      |
      | 1
      |
      * (多)
[posts]
 PK id          INTEGER
 FK user_id     INTEGER  → users.id
    title       TEXT
    body        TEXT
    published   BOOLEAN
    created_at  TIMESTAMP
      |
      | 1
      |
      * (多)
[comments]
 PK id          INTEGER
 FK post_id     INTEGER  → posts.id
 FK user_id     INTEGER  → users.id
    body        TEXT
    created_at  TIMESTAMP

[posts] *---* [tags]  (中間テーブル: post_tags)
[post_tags]
 FK post_id     INTEGER  → posts.id
 FK tag_id      INTEGER  → tags.id

[tags]
 PK id          INTEGER
    name        TEXT UNIQUE
```

## 8. テーブル設計のチェックリスト

- [ ] 各テーブルに主キーがある
- [ ] 各列に適切なデータ型が設定されている
- [ ] NULL を許容する列と許容しない列が適切に設定されている
- [ ] UNIQUE 制約が必要な列に設定されている(メールアドレスなど)
- [ ] 外部キーが適切に設定されている
- [ ] 第3正規形(3NF)を満たしているか確認した
- [ ] `created_at` / `updated_at` カラムがある(後で必ず必要になる)

---

## まとめ

- RDB はデータをテーブルで管理し、テーブル間の関係を外部キーで表す
- 主キーは各行を一意に識別する。外部キーはテーブル間の参照整合性を保つ
- テーブル間の関係は「1対1」「1対多」「多対多」の 3 種類
- 多対多は中間テーブルで表現する
- 正規化によりデータの重複を排除し、更新・削除・挿入の異常を防ぐ

## 確認問題

1. 「1 人のユーザーは複数の注文を持ち、1 つの注文には複数の商品が含まれる」というシステムのテーブル設計を考えてください。必要なテーブルと主キー・外部キーを書いてください。
2. 外部キー制約の役割を説明してください。外部キーがない場合、どのような問題が起きますか？
3. 正規化を「やりすぎる」とどのような問題が起きますか？(パフォーマンスの観点から考えてください)
4. `created_at` と `updated_at` カラムをほぼすべてのテーブルに追加することが推奨される理由を説明してください。

## よくある間違い

**主キーにビジネスデータを使う**
メールアドレスや社員番号を主キーにすると、それが変わったときに全ての外部キーを更新しなければなりません。連番の整数(`id`)や UUID を主キーにしましょう。

**NULL と空文字を混同する**
NULL は「値が存在しない」、空文字は「空の文字列という値が存在する」です。意味が異なります。設計時にどちらを使うか明確にしてください。

**正規化を全く考慮しない**
正規化を怠ると、データの更新時に複数の場所を変更しなければならず、不整合が生じやすくなります。少なくとも 3NF を意識した設計を心がけてください。
