# Phase 9: ソフトウェア設計・テスト・クリーンコード

> **これは「並走 Phase」です。番号の位置で一度に終わらせるものではありません。**
>
> **Lesson 01・02・07・08・09 は Phase 2 修了後から始めてください。**読みやすい関数の書き方、テストの書き方、リファクタリング、コードレビューは、**コードを書き始めた日から効きます。**7つ先の Phase まで待つ理由がありません。
>
> SOLID・デザインパターン・アーキテクチャは、システムを何本か作った後に読んでください。**設計に失敗した経験がないと、原則の必要性が分かりません。**詳細は下の「受講時期」を参照してください。
>
> 同じ進み方をする Phase が他に 2 つあります([Phase 3](../phase3-dev-tools/) Git、[Phase 4](../phase4-ai-era/) AI活用)。

## 概要

このPhaseでは、「動くコード」を「良いコード」に育てる技術を学びます。
コードは一度書いたら終わりではありません。読まれ、修正され、拡張されます。
良い設計とテストは、その変化に耐えるコードを作る技術です。

## 🌟 旅の始まりに: 巨匠は、バグの発見者に小切手を送る

『The Art of Computer Programming』の著者ドナルド・クヌースは、計算機科学の巨匠中の巨匠です。その彼には有名な習慣があります。**自著の誤りを発見した読者に、報奨金の小切手を送る**のです(金額は1つにつき $2.56 — 「16進数の1ドル」つまり256セント、という数学ジョーク)。

面白いのはここからです。受け取った人のほとんどは**小切手を換金しません。額に入れて壁に飾る**のです。「クヌースの本の誤りを見つけた」という証明は、お金よりはるかに名誉だからです。

彼が開発した組版システム TeX のバージョン番号は、更新のたびに 3.14、3.141、3.1415…と**円周率に近づいていきます**(完成 = π になる日、という美学)。

世界最高の完璧主義者でさえ「自分の作るものには必ず誤りがある」という前提に立ち、発見者に報い、検証に対して世界に開かれている — これが Phase 9 で学ぶ「品質の文化」の極北です。良い設計・良いコードとは、才能の披露ではなく、誤りと共存するための誠実な技術なのです。

## 受講時期 — なぜ分散させるのか

このPhaseを番号の位置まで丸ごと待つのは、**設計上の誤りでした。**

「読みやすい関数を書く」「テストを書く」「リファクタリングする」は、Phase 2 でコードを書き始めた日から必要になります。実際、Phase 2 の模範解答には「Phase 9 のカプセル化と同じ発想」「Phase 9 のテストしやすい設計に直結します」といった記述が繰り返し出てきます。**学習者はすでにここにぶつかっているのに、7つ先まで待たされていました。**

一方で、SOLID やアーキテクチャを最初に読んでも身につきません。**設計に失敗した経験がないと、原則が解決している問題が見えない**からです。原則だけ暗記した状態は、かえって有害な設計を生みます。

そこで、**前提が揃ったレッスンから順に始めます。**

| レッスン | いつ始めるか | なぜその時期か |
|---|---|---|
| **01** 良いコードとは<br>**02** 関数・クラス設計 | **Phase 2 修了後** | 書き始めた日から効く。早いほどよい |
| **07** TDD実践<br>**08** リファクタリング技法 | **Phase 2 修了後** | Phase 2 で `pytest` を学んだ直後が最適。手が動くうちに習慣にする |
| **09** コードレビュー | **Phase 3 修了後** | Pull Request が使えるようになってから |
| **06** テスト戦略 | Phase 6 または 7 の途中 | UI と API の両方を書いてから。何をどの層でテストするかは、層が複数ないと考えられない |
| **03** SOLID原則<br>**04** デザインパターン | **Phase 7 修了後** | 中規模のシステムを1本作ってから。変更に苦しんだ経験が前提 |
| **05** アーキテクチャ入門 | **Phase 8 修了後** | 並行処理と障害を知ってから |
| **10** ドキュメント・ADR | Phase 9 の位置で | 設計判断を記録する対象が揃ってから |

**焦って全部を早く読まないでください。**下 4 行は経験が前提です。読む時期を間違えると「聞いたことはあるが使えない」状態になります。

## 学習目標

このPhaseを修了すると、以下ができるようになります。

**設計スキル**
- 良いコードと悪いコードの違いを言語化できる
- 単一責任原則をはじめとするSOLID原則を実際のコードに適用できる
- Strategy、Factory、Observer、Adapterパターンを適切な場面で使える
- レイヤードアーキテクチャで依存関係を整理できる

**テストスキル**
- テストピラミッドに基づいたテスト戦略を立てられる
- pytestで単体テスト・統合テストを書ける
- TDDのRed-Green-Refactorサイクルで開発できる
- モックを使って外部依存を切り離したテストを書ける

**リファクタリングスキル**
- コードスメルを発見し、名前を付けられる
- 小さく安全なステップでリファクタリングできる
- テストを安全網として活用できる

**チームワークスキル**
- コードレビューで建設的なフィードバックを与えられる
- ADR(Architecture Decision Record)で設計判断を記録できる

## 修了条件チェックリスト

以下を全て達成したらPhase 9修了です。

### 知識確認
- [ ] 凝集度(cohesion)と結合度(coupling)の違いを説明できる
- [ ] SOLID原則の各文字が何を表すか言える
- [ ] Strategy パターンと Factory パターンの使い分けを説明できる
- [ ] テストピラミッドの3層を説明できる
- [ ] TDDのRed-Green-Refactorサイクルを説明できる
- [ ] コードスメルを5つ以上挙げられる

### 実技確認
- [ ] 演習 ex01〜ex05 を全て完了した
- [ ] 各演習で解答前に自分の回答を書いた
- [ ] 総仕上げプロジェクトのレガシーコードに対してテストを書いた
- [ ] テストを安全網にしてリファクタリングを完了した
- [ ] リファクタリング後のコードについてADRを1つ書いた

### アウトプット確認
- [ ] 他の人のコードをレビューし、建設的なフィードバックを1件以上書いた
- [ ] 自分のコードに対するレビューコメントに返答した
- [ ] [Phase 9 実技試験](assessment/)に合格した

## 使い方

総仕上げ後に [Phase 9 実技試験](assessment/)を受験します。先に未知の現行挙動をtestへ固定し、小さな変更で仕様を追加できること、設計判断をADRとして説明できることを評価します。

1. lessons/ を 01 から順に読む
2. 各レッスンの「確認問題」に自分なりの答えを書く
3. exercises/ の該当演習を実施する(解答を見るのは自力で試した後)
4. 第6週に project/ の総仕上げに取り組む
