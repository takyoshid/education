# 解説 ex02: 関数分割と単一責任原則

## 単一責任原則(SRP)とは何か

「1つのクラス・関数は1つの変更理由しか持ってはならない」という原則です。

「変更理由が1つ」という意味は:
- 「ユーザー名のバリデーションルールが変わった」ときに変更するファイル
- 「パスワードのハッシュアルゴリズムを変えた」ときに変更するファイル

これらが同じファイル・クラスにあると、一方の変更が他方に影響を与えるリスクが生まれる。

## 問題1: process_registration の分析

### 責務の特定

元のコードが持っていた責務を列挙する:

1. ユーザー名の書式バリデーション
2. メールアドレスの書式バリデーション
3. パスワードの強度チェック
4. パスワードのハッシュ化 (アルゴリズム: SHA-256 + ソルト)
5. ユーザー辞書の構造定義
6. 確認トークンの生成

### なぜ分割すると良いか

**テストのしやすさ**:
- 分割前: `process_registration("ab", ...)` が「ユーザー名が短い」エラーを出すか確認するためだけに、メール・パスワードも正しい値を用意しなければならない
- 分割後: `_validate_username("ab")` だけテストすればよい

**変更の局所化**:
- 「SHA-256からbcryptに変えたい」→ `_hash_password` だけ変更
- 「パスワードの最小文字数を10にしたい」→ `_validate_password` だけ変更
- どちらの変更も他の関数に触れる必要がない

### オーケストレーターパターン

リファクタリング後の `process_registration` は「何をするか」の流れだけを記述している:

```python
def process_registration(username, email, password):
    _validate_username(username)      # 1. バリデーション
    _validate_email(email)
    _validate_password(password)
    salt = _generate_salt(email)      # 2. ハッシュ化準備
    password_hash = _hash_password(password, salt)
    ...                               # 3. オブジェクト生成
```

この関数はロジックを持たず、詳細は各関数に委譲している。
これを「オーケストレーター(指揮者)」パターンと呼ぶ。

## 問題2: ReportManager の分析

### 神クラス(God Class)の見分け方

以下のサインがある場合、神クラスの疑いがある:
- クラス名に `Manager`、`Handler`、`Helper`、`Utils` がついている
- メソッドが10個以上ある
- クラスを修正する理由が複数ある (「DB変更」「レポート形式変更」「集計ロジック変更」)

### 分割の考え方: 「変更理由」で切る

| クラス | 変更する理由 |
|--------|------------|
| `UserRepository` | ユーザーの保存先・取得方法が変わるとき |
| `OrderRepository` | 注文の保存先・取得方法が変わるとき |
| `SalesCalculator` | 売上集計のビジネスロジックが変わるとき |
| `SalesReportFormatter` | レポートの出力形式が変わるとき |

これら4つの変更が互いに独立している限り、分割は正しい。

### トレードオフ

**メリット**:
- 各クラスが小さく、理解しやすい
- テストが書きやすい (SalesCalculator は list[Order] を受け取るだけ)
- 変更が局所化される

**デメリット**:
- ファイル数・クラス数が増える
- 小さな機能のために「どこに何があるか」を把握するコストが上がる

**判断基準**:
4つの責務が「同じタイミングで変わる」なら分割する必要はない。
「別々のタイミングで独立して変わる」なら分割する価値がある。

---

## まとめ: SRP適用の判断フロー

```
「この関数/クラスを変更する理由はいくつあるか?」

1つ → SRPを満たしている

複数 → 以下を確認:
  - それぞれの変更は独立して起きるか?
    はい → 分割すべき
    いいえ(常にセットで変わる) → 分割しなくてよい
```
