## 問題 1: `title()` の落とし穴

`"hello world".title()` は `"Hello World"` を返しますが、`title()` は「アルファベット以外の文字の直後」をすべて単語の先頭とみなします。

```python
"it's a test".title()   # "It'S A Test"  ← アポストロフィの後ろが大文字に
"o'brien".title()       # "O'Brien"      ← これは偶然うまくいく
"mcdonald".title()      # "Mcdonald"     ← "McDonald" にはならない
```

人名や固有名詞に使うと必ず事故ります。単語の先頭だけを大文字にしたいなら:

```python
" ".join(w.capitalize() for w in s.split())
```

**教訓**: 便利そうなメソッドを見つけたら、「どういう入力で壊れるか」を1つ考えてから使う。

## 問題 2: 3桁区切りと税込計算

```python
f"{8940:,}"      # "8,940"
f"{8940:,.2f}"   # "8,940.00"
```

税込計算に `int(subtotal * 1.1)` を使っています。**この演習の範囲では正しい答えが出ますが、金額計算の書き方としては勧められません。**

正直に言うと、`int(整数 * 1.1)` はかなり広い範囲で正しく動きます。float の `1.1` は正確な 1.1 より**わずかに大きい**値だからです。

```python
>>> from decimal import Decimal
>>> Decimal(1.1)
Decimal('1.100000000000000088817841970012523233890533447265625')
```

そのため切り捨てが 1 円足りなくなる、という事故は起きにくくなっています。問題は、**この「たまたま安全」が、少し条件が変わると崩れる**ことです。実際に壊れる例:

```python
>>> round(2.675, 2)
2.67          # 2.68 を期待するが、2.675 が内部では 2.67499... のため
>>> round(1.005, 2)
1.0           # 1.01 を期待するが、同じ理由で切り下がる
>>> 0.1 + 0.2 == 0.3
False
```

消費税の端数処理は「小数第2位を四捨五入」のような仕様になることが多く、そこで `round()` を使った瞬間に上の罠を踏みます。

```python
from decimal import Decimal, ROUND_HALF_UP

subtotal = Decimal("2980") * 3
total = (subtotal * Decimal("1.1")).quantize(Decimal("1"), rounding=ROUND_HALF_UP)

Decimal("0.1") + Decimal("0.2") == Decimal("0.3")   # True
```

`Decimal` は 10 進数をそのまま扱い、**丸め方も明示的に指定させます**(`ROUND_HALF_UP` / `ROUND_DOWN` など)。金額計算では「どう丸めるか」自体が仕様なので、明示を強制されるのはむしろ利点です。

Phase 2 の実技試験でも `Decimal` を要求しています。**お金に float を使わない**は業務システムの鉄則です。

> **考え方**: 「今は動いている」は根拠になりません。`int(v * 1.1)` が広い範囲で正しいことは、上のように検証すれば確かめられます。しかし検証していない条件(丸め方が変わる、税率が変わる、金額に小数が入る)で崩れます。**動く理由が「たまたま」なら、それは動いていないのと同じ**です。

## 問題 4: 自作 CSV パーサーが壊れる理由

`line.split(",")` は、値の中にカンマがある場合に破綻します。

```
name,note
Alice,"Tokyo, Japan"
```

自作パーサー: `{'name': 'Alice', 'note': '"Tokyo'}` ← 壊れた
`csv.DictReader`: `{'name': 'Alice', 'note': 'Tokyo, Japan'}` ← 正しい

CSV は「カンマで区切るだけの単純な形式」に見えますが、実際には引用符、引用符のエスケープ(`""`)、値の中の改行という仕様があります。**標準ライブラリにあるものを自作しない**こと。

演習として自作するのは学習になりますが、実務コードに持ち込んではいけません。

## 問題 5: 境界値を先に潰す

```python
if not names:      return ""
if len(names) == 1: return names[0]
if len(names) == 2: return f"{names[0]} and {names[1]}"
```

「0 人」のケースは仕様に書かれていませんでしたが、**書かれていないケースこそ最初に考えます**。実務でリストが空になる可能性はほぼ常にあります。

`names[:-1]` と `names[-1]` を使うと、3人以上をまとめて扱えます。

## 問題 6: 車輪の再発明を「してから」標準ライブラリを見る

`wrap_text()` は `textwrap.wrap()` とほぼ同じものです。この演習の狙いは、

1. まず自分で書いてアルゴリズムを理解する
2. **その後で**標準ライブラリを見て、「自分の実装に足りない考慮」に気づく

ことです。`textwrap` はハイフン区切り、タブ展開、インデント維持なども扱います。自作してから読むと、その差分が「何を考慮すべきか」のリストになります。

## 問題 7: 正規表現は「完璧」にならない

URL の正規表現 `https?://[^\s、。」）]+` は、日本語文中の URL を拾うための**妥協した実装**です。

- `https://example.com/a(b)c` のような括弧付き URL は途中で切れる
- 文末の `。` を URL に含めない工夫が必要
- RFC 3986 に厳密に従う正規表現は数千文字になり、実用的ではない

**「どこまでを URL とみなすか」は仕様であり、正規表現はその近似**です。完璧を目指すのではなく、「この用途ではこの妥協で十分」と判断根拠を書き残すのがプロの仕事です。

## 問題 8: なぜ `str.format()` を使わないのか

`render()` を `template.format(**kwargs)` の 1 行で済ませたくなりますが、テンプレート文字列が**利用者の入力**である場合、それは脆弱性になります。

```python
# 利用者が入力したテンプレートだとする
evil = "{user.__class__.__init__.__globals__}"
evil.format(user=some_object)   # 内部情報が漏れうる
```

`str.format()` は `{a.b}`(属性アクセス)や `{a[0]}`(添字アクセス)を解釈します。この性質を悪用する攻撃は **format string injection** と呼ばれます。

自作の `render()` は `\w+`(英数字とアンダースコアのみ)にマッチしたものしか置換しないため、この攻撃を受けません。**「機能が少ない」ことが安全性になる**、という設計の一例です。

なお、テンプレートを開発者しか書かない場合は `str.format()` で構いません。**脅威モデル(誰が何を入力できるか)によって正解が変わる**ことを意識してください。

## この演習で身につく判断

| 場面 | 判断 |
|---|---|
| 文字列メソッドを使う | 壊れる入力を1つ考えてから使う |
| CSV / JSON を扱う | 標準ライブラリを使う。自作しない |
| 金額を計算する | float ではなく `Decimal` |
| 正規表現を書く | 完璧を目指さず、妥協点を記録する |
| 利用者入力を扱う | 機能の少ない方を選ぶ |
