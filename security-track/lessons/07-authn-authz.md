# Lesson 07: 認証・認可・セッション

## 学習目標

- 認証(誰か)と認可(何をしてよいか)を明確に区別する
- セッションと JWT の仕組みとトレードオフを説明できる
- JWT の典型的な脆弱性(`alg:none`・弱い鍵)を攻撃し、直せる
- OAuth 2.0 / OIDC の認可コードフロー(+PKCE)を図示できる
- IDOR(アクセス制御の不備)を再現し、対策できる
- パスワードレス(WebAuthn / パスキー)と MFA を理解する

---

## 0. 認証と認可 — 混同が事故を生む

まず言葉を厳密に。

```
認証(Authentication / AuthN): 「あなたは誰か?」を確かめる
  例: パスワード、指紋、ワンタイムコード

認可(Authorization / AuthZ):  「あなたは“それ”をしてよいか?」を確かめる
  例: この注文を見る権限があるか、管理者機能を使えるか
```

たとえ: 空港。**パスポート審査 = 認証**(あなたが本人か)。**搭乗券 = 認可**(この便に乗ってよいか)。本人確認が済んでも、他人の便には乗れません。

この2つの混同が、Web で最も多い脆弱性(アクセス制御の不備 = OWASP Top 10 の No.1)を生みます。「ログインしている」ことと「その操作をしてよい」ことは**別**なのです。

## 1. セッション方式 — サーバが状態を持つ

Lesson 04 で見たように、HTTP はステートレスです。ログイン状態を保つ古典的な方法が**サーバサイドセッション**です。

```
1. ログイン成功 → サーバがランダムなセッション ID を生成し、サーバ側に保存
   session:abc123 → { userId: 42, role: "user" }
2. ブラウザに Cookie で ID を渡す(Set-Cookie: session=abc123; HttpOnly; Secure)
3. 以降のリクエストで Cookie が自動送信され、サーバが ID からユーザーを特定
```

**特徴**: 状態はサーバ側。ログアウトやセッション無効化が即座にできる(サーバから消すだけ)。ただし複数サーバでセッションストア(Redis 等)の共有が要る。

### セッションの脅威と対策

| 脅威 | 対策 |
|------|------|
| セッション ID の推測 | 十分な長さの暗号論的乱数(Lesson 02 の `secrets`)を使う |
| セッションハイジャック(盗む) | HttpOnly + Secure + HTTPS(Lesson 03/04) |
| セッション固定(fixation) | **ログイン成功時に ID を再生成**する |
| CSRF | SameSite + CSRF トークン(Lesson 06) |

## 2. JWT 方式 — トークンが状態を持つ

**JWT(JSON Web Token)** は、ユーザー情報を**トークン自体に埋め込み**、サーバ側に保存しない方式です。マイクロサービスや SPA で人気。

### 構造(理論)

JWT は3つの Base64URL 部分を `.` で連結したものです。

```
eyJhbGc...  .  eyJzdWI...  .  SflKxwRJ...
└─ヘッダ─┘     └─ペイロード┘    └──署名──┘

ヘッダ:     {"alg":"HS256","typ":"JWT"}       ← 署名アルゴリズム
ペイロード:  {"sub":"42","role":"user","exp":...}  ← 中身(クレーム)
署名:       HMAC-SHA256(header.payload, 秘密鍵)   ← 改ざん検出(Lesson 02!)
```

**重要な理解**: ペイロードは**暗号化されていません**。Base64 は誰でもデコードできます。JWT が守るのは「機密性」ではなく「**完全性**」——署名により「改ざんされていない」ことだけを保証します。だから JWT に**パスワードや秘密情報を入れてはいけません**。

### 検証の仕組み

サーバは受け取った JWT の署名を、自分の秘密鍵で検証します。改ざんされていれば署名が合わず拒否。正しければ、ペイロードの `userId` や `role` を**信頼して**使います。DB を引かずに認証できるのが利点(ステートレス)。

### トレードオフ

| | セッション | JWT |
|--|-----------|-----|
| 状態 | サーバ側 | トークン側(ステートレス) |
| 即時失効 | 簡単(消すだけ) | **難しい**(有効期限まで有効) |
| スケール | ストア共有が必要 | サーバ間で共有不要 |
| 情報漏洩 | ID だけ漏れる | ペイロードが読める(暗号化なし) |

JWT の「即時失効が難しい」は実務で頻繁に問題になります。対策: **短い有効期限 + リフレッシュトークン**、失効リスト(ブラックリスト)、あるいは重要システムでは素直にセッションを使う。

## 3. ハンズオン: JWT を攻撃する

JWT は誤実装が多く、攻撃練習の宝庫です。`pyjwt` で脆弱なパターンを再現します。

### 攻撃① `alg: none`(署名の無効化)

JWT 仕様には `alg: none`(署名なし)という値があります。検証実装が甘いと、攻撃者が署名を消し、ペイロードを自由に書き換えられます。

```python
import jwt, base64, json

# 攻撃者: role を admin に書き換え、alg を none にした偽トークンを自作
header = base64.urlsafe_b64encode(b'{"alg":"none","typ":"JWT"}').rstrip(b'=')
payload = base64.urlsafe_b64encode(b'{"sub":"42","role":"admin"}').rstrip(b'=')
forged = header + b'.' + payload + b'.'   # 署名は空
print(forged.decode())

# ❌ 脆弱なサーバ: アルゴリズムを検証せずデコード
# jwt.decode(token, key, algorithms=["HS256","none"])  ← none を許すと突破される
```

**修正**: 検証時に**許可アルゴリズムを固定**する。

```python
# ✅ 安全: none や意図しないアルゴリズムを拒否
jwt.decode(token, key, algorithms=["HS256"])  # HS256 のみ許可
```

### 攻撃② 弱い署名鍵(HS256 の総当たり)

HS256 は共有鍵(HMAC)。鍵が `secret` や `password` のように弱いと、オフラインで総当たり(`hashcat` / `jwt_tool`)されて偽造されます。

**修正**: 鍵は長くランダムに(32バイト以上、`secrets.token_hex(32)`)。環境変数で管理し、ハードコードしない(Lesson 02)。

### 攻撃③ アルゴリズム混同(RS256 → HS256)

RS256(公開鍵署名)を使うシステムで、攻撃者が alg を HS256 に変え、**公開鍵を HMAC の共有鍵として使って**署名を偽造する古典的攻撃。公開鍵は誰でも入手できるため成立します。

**修正**: アルゴリズムを固定し、鍵の型と用途を厳密に紐付ける。

> これらは Juice Shop や [PortSwigger の JWT ラボ](https://portswigger.net/web-security/jwt)で実際に攻略できます。手を動かすと「JWT は正しく検証しないと紙のバッジ同然」だと骨身に染みます。

## 4. IDOR — 最も多い認可の不備

**IDOR(Insecure Direct Object Reference)** は、「認証は通っているが、認可を確認していない」典型的な脆弱性です。OWASP のアクセス制御不備の代表格。

```python
# ❌ 脆弱: ログインは確認するが「そのデータが本人のものか」を確認しない
@app.get("/api/orders/<order_id>")
@login_required
def get_order(order_id):
    return db.orders.find(order_id)   # 他人の order_id を入れれば見えてしまう
```

`/api/orders/1001` を `/api/orders/1002` に変えるだけで、他人の注文が見える。URL の数字を1つ変えるだけの、子供でもできる攻撃です。だからこそ頻発します。

### 対策: 所有者チェックを必ず入れる

```python
# ✅ 安全: リソースの所有者とログインユーザーが一致するか検証
@app.get("/api/orders/<order_id>")
@login_required
def get_order(order_id):
    order = db.orders.find(order_id)
    if order.user_id != current_user.id:
        abort(403)      # 認可の確認
    return order
```

- すべてのリソースアクセスで**所有権/権限を検証**する
- 推測しにくい ID(UUID)は「気休め」。**根本対策は認可チェック**(UUID でも列挙されうる)
- サーバ側で一元的に認可を強制する(各エンドポイントで書き忘れないよう仕組み化)

## 5. OAuth 2.0 と OpenID Connect — 「Google でログイン」の正体

### まず区別

```
OAuth 2.0:      認可の委譲。「このアプリに、私の Google Drive を読む“許可”を与える」
OpenID Connect: OAuth 2.0 の上に乗る認証層。「このユーザーが“誰か”を証明する」
```

「Google でログイン」は OIDC、「アプリに Google カレンダーへのアクセスを許可」は OAuth、と考えると整理できます。

### 認可コードフロー + PKCE(現代の標準)

```
1. ユーザーが「Google でログイン」をクリック
2. アプリ → 認可サーバ(Google)へリダイレクト(+ code_challenge を送る:PKCE)
3. ユーザーが Google で認証・同意
4. Google → アプリへ「認可コード」を返す(リダイレクト)
5. アプリ → Google のトークンendpointへ、認可コード + code_verifier を送る
6. Google がコードとverifierを検証し、アクセストークン(と ID トークン)を発行
7. アプリはトークンを使って API を呼ぶ / ユーザーを識別する
```

### なぜ「認可コード」を挟むのか(理論)

トークンを直接リダイレクト URL に載せると、ブラウザ履歴・リファラ・ログに残り漏れます。そこで「一度しか使えず短命な**認可コード**」だけをブラウザ経由で渡し、本物のトークンは**サーバ間の裏チャネル**で受け取ります。ブラウザには秘密を通さない、という設計です。

### PKCE(Proof Key for Code Exchange)が防ぐもの

モバイルや SPA では認可コードが盗まれるリスクがあります。PKCE は「最初にランダムな `code_verifier` を作り、そのハッシュ `code_challenge` を送っておき、トークン交換時に元の verifier を提示させる」ことで、**コードを盗んでも verifier がなければ使えない**ようにします。今や公開クライアントでは必須です。

### よくある OAuth の脆弱性

- **redirect_uri の検証不備**: 攻撃者のサイトへコードをリダイレクトさせられる(完全一致で検証する)
- **state パラメータ欠如**: OAuth における CSRF。ランダムな `state` で防ぐ
- **トークンの保管ミス**: アクセストークンを localStorage に置くと XSS で盗まれる

## 6. パスワードを超えて — MFA と WebAuthn

### 多要素認証(MFA)

「知っているもの(パスワード)」に加え、別の要素を要求します。

```
知識要素: パスワード、PIN
所持要素: スマホの認証アプリ(TOTP)、セキュリティキー
生体要素: 指紋、顔
```

SMS ワンタイムコードは、SIM スワップ攻撃に弱いため、**TOTP アプリや物理キーの方が安全**です。

### WebAuthn / パスキー(passkey)— パスワードの終焉

**WebAuthn** は公開鍵暗号(Lesson 02)を使った、フィッシング耐性のある認証です。

```
仕組み:
  端末が公開鍵ペアを生成 → 公開鍵をサーバに登録、秘密鍵は端末の安全領域に
  ログイン時: サーバが送るチャレンジに、端末が秘密鍵で署名 → サーバが公開鍵で検証
```

**なぜフィッシングに強いか**(理論): 署名にはオリジン情報が結び付き、秘密鍵は端末から出ません。偽サイト(別オリジン)には正しい署名を作れず、盗むべきパスワードも存在しない。これが「パスキー」として普及し始めている、認証の未来です。

## 💡 コラム: パスワードを発明した男の、生涯の後悔

パスワードは、コンピュータより古い概念です(古代ローマの歩哨も「合言葉」を使いました)。しかし**コンピュータのパスワード**を発明したのは、1960年代、MIT の **フェルナンド・コルバト** だとされています。彼が開発した時分割システム CTSS は、複数人が1台を共有するため、各自のファイルを守る仕組みが必要でした。そこで彼は各ユーザーにパスワードを割り当てたのです。

皮肉なことに、CTSS は**史上初のパスワード漏洩事件**の舞台にもなりました。ある研究者が、全員のパスワードを平文で保存したファイルを、手違いでログイン画面に表示させてしまったのです(Lesson 02 の「パスワードは平文で保存するな」は、この最初期の失敗から始まっています)。

晩年、コルバトはこう語りました。「パスワードは、**インターネットを安全に使うための、いささか悪夢のようなもの**になってしまった。人は10個も20個も覚えられない」。自らの発明が、半世紀後に世界最大のセキュリティ課題の一つになることを、彼は見届けました。

この後悔こそが、WebAuthn とパスキーが目指す世界の原動力です。「人間に秘密の文字列を記憶させ、それを毎回ネットワークに送らせる」——コルバトの時代には合理的だったこの仕組みは、フィッシングと漏洩の時代には限界を迎えました。あなたが将来、パスワードのいらない認証を設計するとき、それはコルバトが60年前に始めた物語に、ようやく決着をつける仕事なのです。

## 🌟 コラム: 「私を私たらしめるものは何か」— 攻殻機動隊と認証の本質

認証(authentication)とは、突き詰めれば「**あなたが、あなたであることの証明**」です。この一文を、これほど深く問い詰めた作品はありません——『攻殻機動隊』です。

作中の鍵となる概念が「**ゴースト**」。義体(サイボーグの身体)も記憶も電子化・複製可能になった世界で、なお「その人をその人たらしめている、複製できない何か」を、作品はゴーストと呼びます。人格も、記憶も、姿形も偽造できるなら——**何をもって「本人」と認めればいいのか?** これは認証エンジニアが毎日格闘している問いそのものです。

劇場版に登場する「**人形使い(Project 2501)**」は、他人のゴーストをハックし、**本人が疑いようもなく信じてしまう偽の記憶と人格**を植え付けます。被害者は自分の過去を確信していますが、それは丸ごと捏造でした。ここに認証設計の教訓が凝縮されています。**「知っていること(記憶・パスワード)」は偽装・抽出できる**。だから私たちは、より偽造しにくいものへと認証を進化させてきました——「知っていること」から、「**取り出せない秘密鍵**(WebAuthn / パスキー。§6)」へ。端末の安全な領域から出ず、フィッシングサイトには決して渡らない鍵。それは、攻殻機動隊が夢見た「**ハックできないゴースト**」に、現実の暗号技術で近づこうとする試みなのです。

素子(モトコ)は問い続けます。「私の記憶も、この身体も、誰かに与えられたものかもしれない」。認証を設計するあなたも、同じ問いの前に立ちます。**「このシステムは、本当に“本人”を確かめているのか。それとも“本人が知っていそうなこと”を確かめているだけなのか。」** この違いを意識できる人が、なりすましに強い認証を作れます。ゴーストは、暗号の言葉で言えば——**誰にも複製・抽出できない、あなただけの秘密鍵**です。

## まとめ

| 概念 | 要点 |
|------|------|
| 認証 vs 認可 | 「誰か」と「してよいか」は別。混同が最多の脆弱性を生む |
| セッション | サーバが状態を持つ。即時失効が容易。ID 再生成でfixation対策 |
| JWT | トークンが状態を持つ。署名は完全性のみ(暗号化ではない)。失効が難しい |
| JWT 攻撃 | `alg:none`・弱い鍵・アルゴリズム混同。algを固定し強い鍵で検証 |
| IDOR | 認証済みでも認可未確認。所有者チェックを必ず入れる |
| OAuth/OIDC | 認可の委譲/認証。認可コード + PKCE + state が現代標準 |
| MFA/WebAuthn | 多要素・パスキーでフィッシング耐性。パスワードの限界を超える |

## 確認問題

1. 認証と認可の違いを、空港のたとえ以外の具体例で説明してください。
2. 「JWT のペイロードに個人情報を入れても、Base64 だから安全」という主張の誤りを指摘してください。
3. JWT の `alg:none` 攻撃はどのように成立し、どう防ぐか説明してください。
4. IDOR 脆弱性のあるエンドポイントの例を挙げ、修正コードを書いてください。ID を UUID にするだけでは不十分な理由も述べてください。
5. OAuth 2.0 の認可コードフローで、なぜトークンを直接リダイレクトに載せず「認可コード」を挟むのか説明してください。
6. WebAuthn/パスキーがフィッシングに強い理由を、公開鍵暗号とオリジンの観点から説明してください。
