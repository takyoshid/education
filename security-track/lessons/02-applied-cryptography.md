# Lesson 02: 暗号技術の実践と誤用

## 学習目標

- 暗号の3つの道具(対称鍵・公開鍵・ハッシュ)の役割を原理から理解する
- 「暗号化」と「ハッシュ」と「署名」を混同しなくなる
- 現場で頻発する暗号の**誤用**を見抜き、直せる
- パスワード保存・トークン生成・TLS の裏側を説明できる
- 「自作暗号は絶対に使わない」理由を理解する

> この Lesson は理論が主役です。しかし各節に「壊れた実装 → 直す」ハンズオンを置きました。Python の `cryptography` / `hashlib` / `hmac` を使います。

---

## 0. なぜ暗号を学ぶのか — セキュリティの「物理法則」

暗号は、セキュリティにおける物理法則のようなものです。認証も、TLS も、JWT も、パスワード保存も、ブロックチェーンも、すべて暗号という土台の上に立っています。ここが分かっていないと、上のレイヤの「なぜ安全なのか/なぜ危ないのか」が丸暗記になります。

安心してください。**あなたが暗号アルゴリズムを自作することはありません**(してはいけません)。学ぶのは「既にある頑丈な部品を、正しく組み合わせる」技術です。大工が釘の分子構造を知らなくても家を建てられるように、あなたは AES の内部数学を知らなくても安全なシステムを作れます。ただし「どの釘をどこに打つか」は知らねばなりません。

---

## 1. 3つの土台を、まず区別する

暗号技術は目的で3つに大別できます。**最初にこれを混同しないことが何より重要**です。

| 道具 | 守る性質 | たとえ | 代表例 |
|------|---------|--------|--------|
| **対称鍵暗号** | 機密性(盗み見防止) | 同じ鍵で開け閉めする南京錠 | AES |
| **公開鍵暗号** | 機密性 + 鍵配送 + 署名 | 誰でも投函できるが自分しか開けない郵便ポスト | RSA, ECC |
| **ハッシュ関数** | 完全性(改ざん検出) | 指紋・封蝋 | SHA-256 |

さらに、これらを組み合わせた応用が2つ。

| 応用 | 何をする | 使う道具 |
|------|---------|---------|
| **MAC / HMAC** | 「本物かつ改ざんなし」を共有鍵で保証 | ハッシュ + 共有鍵 |
| **デジタル署名** | 「本物かつ改ざんなし」を公開鍵で証明(否認防止) | ハッシュ + 秘密鍵 |

## 2. ハッシュ関数 — データの指紋

**ハッシュ関数**は、任意の長さのデータを固定長の「指紋(ダイジェスト)」に変換する一方通行の関数です。

```python
import hashlib
print(hashlib.sha256(b"hello").hexdigest())
# 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
print(hashlib.sha256(b"hellp").hexdigest())  # 1文字違い
# 7f1... 全く別物になる(雪崩効果 / avalanche effect)
```

暗号学的ハッシュが満たすべき3つの性質(理論):

1. **一方向性(pre-image resistance)**: ダイジェストから元データを復元できない
2. **第二原像困難性**: あるデータと同じダイジェストを持つ別データを作れない
3. **衝突困難性(collision resistance)**: 同じダイジェストを持つ2つのデータの組を作れない

### ⚠️ 誤用1: ハッシュは「暗号化」ではない

初学者が最も混同する点です。ハッシュは**元に戻せない**ので、暗号化(復号できる)とは別物です。「パスワードを暗号化して保存」と言う人がいたら、それはたいてい間違い。正しくは「ハッシュ化して保存」です(後述)。

### ⚠️ 誤用2: MD5 / SHA-1 はもう使わない

MD5 と SHA-1 は**衝突を現実的に作れてしまう**ことが証明済みです。2017年、Google は SHA-1 の衝突(同じハッシュを持つ異なる2つの PDF)を実際に生成して見せました(**SHAttered** 攻撃)。改ざん検出や署名に MD5/SHA-1 を使ってはいけません。**SHA-256 以上**を使います。

---

## 3. パスワードの保存 — ハッシュだけでは足りない

「パスワードは平文で保存しない、ハッシュ化する」——正しい。しかし**ただの SHA-256 では不十分**です。理由を理論から。

### なぜ単純ハッシュではダメか

1. **レインボーテーブル**: よくあるパスワードの `SHA-256` を事前計算した巨大な辞書が出回っています。`hash("password123")` を引くだけで元が分かります。
2. **高速すぎる**: SHA-256 は GPU で毎秒**数十億回**計算できます。総当たりが速すぎる。同じパスワードのユーザーが同じハッシュになるのも問題です。

### 対策: ソルト + 低速な専用アルゴリズム

```python
# ❌ 危険な例
import hashlib
def store_bad(pw): return hashlib.sha256(pw.encode()).hexdigest()

# ✅ 正しい例: bcrypt(ソルト内蔵・意図的に低速)
import bcrypt
def store_good(pw: str) -> bytes:
    # gensalt() がユーザーごとに違うソルトを自動生成し、ハッシュに埋め込む
    return bcrypt.hashpw(pw.encode(), bcrypt.gensalt(rounds=12))

def verify(pw: str, stored: bytes) -> bool:
    return bcrypt.checkpw(pw.encode(), stored)
```

- **ソルト(salt)**: ユーザーごとに違うランダム値を混ぜる。→ レインボーテーブルが無効になり、同じパスワードでもハッシュが変わる
- **低速化(work factor)**: bcrypt / scrypt / **Argon2** は「わざと遅く」設計されている。正規ログインは1回だけなので遅くて構わないが、攻撃者の総当たりは非現実的に遅くなる

> **2024年現在の推奨**: 新規なら **Argon2id**、枯れた実績重視なら **bcrypt**。`hashlib.sha256` でパスワードを保存しているコードを見たら、それは脆弱性です。

### ⚠️ ペッパー(pepper)という追加防御

ソルトは DB に一緒に保存されます。さらに **アプリ側の秘密鍵(pepper)** をコードや環境変数側に置いて混ぜると、DB だけが漏れても解読が困難になります(多層防御)。

## 4. 対称鍵暗号 — 同じ鍵で開け閉め

**対称鍵暗号**は、暗号化と復号に**同じ鍵**を使います。高速で、大きなデータの暗号化に向きます。標準は **AES**(Advanced Encryption Standard)。

### ⚠️ 誤用3: ECB モードを使う

AES には「モード」があります。中でも **ECB モードは絶対に使ってはいけません**。理由が視覚的に有名です。

```
ECB モード: 同じ平文ブロック → 常に同じ暗号文ブロック
→ 画像を ECB で暗号化すると、輪郭がそのまま残る(有名な「ECB ペンギン」)
```

同じ入力が同じ出力になるため、パターンが漏れます。

### ⚠️ 誤用4: 認証なしの暗号化(改ざんに気づけない)

暗号化しても、攻撃者が暗号文を**書き換える**ことは可能です。復号すると壊れたデータになりますが、「壊れている」と気づけないと危険。そこで **AEAD(Authenticated Encryption with Associated Data)** を使います。暗号化と同時に改ざん検出タグを付けるモードです。

```python
# ✅ 正しい対称暗号: AES-GCM(AEAD。機密性 + 完全性を同時に守る)
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)  # 32バイトの鍵
aesgcm = AESGCM(key)
nonce = os.urandom(12)  # ★毎回異なるランダム値(絶対に使い回さない)

ct = aesgcm.encrypt(nonce, b"secret message", b"user-id-42")  # 最後は関連データ(AAD)
pt = aesgcm.decrypt(nonce, ct, b"user-id-42")   # 改ざんされていれば例外が飛ぶ
print(pt)  # b'secret message'
```

- **nonce(number used once)**: GCM では**同じ鍵で同じ nonce を二度使うと壊滅的**(鍵が漏れる)。毎回ランダム or カウンタで一意にする
- **AAD(関連データ)**: 暗号化はしないが改ざん検出の対象に含めるデータ(例: ユーザー ID)

> 💡 迷ったら **AES-256-GCM** か、より事故りにくい **libsodium / NaCl の `secretbox`**(XSalsa20-Poly1305)を使えば安全です。

## 5. 公開鍵暗号 — 鍵配送問題を解く魔法

対称鍵には根本問題があります。「**その共有鍵を、どうやって安全に相手へ渡すのか?**」(鍵配送問題)。盗聴されている回線で鍵を送ったら意味がありません。

**公開鍵暗号(非対称暗号)**がこれを解決します。鍵を「**公開鍵**」と「**秘密鍵**」のペアにします。

```
公開鍵: 誰にでも配ってよい。これで「暗号化」or「署名検証」ができる
秘密鍵: 自分だけが持つ。これで「復号」or「署名」ができる

たとえ: 郵便ポスト
  投函口(公開鍵) = 誰でも手紙を入れられる
  取り出す鍵(秘密鍵) = 自分だけが中身を取り出せる
```

代表は **RSA** と **楕円曲線暗号(ECC)**。ECC は短い鍵で同等の強度を出せるため、現代では主流です。

### なぜこれが「魔法」か(理論)

公開鍵暗号は「**一方向にしか計算しやすくない数学の問題**(素因数分解や離散対数)」に基づいています。「公開鍵から秘密鍵を逆算する」のが、現実的な時間では不可能なほど難しい。この非対称性が安全性の源です。

> ⚠️ **量子コンピュータの脅威**: 将来の大規模量子コンピュータは RSA/ECC を破れる可能性があり、NIST が**耐量子暗号(post-quantum cryptography)** の標準化を進めています(2024年に最初の標準を発表)。長期的に守るべきデータでは意識が必要です。

### 鍵交換: Diffie-Hellman

実際の TLS では「公開鍵でデータそのものを暗号化」よりも、「公開鍵の技術で**対称鍵を安全に合意する**」使い方が主流です。**Diffie-Hellman 鍵交換**は、盗聴されている回線でも、双方だけが知る共有秘密を作り出せる仕組みです。さらに**前方秘匿性(Forward Secrecy)** — 将来サーバの秘密鍵が漏れても、過去の通信は復号されない — を提供します。

## 6. デジタル署名 — 「本物」と「改ざんなし」を証明

公開鍵を**逆向き**に使うと、署名になります。

```
署名:   送信者が【秘密鍵】でハッシュを暗号化 → これが署名
検証:   受信者が【公開鍵】で署名を復号 → 本文のハッシュと一致すれば本物
```

これで3つを同時に保証します。

- **完全性**: 改ざんされればハッシュが変わり、検証が失敗する
- **認証**: その秘密鍵の持ち主しか作れない署名
- **否認防止(non-repudiation)**: 「私は署名していない」と言い逃れできない

ソフトウェア配布の署名、TLS 証明書、JWT(Lesson 07)、Git のコミット署名など、至るところで使われています。

```python
# ✅ Ed25519 署名(高速・安全な現代的署名方式)
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey

priv = Ed25519PrivateKey.generate()
pub = priv.public_key()

sig = priv.sign(b"deploy v2.0")            # 秘密鍵で署名
pub.verify(sig, b"deploy v2.0")            # 公開鍵で検証(改ざんなら例外)
```

### HMAC — 共有鍵版の改ざん検出

署名は公開鍵が必要ですが、**双方が同じ秘密鍵を共有している**場面では、より軽量な **HMAC** を使います。API リクエストの署名(Webhook 検証など)で頻出します。

```python
import hmac, hashlib
secret = b"shared-secret"
msg = b"amount=100&to=alice"
tag = hmac.new(secret, msg, hashlib.sha256).hexdigest()

# 検証は必ず「定数時間比較」で(理由は次節)
def verify(msg, tag):
    expected = hmac.new(secret, msg, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, tag)   # ✅ タイミング攻撃に強い
```

### ⚠️ 誤用5: `==` でトークンを比較する(タイミング攻撃)

`if token == expected:` のような普通の比較は、**先頭から1文字ずつ照合し、違った時点で処理を打ち切ります**。つまり「正解に近いほど比較にかかる時間が長くなる」。攻撃者はこの数マイクロ秒の差を測り、1文字ずつトークンを当てられます(**タイミング攻撃**)。秘密の比較には必ず `hmac.compare_digest`(定数時間比較)を使います。これは理論を知らないと絶対に気づけない、実に美しい攻撃です。

## 7. TLS の裏側 — これまでの道具の総合演習

Lesson 03 で実務を扱いますが、ここで暗号の観点から TLS を俯瞰します。TLS は、これまで学んだ道具を**全部組み合わせて**います。

```
1. 証明書の検証   … デジタル署名(サーバが本物か。CA が署名した証明書)
2. 鍵交換         … Diffie-Hellman(対称鍵を安全に合意。前方秘匿性)
3. 本体の通信     … 対称鍵暗号 AES-GCM(高速な AEAD で本文を暗号化 + 改ざん検出)
```

なぜ公開鍵だけで全部やらないのか? 公開鍵暗号は**遅い**からです。そこで「最初だけ公開鍵で対称鍵を安全に共有し、あとは高速な対称鍵で通信する」という**ハイブリッド方式**を取ります。この設計思想は美しく、暗号の知識が全部つながる瞬間です。

## 8. 黄金律: 自分で暗号を作らない・古い設定を使わない

```
❌ 自作の暗号アルゴリズム(「XOR で難読化」等は暗号ではない)
❌ MD5 / SHA-1 を署名や改ざん検出に
❌ AES-ECB / nonce 使い回し
❌ パスワードを SHA-256 だけで保存
❌ 秘密の比較に ==(タイミング攻撃)
❌ 乱数に random モジュール(暗号用途は secrets を使う)

✅ 実績ある高レベルライブラリ(libsodium/PyNaCl, cryptography)
✅ パスワードは Argon2id / bcrypt
✅ 対称暗号は AES-256-GCM か XSalsa20-Poly1305
✅ 署名は Ed25519、鍵交換は X25519、乱数は secrets / os.urandom
✅ TLS は 1.2 以上(できれば 1.3)
```

> **ケルクホフスの原理(Kerckhoffs's principle)**: 「暗号システムは、鍵以外のすべてが公開されても安全でなければならない」。裏を返せば、**アルゴリズムを秘密にすることに安全性を頼ってはいけない**(security by obscurity の否定)。だからこそ、世界中の専門家に検証され尽くした公開アルゴリズムを使うのが正解なのです。

## 💡 コラム: 640年破られなかった暗号と、機械が破った暗号

16世紀、フランスの外交官 **ブレーズ・ド・ヴィジュネル** の名を冠した「**ヴィジュネル暗号**」は、複数のシフトを組み合わせる巧妙さから「**解読不能の暗号(le chiffre indéchiffrable)**」と300年間畏れられました。しかし19世紀、数学者バベッジらが統計的なパターン分析でこれを打ち破ります。「解読不能」は幻想でした。

時代は下り第二次大戦。ナチス・ドイツは **エニグマ** という機械式暗号で、毎日1.5京(10京分の1.5)通りにも及ぶ設定を切り替え、無敵を確信していました。これを打ち破ったのが、**アラン・チューリング** らブレッチリー・パークの暗号解読者たちです。彼らは「暗号文のどこかに必ず現れる定型句(天気予報や『Heil Hitler』)」という運用上の隙(既知平文)を突き、**Bombe** という電気機械でエニグマの設定を絞り込みました。この解読は戦争を数年縮めたと言われます。そしてチューリングがこの過程で育てた計算の理論は、あなたが今触れているコンピュータそのものの母胎になりました。

2つの物語の教訓は同じです。**「破られない暗号」を過信した側が敗れ、暗号そのものではなく“運用の隙”から崩れた。** 現代でも、AES が数学的に破られることはまずありません。破られるのは、nonce の使い回し、鍵の漏洩、`==` による比較——つまり**使い方**です。あなたが守るべきは、アルゴリズムではなく運用なのです。

## まとめ

| 概念 | 要点 |
|------|------|
| ハッシュ | 一方向の指紋。改ざん検出用。SHA-256 以上。MD5/SHA-1 は禁止 |
| パスワード保存 | Argon2id / bcrypt(ソルト内蔵・低速)。単純ハッシュは脆弱 |
| 対称鍵 | 高速。AES-256-GCM(AEAD)。ECB 禁止・nonce 使い回し禁止 |
| 公開鍵 | 鍵配送を解決。RSA/ECC。復号=秘密鍵、暗号化=公開鍵 |
| 署名 | 完全性 + 認証 + 否認防止。ハッシュを秘密鍵で。Ed25519 |
| HMAC | 共有鍵版の改ざん検出。比較は `compare_digest`(定数時間) |
| TLS | 署名 + 鍵交換 + 対称暗号のハイブリッド。全部の総合演習 |
| 黄金律 | 自作しない。枯れたライブラリを正しく使う。運用こそが弱点 |

## 確認問題

1. 「パスワードを AES で暗号化して DB に保存する」設計の何が問題か、より良い方法とともに説明してください。
2. AES-GCM で nonce を使い回すと何が起きますか。なぜ危険か説明してください。
3. デジタル署名が同時に保証する3つの性質を挙げ、それぞれどの暗号部品が担っているか説明してください。
4. `if provided_token == secret_token:` というトークン比較のどこが危険か、攻撃の名前を挙げて説明し、修正案を書いてください。
5. TLS が「公開鍵暗号だけ」でなく対称鍵暗号と組み合わせるハイブリッド方式を取る理由を説明してください。
6. (発展)`hashlib.sha256("password".encode())` でパスワードを保存しているコードをレビューで見つけました。指摘コメントを、理由と修正案つきで書いてください。
