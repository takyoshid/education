# Lesson 10: クラウド・コンテナ・Kubernetes セキュリティ

## 学習目標

- クラウドの「責任共有モデル」を理解する
- IAM の最小権限を設計でき、過剰権限の危険を説明できる
- コンテナの分離の仕組みと「コンテナ脱獄」のリスクを理解する
- 安全な Dockerfile / コンテナ実行を書ける
- Kubernetes の主要な攻撃面と対策を知る
- クラウドの設定ミス(S3 公開等)を防げる

## 0. 誰が何を守るのか — 責任共有モデル

クラウドで最初に理解すべきは、**責任共有モデル(Shared Responsibility Model)** です。

```
クラウド事業者(AWS等)が守る:  物理データセンター、ハードウェア、
                              ハイパーバイザ、マネージドサービスの基盤
                              =「クラウド“の”セキュリティ」

あなた(利用者)が守る:        データ、IAM 設定、ネットワーク設定、
                              OS/アプリのパッチ、暗号化、アクセス制御
                              =「クラウド“における”セキュリティ」
```

クラウド事故の**大多数は利用者側の設定ミス**です。「AWS を使えば安全」ではなく、「AWS は基盤を守る。境界から上はあなたの責任」。この線引きを間違えると、S3 の公開設定ミスで数億件が流出、という定番事故を起こします。

## 1. IAM — クラウドセキュリティの心臓

**IAM(Identity and Access Management)** は「誰が・何に・何をできるか」を制御します。クラウドセキュリティの中核であり、Lesson 08 のキャピタル・ワン事件の被害を拡大させたのも IAM の過剰権限でした。

### 最小権限を設計する

```json
// ❌ 危険: 何でもできる(よく "とりあえず" で付けられる)
{ "Effect": "Allow", "Action": "*", "Resource": "*" }

// ✅ 最小権限: 特定バケットの読み取りだけ
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::my-app-bucket/*"
}
```

### IAM のベストプラクティス

```
✅ 最小権限を徹底(必要な操作・リソースだけ許可)
✅ 人間はフェデレーション(SSO)+ MFA。長期アクセスキーを避ける
✅ アプリ/インスタンスには「ロール」を割り当て、キーを埋め込まない
✅ 一時認証情報(STS)を使い、寿命を短く
✅ ルートアカウントは封印(日常操作に使わない・MFA 必須)
✅ 定期的に未使用権限を棚卸し(IAM Access Analyzer 等)
```

### なぜ過剰権限が致命的か(理論)

一つのサービスが侵害されたとき、そのサービスの権限がそのまま攻撃者の権限になります。過剰権限は「侵害の**爆発半径(blast radius)**」を最大化します。最小権限は、侵入されても被害を一部屋に閉じ込める壁です(Lesson 09 の多層防御)。

## 2. コンテナの分離 — その実体と限界

Lesson 00 で「コンテナは VM より分離が薄い」と触れました。ここを深掘りします。

### コンテナは「隔離された VM」ではない

```
VM:      OS(カーネル)ごと分離。ハイパーバイザが仕切る(分離が強い)
コンテナ: ホストのカーネルを共有し、Linux の機能で「隔離して見せている」

隔離を作る Linux の機能:
  namespaces … プロセス/ネットワーク/ファイルシステムの「見え方」を分離
  cgroups    … CPU/メモリの使用量を制限
  capabilities/seccomp … 使えるシステムコールを制限
```

つまりコンテナは「同じカーネルの上で、隔離されているように振る舞うプロセス」です。カーネルに脆弱性があれば、あるいは設定が甘ければ、その隔離を破ってホストに出られます。これが**コンテナ脱獄(container escape)** です。

### コンテナ脱獄を招く設定

```
❌ --privileged で実行(ほぼすべての隔離が無効化される)
❌ Docker socket(/var/run/docker.sock)をコンテナにマウント
   → コンテナ内から新しい特権コンテナを作れる = ホスト乗っ取り
❌ ホストのファイルシステム(/)をマウント
❌ 危険な capabilities(CAP_SYS_ADMIN 等)を付与
❌ root ユーザーでコンテナを実行
```

## 3. 安全な Dockerfile とコンテナ実行

Lesson 08 のアプリ層に続き、コンテナ層の守りを固めます。

```dockerfile
# ✅ セキュアな Dockerfile
FROM node:20-alpine                       # 小さいベースイメージ(攻撃面が狭い)

RUN addgroup -S app && adduser -S app -G app   # 非 root ユーザーを作成
WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force

COPY --chown=app:app . .
USER app                                   # ★非 root で実行
EXPOSE 3000
CMD ["node", "src/index.js"]
```

```bash
# ✅ 実行時の防御
docker run \
  --read-only \                    # ファイルシステムを読み取り専用に
  --cap-drop ALL \                 # すべての capability を落とす
  --security-opt no-new-privileges \  # 実行中の権限昇格を禁止
  --user 1000:1000 \               # 非 root
  --memory 512m --cpus 1 \         # リソース制限(DoS 緩和)
  myapp:latest
```

### イメージの脆弱性スキャンとサプライチェーン

```bash
# Trivy でイメージの既知脆弱性をスキャン(Lesson 13 のサプライチェーンにも直結)
trivy image --severity HIGH,CRITICAL myapp:latest

# ベースイメージは公式・最小・固定タグ(digest)で。latest は避ける
FROM node:20.11.1-alpine@sha256:...   # digest で固定すると改ざんに強い
```

- **信用できないイメージを動かさない**(Docker Hub の野良イメージにマルウェア入りが多数)
- **マルチステージビルド**でビルド用ツールを本番イメージに残さない
- **シークレットをイメージに焼き込まない**(レイヤに残る。実行時に注入する)

## 4. Kubernetes(K8s)の攻撃面

コンテナを大規模運用する Kubernetes は、強力ですが攻撃面も広大です。主要ポイントを押さえます。

### 主な攻撃面と対策

| 攻撃面 | リスク | 対策 |
|--------|--------|------|
| **API サーバ** | K8s の頭脳。露出すると致命的 | 認証・RBAC・ネットワーク制限 |
| **RBAC** | 過剰権限のサービスアカウント | 最小権限のロール。`cluster-admin` を配らない |
| **Pod のセキュリティ** | 特権 Pod・root 実行 | Pod Security Standards(restricted)を強制 |
| **Secrets** | etcd に平文で保存されうる | 暗号化(EncryptionConfig)・外部シークレットマネージャ |
| **ネットワーク** | Pod 間が素通り | NetworkPolicy でデフォルト拒否 → 必要な通信だけ許可 |
| **etcd** | 全設定・Secret の保管庫 | 暗号化・アクセス制限・相互 TLS |
| **kubelet** | ノード上のエージェント | 匿名アクセス無効・認可有効 |

### セキュアな Pod 設定の例

```yaml
apiVersion: v1
kind: Pod
metadata: { name: secure-app }
spec:
  securityContext:
    runAsNonRoot: true            # root を禁止
    runAsUser: 1000
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: app
      image: myapp:1.2.3@sha256:...   # digest 固定
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities: { drop: ["ALL"] }
      resources:
        limits: { memory: "512Mi", cpu: "500m" }   # 制限で DoS 緩和
```

### ゼロトラストの実装

Lesson 03 のゼロトラストが、ここで具体化します。**NetworkPolicy でデフォルト全拒否**にし、「サービス A は B にだけ話せる」と明示的に許可する。**サービスメッシュ(Istio 等)** で Pod 間通信を相互 TLS(mTLS)で暗号化・認証する。「内部だから信頼」を捨てる設計です。

## 5. クラウドの設定ミス — 最頻出の事故

高度な攻撃より、**設定ミス**がクラウド事故の主因です。

| 定番ミス | 結果 | 対策 |
|---------|------|------|
| S3 バケットを公開 | データ大量流出 | ブロックパブリックアクセスを有効・既定で非公開 |
| セキュリティグループを 0.0.0.0/0 に開放 | DB/管理ポートが全世界に | 必要な送信元 IP だけ許可 |
| メタデータ露出(IMDSv1) | SSRF でクレデンシャル窃取(Lesson 08) | IMDSv2 強制 |
| ログ/監査を無効 | 侵害に気づけない | CloudTrail 等を有効化(Lesson 12) |
| 暗号化なし | 保存データが平文 | 保存時暗号化(KMS)を既定に |
| ハードコードされた鍵 | Git 経由で流出 | シークレットマネージャ・Secrets Scanning |

### CSPM と IaC スキャン

- **CSPM(Cloud Security Posture Management)**: クラウド設定を継続的に監査し、公開バケット等を自動検出
- **IaC スキャン**: Terraform/CloudFormation を **checkov / tfsec / Trivy** でデプロイ前に検査(設定ミスを本番前に潰す。Lesson 13 の DevSecOps)

## 💡 コラム: 世界の半分を止めた「設定ミス」たち

2017年、米調査会社が管理していた **1億9800万人分の米国有権者データ**が、パスワードなしで誰でもアクセスできる S3 バケットに置かれていました。攻撃コードは一行も要りません。URL を知っていれば、ブラウザで開くだけで全米有権者のプロフィールが読めたのです。同種の「公開 S3」事故は、Verizon、Accenture、軍関連まで、数え切れないほど繰り返されました。

クラウド時代のセキュリティ事故には、はっきりした逆説があります。**サーバルームに物理的に侵入するより、チェックボックス一つの押し忘れのほうが、桁違いに大きな被害を生む。** かつて攻撃者はファイアウォールを突破する必要がありました。今は、誰かが `Block Public Access` のチェックを外したバケットを、スキャナで探すだけでいい。攻撃の主戦場は「破る」から「探す」へ移りました。

さらに2024年、この構図は連鎖的な事件で頂点に達します。クラウドデータ企業 **Snowflake** の顧客企業が、MFA を有効にしていなかったアカウントを次々に侵害され、大手通信・金融を含む多数の企業から膨大なデータが盗まれました。破られたのは Snowflake 自身の基盤ではありません——**利用者側の「MFA 未設定」という、責任共有モデルの利用者側**でした。

教訓は Lesson の冒頭に戻ります。**クラウドは基盤を守る。しかし境界から上——IAM、MFA、バケットの公開設定、暗号化——は、最後まであなたの責任。** 派手なゼロデイに憧れる前に、まず「公開設定になっていないか」「MFA は有効か」「権限は絞ってあるか」を確認する。地味なチェックリストこそが、1億人を守る盾なのです。

## まとめ

| 概念 | 要点 |
|------|------|
| 責任共有モデル | 事業者は基盤、利用者はデータ・設定・IAM。事故の多くは利用者側 |
| IAM | 最小権限。過剰権限は爆発半径を最大化。ロール + 一時認証情報 |
| コンテナ分離 | カーネル共有ゆえ VM より薄い。脱獄に注意。--privileged 厳禁 |
| セキュア実行 | 非 root・cap-drop・read-only・no-new-privileges・イメージスキャン |
| Kubernetes | API/RBAC/Pod/Secret/NetworkPolicy。最小権限とデフォルト拒否 |
| 設定ミス | S3 公開・ポート開放・IMDSv1・平文鍵。CSPM/IaC スキャンで防ぐ |

## 確認問題

1. クラウドの責任共有モデルで、「利用者が守るべきもの」を4つ挙げてください。
2. IAM で `Action: "*", Resource: "*"` が危険な理由を「爆発半径」の観点から説明してください。
3. コンテナが VM より分離が弱いのはなぜか、カーネルの観点から説明してください。
4. `docker run --privileged` や Docker socket のマウントがなぜ危険か説明してください。
5. Kubernetes で「デフォルト拒否のネットワーク」を設定する意義を、ゼロトラストの観点から説明してください。
6. 公開 S3 バケット事故が「攻撃コード不要」で起きる理由を説明し、防ぐ設定を2つ挙げてください。
