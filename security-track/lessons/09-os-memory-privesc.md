# Lesson 09: OS・メモリ安全性・権限昇格

## 学習目標

- スタックとメモリの基本から、バッファオーバーフローの原理を理解する
- なぜ「メモリ安全でない言語」が危険なのかを説明できる
- 現代の緩和技術(ASLR・DEP・スタックカナリア)の役割を理解する
- Linux の権限モデルと、権限昇格(privilege escalation)の典型パターンを知る
- 最小権限・多層防御を OS レベルで実践できる

> この Lesson は理論(特にメモリ)を丁寧に。実習は Linux 権限昇格を安全なラボ(TryHackMe/HTB/自分の VM)で。

---

## 0. なぜアプリだけでなく OS を学ぶのか

攻撃者の目標はしばしば「サーバの完全な支配(root 権限)」です。Web の脆弱性(Lesson 05〜08)で最初の足がかり(一般ユーザー権限のシェル)を得たら、次は **権限昇格**で管理者に成り上がろうとします(Lesson 01 の Kill Chain: Exploitation → Privilege Escalation)。その舞台が OS です。

また、C/C++ で書かれた膨大な既存ソフトウェア(OS カーネル、ブラウザ、組み込み)には**メモリ安全性**の問題が潜みます。その原理を知ることは、セキュリティエンジニアの教養です。

## 1. メモリとスタック — 最小限の前提

プログラム実行中、メモリはいくつかの領域に分かれます。関数呼び出しで使われるのが**スタック**です。

```
高アドレス
  ┌─────────────┐
  │   スタック    │ ← 関数のローカル変数・戻りアドレスが積まれる(下方向に伸びる)
  │      ↓       │
  │             │
  │      ↑       │
  │   ヒープ      │ ← 動的確保(malloc/new)
  ├─────────────┤
  │  データ/BSS   │ ← グローバル変数
  │   コード      │ ← プログラム本体
  └─────────────┘
低アドレス
```

関数を呼ぶと、スタックに「**スタックフレーム**」が積まれます。この中に、ローカル変数(バッファなど)と、**関数が終わったら戻る先のアドレス(リターンアドレス)** が並びます。ここが攻撃の核心です。

---

## 2. バッファオーバーフローの原理

### 何が起きるか

C 言語には「配列の範囲チェック」がありません。用意した箱(バッファ)より大きなデータを書き込むと、**隣のメモリを上書き**してしまいます。

```c
// ❌ 危険: 入力長をチェックしない
void vulnerable() {
    char buffer[64];       // 64バイトの箱
    gets(buffer);          // 入力を無制限に読み込む(gets は使用禁止関数)
}
```

64バイトを超える入力を与えると、`buffer` を溢れて、その先にある**リターンアドレスまで上書き**できます。

```
スタックフレーム:
  [ buffer(64バイト) ][ 保存レジスタ ][ リターンアドレス ]
    ↑ ここに 64バイト超を書くと ───────────> ここまで上書きできる
```

### なぜ「乗っ取り」になるのか(理論)

リターンアドレスを上書きできるということは、「関数終了後にどこへ飛ぶか」を攻撃者が決められるということです。攻撃者は:

1. 自分の悪意あるコード(**シェルコード** = シェルを起動する機械語)をメモリに置く
2. リターンアドレスを、そのシェルコードの位置に書き換える
3. 関数が終わると、CPU は攻撃者のコードへ「戻り」、実行してしまう

こうして、入力を処理するだけのプログラムが、攻撃者に**任意コード実行(RCE)** を許します。1988年のモリスワーム(Lesson 00)も、この種のオーバーフローを使いました。

---

## 🌟 コラム: NAND ゲートから見ると、乗っ取りの正体が「見える」

もしあなたが『**コンピュータシステムの理論と実装**』(通称 **Nand2Tetris**)のように、NAND ゲート1個から CPU・スタック・機械語を**自分の手で作った**経験があるなら、このバッファオーバーフローは、抽象論ではなく**回路と機械語の動きとして「見える」**はずです。逆に、まだの人にとっては、この攻撃を理解することが低レイヤを学ぶ最高の動機になります。

Nand2Tetris で自作する要素を思い出してください。

- **メモリは、ただのアドレス付きの箱の列**でした。「buffer」も「リターンアドレス」も、特別な区別なく隣り合って並んでいる — だから溢れれば隣を上書きできる。**メモリ自身は「これはデータ、これは戻り先」を区別しない**。この無防備さこそ、オーバーフローの根本原因です。
- あなたが実装した **CPU は、命令を機械的に1つずつ実行する**だけの装置でした。「このアドレスへジャンプせよ」と書かれていれば、そこが正規のコードか攻撃者のシェルコードかを**CPU は問いません**。リターンアドレスの書き換えが「乗っ取り」になるのは、CPU にこの善悪の判断がないからです。
- 本の後半で作った **スタックVM** は、関数呼び出しのたびにフレームを積み、戻り先を保存しました。あの `push`/`pop` と「戻りアドレスの退避」を自分で書いた人は、「戻りアドレスがスタック上のどこに、なぜ置かれるか」を回路レベルで知っています。攻撃者が狙うのは、まさにあなたが実装したその1ワードです。

```
Nand2Tetris で作った世界:  NAND → 論理ゲート → ALU → CPU → 機械語 → スタックVM → コンパイラ → OS
セキュリティが突く場所:                              ↑ここ(命令ポインタ)  ↑ここ(戻りアドレス)
```

つまり **Nand2Tetris は「コンピュータがなぜ動くか」を建てる本、この Lesson は「その動き方をどう悪用するか」を学ぶ場所**です。同じ地下室を、片方は建築士として、片方は侵入者として見ている。両方の視点を持つ人は、メモリ安全性(なぜ Rust が範囲チェックを入れるのか)も、緩和技術(ASLR がなぜ「飛び先アドレスの予測」を潰すのか)も、Pwn 系 CTF やリバースエンジニアリング(Lesson 14)も、丸暗記ではなく**第一原理から**理解できます。低レイヤに進みたいなら、この本と Lesson 09 の並走は、そのまま最強の相乗効果になります。

## 3. 現代の緩和技術 — なぜ今は難しくなったか

上記は「古典的な」攻撃で、現代の OS には何層もの防御が入っています。攻撃と防御の軍拡競争の歴史そのものです。

| 緩和技術 | 何をするか | どう効くか |
|---------|-----------|-----------|
| **DEP / NX bit** | データ領域(スタック)を実行不可にする | スタックに置いたシェルコードを実行できない |
| **ASLR** | メモリ配置を毎回ランダム化 | 攻撃者が「飛ぶ先のアドレス」を予測できない |
| **スタックカナリア** | バッファと戻りアドレスの間に見張りの値を置く | 上書きされると検知して即座に停止 |
| **PIE** | 実行ファイルの配置もランダム化 | ASLR を実行コードにも適用 |
| **CFI** | 正規の飛び先以外へのジャンプを禁止 | 制御フローの乗っ取りを防ぐ |

### 攻撃側の進化: ROP

DEP で「新しいコードを実行」できなくなると、攻撃者は **ROP(Return-Oriented Programming)** を編み出しました。既存コードの断片(ガジェット)を数珠つなぎにして、目的の動作を組み立てる技法です。防御が上がれば攻撃も進化する——この終わりなき軍拡が、メモリ安全性研究の最前線です。

### 根本解決: メモリ安全な言語

これらの緩和は「対症療法」です。根本原因は「範囲チェックのない言語」。そこで **Rust** や Go、あるいは管理された言語(Python/Java/C#)は、**言語レベルでメモリ安全性を保証**します。

> Microsoft と Google の調査では、**深刻な脆弱性の約7割がメモリ安全性の問題**でした。だから米政府(CISA/NSA)や各社が「新規開発はメモリ安全な言語(Rust 等)で」と強く推奨しています。C/C++ を捨てるのではなく、新しい攻撃面をこれ以上増やさない戦略です。

## 4. Linux の権限モデル

権限昇格を理解するため、Linux の権限の基本を押さえます。

```
ユーザー: root(UID 0、全能)と 一般ユーザー
パーミッション: 各ファイルに rwx(読み/書き/実行) × 所有者/グループ/その他
特別な権限:
  SUID(Set User ID): そのファイルを実行すると「所有者の権限」で動く
  sudo: 設定された範囲で root 権限を借りる
  capabilities: root 権限を細かく分割した能力(CAP_NET_RAW 等)
```

### SUID の光と影

`passwd` コマンドは、一般ユーザーが自分のパスワードを変えるために `/etc/shadow`(root しか書けない)を更新する必要があります。そこで `passwd` には SUID が付き、実行時だけ root 権限で動きます。便利ですが、**SUID が付いた脆弱なプログラムは権限昇格の入口**になります。

---

## 5. 権限昇格の典型パターン(ハンズオンの視点)

一般ユーザーのシェルを得た攻撃者が root を狙う、代表的な道筋です。TryHackMe の "Linux PrivEsc" や HTB のマシンで実際に練習できます。

### 偵察が9割

```bash
# 現在の権限・sudo で何が使えるか
id
sudo -l                    # パスワードなしで実行できるコマンドは?(誤設定の宝庫)

# SUID が付いたバイナリを探す
find / -perm -4000 -type f 2>/dev/null

# 書き込み可能な重要ファイル・cron ジョブ
ls -la /etc/cron.d/ /etc/crontab
find / -writable -type f 2>/dev/null | grep -v /proc

# カーネルバージョン(既知の脆弱性 = カーネル exploit)
uname -a
```

### よくある昇格経路

| 経路 | 内容 |
|------|------|
| **sudo の誤設定** | パスワードなしで `vim`/`find`/`less` 等を root 実行可 → シェル脱出で root |
| **SUID バイナリ** | 脆弱な/悪用可能な SUID プログラム([GTFOBins](https://gtfobins.github.io/) 参照) |
| **書き込み可能な cron** | root が定期実行するスクリプトを一般ユーザーが書き換えられる |
| **カーネル exploit** | 古いカーネルの既知脆弱性(Dirty COW 等)を突く |
| **PATH ハイジャック** | root が相対パスでコマンドを呼ぶと、偽コマンドを PATH に置いて実行させる |
| **平文の認証情報** | 設定ファイル・履歴・環境変数に残ったパスワード/鍵 |

> **GTFOBins** は「普通のコマンドを使って権限昇格やシェル脱出をする手法」の一覧です。攻撃側の必携ツールであり、防御側は「自分のサーバにこれらの SUID/sudo 設定がないか」を確認するために使います。

### 防御(OS ハードニング)

```
✅ 最小権限: sudo 権限を絞る。不要な SUID を外す(find で棚卸し)
✅ パッチ適用: カーネル・パッケージを最新に(既知 exploit を塞ぐ)
✅ ファイル権限の点検: cron/設定ファイルの書き込み権限を最小化
✅ シークレットを平文で置かない(Lesson 02)
✅ コンテナ/名前空間で分離、seccomp/AppArmor/SELinux で行動を制限
✅ 監査ログ(auditd)で不審な昇格を検知(Lesson 12)
```

## 6. 最小権限と分離 — 設計思想として

この Lesson の実践的な結論は、Lesson 01 で学んだ原則の再確認です。

- **最小権限(Least Privilege)**: プロセス・ユーザー・サービスには、必要最小限の権限だけを与える。Web サーバを root で動かさない。コンテナを非 root ユーザーで動かす(Lesson 10)
- **多層防御(Defense in Depth)**: 一つ破られても次がある。Web の脆弱性で侵入されても、権限分離とハードニングで root までは行かせない
- **フェイルセーフ**: 迷ったら「拒否」に倒す

「侵入は起きる」前提で、**侵入されても被害を最小に閉じ込める**——これが現代の防御の基本姿勢です。

## 💡 コラム: 牛が地面を掘る脆弱性「Dirty COW」— 9年間眠っていた穴

2016年、Linux カーネルに **Dirty COW(CVE-2016-5195)** と名付けられた権限昇格の脆弱性が公表されました。COW は "Copy-On-Write"(書き込み時コピー)というメモリ管理の仕組みの略で、その処理に潜む**競合状態(race condition)** を突くと、一般ユーザーが本来書き換えられないはずの root 所有ファイルを書き換え、root 権限を奪えました。世界中のほぼすべての Linux サーバ、そして Android 端末が影響を受けました。

衝撃的だったのは、このバグが**約9年間**もカーネルのソースコードに存在し続けていたことです。オープンソースで、世界中の何万人もの目に晒されていたコードの中に、これほど深刻な穴が、誰にも気づかれず眠っていた。しかも、その原因となったコードは、かつて別の問題を「修正」しようとして加えられたものでした。

発見者のフィル・オースターは、なぜ牛のロゴまで作って大々的に公表したのか。「地味なバグは無視されて放置される。名前とロゴを付けて“事件化”しないと、みんな真剣にパッチを当てないんだ」と彼は語りました。事実、Heartbleed 以降、重大な脆弱性には名前とロゴが付く文化が定着しました。マーケティングではなく、**「早くパッチを当てさせるための仕掛け」** なのです(Lesson 00 の Equifax は、パッチ放置で1.47億人を失いました)。

Dirty COW が教えるのは2つ。**(1) 「多くの目に晒されているコードは安全」は幻想**——オープンソースでも、レビューされない前提や複雑な並行処理には穴が潜む。**(2) メモリ安全な言語の重要性**——この種の低レベルなバグは、C で書かれたカーネルだからこそ起きました。あなたが将来 OS やドライバに近い層を触るなら、牛が地面を掘る音を思い出してください。

## まとめ

| 概念 | 要点 |
|------|------|
| バッファオーバーフロー | 範囲チェックなしで隣接メモリ(戻りアドレス)を上書き→RCE |
| 緩和技術 | DEP・ASLR・カナリア・PIE・CFI。攻撃(ROP)との軍拡競争 |
| メモリ安全な言語 | 根本解決。深刻脆弱性の約7割がメモリ問題。Rust 等が推奨 |
| Linux 権限 | root/一般、rwx、SUID、sudo、capabilities |
| 権限昇格 | sudo 誤設定・SUID・書込可 cron・カーネル exploit・PATH・平文鍵 |
| 防御 | 最小権限・パッチ・SUID 棚卸し・分離・監査ログ。「侵入前提」で被害を閉じ込める |

## 確認問題

1. バッファオーバーフローが「任意コード実行」に至る流れを、リターンアドレスに触れて説明してください。
2. ASLR とスタックカナリアは、それぞれ攻撃のどの段階を妨げるか説明してください。
3. 「メモリ安全な言語を使えばバッファオーバーフローが起きない」のはなぜか、C との違いで説明してください。
4. SUID ビットの正当な用途と、それが権限昇格に悪用される理由を説明してください。
5. 一般ユーザーのシェルを得た攻撃者が最初に行う「偵察」で、どんな情報を集めるか3つ挙げてください。
6. Web アプリを root で動かすべきでない理由を、多層防御・最小権限の観点から説明してください。
