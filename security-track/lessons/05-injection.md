## 0. インジェクションの本質 — たった一つの原理

OWASP Top 10 に長年君臨する「インジェクション」。SQLi、コマンドインジェクション、XXE、LDAP、NoSQL…種類は多いですが、**本質は一つ**です。

> **「データ」として扱うべきユーザー入力が、「コード(命令)」として解釈されてしまう。**

プログラムは「命令」と「データ」を混ぜて文字列を組み立てます。その境界が曖昧だと、攻撃者はデータのふりをして命令を紛れ込ませます。

```
開発者の意図:  [命令 ][    データ    ]
                SELECT ... WHERE name = 'ユーザー入力'

攻撃者の入力:  ' OR '1'='1
実際の解釈:    SELECT ... WHERE name = '' OR '1'='1'
                                       └── これが「命令」になってしまった
```

この一文を理解すれば、あらゆるインジェクションが同じ形に見えてきます。対策も一つの原則に集約されます——**命令とデータを厳密に分離する**。

## 1. SQL インジェクション(SQLi)の原理

### 脆弱なコードはこう生まれる

```python
# ❌ 脆弱: ユーザー入力を文字列連結で SQL に埋め込む
def login(username, password):
    query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
    return db.execute(query)
```

一見普通です。しかし `username` に `admin' -- ` を入れると:

```sql
SELECT * FROM users WHERE username = 'admin' -- ' AND password = '...'
```

`--` は SQL のコメント。パスワード条件が**まるごと無効化**され、パスワードを知らなくても admin でログインできます。

### 認証を突破する古典的ペイロード

| 入力 | 結果 |
|------|------|
| `' OR '1'='1` | 常に真になり全行が該当 |
| `admin'--` | 以降をコメントアウトしパスワード検証を無効化 |
| `' OR 1=1 LIMIT 1--` | 最初の1ユーザー(多くは admin)でログイン |

## 3. SQLi の発展形 — データを吸い出す

認証突破は入口です。攻撃者はさらにデータを盗みます。

### UNION ベース SQLi

`UNION SELECT` で、本来のクエリ結果に**別テーブルの中身**を継ぎ足して表示させます。

```sql
-- 検索機能: SELECT name, price FROM products WHERE name LIKE '%入力%'
-- 攻撃入力:  ' UNION SELECT username, password FROM users--
-- → 商品一覧の表示欄に、ユーザー名とパスワードが並ぶ
```

成立条件(理論): 継ぎ足す列数と型を、元のクエリに合わせる必要があります。攻撃者は `ORDER BY 1,2,3...` や `UNION SELECT NULL,NULL...` で列数を探ります。この「探る」プロセスこそ攻撃の実際です。

### ブラインド SQLi(結果が画面に出ない場合)

エラーやデータが直接表示されなくても、**アプリの反応の差**で1ビットずつ情報を引き出せます。

```
真偽ベース:  ' AND (SELECT SUBSTR(password,1,1) FROM users LIMIT 1)='a'--
  → ページが「正常表示」なら1文字目は 'a'、「エラー/空」なら違う
  → これを全文字・全桁で繰り返し、パスワードを1文字ずつ復元

時間ベース:  ' AND IF(条件, SLEEP(5), 0)--
  → 応答が5秒遅れたら条件が真。表示が一切変わらなくても抜ける
```

気の遠くなる作業ですが、これを自動化するのが次の `sqlmap` です。

### sqlmap(仕組みを知り、防御に活かす)

```bash
# ※自分のラボ/許可された標的のみ
sqlmap -u "http://localhost:3000/rest/products/search?q=test" --batch --dbs
```

`sqlmap` は上記の探索を自動化し、DB 名・テーブル・中身まで吸い出します。**攻撃者がこれほど簡単にできる**という事実が、「一箇所でも脆弱な連結があれば終わり」という危機感につながります。防御側は、自分のアプリに sqlmap をかけて穴を確認する(許可の範囲で)使い方をします。

## 4. 正しい対策 — パラメータ化クエリ(プリペアドステートメント)

対策は「入力をエスケープする」ではありません(抜け漏れます)。**命令とデータを構造的に分離する**——それがパラメータ化クエリです。

```python
# ✅ 安全: プレースホルダを使う。値は「データ」としてのみ扱われる
def login(username, password):
    query = "SELECT * FROM users WHERE username = ? AND password = ?"
    return db.execute(query, (username, password))
```

### なぜこれで完全に防げるのか(理論)

パラメータ化では、DB は**先にクエリの構造(命令)をコンパイル**し、後から値(データ)を「純粋な値」として当てはめます。値の中にどんな `'` や `--` があっても、それは「文字列データの一部」でしかなく、**クエリ構造には一切影響しません**。命令とデータの境界が、文字列処理ではなくプロトコルレベルで保証されるのです。これがエスケープより本質的に優れる理由です。

### ORM も正しく使えば安全

```python
# ✅ ORM(SQLAlchemy)は内部でパラメータ化する
user = session.query(User).filter(User.username == username).first()

# ❌ ただし生 SQL を文字列連結すれば ORM でも脆弱
session.execute(f"SELECT * FROM users WHERE name = '{username}'")  # 台無し
```

### 多層防御

- **入力バリデーション**: 想定される形式(メール形式・英数字のみ等)を検証。ただし**これは補助**。主対策はパラメータ化
- **最小権限の DB ユーザー**: アプリ用 DB ユーザーに `DROP` や他テーブルへの権限を与えない。万一突破されても被害を限定
- **WAF**: 既知の攻撃パターンを遮断(すり抜けは前提。あくまで一層)
- **エラーメッセージを出さない**: SQL エラーをそのまま返すとブラインドが楽になる

## 5. コマンドインジェクション

原理は SQLi と同じ——ユーザー入力が**OS コマンド**として解釈されます。

```python
# ❌ 脆弱: 入力を shell コマンドに連結
import os
def ping(host):
    os.system(f"ping -c 1 {host}")   # host = "8.8.8.8; rm -rf /" なら?

# 攻撃入力: 8.8.8.8; cat /etc/passwd
# 実行される: ping -c 1 8.8.8.8; cat /etc/passwd
```

`;` `&&` `|` `$(...)` `` `...` `` などのシェルメタ文字で、任意コマンドを連結されます。

### 対策

```python
# ✅ 安全: シェルを介さず、引数を配列で渡す(メタ文字が解釈されない)
import subprocess
def ping(host):
    subprocess.run(["ping", "-c", "1", host], shell=False)  # shell=False が肝
```

- **`shell=True` を使わない**。配列でコマンドと引数を分離(= 命令とデータの分離、またこの原則)
- そもそも**OS コマンドを呼ばずライブラリで代替**できないか考える
- どうしても入力を渡すなら厳格なホワイトリスト検証

DVWA の "Command Injection" ページ(Low → High)で、`127.0.0.1; ls` のようなペイロードを試し、難易度が上がると何が制限されるかを観察すると理解が深まります。

## 6. XXE(XML External Entity)

XML パーサの機能を悪用する攻撃です。XML には「外部エンティティ」を読み込む機能があり、これを悪用するとサーバのファイルを読まれたり、SSRF(Lesson 08)の踏み台にされます。

```xml
<!-- ❌ 攻撃ペイロード: 外部エンティティでサーバのファイルを読む -->
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<data>&xxe;</data>
<!-- パーサが /etc/passwd を読み込み、レスポンスに含めてしまう -->
```

### 対策

```python
# ✅ 外部エンティティの解決を無効化する
from lxml import etree
parser = etree.XMLParser(resolve_entities=False, no_network=True)
```

- XML パーサの**外部エンティティ/DTD 処理を無効化**する(多くの言語で設定可能)
- 可能なら XML をやめて **JSON** を使う(XXE のリスク自体が消える)

## 7. インジェクションを一望する

| 種類 | 混入先 | 危険なコード | 対策 |
|------|--------|------------|------|
| SQLi | SQL クエリ | 文字列連結 | パラメータ化クエリ |
| コマンド | OS シェル | `os.system(f"...")` | 配列渡し・`shell=False` |
| XXE | XML パーサ | 外部エンティティ許可 | エンティティ解決を無効化 |
| NoSQL | Mongo 等のクエリ | 入力を演算子として渡す | 型検証・演算子を弾く |
| LDAP | ディレクトリ検索 | フィルタ文字列連結 | エスケープ・パラメータ化 |
| テンプレート(SSTI) | テンプレートエンジン | ユーザー入力をテンプレートに | ユーザー入力をテンプレートにしない |

**すべてに共通する原則**: 「命令」と「データ」を混ぜて文字列で組み立てず、構造的に分離する。この一文が Lesson 05 の全てです。

## 💡 コラム: ボビー・テーブルくんと、1998年から変わらない王者

プログラマーに絶大な人気を誇るウェブ漫画 xkcd に、伝説的な一コマがあります。学校から母親に電話がかかってきます。「お宅の息子さんの名前のことで…」。母の名は **Robert'); DROP TABLE Students;-- **。学校の生徒管理システムは、この名前をそのまま SQL に埋め込み、生徒データベースを丸ごと消し飛ばしてしまったのです。母は悪びれず言います。「あなたたちのデータベースの入力検証が甘いのが悪いのよ。これに懲りたわね」。以来、SQL インジェクションは英語圏で "**Little Bobby Tables**" の愛称で語り継がれています。

笑い話に聞こえますか? しかしこれは1998年、Phrack 誌の記事 "NT Web Technology Vulnerabilities" で SQL インジェクションが公に解説されて以来、**四半世紀にわたって OWASP Top 10 のトップ級に居座り続けている**、現役最強の脆弱性です。冒頭で触れた通り、対策は1998年から変わっていません——「パラメータ化クエリを使う」。たったこれだけ。

なぜこんな単純な対策で防げる攻撃が、今も世界中のサービスを破り続けているのか。答えは残酷です。**たった一箇所、たった一人の開発者が、たった一度、文字列連結を書けば、そこが穴になる**から。何万行が完璧でも、`f"...{input}..."` が一行あれば陥落します。だからこそセキュリティは「全員が・毎回・例外なく」正しく書く文化の問題であり、それを支えるのがコードレビューと自動検査(Lesson 13)なのです。ボビー・テーブルくんは、25年経った今も、あなたのコードレビューを待っています。

## まとめ

| 概念 | 要点 |
|------|------|
| 本質 | データがコード(命令)として解釈される。全インジェクション共通 |
| SQLi | 文字列連結が原因。`' OR 1=1--` で認証突破、UNION/ブラインドで窃取 |
| 対策の王道 | パラメータ化クエリ。命令とデータを構造的に分離 |
| コマンドi | `shell=False` + 配列渡し。そもそもシェルを呼ばない |
| XXE | 外部エンティティを無効化。可能なら JSON へ |
| 多層防御 | 最小権限 DB・入力検証・WAF・エラー秘匿は「補助」。主対策はパラメータ化 |

---

## 確認問題

1. インジェクション攻撃全般に共通する「本質」を一文で説明してください。
2. `SELECT * FROM users WHERE name = '{input}'` に `' OR 1=1--` を入れると、なぜ認証が突破されるのか、展開後のクエリを示して説明してください。
3. パラメータ化クエリが「エスケープ」より本質的に優れる理由を、DB がクエリを処理する順序に触れて説明してください。
4. ブラインド SQLi で、画面に何も表示されないのに情報を抜けるのはなぜか、真偽ベース/時間ベースの例で説明してください。
5. `os.system(f"convert {filename} out.png")` の危険性を指摘し、安全な書き換えを示してください。
6. 「WAF を入れたので SQLi は対策済み」という主張の問題点を、多層防御の観点から述べてください。
