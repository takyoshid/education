# Lesson 12: ブルーチームとインシデントレスポンス

## 学習目標

- ログ・SIEM・検知エンジニアリングの役割を理解する
- 「侵害の兆候(IoC)」を見つけ、ログから攻撃を再構築できる
- インシデントレスポンスの6フェーズを実行できる
- デジタルフォレンジックの初動(証拠保全)を理解する
- ポストモーテムで組織を強くする方法を知る

---

## 0. 攻撃者は一度成功すればいい。守る側は毎回勝たねばならない

これがブルーチーム(防御側)の宿命です。攻撃者は千回失敗しても一回成功すれば侵入できます。守る側は、その一回を検知し、被害が広がる前に止めなければなりません。だから防御の思想は「侵入を防ぐ」だけでなく、**「侵入は起きる前提で、早く気づき、素早く封じ込める」** へと重心を移しています(Lesson 09 の姿勢)。

Lesson 01 の Kill Chain を思い出してください。攻撃者は7段階を進みます。**防御側はどこか一段で気づいて断ち切れば勝てる。** そのための「気づく力」を作るのがこの Lesson です。

---

## 1. ログ — 見えないものは守れない

防御の出発点はログです。**記録がなければ、侵害されても気づけず、後から何が起きたかも分かりません**(Lesson 10 の「ログ無効」が最悪の設定なのはこのため)。

### 何を記録すべきか

```
✅ 認証イベント(ログイン成功/失敗、権限昇格)
✅ アクセスログ(誰が・いつ・何に・どこから)
✅ 重要操作(データ削除、設定変更、権限付与)
✅ ネットワーク(接続元/先、異常な通信量)
✅ システム(プロセス起動、ファイル変更 — Lesson 09 の auditd)
✅ クラウド監査ログ(AWS CloudTrail 等 — Lesson 10)
```

### ログ設計の原則

- **改ざん防止**: 攻撃者は痕跡を消そうとする(ATT&CK の Defense Evasion)。ログは書き込み専用の別システムへ集約する
- **十分な保持期間**: 侵害は平均数ヶ月見つからない。短すぎる保持は致命的
- **相関できる形式**: タイムスタンプ(UTC)・ユーザー ID・リクエスト ID を揃え、横断検索できるように
- **秘密を記録しない**: パスワード・トークンをログに出さない(Lesson 02)

## 2. SIEM と検知エンジニアリング

### SIEM とは

**SIEM(Security Information and Event Management)** は、各所のログを一箇所に集約・相関分析し、脅威を検知する仕組み(Splunk、Elastic Security、Microsoft Sentinel など)。個々のログでは無害でも、**繋げると攻撃が見える**のがポイントです。

```
単体では無害:
  ・深夜のログイン失敗が数回
  ・普段と違う国からのアクセス
  ・大量のデータダウンロード
繋げると:
  → 総当たり成功 → 不審な地域 → データ持ち出し = 侵害の可能性
```

### 検知エンジニアリング(Detection Engineering)

「どんなパターンを見たらアラートを出すか」を設計・実装する仕事です。Lesson 01 の **MITRE ATT&CK** をマップにして、「自社は各攻撃手法を検知できるか」の穴を埋めます。

```yaml
# 検知ルールの例(概念。Sigma 形式風)
title: 短時間に大量のログイン失敗(ブルートフォース)
detection:
  selection:
    event: authentication_failure
  timeframe: 5m
  condition: selection | count() by source_ip > 20
level: high
```

### 検知の質 — 誤検知との戦い

```
真陽性(True Positive):  攻撃を正しく検知 ✅
偽陽性(False Positive): 正常を攻撃と誤検知 → アラート疲れ(狼少年)
偽陰性(False Negative): 攻撃を見逃す → 最悪
```

**アラート疲れ**は現実の脅威です。誤検知が多すぎると、本物のアラートが埋もれます。「感度を上げる」と偽陽性が増え、「絞る」と偽陰性が増える——このバランス調整が検知エンジニアの腕の見せ所です。

## 3. ハンズオン: ログから攻撃を読む

実際のアクセスログから侵害を見つける練習です(演習 `06-incident-response.md` で本格的に)。

### 攻撃の「兆候」を探す

```bash
# 大量の 401/403(総当たり・認可回避の試行)
grep -E ' (401|403) ' access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head

# SQLi/XSS の痕跡(URL に攻撃ペイロード)
grep -Ei "union.*select|' or |<script|\.\./|/etc/passwd" access.log

# 1つの IP からの異常なリクエスト数(スキャン・総当たり)
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# 通常と違う User-Agent(sqlmap, nikto, curl など攻撃ツール)
grep -Ei "sqlmap|nikto|nmap|masscan|hydra" access.log
```

### 攻撃者の「1日」を再構築する

ログを時系列で並べ、攻撃のストーリーを組み立てます。

```
09:14  同一IPから /admin, /backup, /.git へ次々アクセス(偵察・列挙)
09:20  /login に大量の POST(総当たり)
09:23  /login が突然 200(突破された?)
09:24  /api/users/1, /2, /3... と連番アクセス(IDOR でデータ収集)
09:31  巨大なレスポンスサイズ(データ持ち出し)
```

これができると、あなたは Lesson 00 のクリフォード・ストールと同じことをしています——**違和感を時系列で繋ぎ、攻撃者の足跡を再構築する**。

### IoC(Indicator of Compromise)

侵害の痕跡となる具体的な指標。攻撃者の IP、マルウェアのハッシュ、不審なドメイン、特徴的なファイルパスなど。IoC を集めて共有することで、同じ攻撃を他組織でも早期発見できます(脅威インテリジェンス)。

## 4. インシデントレスポンス(IR)の6フェーズ

侵害が起きたとき、慌てないための標準手順(NIST/SANS)。

```
1. 準備(Preparation)      … 手順・連絡網・ツールを平時に整える(最重要)
2. 検知と分析(Detection)   … 何が起きたか特定。範囲と深刻度を評価
3. 封じ込め(Containment)   … 被害の拡大を止める(隔離・アカウント無効化)
4. 根絶(Eradication)      … 原因を除去(マルウェア削除・脆弱性修正)
5. 復旧(Recovery)         … 正常化。監視しながら段階的に戻す
6. 教訓(Lessons Learned)   … ポストモーテムで次に活かす
```

### 「準備」が9割

インシデント発生後に手順を考えるのは手遅れです。平時に「誰が指揮を取るか」「どう連絡するか」「どこにバックアップがあるか」を決め、**訓練(机上演習)** をしておく。消防訓練と同じで、本番で慌てないための日常です。

### 封じ込めのジレンマ

```
すぐ電源を切る → 攻撃を止められるが、メモリ上の証拠が消える
稼働させ続ける → 証拠を保全できるが、被害が広がるかも
```

このトレードオフを、事前に決めた方針とその場の判断で解きます。**「証拠保全」と「被害停止」の両立**が IR の難所です。

## 5. デジタルフォレンジック — 証拠の科学

**フォレンジック**は、何が起きたかを証拠から科学的に解明する営みです。訴訟や責任追及に使えるよう、証拠の完全性が命です。

### 証拠保全の鉄則

```
✅ Order of Volatility(揮発性の高い順に保全):
   メモリ(RAM)→ ネットワーク接続 → プロセス → ディスク → ログ
   (電源を切るとメモリは消える。順番が重要)

✅ Chain of Custody(証拠の連鎖):
   誰が・いつ・どう証拠を扱ったかを記録。改ざんされていない証明

✅ ハッシュで完全性を担保(Lesson 02):
   ディスクイメージのハッシュを取り、複製が原本と同一だと証明

✅ 原本は触らず、複製(イメージ)を解析する
```

### 何を調べるか

- **タイムライン分析**: ファイルのアクセス/変更時刻を並べ、攻撃の流れを再構築
- **メモリフォレンジック**: 実行中のマルウェア、暗号鍵、注入コードを RAM から発見(Volatility 等)
- **ディスクフォレンジック**: 削除ファイルの復元、隠しデータ、ログ
- **ネットワークフォレンジック**: パケットキャプチャから通信を再構築(Lesson 03 の Wireshark)

## 6. ポストモーテム — 失敗を組織の力に変える

インシデントの後、**「誰が悪いか」ではなく「何が悪かったか」** を問う振り返りを行います。これが**ブレームレス(非難なし)ポストモーテム**です。

### なぜ「非難なし」か(理論)

人を責める文化では、失敗が隠蔽されます。隠されたら学べません。「担当者 X がミスした」で止めると、「なぜそのミスが起こりうる仕組みだったのか」に到達しません。**個人の失敗は、システムの弱さの症状**と捉え、仕組みを直します。

```
❌ 「A さんがパッチを当て忘れた」→ A さんを叱る → 再発する
✅ 「パッチ適用が手作業で、抜け漏れる仕組みだった」
   → 自動化・監視を入れる → 再発しない仕組みに
```

### ポストモーテムの構成

```
1. 何が起きたか(タイムライン)
2. 影響(誰が・どれだけ)
3. 根本原因(なぜを繰り返す。5 Whys)
4. うまくいったこと/いかなかったこと
5. 再発防止のアクション(担当・期限つき)
```

Lesson 00 の Equifax、Lesson 08 のキャピタル・ワン——これらが世界の教訓になったのは、事故が分析・共有されたからです。**あなたのインシデントも、正しく振り返れば、組織を強くする資産になります。**

## 💡 コラム: ハニーポットという「おとり」と、ストールの遺産

Lesson 00 で、クリフォード・ストールが偽の機密文書で侵入者を釣った話をしました。彼が即興でやったこの手口は、今や **ハニーポット(honeypot)** という確立された防御技術になっています。

ハニーポットとは、**わざと侵入されやすく見せかけた「おとりのシステム」** です。攻撃者がそこに手を出せば、(1) 本物の資産から気をそらせ、(2) 攻撃者の手口・ツール・目的を安全に観察でき、(3) そもそも「ハニーポットに触れた」こと自体が「これは攻撃者だ」という極めて精度の高いアラートになります。正規ユーザーは、存在すら知らないおとりサーバにアクセスする理由がないからです——つまり**偽陽性がほぼゼロの検知器**。

さらに発展した「ハニートークン」は面白いアイデアです。使われるはずのない偽の認証情報やファイル(例: `passwords_final.xlsx` という名の罠ファイル、決して使わない偽の API キー)を各所に置いておき、**それが一度でも使われたら侵害の確定的な証拠**とする。攻撃者は「宝物」だと思って掴んだ瞬間、警報を鳴らしているのです。

この発想の美しさは、防御を「壁を高くする」だけでなく「**攻撃者に罠を踏ませ、その存在を暴く**」という能動的なゲームに変えたことです。ストールが75セントの謎から始めた「違和感を追い、おとりで相手を観察する」という探偵仕事は、40年を経て、世界中の SOC(セキュリティ監視センター)の日常になりました。防御は、じっと耐えるだけの仕事ではありません。**知恵で罠を張り、攻撃者に自ら正体を明かさせる**——それがブルーチームの醍醐味です。

## まとめ

| 概念 | 要点 |
|------|------|
| 防御の宿命 | 攻撃者は一度成功すればいい。守る側は毎回勝つ。侵入前提で早く気づく |
| ログ | 見えないものは守れない。改ざん防止・十分な保持・相関可能に |
| SIEM/検知 | ログを相関し脅威を検知。ATT&CK で穴を埋める。誤検知とのバランス |
| ログ解析 | 401/403 急増・攻撃ペイロード・異常な IP を追い、時系列で再構築 |
| IR 6フェーズ | 準備→検知→封じ込め→根絶→復旧→教訓。準備が9割 |
| フォレンジック | 揮発性順に保全・証拠の連鎖・ハッシュで完全性。原本は触らない |
| ポストモーテム | 非難なし。個人でなく仕組みを直す。事故を組織の力に変える |

## 確認問題

1. 「攻撃者は一度成功すればよく、守る側は毎回勝たねばならない」が、防御の設計思想にどう影響するか説明してください。
2. 個々のログでは無害な事象が、SIEM で相関すると攻撃に見える例を挙げてください。
3. 検知における偽陽性・偽陰性のトレードオフと、「アラート疲れ」の問題を説明してください。
4. インシデントレスポンスの6フェーズを挙げ、「準備」が最重要とされる理由を述べてください。
5. フォレンジックで「揮発性の高い順に証拠を保全する」理由を説明してください。
6. ブレームレス・ポストモーテムがなぜ再発防止に有効なのか、隠蔽との関係で説明してください。
