# Lesson 03: ネットワークと TLS の攻防

## 学習目標

- TCP/IP の各層を「攻撃者の視点」で理解する
- nmap でポートスキャンし、攻撃面を可視化できる
- Wireshark でパケットを観察し、平文通信の危険を体感する
- 中間者攻撃(MITM)の原理と、TLS がそれをどう防ぐかを説明できる
- DNS・ARP の弱点と、ゼロトラストの考え方を理解する

---

## 0. ネットワークは「信用できない土管」

セキュリティにおけるネットワークの大前提はこれです。

> **通信経路は、誰かに盗み見られ・書き換えられている前提で設計する。**

インターネットのパケットは、あなたの手を離れた瞬間、無数のルータ・スイッチ・Wi-Fi アクセスポイントを通ります。そのどこか一つでも悪意があれば、平文の通信は丸見えです。カフェの Wi-Fi、ホテルのネット、ISP——すべて「信用できない土管」です。この前提が、暗号(Lesson 02)がなぜ必要かの答えでした。

---

## 1. TCP/IP を攻撃者の目で見る

Web の通信は層(レイヤ)に分かれています。各層に固有の攻撃があります。

```
アプリ層    HTTP/DNS/TLS  … Web 攻撃(Lesson 04〜08)、DNS 偽装
トランスポート層 TCP/UDP    … ポートスキャン、SYN フラッド(DoS)
インターネット層 IP         … IP 偽装(spoofing)、経路ハイジャック
リンク層    Ethernet/ARP/WiFi … ARP スプーフィング、Wi-Fi 盗聴
```

### ポートとは、そして攻撃面

サーバは「ポート番号」ごとに違うサービスを待ち受けます(HTTP=80、HTTPS=443、SSH=22、PostgreSQL=5432 など)。攻撃者はまず「**どのポートが開いているか**」を調べます。開いているポートは、そのままそのサーバの**攻撃面**だからです。

```
開いているポート = そのサーバが外に見せているドア
→ ドアが多いほど、どれか一つが脆弱である確率が上がる
→ 使っていないサービスは止める(攻撃面の最小化)
```

## 2. ハンズオン: nmap でポートスキャン

**nmap** は世界標準のポートスキャナです。まず自分のマシンや、許可されたラボの標的だけをスキャンします(倫理ルールを思い出してください)。

Lesson 00 で起動した Juice Shop(`localhost:3000`)を標的に:

```bash
# 基本スキャン(よく使われる1000ポート)
nmap localhost

# バージョン検出 + よく使うポート(-sV: サービス版, -T4: 高速)
nmap -sV -T4 127.0.0.1

# 全65535ポートを調べる(時間がかかる)
nmap -p- 127.0.0.1

# OS 推定やスクリプトも(-A: 積極的)。※許可された標的のみ
nmap -A 127.0.0.1
```

出力の読み方(理論):

```
PORT     STATE    SERVICE   VERSION
3000/tcp open     http      Node.js Express
```

- `open`: 待ち受けている(攻撃面)
- `closed`: ポートは応答するがサービスなし
- `filtered`: ファイアウォールに遮られ、開閉すら分からない

### なぜ「filtered」が防御的に重要か

ファイアウォールで `filtered` にすると、攻撃者は「そこにサービスがあるか」すら分かりません。**攻撃は偵察から始まる**ので、偵察を困難にすること自体が防御になります(Lesson 01 の Kill Chain 第1段階を断つ)。

> ⚠️ **nmap は許可なしに他人のサーバへ撃たない**。ポートスキャンだけでも、国や状況によっては不正アクセスと見なされ得ます。TryHackMe/HTB など合法的な練習場か、自分のラボで。

## 3. ハンズオン: Wireshark で「平文の恐怖」を見る

**Wireshark** はパケットを可視化するツールです。「HTTP は平文」という言葉を、目で見て腹落ちさせます。

1. Wireshark を起動し、ローカルループバック(またはラボの)インターフェースをキャプチャ開始
2. フィルタに `http` と入力
3. ブラウザで **HTTP(HTTPS でない)** のログインフォームを送信(DVWA のログインなどで)
4. キャプチャされた `POST` パケットを開き、`Follow → HTTP Stream` を見る

すると、**ユーザー名とパスワードが生のテキストで表示されます**。

```
POST /login HTTP/1.1
...
username=admin&password=SuperSecret123
```

これがカフェの Wi-Fi で起きていたら——同じ回線の誰でもこれを読めます。**HTTP を使ってはいけない理由**が、理屈でなく体感で分かります。

次に HTTPS で同じことをすると、`tls` フィルタでは中身が暗号化されて読めません。これが暗号(Lesson 02)の効果です。

## 4. 中間者攻撃(MITM)の原理

**中間者攻撃(Man-in-the-Middle)** は、通信の途中に割り込んで盗聴・改ざんする攻撃です。

```
正常:   [Alice] ───────────────────> [Bob]

MITM:   [Alice] ──> [攻撃者] ──> [Bob]
                     ↑ Alice には「私が Bob だ」、
                       Bob には「私が Alice だ」と偽る
```

Lesson 00 で mitmproxy を使ったとき、あなたは自分自身に対して MITM を行っていました。プロキシがブラウザとサーバの間に入り、通信を復号していましたね。あれがまさに MITM の仕組みです。

### 攻撃者はどうやって「間に入る」のか

- **ARP スプーフィング**: LAN 内で「ゲートウェイの MAC アドレスは私です」と嘘の ARP 応答を流し、通信を自分に引き込む
- **不正 Wi-Fi(Evil Twin)**: 正規と同じ名前(SSID)の偽アクセスポイントを立て、接続させる
- **DNS 偽装**: 名前解決を乗っ取り、偽サーバへ誘導(次節)

## 5. TLS は MITM をどう防ぐか — 証明書の役割

Lesson 02 で TLS の暗号面を見ました。ここでは「**なりすまし(MITM)をどう防ぐか**」に絞ります。

暗号化するだけでは MITM を防げません。攻撃者と暗号通信を確立してしまえば、盗聴は成立するからです。鍵は「**相手が本物のサーバだと、どう確かめるか**」。ここで **証明書(certificate)** が効きます。

```
1. サーバは「証明書」を提示する
   → 証明書 = サーバの公開鍵 + ドメイン名 + CA のデジタル署名
2. ブラウザは、その証明書が信頼された CA(認証局)によって
   署名されているかを検証する(Lesson 02 のデジタル署名!)
3. 署名が正しく、ドメイン名も一致すれば「本物」と判断
```

攻撃者が MITM しようとしても、`example.com` の正規証明書に対応する**秘密鍵を持っていない**ため、偽の証明書はブラウザに拒否されます(あの赤い警告画面)。

### 証明書が保証する「もの」と「しないこと」

- ✅ 保証する: 「この通信相手は、確かに `example.com` を管理している者だ」
- ❌ 保証しない: 「その相手が善良である」——フィッシングサイトも正規の証明書を取れます。「鍵マークがある=安全」ではない点に注意

### なぜ mitmproxy は復号できたのか(伏線回収)

Lesson 00 で mitmproxy の CA 証明書を**自分でブラウザに信頼させた**からです。つまり「攻撃者の CA を信頼する」と自ら宣言した状態。だから MITM が成立しました。逆に言えば、**信頼する CA を汚染されなければ TLS は堅牢**です。企業のセキュリティ製品が通信を検査できるのも同じ仕組み(社内 CA を端末に配布)です。

### 防御を固める設定

- **HSTS(HTTP Strict Transport Security)**: 一度アクセスしたら次回から HTTP を拒否し必ず HTTPS に。初回の HTTP→HTTPS の隙(SSL ストリッピング)を塞ぐ
- **証明書ピンニング(pinning)**: 特定の証明書/公開鍵だけを信頼(モバイルアプリで有効)
- **TLS 1.2 以上**(できれば 1.3)。古い SSL/TLS・弱い暗号スイートを無効化

## 6. DNS — インターネットの電話帳を狙う

**DNS(Domain Name System)** はドメイン名(`example.com`)を IP アドレスに変換します。ここが乗っ取られると、正しい URL を入力しても偽サイトに飛ばされます。

```
DNS スプーフィング/キャッシュポイズニング:
  「example.com は 6.6.6.6(攻撃者のサーバ)です」という
   偽の応答をキャッシュに紛れ込ませる
→ ユーザーは正しい URL を打ったのに偽サイトへ
```

対策の理論:

- **DNSSEC**: DNS 応答にデジタル署名を付け、改ざんを検出(またしても署名!)
- **DoH / DoT(DNS over HTTPS / TLS)**: DNS クエリ自体を暗号化し、盗聴・改ざんを防ぐ

DNS 関連は Web 攻撃とも深く絡みます。**サブドメインテイクオーバー**(廃止したサービスを指す DNS レコードを攻撃者が乗っ取る)や、後の Lesson 08 の SSRF とも関係します。

## 7. ファイアウォールとゼロトラスト

### 従来の「境界防御」とその限界

昔の発想は「城壁の内側(社内ネットワーク)は安全、外側は危険」でした。ファイアウォールで境界を守り、中に入れば信頼する。しかしこのモデルは、**一度侵入されると内部を自由に横移動(lateral movement)される**弱点があります(Lesson 01 の Kill Chain・ATT&CK)。リモートワークやクラウドで「内と外」の境界も曖昧になりました。

### ゼロトラスト(Zero Trust)

```
従来:   「ネットワークの内側なら信頼する」
ゼロトラスト: 「誰も・何も、最初から信頼しない。毎回検証する」
        (Never trust, always verify)
```

- ネットワークの位置ではなく、**リクエストごとに認証・認可**する
- **最小権限**を徹底(必要なリソースにだけアクセス許可)
- デバイスの状態・ユーザーの振る舞いも継続的に評価

Google の **BeyondCorp** が有名な実装例です。現代のクラウド設計(Lesson 10)は、このゼロトラストが前提になっています。

## 8. DoS / DDoS — 可用性への攻撃

STRIDE の "D"(Denial of Service)。サーバを高負荷で応答不能にする攻撃です。

- **SYN フラッド**: TCP の3ウェイハンドシェイクを途中で放置し、接続テーブルを枯渇させる
- **増幅攻撃(amplification)**: 小さなリクエストで大きな応答を返すサービス(DNS, NTP)を踏み台に、偽装した被害者へ大量応答を集中させる
- **DDoS**: 多数のマシン(ボットネット)から一斉に

対策: レート制限、CDN / WAF(Cloudflare 等)、オートスケール、アノマリ検知。完全な防止は難しく、「**吸収して耐える**」設計が中心になります。

## 💡 コラム: 世界を止めた「Mirai」— 監視カメラの反乱

2016年10月、大手 DNS プロバイダ **Dyn** が巨大な DDoS 攻撃を受け、Twitter・Netflix・GitHub・Spotify など米国の主要サイトが軒並みアクセス不能になりました。攻撃の出どころは、スパコンでもハッカー集団のPCでもありません。**世界中の、ごく普通の監視カメラや家庭用ルータ、ビデオレコーダー**でした。

犯人は **Mirai(未来)** というマルウェア。その手口は拍子抜けするほど単純です——工場出荷時のまま変更されていない**初期パスワード**(`admin/admin`、`root/12345` など)を、たった60通りほどのリストで次々に試すだけ。 IoT 機器の持ち主は、自分のカメラが世界的攻撃に加担していることすら知りませんでした。数十万台の「乗っ取られた家電」が、一斉に Dyn へパケットを浴びせたのです。

そして衝撃的なのは、作者が Mirai のソースコードを**インターネットに公開**したこと。以後、亜種が無数に生まれ、今も IoT を狙い続けています。

この事件が突きつけた真実は2つ。**(1) 最も弱い一台が、全体の脅威になる**——ゼロトラストが「何も信頼しない」と言うのはこのためです。**(2) 最先端の攻撃より、初期パスワードの放置という“基本の欠落”のほうが、はるかに大きな被害を生む。** あなたが将来 IoT やサーバを設計するとき、真っ先にやるべきは高度な防御ではなく、「初期パスワードを強制変更させること」なのです。

## まとめ

| 概念 | 要点 |
|------|------|
| 大前提 | ネットワークは盗聴・改ざんされる前提で設計する |
| ポートスキャン | nmap で攻撃面を可視化。開いたポート=ドア。不要なら閉じる |
| 平文の危険 | HTTP は Wireshark で丸見え。HTTPS 必須 |
| MITM | 通信に割り込む攻撃。TLS の証明書検証で「なりすまし」を防ぐ |
| 証明書 | 「相手が本物のドメイン管理者」を保証。善良さは保証しない |
| DNS | 電話帳を狙う攻撃。DNSSEC/DoH で守る |
| ゼロトラスト | 「内側だから信頼」をやめ、毎回検証・最小権限 |
| DDoS | 可用性攻撃。防ぐより吸収して耐える設計 |

## 確認問題

1. nmap で `open` / `closed` / `filtered` の違いを説明し、防御側が `filtered` を選ぶ利点を述べてください。
2. HTTPS が「暗号化」だけでなく「なりすまし防止」も実現できる仕組みを、証明書とデジタル署名の言葉で説明してください。
3. 「鍵マーク(HTTPS)が付いているから安全なサイトだ」という主張の誤りを指摘してください。
4. Lesson 00 で mitmproxy が HTTPS を復号できたのはなぜか、TLS の信頼モデルの観点から説明してください。
5. ゼロトラストが従来の境界防御と根本的に異なる点を、Kill Chain の「横展開(lateral movement)」に触れつつ説明してください。
6. Mirai の事例から、IoT 機器を設計するエンジニアが最初にやるべき対策を1つ挙げ、理由を述べてください。
