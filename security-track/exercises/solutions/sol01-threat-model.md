# 模範解答 01: 脅威モデル(家計簿 SaaS)

> これは「唯一の正解」ではなく、思考の型を示すもの。あなたの答えがこれより多くの脅威を挙げていれば、それは素晴らしい。

## 1. 攻撃面(例)

外部:
1. ログイン/登録フォーム(認証情報の総当たり・SQLi)
2. パスワードリセット(トークン推測・アカウント乗っ取り)
3. 銀行 API 連携コールバック(OAuth の redirect_uri・state)
4. 家族招待(招待リンク・メール)
5. CSV エクスポート(IDOR・パストラバーサル)
6. 管理者ダッシュボード(認可不備・アクセス制御)
7. ファイル/画像アップロード(あれば)
8. API エンドポイント全般(IDOR・レート制限)

内部:
9. データベース(取引明細・個人情報)
10. 銀行 API のアクセストークン保管
11. メール送信基盤(なりすまし送信)
12. クラウドメタデータ(SSRF の標的)・シークレット

## 2. 信頼境界(例)

- ブラウザ ↔ Web アプリ(外部入力が入る最重要境界)
- Web アプリ ↔ データベース
- Web アプリ ↔ 外部銀行 API / メール送信(第三者サービス)
- 一般ユーザー権限 ↔ 管理者権限

## 3. DFD(テキスト版)

```
[ユーザー] --(1)ログイン/操作--> ((Webアプリ)) --(2)クエリ--> [DB]
                                    │
                                    ├--(3)明細取得--> [銀行API]
                                    ├--(4)招待メール--> [メール送信]
                                    └--(5)エクスポート--> [ユーザー]
       信頼境界: (1)外部入力  (2)/(3)/(4) 外部サービス
```

## 4. STRIDE 表(抜粋10件)

| 要素 | STRIDE | 脅威 | 対策 |
|------|--------|------|------|
| ログイン(1) | S | クレデンシャルスタッフィング | レート制限・MFA・パスワード漏洩チェック |
| ログイン(1) | S | セッションハイジャック | HttpOnly/Secure/SameSite Cookie |
| クエリ(2) | I | SQLi で全明細窃取 | パラメータ化・最小権限 DB ユーザー |
| API | E | IDOR で他人の家計を閲覧 | リソース所有者チェック |
| 管理画面 | E | 一般ユーザーが管理機能へ | サーバ側の認可強制・ロール検証 |
| 招待(4) | S | 招待リンク推測で不正参加 | 予測不可能なトークン・期限 |
| 銀行連携(3) | T | OAuth state 欠如で CSRF | state + PKCE + redirect_uri 完全一致 |
| エクスポート(5) | I | パストラバーサルでファイル奪取 | パス正規化・基準ディレクトリ検証 |
| 全体 | R | 「私は操作していない」と否認 | 監査ログ(認証・重要操作) |
| Web アプリ | D | 大量リクエストでダウン | レート制限・WAF・オートスケール |
| トークン保管 | I | 銀行トークン漏洩 | 暗号化・シークレットマネージャ |
| メール(4) | S | なりすまし送信 | SPF/DKIM/DMARC |

## 5. リスク優先度トップ3(例)

1. **SQLi(認証/明細)** — 起こりやすさ高 × 影響甚大(全データ流出)。即修正
2. **IDOR** — 起こりやすさ高(URL 変更だけ) × 影響大(全ユーザーの家計)。即修正
3. **管理画面の認可不備** — 影響致命的(全権限)。即修正

理由: いずれも「全ユーザーに波及」かつ「攻撃が容易」。CIA すべてを一撃で損なう。

## 6. 招待機能の abuse case(例)

| 悪用シナリオ | 対策 |
|-------------|------|
| 招待トークンを総当たり/推測して他家庭に侵入 | 十分長い乱数トークン + 短い有効期限 + 使い捨て |
| 退会した元家族が引き続きデータを見られる | 招待の失効・アクセス権の即時剥奪 |
| 招待メールを乗っ取り、被害者を攻撃者の家計に紐付けて情報を吸う | 招待受諾時に本人確認・既存アカウントとの整合チェック |

## 学びのポイント

- 見落としやすいのは **R(否認)= 監査ログ** と **E(権限昇格)= 認可**。この2つを毎回意識する。
- 対策は必ず「技術的施策」で書く。「注意する」は対策ではない。
