# 模範解答 06: ログから侵害を暴く

## レベル1: 検出

```bash
# IP ごとのリクエスト数(攻撃元の炙り出し)
awk '{print $1}' access.log | sort | uniq -c | sort -rn
#   → 203.0.113.7 が突出。198.51.100.23 は正常ユーザー(Mozilla, 通常ページ)

# 攻撃ツールの痕跡(User-Agent)
grep -Ei "curl|python-requests|sqlmap|nikto" access.log
#   → curl(偵察)と python-requests(自動化された攻撃)

# 攻撃ペイロード
grep -Ei "union|select|\.\./|/etc/passwd|\.git" access.log
#   → /.git/config(偵察)、UNION SELECT(SQLi)
```

**攻撃元**: `203.0.113.7`。根拠: リクエスト数が突出、攻撃ツールの UA、偵察→総当たり→SQLi→大量持ち出しの一貫した攻撃パターン。

## レベル2: タイムライン再構築

| 時刻 | ログ | 段階(Kill Chain) |
|------|------|------------------|
| 09:14 | `/.git/config`, `/admin`(403), `/backup.zip` | **偵察・列挙**(隠しファイル/管理画面探し) |
| 09:20 | `/login` に 401 が連続4回(python-requests) | **総当たり(Brute Force)** |
| 09:23:47 | `/login` が **200**(それまで 401) | **★侵害成立**(認証突破) |
| 09:24 | `/api/users/1,2,3...` 連番 200 | **IDOR でデータ収集** |
| 09:24:59 | `/api/search?q=' UNION SELECT * FROM users--` | **SQLi でユーザーテーブル窃取** |
| 09:31 | `/api/export?all=true` レスポンス **4.2MB** | **データ持ち出し(Exfiltration)** |

**侵害成立の行**: `09:23:47 POST /login 200`。それ以前は 401(失敗)が連続し、突然 200(成功)に変わったため。総当たりが成功した瞬間と判断できる。

## レベル3: 対応

### 6フェーズ初動計画

1. **準備**(平時): 本演習では事後だが、連絡網・手順・ログ集約があった前提
2. **検知と分析**: 上記タイムライン。影響範囲 = users テーブル全体 + export された全データ
3. **封じ込め**:
   - `203.0.113.7` を即時ブロック(WAF/FW)
   - 突破されたアカウントのセッション/トークンを全失効
   - 影響アカウントのパスワード強制リセット
   - (証拠保全のためログ・メモリを先に確保してから)
4. **根絶**: SQLi と IDOR の脆弱性を修正、総当たり対策(レート制限・MFA)を導入
5. **復旧**: 監視を強化しつつサービス正常化。流出範囲を確定し、必要なら利用者・当局へ通知
6. **教訓**: ポストモーテム(下記)

### 防止・検知の提案(横断)

| 対策 | 対応 Lesson |
|------|------------|
| パラメータ化クエリ(SQLi 根絶) | 05 |
| リソース所有者チェック(IDOR) | 07 |
| ログインのレート制限・アカウントロック・MFA | 03/07 |
| `.git`/バックアップを公開しない | 11 |
| 大量エクスポート・連番アクセスの検知ルール(SIEM) | 12 |
| WAF で既知ペイロードを遮断(多層) | 05/08 |

検知ルール例: 「同一 IP から5分で 401 が10回超 → アラート」「1リクエストのレスポンスが通常の100倍 → アラート」。

### ブレームレス・ポストモーテム

```
何が起きたか: 09:14〜09:31、単一 IP による偵察→総当たり突破→IDOR/SQLi→
              全ユーザーデータの持ち出し。
根本原因(仕組みの問題):
  - ログインにレート制限がなく総当たりを許した
  - API に認可チェックがなく IDOR を許した
  - 検索がパラメータ化されておらず SQLi を許した
  - 異常な大量エクスポートを検知する仕組みがなかった
再発防止(担当・期限つき):
  - [ ] 全 API に認可ミドルウェアを強制(担当X / 2週間)
  - [ ] 全クエリのパラメータ化を SAST で強制(担当Y / 1週間)
  - [ ] レート制限 + MFA 導入(担当Z / 2週間)
  - [ ] SIEM に持ち出し検知ルール追加(担当W / 3週間)
※個人を責めない。上記はいずれも「仕組みで防ぐ」施策。
```

## 学びのポイント

- 単体では無害な行(401、200、連番)も、**時系列で繋ぐと攻撃の物語になる**(Lesson 12)。
- 対応は「止める」だけでなく「証拠保全 → 根絶 → 再発防止」まで。
- ポストモーテムは犯人探しでなく仕組み直し。
